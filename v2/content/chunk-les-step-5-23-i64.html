Continuation · checked fixture R04 — ReTool trajectories: tool outputs are observations

Checked continuation mechanism and declared fixture; this is not certification of every inherited claim.

The model learns when/what to call; interpreter outputs supply context for its next action.

Prerequisites: Clipped surrogate and advantage sign, Shifted next-token targets and masked loss

Notation and assumptions

Separate assistant-generated action/text positions from tool-output observations. Reward and policy-loss masks must follow the actual training implementation.

Derivation and mechanism

  1. Generate an assistant action that may invoke a tool.
  2. Execute under the declared sandbox and return output/error as observation.
  3. Continue generation with that observation; score only eligible generated positions under the policy loss.

Worked example

Toy token losses[1,10,3],mask[1,0,1]→(1+3)/2=2. Including the tool output would average14/3. Error observations can support a corrected call, but tool text is not itself a sampled assistant action.

Limitations

  • This mask example does not execute arbitrary tool code or reproduce full ReTool PPO.
  • Timeouts, malformed calls, sandbox errors and output truncation need explicit trajectory policies.

Connections to later concepts

  • T01-style target masks prevent observation tokens from being treated as generated actions; B01-style verification affects reward rather than token provenance.

Step 5.23 — ReTool Full Rollout Engine

Plan node: I9 · chat order #64

Now we move from “how the cold-start model is trained” to the most important operational part:

\boxed{ \text{How does one complete ReTool rollout actually execute from start to finish?} }

This is where all the pieces we have studied come together:

\boxed{ \text{LLM} \rightarrow \text{code} \rightarrow \text{sandbox} \rightarrow \text{feedback} \rightarrow \text{LLM} \rightarrow \text{answer} \rightarrow \text{reward} \rightarrow \text{PPO} }

The ReTool slides describe the rollout as a single hybrid token sequence containing model reasoning, model-generated code, real interpreter feedback, and the final answer. (Source: retool-slides)

5.23.1 Start with one question

Suppose the training question is:

\boxed{q=\text{“Solve this computationally difficult problem.”}}

and the ground-truth answer is:

\boxed{a=699}.

The model starts generating from q.

At this moment, the policy is:

\boxed{\pi_{\text{old}}}

because this is the policy used to collect the RL rollout.

5.23.2 Token 1 onward: ordinary generation

The model begins:

I need to find the valid candidate.

Then perhaps:

A direct manual search would be tedious.

These are ordinary policy-generated tokens.

Formally:

o_1,o_2,\ldots,o_t \sim \pi_{\text{old}}(\cdot\mid s_t).

Nothing special has happened yet.

5.23.3 The model reaches a tool decision

Eventually it generates:

<code>

This is a critical event.

The model has effectively taken the action:

\boxed{ a_t=\text{invoke computational tool} }

The ReTool prompt gives the model the ability to use executable Python, but does not hard-code when to use it. That timing is meant to be learned through RL. (Source: retool-slides)

5.23.4 The model now generates code

For example:

for x in range(1, 1000):
    ...

The model continues until it reaches:

</code>

At that moment:

\boxed{ \text{generation pauses} }

The slide explicitly states that code is sent to the real sandbox when </code> is detected. (Source: retool-slides)

5.23.5 Important: the model does NOT generate the next observation

The model generated:

\boxed{\text{code}}

but the next result comes from:

\boxed{\text{environment}}.

So the system executes:

\text{Code} \longrightarrow \text{Sandbox} \longrightarrow \text{Output / Error}.

This is the point where the LLM temporarily gives control to an external environment.

5.23.6 The sandbox returns real feedback

Suppose the code returns:

699

The system inserts something conceptually like:

<interpreter>
699
</interpreter>

into the rollout.

The model now sees:

\boxed{ \text{its previous reasoning} + \text{its code} + \text{actual computation result} }

and generation resumes. (Source: retool-slides)

5.23.7 The rollout is still one trajectory

This point is easy to misunderstand.

We do NOT create separate trajectories:

\tau_1=\text{reasoning}
\tau_2=\text{code}
\tau_3=\text{interpreter}

Instead, ReTool treats everything as one trajectory:

\boxed{ \tau= t_1 \oplus c_1 \oplus f_1 \oplus t_2 \oplus c_2 \oplus f_2 \oplus o }

The slide explicitly describes this concatenation into a single token sequence. (Source: retool-slides)

5.23.8 Why this matters

Because the eventual reward belongs to the whole strategy.

Suppose:

\tau= \text{reason} \rightarrow \text{code} \rightarrow \text{feedback} \rightarrow \text{correction} \rightarrow \text{final answer}.

The reward doesn't separately say:

R_{\text{reason}}=...
R_{\text{code}}=...
R_{\text{feedback}}=...

Instead:

\boxed{ R(\tau)=+1 }

if the final answer is correct.

Thus PPO must determine how to assign learning signal across the model's own decisions throughout the trajectory.

5.23.9 Second tool call

Now imagine the first result is not enough.

The model reasons:

The candidate is 699, but I should verify the condition.

Then it generates another:

<code>
...
</code>

The sandbox executes again.

Suppose it returns:

valid

Now the trajectory is:

\boxed{ t_1 \oplus c_1 \oplus f_1 \oplus t_2 \oplus c_2 \oplus f_2 }

and generation resumes again.

This can repeat until the model chooses to produce its final answer. (Source: retool-slides)

5.23.10 The final answer

Eventually:

\boxed{699}

is produced.

The system extracts the answer from the \boxed{} expression.

So:

\hat a=699.

Ground truth:

a=699.

5.23.11 The verifier computes the reward

ReTool uses a rule-based correctness checker.

Therefore:

R(a,\hat a)= \begin{cases} +1,&\text{equivalent}\\ -1,&\text{otherwise} \end{cases}

So here:

\boxed{ R=+1 }

The ReTool deck explicitly says this is the entire reward and deliberately does not add a separate reward merely for successfully executing code. (Source: retool-slides)

5.23.12 Why does the reward arrive only at the end?

Consider two trajectories.

Trajectory A
reason
→ code
→ useful result
→ correct answer

Reward:

+1.
Trajectory B
reason
→ useless code
→ useless result
→ wrong answer

Reward:

-1.

The model therefore has to discover that tool use is valuable when it improves eventual task success.

That is why the deck says that correctness-only reward forces each code call to “earn its keep” through its contribution to the final result. (Source: retool-slides)

5.23.13 Now the PPO stage begins

The rollout is now complete.

We have:

\boxed{\tau}

and:

\boxed{R(\tau)}.

We now need to turn that into learning signals.

For each policy-generated token o_t, PPO evaluates:

\boxed{ r_t(\theta) = \frac{ \pi_\theta(o_t\mid s_t;CI) }{ \pi_{\text{old}}(o_t\mid s_t;CI) } }

as given in the ReTool objective. (Source: retool-slides)

5.23.14 What exactly is s_t here?

This is extremely important.

In ordinary text-only RL:

s_t= [q,\text{previous generated tokens}].

In ReTool:

\boxed{ s_t= [q,\text{reasoning},\text{code},\text{interpreter feedback},\ldots] }

So after the sandbox says:

699

the next policy decision is conditioned on that new observation.

This is where the environment actually changes the model's future behavior.

5.23.15 Example: before and after tool feedback

Before execution:

P(\text{“699”}\mid s_t) = \text{some probability}.

After the interpreter returns:

699,

the context changes:

s_t\rightarrow s_{t+1}.

The model may now assign:

P(\text{“The answer is”}\mid s_{t+1})

a much larger probability.

Therefore the external tool isn't merely attached to the end of the system.

It changes the future token distribution of the policy.

5.23.16 Now the most important engineering detail: interpreter masking

Suppose the trajectory is:

Token 1: I
Token 2: will
Token 3: calculate
Token 4: <code>
Token 5: print
...
Token 20: </code>

Token 21: <interpreter>
Token 22: 699
Token 23: </interpreter>

Token 24: Therefore
Token 25: ...

Tokens 21–23 came from the environment.

So:

\boxed{ \text{do not train the policy to predict them} }

The ReTool slide explicitly says interpreter-generated tokens are excluded from the loss. (Source: retool-slides)

5.23.17 Why exactly?

Suppose the sandbox returns:

17\times41=697.

The model did not choose:

697.

The environment did.

Therefore giving the policy a token-level prediction loss for 697 would amount to saying:

“Model, you should have predicted this environment output.”

But the model had no control over that output.

So:

\boxed{ \text{credit only decisions made by the policy} }

is the correct learning principle.

5.23.18 Visualize the loss mask

Imagine:

Tokens:
[ reasoning reasoning code code code INT INT INT reasoning reasoning final ]

Mask:
[    1        1    1    1    1    0   0   0      1        1     1  ]

where:

1=\text{policy token}
0=\text{interpreter token}.

Thus the policy loss only sees:

\boxed{ \text{model-generated tokens} }

and ignores:

\boxed{ \text{environment-generated tokens} }.

5.23.19 Another important point: the feedback is still in the context

Masking does not mean removing interpreter output.

This distinction is critical.

The interpreter output is:

\boxed{ \text{visible to the model} }

but:

\boxed{ \text{not treated as a policy prediction target} }.

So the model can read:

<interpreter>
699
</interpreter>

and use 699 in later reasoning.

But the loss does not ask the model to generate 699.

5.23.20 Second engineering optimization: KV-cache reuse

Now suppose the model has already generated:

N=5000

tokens before making its code call.

All of those tokens already have cached keys and values.

When the interpreter returns:

M=50

new tokens, ReTool does not need to recompute the entire previous prefix.

Instead:

\boxed{ K,V_{\text{old prefix}} \text{ are reused} }

and only the new feedback is appended.

The slide explicitly identifies this as one of the engineering details making multi-turn tool use affordable at RL scale. (Source: retool-slides)

5.23.21 Why this is such a big deal

Without cache reuse:

\text{tool call} \rightarrow \text{reprocess entire prefix}.

With reuse:

\text{tool call} \rightarrow \text{reuse prefix cache} + \text{process new observation}.

So repeated tool calls become much more manageable.

5.23.22 Numerical KV-cache question

Suppose:

L_{\text{old}}=8000

cached tokens.

Interpreter adds:

L_{\text{new}}=100.

With KV reuse, the new feedback extends the cache by:

\boxed{100\text{ tokens}}

rather than requiring the whole 8100-token history to be treated as new input for cache construction.

Again, this is the conceptual cache-efficiency calculation; the deck's claim is specifically that the old prefix can be reused and only new interpreter-feedback tokens need cache computation/appending. (Source: retool-slides)

5.23.23 Why asynchronous execution is needed

Now imagine a batch of 1000 rollouts.

One rollout's code:

20\text{ ms}

another:

100\text{ ms}

another:

2\text{ s}

another:

8\text{ s}.

If all code execution were strictly synchronous, slow executions could cause the entire generation pipeline to wait.

ReTool therefore uses an asynchronous sandbox pool so slow executions do not stall the rest of RL training. (Source: retool-slides)

5.23.24 Distributed-systems interpretation

You can view the system as:

\boxed{ \text{Inference workers} }

communicating with:

\boxed{ \text{Sandbox worker pool} }

through asynchronous requests/results.

Conceptually:

LLM Worker
   │
   │ code request
   ▼
Queue
   │
   ├──► Sandbox 1
   ├──► Sandbox 2
   ├──► Sandbox 3
   └──► Sandbox N
   │
   ▼
Execution result
   │
   ▼
LLM Worker

That architecture follows the slide's description of an asynchronous sandbox pool; details such as the exact queue technology are not specified by the supplied slides.

5.23.25 What happens if the code crashes?

This is one of ReTool's most interesting properties.

Suppose the model produces:

greedy()

but greedy is undefined.

The environment returns:

\boxed{\text{NameError}}

The model sees that real feedback.

It can then reason:

The function has not been defined.

and produce corrected code.

The supplied slide presents this as an emergent self-correction behavior that appeared through RL rather than being explicitly demonstrated in a training example. (Source: retool-slides)

5.23.26 This is the birth of tool-mediated self-correction

Text-only self-correction:

\text{model} \rightarrow \text{its own critique} \rightarrow \text{its own revision}

ReTool can do:

\boxed{ \text{model} \rightarrow \text{real execution} \rightarrow \text{real error} \rightarrow \text{revision} }

That is much more grounded because the correction is based on an externally generated observation.

5.23.27 Why is an error useful for RL?

Suppose:

\text{Code}_1 \rightarrow \text{NameError} \rightarrow \text{Code}_2 \rightarrow \text{correct answer}.

The overall trajectory receives:

R=+1.

Thus the successful trajectory contains:

\boxed{ \text{failure} + \text{recovery} }

The RL optimizer can reinforce the policy behavior surrounding that successful recovery.

This is why useful behavior can emerge even without an SFT example showing exactly that same error correction. (Source: retool-slides)

5.23.28 Important distinction: the environment isn't being trained

The policy is trained.

The sandbox is an environment that provides feedback.

So:

\boxed{ \theta_{\text{LLM}} \rightarrow \text{updated} }

while the code interpreter remains the external execution mechanism.

This is conceptually the standard agent-environment separation.

5.23.29 Full rollout in mathematical notation

Let's define:

\tau= (o_1,o_2,\ldots,o_T)

with some positions corresponding to interpreter outputs.

The model generates certain positions according to:

o_t\sim\pi_{\text{old}}(\cdot\mid s_t).

When a code boundary is reached:

c_i \rightarrow E(c_i) = f_i

where E is the sandbox execution function.

Then:

s_{t+1} = s_t\oplus c_i\oplus f_i.

Eventually:

\hat a=\operatorname{Extract}(\tau).

Then:

R(\tau) = \begin{cases} +1,&\operatorname{Equivalent}(a,\hat a)\\ -1,&\text{otherwise}. \end{cases}

That scalar reward then drives PPO.

5.23.30 The complete lifecycle

Now the entire ReTool rollout can be written as:

\boxed{ q }
\downarrow
\boxed{ \pi_{\text{old}}\text{ generates reasoning} }
\downarrow
\boxed{ \text{model chooses code} }
\downarrow
\boxed{ \text{sandbox execution} }
\downarrow
\boxed{ \text{real output/error} }
\downarrow
\boxed{ \text{output inserted into context} }
\downarrow
\boxed{ \text{model resumes} }
\downarrow
\boxed{ \text{repeat if necessary} }
\downarrow
\boxed{ \text{final }\boxed{a} }
\downarrow
\boxed{ R\in\{-1,+1\} }
\downarrow
\boxed{ \text{PPO advantage + ratio + clipping} }
\downarrow
\boxed{ \text{update policy} }

5.23.31 Full numerical example

Let's make one trajectory.

Model-generated tokens:

T_M=900.

Interpreter tokens:

T_I=100.

Total trajectory:

T=1000.

The model makes two tool calls.

First call

Code tokens:

150.

Interpreter:

30.
Second call

Code tokens:

200.

Interpreter:

70.

The remaining model-generated tokens are:

900-(150+200)=550

which can include reasoning and final answer.

Check:

550+150+200+30+70 = \boxed{1000}.

Thus the interpreter contributes:

\frac{100}{1000} = \boxed{10\%}

of trajectory tokens.

But those 100 tokens are masked from the policy loss while remaining visible in the context.

5.23.32 PPO numerical example on one generated token

Suppose a model-generated token has:

\pi_{\text{old}}=0.10

and candidate new policy:

\pi_\theta=0.13.

So:

r_t=1.3.

Suppose:

\hat A_t=0.6

and:

\epsilon=0.2.

Then:

\operatorname{clip}(1.3,0.8,1.2)=1.2.

Raw:

1.3(0.6)=0.78.

Clipped:

1.2(0.6)=0.72.

Therefore:

\boxed{ J_t=\min(0.78,0.72)=0.72. }

The model still benefits from making that useful action more likely, but PPO limits the optimization incentive for a movement beyond the clipping region.

5.23.33 What exactly is being learned?

Not simply:

\boxed{\text{“Use Python.”}}

The model is learning something much richer:

\boxed{ \text{Given the current state, what action sequence maximizes eventual correctness?} }

The action sequence can contain:

\text{text} \rightarrow \text{code} \rightarrow \text{interpretation} \rightarrow \text{text} \rightarrow \text{code} \rightarrow \text{final answer}.

That is why ReTool is better understood as strategic tool-use learning, not merely tool calling.

5.23.34 Why the result is interesting

The supplied results show a dramatic difference between:

\text{SFT only}
\text{text-only RL}

and:

\boxed{\text{RL + real code interpreter}}

on AIME2024 for the specified Qwen2.5-32B-Instruct setup:

26.7\% \rightarrow 40.9\% \rightarrow 40.0\% \rightarrow 67.0\%.

The supplied slide attributes the large jump specifically to combining RL with the ability to call a real code interpreter, rather than to SFT or text-only RL alone. (Source: retool-slides)

5.23.35 Training efficiency result

The supplied deck also reports that ReTool's accuracy curve rises much faster and reaches its plateau around step 400, while the text-only baseline continues improving beyond step 1000.

It reports ReTool reaching its higher accuracy using approximately:

\boxed{37\%}

of the training steps used by that text-only RL baseline. (Source: retool-slides)

This supports a deeper interpretation:

\boxed{ \text{tools don't merely increase capability; they can simplify exploration} }

because certain computations no longer have to be discovered entirely through token-level reasoning.

5.23.36 One subtle but powerful conclusion

Earlier we said:

\text{RL} = \text{discover/strengthen behavior}.

ReTool reveals what kind of behavior can be discovered:

\boxed{ \text{interaction strategy} }

not just verbal reasoning.

The model can discover:

\text{“I should calculate now.”}
\text{“That output looks suspicious.”}
\text{“The interpreter gave me an error.”}
\text{“I should fix the code.”}
\text{“Now I have enough evidence to answer.”}

That is a qualitatively richer policy than:

\boxed{ \text{keep generating text until answer} }.

5.23.37 Exam checkpoint

You should now be able to explain all six of these without memorizing the deck:

1. What is the ReTool rollout?
\boxed{ \text{single hybrid trajectory of reasoning + code + interpreter feedback + answer} }
2. Who generates interpreter tokens?
\boxed{\text{the external sandbox}}
3. Are interpreter tokens trained with the policy loss?
\boxed{\text{No, they are masked.}}
4. Why reuse KV cache?
\boxed{ \text{to avoid recomputing the entire prefix after tool execution} }
5. Why asynchronous sandbox execution?
\boxed{ \text{to prevent slow code executions from stalling RL generation} }
6. What does PPO actually learn?
\boxed{ \text{which model-generated actions, including tool-use decisions, lead to successful outcomes} }

These points are directly grounded in the ReTool rollout and engineering slides. (Source: retool-slides)

5.23.38 Master picture for Steps 5.20–5.23

We can now compress everything into one equation chain:

\boxed{ \underbrace{ D_{\text{init}} \rightarrow D_{\text{CI}} \rightarrow \text{SFT} }_{\text{learn protocol}} }

then:

\boxed{ \underbrace{ \text{policy rollout} \rightarrow \text{code execution} \rightarrow \text{environment feedback} \rightarrow \text{final answer} }_{\text{generate hybrid trajectory}} }

then:

\boxed{ \underbrace{ R=\pm1 \rightarrow \hat A_t \rightarrow r_t \rightarrow \operatorname{clip} \rightarrow \nabla_\theta }_{\text{PPO learns strategy}} }

So the overall ReTool idea is:

\boxed{ \textbf{SFT teaches the model how to talk to the tool;} \quad \textbf{RL teaches the model when and why to use it.} }
