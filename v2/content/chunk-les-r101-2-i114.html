R101.2 — Data Parallelism: Using Multiple GPUs to Make Training Faster

Plan node: A5 · chat order #114

We have just seen Gradient Accumulation solve one problem:

\boxed{\text{GPU memory limitation}}

But it creates a new realization:

Even when we can fit the model and batch, training may still be too slow.

The source now introduces Data Parallelism as the first major multi-GPU strategy. (Source: Build a DeepSeek Model (From Scratch))

1. The problem changes

Suppose one GPU can process:

16\text{ samples}

per training operation.

With one GPU:

GPU 0
  ↓
16 samples
  ↓
Forward
  ↓
Backward

Then it processes the next batch.

So computation happens sequentially.

The obvious question is:

\boxed{ \text{Can several GPUs process different data at the same time?} }

Yes.

That is the core idea of Data Parallelism. (Source: Build a DeepSeek Model (From Scratch))

2. What does "data parallel" actually mean?

The key is:

\boxed{ \text{same model, different data} }

Suppose we have four GPUs.

We create:

GPU 0 → Model copy 0
GPU 1 → Model copy 1
GPU 2 → Model copy 2
GPU 3 → Model copy 3

Each model copy has the same parameters.

But each GPU receives a different part of the batch:

Global batch
      │
 ┌────┼────┬────┐
 ▼    ▼    ▼    ▼
GPU0 GPU1 GPU2 GPU3
 16   16   16   16

The source describes exactly this arrangement: split the batch across GPUs while each GPU holds an identical copy of the entire model. (Source: Build a DeepSeek Model (From Scratch))

3. What happens on each GPU?

Each GPU independently performs:

\boxed{ \text{Forward} \rightarrow \text{Loss} \rightarrow \text{Backward} }

For example:

GPU 0:
data A → model → gradients A

GPU 1:
data B → model → gradients B

GPU 2:
data C → model → gradients C

GPU 3:
data D → model → gradients D

This happens in parallel.

So rather than waiting for GPU 0 to finish before beginning GPU 1, all GPUs work simultaneously.

4. But now we have a problem

Each GPU has calculated a different gradient.

For example:

g_0,\quad g_1,\quad g_2,\quad g_3.

If GPU 0 updates using only g_0, while GPU 1 updates using only g_1, the models would start moving in different directions.

Then:

GPU 0 model ≠ GPU 1 model

which is not what we want.

We want every GPU to apply the same global gradient.

5. The solution: synchronize gradients

The source explains that after the local backward passes, gradients are:

\boxed{\text{gathered, aggregated, and averaged}}

across GPUs. (Source: Build a DeepSeek Model (From Scratch))

Conceptually:

g_{\text{global}} = \frac{ g_0+g_1+g_2+g_3 }{4}.

Then every GPU uses:

g_{\text{global}}

to update its local model.

6. Full Data Parallel workflow

The source's conceptual workflow is:

                 GLOBAL BATCH
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        GPU 0       GPU 1       GPU 2 ... GPU N
        Model       Model       Model
        Copy 0      Copy 1      Copy 2
          │           │           │
          ▼           ▼           ▼
      Forward     Forward     Forward
          │           │           │
          ▼           ▼           ▼
      Backward    Backward    Backward
          │           │           │
          └───────────┼───────────┘
                      ▼
              Gradient averaging
                      │
                      ▼
                 Same update
                      │
                      ▼
             synchronized models

(Source: Build a DeepSeek Model (From Scratch))

7. Why does this make training faster?

Suppose one GPU needs:

T

seconds to process its mini-batch.

With four GPUs, four different mini-batches can be processed approximately simultaneously.

Ideally:

\boxed{ \text{throughput}\approx4\times }

compared with one GPU.

The exact speedup will not be perfectly linear because communication and other overheads exist, but the source presents Data Parallelism as the direct "more GPUs, less time" approach. (Source: Build a DeepSeek Model (From Scratch))

8. Very important: Data Parallelism does NOT make the model smaller

This is one of the most important interview points.

Suppose the model requires:

20\text{ GB}

of memory.

In 4-GPU data parallelism:

GPU 0 → 20 GB model
GPU 1 → 20 GB model
GPU 2 → 20 GB model
GPU 3 → 20 GB model

So the model is replicated.

We have not split its parameters.

Therefore:

\boxed{ \text{Data Parallelism solves throughput, not model-size memory.} }

This distinction becomes crucial later when the source introduces Model Parallelism. (Source: Build a DeepSeek Model (From Scratch))

9. Two PyTorch approaches in the source

The source introduces two implementations:

\boxed{\texttt{nn.DataParallel}}

and:

\boxed{\texttt{nn.DistributedDataParallel}}

or:

\boxed{\text{DP vs DDP}}.

It describes DP as the older and simpler approach, while DDP is the modern industry-standard approach for serious large-scale training. (Source: Build a DeepSeek Model (From Scratch))

We need to understand why.

10. nn.DataParallel — the centralized design

Think of DP as:

             Main GPU
             GPU 0
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
    GPU 1     GPU 2    GPU 3

GPU 0 acts as the central coordinator.

The source gives a five-stage flow.

11. DP Step 1 — Scatter

The full batch is initially loaded on the main GPU.

Then GPU 0 scatters chunks of the batch to the other GPUs.

For example:

Full batch = 64

GPU 0 → 16
GPU 1 → 16
GPU 2 → 16
GPU 3 → 16

(Source: Build a DeepSeek Model (From Scratch))

12. DP Step 2 — Parallel forward pass

Each GPU runs a forward pass using its local data chunk.

GPU 0 → Forward(batch0)
GPU 1 → Forward(batch1)
GPU 2 → Forward(batch2)
GPU 3 → Forward(batch3)

So far this looks good.

13. DP Step 3 — Gather

Here is where the centralized design starts hurting.

The outputs from the GPUs are sent back to GPU 0.

Conceptually:

GPU 1 ──┐
GPU 2 ──┼──→ GPU 0
GPU 3 ──┘

The source says the logits are gathered back to the main GPU. (Source: Build a DeepSeek Model (From Scratch))

14. DP Step 4 — Centralized computation

GPU 0 now performs the centralized loss/backward work described by the source.

So GPU 0 is handling much more responsibility:

GPU 0:
- receives the data
- distributes the data
- gathers outputs
- computes centralized work
- updates weights

while the other GPUs have a much simpler role.

This creates the fundamental bottleneck.

15. DP Step 5 — Replicate the updated model again

After GPU 0 updates its model, the newly updated model has to be replicated out to the other GPUs for the next forward pass.

So the cycle becomes:

GPU 0
  ↓
scatter
  ↓
other GPUs
  ↓
forward
  ↓
gather
  ↓
GPU 0
  ↓
update
  ↓
copy model again
  ↓
repeat

(Source: Build a DeepSeek Model (From Scratch))

16. Why is DP bad for large-scale LLM training?

The source identifies two major problems.

Problem 1 — Central bottleneck

GPU 0 does substantially more work.

Problem 2 — Communication bottleneck

A lot of communication is funneled through one main GPU.

Therefore:

\boxed{ \text{poor load balance} + \text{communication bottleneck} \Rightarrow \text{poor scalability} }

The source consequently says DP is rarely used for modern large-scale training. (Source: Build a DeepSeek Model (From Scratch))

17. DP vs single GPU

Let's make the distinction very concrete.

Single GPU
Data
 ↓
GPU
 ↓
Model
 ↓
Gradient
 ↓
Update
DataParallel
             GPU 0
             / | \
            /  |  \
           ▼   ▼   ▼
         GPU1 GPU2 GPU3
            │
            ▼
         gather
            │
            ▼
           GPU0
            │
          update

The multiple GPUs exist, but GPU 0 remains the boss.

18. Why DDP is fundamentally different

The source introduces DDP as a decentralized model.

Instead of:

\boxed{\text{one boss GPU}}

we have:

\boxed{\text{peer GPUs}}

Each GPU has:

  • its own process,
  • its own model copy,
  • its own optimizer,
  • its own data shard.

(Source: Build a DeepSeek Model (From Scratch))

This is the key conceptual leap.

19. DDP architecture

Instead of:

           GPU 0
          /     \
       GPU 1    GPU 2
                 |
                GPU 3

think:

GPU 0  ↔  GPU 1
 ↕         ↕
GPU 2  ↔  GPU 3

There is no central "boss" GPU.

The source describes each GPU as an independent peer/process. (Source: Build a DeepSeek Model (From Scratch))

20. DDP Step 1 — One process per GPU

Each GPU gets its own process.

So with four GPUs:

Process 0 → GPU 0
Process 1 → GPU 1
Process 2 → GPU 2
Process 3 → GPU 3

Each process owns its local copy of the model.

21. DDP Step 2 — Shard the data

Each process gets its own unique data slice.

So:

Dataset
   │
   ├── Process 0 → shard 0
   ├── Process 1 → shard 1
   ├── Process 2 → shard 2
   └── Process 3 → shard 3

There is no central GPU distributing the batch every iteration.

The source uses DistributedSampler for this partitioning. (Source: Build a DeepSeek Model (From Scratch))

22. DDP Step 3 — Local forward + backward

Each process independently computes:

L_0,L_1,L_2,L_3

and:

g_0,g_1,g_2,g_3.

So:

GPU 0 → local forward/backward
GPU 1 → local forward/backward
GPU 2 → local forward/backward
GPU 3 → local forward/backward

Everything is happening in parallel.

23. DDP Step 4 — All-Reduce

This is the heart of DDP.

The source calls out All-Reduce as the core communication mechanism. (Source: Build a DeepSeek Model (From Scratch))

Conceptually:

g_0,g_1,g_2,g_3

are combined into:

\boxed{ g_{\text{avg}} = \frac{g_0+g_1+g_2+g_3}{4} }

and every process ends up with the same averaged gradient.

24. Why is All-Reduce better?

Because we no longer make GPU 0 do all the communication.

Instead, the GPUs participate as peers.

The source mentions efficient communication algorithms such as Ring-AllReduce and explains that communication can be overlapped with backward computation, hiding some communication latency. (Source: Build a DeepSeek Model (From Scratch))

This gives:

\boxed{ \text{better utilization} + \text{less central bottleneck} }

25. DDP Step 5 — Every GPU updates locally

Once every GPU has the same averaged gradient:

g_{\text{avg}},

each process can independently execute:

optimizer.step()

because every GPU started with the same parameters and has the same gradient.

Therefore:

\theta_0' = \theta_1' = \theta_2' = \theta_3'.

The replicas remain synchronized.

(Source: Build a DeepSeek Model (From Scratch))

26. This gives us the key DDP invariant

After synchronization:

\boxed{ \text{all model replicas have identical weights} }

That invariant must continue after every optimizer update.

Otherwise the replicas would diverge.

27. DP vs DDP — the interview table

Property DataParallel (DP) DistributedDataParallel (DDP)
Model copies One per GPU One per GPU
Architecture Centralized Decentralized
Processes Central mechanism One process/GPU
Data distribution Main GPU scatters Distributed sampler
Gradient synchronization Centralized All-Reduce
Main bottleneck Main GPU Much better balanced
Scalability Poorer Much better
Source's recommendation Older/simple Modern/industry-standard

(Source: Build a DeepSeek Model (From Scratch))

28. The most important distinction so far

Remember these three ideas:

\boxed{ \text{Gradient Accumulation} }

means:

same GPU(s), process several small batches before one optimizer update.

\boxed{ \text{Data Parallelism} }

means:

replicate the model and split the data across GPUs.

\boxed{ \text{Model Parallelism} }

means:

split the model itself across GPUs.

The first two solve different bottlenecks.
