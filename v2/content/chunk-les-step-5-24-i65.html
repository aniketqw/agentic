Step 5.24 — What ReTool Actually Discovers During RL

Plan node: I9 · chat order #65

Now we reach one of the most interesting parts of the ReTool material.

Up to Step 5.23, we understood how the rollout is generated and how PPO updates the model.

Now the question becomes:

\boxed{\text{What behavior actually changes as RL training progresses?}}

The supplied deck answers this using six measurable behavioral signals. Crucially, the slide says these behaviors were not manually prescribed; they emerged from optimizing the single correctness reward. (Source: retool-slides)

5.24.1 First understand what is being measured

At every saved RL checkpoint, ReTool evaluates the model's own generated responses.

The six metrics are:

\boxed{ \text{response length} }
\boxed{ \text{code ratio} }
\boxed{ \text{code lines} }
\boxed{ \text{correct code count} }
\boxed{ \text{code pass rate} }
\boxed{ \text{code invocation timing} }

The important point is:

\boxed{ \text{none of these were separately optimized as explicit rewards} }

according to the slide.

The only reward was:

\boxed{ R= \begin{cases} +1 & \text{correct}\\ -1 & \text{incorrect} \end{cases} }

Yet the six behaviors changed systematically. (Source: retool-slides)

That is the first major lesson.

5.24.2 Signal 1 — Response length

Before RL, the model's responses were approximately:

\boxed{10,000\text{ tokens}}

on the reported measurement.

After RL, they ended around:

\boxed{6,000\text{ tokens}}

which is roughly a:

\frac{10000-6000}{10000}\times100 = \boxed{40\%}

reduction. (Source: retool-slides)

But something more interesting happens during training.

The curve does not simply decrease monotonically.

The slide says response length:

  1. falls sharply at first,
  2. then rises again,
  3. and ultimately ends substantially shorter than before RL. (Source: retool-slides)

5.24.3 Why does response length initially fall?

Before RL, the model may perform computation manually in text:

First calculate this...
Then calculate that...
Let's check another possibility...
Now substitute...
Let's recompute...

After discovering useful code-based strategies, it can replace many textual arithmetic steps with:

...

followed by:

<interpreter>
...
</interpreter>

So:

\boxed{ \text{manual textual computation} \rightarrow \text{compact executable computation} }

This compresses the reasoning trajectory.

The slide explicitly attributes the initial length reduction to code replacing laborious manual calculation. (Source: retool-slides)

5.24.4 Why does response length rise again?

This is the subtle part.

After learning basic code usage, the model starts discovering more elaborate computational strategies.

So the trajectory becomes:

\text{simple reasoning} \rightarrow \text{compact code} \rightarrow \text{more sophisticated code strategies}.

The code itself can become larger and more powerful.

Therefore:

\boxed{ \text{better tool use does not necessarily mean fewer tokens at every stage} }

The final result is still about 40% shorter, but the path there involves more sophisticated behavior. (Source: retool-slides)

5.24.5 Signal 2 — Code ratio

Now define the intuition behind code ratio.

Conceptually:

\boxed{ \text{Code Ratio} = \frac{\text{responses containing code}} {\text{total responses}} }

The reported trend is striking.

Initially:

\boxed{\text{under }20\%}

of responses used code.

By the end:

\boxed{\text{nearly }98\%}

of responses used code. (Source: retool-slides)

5.24.6 What does that mean?

Before RL:

\text{Most responses} \rightarrow \text{text-only}.

After RL:

\text{Almost all responses} \rightarrow \text{tool-augmented}.

So the policy has discovered:

\boxed{ \text{code is broadly useful for this task distribution} }

under the learned reward.

This is extremely important because nobody directly said:

“Use Python in 98% of your answers.”

Instead:

\boxed{ \text{correctness reward} \rightarrow \text{policy discovers high-value code use} }

according to the reported analysis. (Source: retool-slides)

5.24.7 But doesn't this look like overuse?

Yes—and this is an important nuance.

A code ratio of nearly 98% means the model learned to use code very frequently on the evaluated task distribution.

That does not imply:

\boxed{ \text{98\% is universally optimal} }

The deck only reports the behavior that emerged in this training/evaluation setup.

You should not generalize that number to arbitrary tasks.

This is a source-derived observation, not a universal law.

5.24.8 Signal 3 — Number of code lines

Now we go deeper.

The model isn't merely calling code more often.

The code itself becomes more substantial.

The slide reports that the number of code lines rises throughout training and becomes nearly:

\boxed{5\times}

longer by the end. (Source: retool-slides)

So we have:

\boxed{ \text{code frequency}\uparrow }

and simultaneously:

\boxed{ \text{code complexity/size}\uparrow }

at least as measured by line count.

5.24.9 Why is that important?

Suppose early behavior is:

print(a * b)

That is raw arithmetic.

Later behavior might look more like:

for candidate in candidates:
    if condition_1(candidate):
        if condition_2(candidate):
            ...

Now the model is using the tool not merely as a calculator.

It's delegating a larger computational subproblem.

Therefore:

\boxed{ \text{tool role expands} }

from:

\text{calculator}

toward:

\boxed{ \text{computational reasoning module} }.

5.24.10 Signal 4 — Correct code counts

The slide reports that the number of correct code executions on the test set rises approximately:

\boxed{5\times}.

So we now have three simultaneous trends:

\text{more responses use code}
\text{code blocks become longer}
\text{more of those code executions are correct}.

This is evidence that the model is not merely generating random or increasingly verbose code.

The useful computational behavior itself is improving. (Source: retool-slides)

5.24.11 Signal 5 — Code pass rate

This is arguably the most informative metric.

The reported pattern is:

\boxed{ \text{correct final-answer responses} \rightarrow \text{code pass rate near 100\%} }

while:

\boxed{ \text{incorrect final-answer responses} \rightarrow \text{lower code pass rate}. }

The deck calls buggy code a leading indicator of a wrong final answer. (Source: retool-slides)

5.24.12 Why is this important?

Consider:

Successful trajectory
\text{correct code} \rightarrow \text{useful result} \rightarrow \text{correct answer}.
Failed trajectory
\text{buggy code} \rightarrow \text{bad/no result} \rightarrow \text{wrong answer}.

So code correctness is strongly associated with final reasoning success in the reported experiment.

This suggests that the external tool doesn't merely act as a computational accelerator:

\boxed{ \text{the quality of the interaction itself becomes diagnostic} }

for the final answer.

5.24.13 Signal 6 — Tool invocation timing

This is especially important for understanding strategy.

Early in training, the model tends to:

\boxed{ \text{reason in text first} \rightarrow \text{use code later} }

The slide reports that tool invocation gradually shifts earlier in the response. (Source: retool-slides)

So the model learns:

\boxed{ \text{reach for the tool sooner} }

when it recognizes that computation will be useful.

5.24.14 Why does earlier tool use help?

Imagine a problem that requires a long search.

Text-first strategy:

500\text{ reasoning tokens} \rightarrow \text{finally invoke code}.

Tool-early strategy:

50\text{ reasoning tokens} \rightarrow \text{invoke code}.

The second strategy can obtain an objective computational result earlier, which can then influence all subsequent reasoning.

So:

\boxed{ \text{earlier external feedback} \rightarrow \text{earlier correction/grounding} }

This is one reason tool integration can simplify the exploration problem.

The source explicitly reports the timing shift but does not give a universal mathematical rule saying “earlier is always better.” That broader claim would be an inference.

5.24.15 Put all six signals together

Now the six signals tell a coherent story.

1. Response length
\boxed{\downarrow}

overall.

2. Code ratio
\boxed{\uparrow}

from under 20% to nearly 98%.

3. Code line count
\boxed{\uparrow}

nearly 5×.

4. Correct code count
\boxed{\uparrow}

approximately 5×.

5. Code pass rate
\boxed{ \text{high for correct responses} }

and lower for incorrect ones.

6. Invocation timing
\boxed{ \text{moves earlier} }

The interesting combination is:

\boxed{ \text{less textual labor} + \text{more sophisticated computation} }

5.24.16 This is a genuine strategy shift

The phrase to remember is:

\boxed{ \textbf{RL is changing how the model solves the problem} }

rather than merely:

\boxed{ \textbf{RL is changing the model's final answer probability} }

The six metrics show evidence of a behavioral strategy transformation.

5.24.17 The “aha moment”

Now we reach the most interesting example from the deck.

The model generates code containing:

greedy()

But greedy() has not been defined.

The sandbox returns:

\boxed{\text{NameError}}

The model reads the traceback and recognizes the problem.

It then generates corrected code.

The slide presents this as an emergent behavior: no training example explicitly demonstrated this exact “fix after error” behavior, yet it emerged through optimizing correctness reward. (Source: retool-slides)

5.24.18 Why is this an “aha moment”?

Because the model has effectively learned:

\boxed{ \text{tool failure} \rightarrow \text{inspect feedback} \rightarrow \text{diagnose} \rightarrow \text{repair} \rightarrow \text{continue} }

This is much more sophisticated than:

\text{generate code} \rightarrow \text{hope it works}.

It has acquired an interaction strategy.

5.24.19 Where did the learning signal come from?

The model did not receive a reward saying:

+0.3

for fixing errors.

It only received the final correctness reward:

R= \begin{cases} +1\\ -1 \end{cases}

Therefore, the reasoning is:

\boxed{ \text{successful recovery} \rightarrow \text{higher chance of final correctness} }

and PPO reinforces trajectories containing such useful behavior.

This is precisely why the deck calls it emergent. (Source: retool-slides)

5.24.20 Numerical reward illustration

Imagine two policies encountering the same code bug.

Policy A
\text{error} \rightarrow \text{give up} \rightarrow R=-1.
Policy B
\text{error} \rightarrow \text{inspect traceback} \rightarrow \text{fix} \rightarrow \text{correct answer} \rightarrow R=+1.

Then trajectories resembling Policy B receive the better learning signal.

Over repeated RL updates:

P(\text{error recovery behavior})

can increase.

This is the mechanism by which a self-correction strategy can emerge without a dedicated error-repair reward.

5.24.21 Another major discovery: code's role changes

Before RL, the slide says code is used predominantly for:

\boxed{ 79.1\% }

of code snippets for raw calculation.

After RL:

\boxed{ 51.4\% }

of code snippets are for calculation. (Source: retool-slides)

That means:

79.1\%-51.4\% = \boxed{27.7\text{ percentage points}}

of the distribution shifts away from raw calculation.

5.24.22 Where does that usage go?

The slide identifies new roles including:

\boxed{\text{optimization}}
\boxed{\text{geometric calculation}}
\boxed{\text{solution search}}

So code evolves from:

\boxed{ \text{calculator} }

toward:

\boxed{ \text{general computational reasoning tool} }.

This is an especially important result because it demonstrates that the model learned new uses for the tool, not merely more frequent use of the same calculator behavior. (Source: retool-slides)

5.24.23 Let's quantify that shift

Suppose, purely illustratively, there are:

1000

code snippets before RL.

At 79.1% calculation:

791

are calculation-oriented.

After RL, at 51.4%:

514

are calculation-oriented.

Thus:

791-514 = \boxed{277}

fewer snippets fall into that category.

The remaining:

486

snippets belong to other categories.

These numbers are a direct arithmetic illustration of the percentages reported in the slide, not additional source statistics. (Source: retool-slides)

5.24.24 Why is this result so important?

Because it demonstrates:

\boxed{ \text{tool use} \neq \text{calculator use} }

A sufficiently capable model can learn to use code for:

\text{search}
\text{optimization}
\text{geometry}

and other computational subroutines.

Thus:

\boxed{ \text{external computation becomes part of the reasoning strategy} }

5.24.25 Same question, two reasoning styles

The slide provides a particularly useful comparison.

For the same four-digit-integer problem:

Text-only reasoning

The model performs a long manual modular-arithmetic derivation and reaches:

\boxed{629}

which is wrong.

A single arithmetic mistake propagates through later steps.

Code-interpreter reasoning

The model delegates the arithmetic to two short code blocks and reaches:

\boxed{699}

which is confirmed by the interpreter. (Source: retool-slides)

5.24.26 This illustrates the core advantage

Text-only:

\boxed{ \text{many dependent manual operations} }

A single error:

\boxed{ e_1 \rightarrow e_2 \rightarrow e_3 \rightarrow \cdots }

can corrupt the entire chain.

Tool-assisted:

\boxed{ \text{delegate exact computation} }

and receive:

\boxed{ \text{externally verified intermediate result} }.

The model can then reason from a more reliable computational observation.

5.24.27 Tool use therefore changes the location of computation

This is an excellent mental model.

Before:

\boxed{ \text{LLM} \rightarrow \text{does everything itself} }

After ReTool:

\boxed{ \text{LLM} \leftrightarrow \text{external computation} }

The intelligence is no longer just:

\text{generate tokens}.

It becomes:

\boxed{ \text{decide what to compute internally} + \text{decide what to delegate externally} }

5.24.28 Why this is “agentic RL”

Now the final slide's conclusion makes sense.

The course's progression is:

\boxed{ \text{single answer trajectory} }

then:

\boxed{ \text{long reasoning trajectory} }

then:

\boxed{ \text{reasoning + external actions + feedback} }

That corresponds to:

\boxed{ \text{DeepSeekMath} \rightarrow \text{DeepSeek-R1} \rightarrow \text{ReTool} }

The supplied deck calls this progression toward a richer notion of trajectory and identifies it as the essence of agentic RL. (Source: retool-slides)

5.24.29 The deep connection to our previous lessons

Recall our earlier distinction:

RL
\boxed{ \text{discover / strengthen behavior} }
Distillation
\boxed{ \text{transfer / compress behavior} }

ReTool adds:

\boxed{ \text{discover / strengthen interaction strategy} }

So now the overall evolution is:

\text{reasoning behavior} \rightarrow \text{tool-use behavior} \rightarrow \text{agentic behavior}.

12\times5 = \boxed{60\text{ lines}}.

5.24.31 Exam-style conceptual question

Question:

Why is the emergence of error correction especially strong evidence that ReTool is learning a strategy rather than merely memorizing tool-call syntax?

Because the supplied example shows:

\text{invalid code} \rightarrow \text{real sandbox error} \rightarrow \text{interpretation of error} \rightarrow \text{code repair} \rightarrow \text{successful completion}

without an explicit training example demonstrating that exact repair behavior. The reported explanation is that correctness-only RL makes successful recovery valuable because it increases the probability of eventually obtaining the correct answer. (Source: retool-slides)

5.24.32 Final ReTool behavioral model

By the end of our ReTool sequence, you should mentally see:

\boxed{ \text{Before RL} }
\text{text-heavy} + \text{rare code} + \text{mostly arithmetic use}

and:

\boxed{ \text{After RL} }
\text{shorter overall responses} + \text{very frequent code} + \text{longer/more sophisticated code} + \text{more correct code} + \text{earlier tool invocation} + \text{error recovery}

All of those behaviors emerge under the single correctness objective reported by the deck. (Source: retool-slides)

5.24.33 The most important takeaway

ReTool does not simply teach:

\boxed{ \text{“LLM + calculator”} }

It teaches a policy of:

\boxed{ \text{reason} \rightarrow \text{decide whether computation helps} \rightarrow \text{invoke tool} \rightarrow \text{read feedback} \rightarrow \text{adapt} \rightarrow \text{verify} \rightarrow \text{answer} }

And the remarkable part is that the RL objective does not explicitly specify all those intermediate behaviors.

Instead:

\boxed{ \text{correctness reward} \rightarrow \text{emergent strategy} }

This is the central lesson of Step 5.24. (Source: retool-slides)
