Step 5.31 — IndicGenBench: Why a Second Indic Benchmark Is Needed

Plan node: I11 · chat order #72

We now enter the IndicGenBench material.

This is the natural continuation after IndicXTREME.

The key distinction is:

\boxed{ \text{IndicXTREME asks: “Can the model understand/classify Indic text?”} }

while:

\boxed{ \text{IndicGenBench asks: “Can the model actually generate useful Indic text?”} }

The supplied deck explicitly frames IndicGenBench as a benchmark for generation capabilities such as summarization, translation, and question answering, in contrast to IndicXTREME's classification/NLU emphasis. (Source: indicgenbench-slides)

5.31.1 Start with the problem

Suppose an LLM performs well on an Indic classification task:

\text{Hindi sentence}\rightarrow\text{positive}.

That tells us something about:

\boxed{\text{understanding}}

but a real user often wants the model to produce language.

For example:

\text{English article} \rightarrow \text{Hindi summary}

or:

\text{English sentence} \rightarrow \text{Tamil translation}

or:

\text{Hindi question} \rightarrow \text{Hindi answer}.

These are generation problems.

So the benchmark needs to test:

\boxed{ \text{Can the model produce correct, faithful, fluent Indic-language output?} }

5.31.2 The motivation slide gives a striking result

The deck says that Singh et al. built IndicGenBench to expose a large generation gap:

on every one of five generation tasks, even the best model scores far below its own English performance. (Source: indicgenbench-slides)

So conceptually:

\boxed{ \text{English capability} > \text{Indic generation capability} }

across all five reported generation tasks.

This is important because a multilingual model can appear strong globally while still having a substantial target-language generation deficit.

5.31.3 Why is generation harder to evaluate than classification?

Consider classification:

x\rightarrow y

where y might be:

\{\text{positive, negative}\}.

Evaluation is easy:

\boxed{ \hat y=y? }

Generation is different.

Suppose the gold summary is:

“The mission launched successfully after several delays.”

The model writes:

“After multiple delays, the mission was finally launched successfully.”

Are these equivalent?

Yes, semantically.

But exact string matching would say:

\boxed{\text{different}}

even though the generation is good.

Therefore generation benchmarks need metrics capable of handling:

\boxed{ \text{multiple valid ways of expressing the same meaning} }.

That is why IndicGenBench's metric design becomes important.

5.31.4 Scope of IndicGenBench

The deck defines:

\boxed{29\text{ Indic languages}}

across:

\boxed{13\text{ scripts}}

and:

\boxed{4\text{ language families}}.

The 29 languages are divided into three resource tiers:

\boxed{9\text{ Higher}}
\boxed{7\text{ Medium}}
\boxed{13\text{ Low}}.

(Source: indicgenbench-slides)

This is already a major difference from our previous benchmark discussion.

IndicGenBench explicitly makes resource level a central experimental variable.

5.31.5 “Higher-resource” does NOT mean high-resource globally

This is an important source-specific warning.

The deck gives Hindi as an example:

\boxed{\sim160,000\text{ Wikipedia articles}}

versus:

\boxed{6.6\text{M+ for English}}.

So “Higher” means:

\boxed{ \text{higher relative to other Indic languages} }

not:

\boxed{ \text{high-resource by global standards} }.

(Source: indicgenbench-slides)

This prevents a very common misinterpretation.

5.31.6 Why classify languages into resource tiers?

Because we want to ask:

\boxed{ \text{Does generation quality decline as language resources decline?} }

So instead of reporting only one average:

\text{Average performance}=X,

we can investigate:

\boxed{ \text{Higher} \rightarrow \text{Medium} \rightarrow \text{Low} }

and observe whether performance follows the same direction.

The later results slide says it does: performance drops from High to Medium to Low across every task. (Source: indicgenbench-slides)

5.31.7 The five generation tasks

IndicGenBench contains five generation tasks.

The deck describes them as:

\boxed{\text{CrossSum-IN}}

cross-lingual summarization,

\boxed{\text{FLORES-IN}}

machine translation,

\boxed{\text{XQuAD-IN}}

multilingual QA,

and two versions of:

\boxed{\text{XorQA-IN}}

cross-lingual QA. (Source: indicgenbench-slides)

So:

\boxed{ 1+1+1+2=5 }

generation tasks.

5.31.8 Why does the benchmark mostly translate existing datasets?

This is one of the most important design decisions in the deck.

Instead of creating every benchmark entirely from scratch, the researchers start with existing English-source benchmarks:

\boxed{\text{CrossSum}}
\boxed{\text{FLORES-200}}
\boxed{\text{XQuAD}}
\boxed{\text{XOR-TyDi}}.

Then they add professional human translations into Indic languages. (Source: indicgenbench-slides)

At first this may seem like a weakness:

Why not create everything directly in Indic languages?

The deck gives three explicit reasons.

5.31.9 Reason 1 — Multi-way parallel data

Suppose we start from the same source example:

x

and create:

y_{\text{Hindi}}, y_{\text{Tamil}}, y_{\text{Bengali}}, \ldots

all corresponding to the same source.

Now comparisons become much cleaner.

We can ask whether a model's performance difference comes from:

\boxed{\text{language}}

rather than:

\boxed{\text{different underlying task content}}.

This is exactly why the deck values multi-way parallel data. (Source: indicgenbench-slides)

5.31.10 Example

Suppose the source is one English sentence:

x=\text{“The satellite launched successfully.”}

Create translations into:

\text{Hindi}
\text{Tamil}
\text{Bengali}

and so on.

Because every language began with the same x, comparisons become:

\boxed{ \text{same task} + \text{same underlying content} + \text{different target language} }

which is very useful for studying cross-lingual generalization.

5.31.11 Reason 2 — Clean source text may not exist in low-resource languages

Suppose researchers want to build a fresh QA dataset in a very low-resource language.

They need:

\text{clean documents} + \text{questions} + \text{answers} + \text{quality control}.

But high-quality source material may not exist at sufficient scale.

The deck specifically points out that some low-resource languages do not have clean knowledge corpora such as Wikipedia at the level needed for fresh dataset construction. (Source: indicgenbench-slides)

Translation provides a way around that.

Instead of:

\boxed{ \text{find huge clean Indic source corpus} }

we can:

\boxed{ \text{start from already-developed English benchmark} }

and translate it.

5.31.12 Reason 3 — Reuse existing quality control

Existing datasets have already gone through substantial:

\text{design}
\text{validation}
\text{quality control}.

So IndicGenBench can inherit that work and focus additional effort on:

\boxed{ \text{high-quality human Indic translation} }.

The deck explicitly lists this as its third motivation. (Source: indicgenbench-slides)

5.31.13 This is an important benchmark-design tradeoff

Translation-based construction gives:

\boxed{ \text{comparability} + \text{scalability} + \text{reusable task design} }

but introduces another possible problem:

\boxed{ \text{translation artifacts/errors} }.

And the deck later demonstrates exactly that translation quality matters, especially for some tasks. (Source: indicgenbench-slides)

So the design tradeoff is:

\boxed{ \text{clean common source} \quad\text{vs}\quad \text{native-language authenticity} }

and the benchmark tries to balance the two through professional human translation.

5.31.14 Human translators

The deck says the translators were:

\boxed{\text{professional data labelers}}

working through the authors' organization and an external vendor.

They were paid competitively according to the labor laws and prevailing market rates of each region. (Source: indicgenbench-slides)

One reported detail is particularly interesting:

\boxed{2.80\text{ USD/hour}}

for Pashto versus:

\boxed{15.90\text{ USD/hour}}

for Tibetan.

That is a:

\frac{15.90}{2.80} \approx \boxed{5.68\times}

difference, which the slide summarizes as a:

\boxed{5.7\times}

pay range across languages. (Source: indicgenbench-slides)

5.31.15 Why is this mentioned in a technical lecture?

Because dataset construction is not just:

\boxed{\text{NLP algorithm}}

It is also:

\boxed{ \text{human annotation process} + \text{labor practices} + \text{quality control} }.

The quality of a benchmark depends on the people producing and validating its data.

5.31.16 First major task: CrossSum-IN

Now we begin the individual task architecture.

\boxed{\text{CrossSum-IN}}

is cross-lingual summarization.

The source benchmark is:

\boxed{\text{CrossSum}}

which itself comes from:

\boxed{\text{XL-Sum}}

and is based on BBC news articles and summaries across languages. (Source: indicgenbench-slides)

The generation task is:

\boxed{ \text{article} \rightarrow \text{summary in target language} }

5.31.17 Why is this “cross-lingual” summarization?

The source article and target summary can involve different languages.

In the benchmark's construction, the deck starts from English article-summary pairs and creates target-language summaries.

The key requirement is that the model should generate the summary:

\boxed{ \text{directly in the target language} }

rather than:

\text{source} \rightarrow \text{English intermediate} \rightarrow \text{target}.

The example slide explicitly emphasizes faithful compressed generation directly in the target language. (Source: indicgenbench-slides)

5.31.18 CrossSum-IN construction

For each language, the dataset uses:

\boxed{ 100\text{ train} + 100\text{ dev} + 500\text{ test} }

examples.

Thus:

100+100+500 = \boxed{700}

examples per language.

There are:

\boxed{29\text{ languages}}.

Therefore:

700\times29 = \boxed{20,300}

examples total.

The deck explicitly reports this number and confirms it by direct arithmetic. (Source: indicgenbench-slides)

5.31.19 Numerical exam question

Given:

29\text{ languages}

and:

700\text{ examples/language},

compute total examples:

29\times700 = \boxed{20,300}.

Then:

Training examples:

29\times100 = \boxed{2,900}.

Development:

29\times100 = \boxed{2,900}.

Test:

29\times500 = \boxed{14,500}.

Check:

2900+2900+14500 = \boxed{20,300}.

5.31.20 Second major task: FLORES-IN

The next task is:

\boxed{\text{FLORES-IN}}

for machine translation.

The source dataset is:

\boxed{\text{FLORES-200}}.

Unlike CrossSum, FLORES already contains high-quality human-annotated multilingual parallel data.

So IndicGenBench reuses as much as possible and translates into languages not already covered. (Source: indicgenbench-slides)

5.31.21 FLORES split structure

The source FLORES-200 split has:

\boxed{997\text{ dev}}
\boxed{1012\text{ devtest}}
\boxed{992\text{ test}}

but the deck says the non-public test is not used for this construction.

Therefore:

997+1012 = \boxed{2009}

sentences per language.

For:

29

languages:

2009\times29 = \boxed{58,261}

examples.

The slide reports approximately:

\boxed{58.2K}.

(Source: indicgenbench-slides)

5.31.22 Important exception

The deck says FLORES-IN is:

\boxed{\text{the only task with no training split}}

in IndicGenBench.

Why?

Because this is fundamentally a benchmark of translation over an established parallel evaluation set, and the source FLORES structure is reused directly rather than creating a new task-specific training split for the benchmark. (Source: indicgenbench-slides)

5.31.23 What does FLORES-IN actually ask the model to do?

Very simply:

\boxed{ \text{source sentence} \rightarrow \text{target-language sentence} }

No question.

No long context.

No multiple-choice alternatives.

Just translation.

The deck emphasizes that the same source sentence is represented across all target languages, making the dataset n-way parallel. (Source: indicgenbench-slides)

5.31.24 Why is n-way parallelity valuable?

Suppose:

x_{\text{English}}

has translations:

y_{\text{Hindi}}, y_{\text{Tamil}}, y_{\text{Punjabi}}, y_{\text{Bengali}}, \ldots

Then each language is being tested against the same semantic source.

Thus:

\boxed{ \text{language comparison becomes cleaner} }

because the underlying content is held constant.

5.31.25 Third task: XQuAD-IN

The next task is:

\boxed{\text{XQuAD-IN}}

for multilingual reading comprehension / QA.

The source is:

\boxed{\text{XQuAD}}

which itself derives from:

\boxed{\text{SQuAD}}

and contains English Wikipedia passages and short-span questions/answers. (Source: indicgenbench-slides)

The generation problem is:

\boxed{ \text{context + question} \rightarrow \text{answer} }

in the target language.

5.31.26 Fourth and fifth tasks: XorQA-IN

This is particularly interesting because one underlying translation effort produces two tasks.

The source is:

\boxed{\text{XOR-TyDi}}.

The original data has:

\boxed{\text{non-English question}}

paired with:

\boxed{\text{English evidence passage}}

and an answer.

(Source: indicgenbench-slides)

IndicGenBench expands this into:

\boxed{\text{XorQA-IN-EN}}

and:

\boxed{\text{XorQA-IN-XX}}.

We will study the exact distinction in the next step.

5.31.27 Why two variants?

Because the model can be asked to:

Variant 1

Read a target-language question, retrieve evidence from English, and answer in:

\boxed{\text{English}}.
Variant 2

Read the same kind of cross-lingual setup but generate the answer in:

\boxed{\text{the target language}}.

So these test different abilities.

5.31.28 First major metric: chrF

For:

\boxed{\text{CrossSum-IN}}

and:

\boxed{\text{FLORES-IN}},

the benchmark uses:

\boxed{\text{chrF}}

or character-level F-score.

The deck specifically chooses character-level scoring because token-based metrics such as:

\boxed{\text{ROUGE}}

and:

\boxed{\text{BLEU}}

can be unreliable for low-resource languages, where tokenization itself may be problematic. (Source: indicgenbench-slides)

5.31.29 Why character-level evaluation?

Suppose a tokenizer splits one word into:

5

subword pieces in one language but only:

1

piece in another.

Then a token-level metric can become sensitive to tokenizer behavior.

Character-level comparison is less dependent on the model's subword segmentation.

So conceptually:

\boxed{ \text{tokenization artifact} \downarrow }

when moving from token-level to character-level evaluation.

The source specifically motivates chrF on this basis. (Source: indicgenbench-slides)

5.31.30 Second metric family: token F1

For:

\boxed{\text{XQuAD-IN}}

and both:

\boxed{\text{XorQA-IN}}

variants, the benchmark uses:

\boxed{\text{token-overlap F1}}.

This is inherited from the SQuAD-style QA literature. (Source: indicgenbench-slides)

Recall:

Precision=\frac{TP}{TP+FP}
Recall=\frac{TP}{TP+FN}

and:

\boxed{ F1= \frac{2PR}{P+R} }.

5.31.31 So the benchmark has two metric families

\boxed{ \text{Generation of free text} \rightarrow \text{chrF} }

for:

\text{summary}

and:

\text{translation}.

While:

\boxed{ \text{short-span QA} \rightarrow \text{token F1} }

because the answer is expected to overlap a gold answer span.

This is an important exam distinction.

5.31.32 Numerical chrF intuition

The source does not give the underlying chrF formula on this slide, so we should not invent a full implementation equation and pretend it comes from the deck.

The safe understanding is:

\boxed{ \text{chrF compares character-level n-gram overlap using an F-score formulation} }

which reduces sensitivity to subword/tokenization differences.

That is the benchmark-design lesson supported by the source. (Source: indicgenbench-slides)

5.31.33 IndicGenBench vs IndicXTREME

Now the distinction should be crystal clear.

IndicXTREME IndicGenBench
Primarily NLU Primarily generation
Classification-heavy Summarization/translation/QA
Accuracy/F1 chrF/token F1
9 tasks 5 generation tasks
Tests understanding/transfer Tests output generation
20-language contribution scope stated in deck 29-language scope

The first five columns are conceptual descriptions grounded in the supplied decks. The language counts come directly from their respective slides. (Source: indicgenbench-slides)

5.31.34 The important conceptual relationship

We should not think:

\boxed{ \text{IndicXTREME vs IndicGenBench} = \text{same benchmark twice} }

Instead:

\boxed{ \text{IndicXTREME} = \text{Can the model understand?} }

and:

\boxed{ \text{IndicGenBench} = \text{Can the model generate?} }

A model can be strong at one and weak at the other.

5.31.35 Why is that scientifically important?

Imagine a model with:

90\%

classification performance.

But when asked to generate an Indic summary, its chrF is poor.

Then:

\boxed{ \text{understanding capability} \not\Rightarrow \text{generation capability} }

This is one of the central gaps that IndicGenBench is designed to expose. (Source: indicgenbench-slides)

5.31.37 Exam-style conceptual question

Question:

Why does IndicGenBench translate established benchmarks instead of constructing every dataset from scratch?

The deck gives three reasons:

\boxed{ \text{multi-way parallel data} }

for separating task knowledge from language effects and measuring cross-lingual generalization,

\boxed{ \text{lack of clean source data for many low-resource languages} }

and:

\boxed{ \text{reuse of existing benchmark quality control} }.

(Source: indicgenbench-slides)

5.31.38 Exam-style conceptual question

Question:

Why does IndicGenBench use chrF for summarization and translation rather than simply BLEU/ROUGE?

Because the deck argues that token-level metrics can be unreliable for low-resource languages where tokenization itself is a weak link. Character-level F-score reduces this dependence. (Source: indicgenbench-slides)

5.31.39 The deeper lesson

IndicGenBench is not merely “another multilingual benchmark.”

It addresses a different failure mode:

\boxed{ \text{A model can understand an Indic language without being able to generate it well.} }

Therefore the evaluation chain becomes:

\boxed{ \text{IndicCorp} \rightarrow \text{pretraining resources} }
\downarrow
\boxed{ \text{IndicXTREME} \rightarrow \text{understanding/NLU evaluation} }
\downarrow
\boxed{ \text{IndicGenBench} \rightarrow \text{generation evaluation} }

Together they give a much more complete view of multilingual Indic capability.

5.31.40 Final mental model

Remember:

\boxed{ \text{IndicXTREME} = \text{UNDERSTAND} }
\boxed{ \text{IndicGenBench} = \text{GENERATE} }

IndicGenBench covers:

\boxed{29\text{ languages}}
\boxed{13\text{ scripts}}
\boxed{4\text{ families}}
\boxed{3\text{ resource tiers}}

and:

\boxed{5\text{ generation tasks}}.

(Source: indicgenbench-slides)

Its construction philosophy is:

\boxed{ \text{existing high-quality benchmark} \rightarrow \text{professional human translation} \rightarrow \text{parallel Indic evaluation} }

rather than rebuilding the entire task ecosystem from scratch.

And the first major warning is already visible:

\boxed{ \text{even the best models perform substantially worse in Indic generation than in English} }

across all five generation tasks in the benchmark's reported analysis. (Source: indicgenbench-slides)
