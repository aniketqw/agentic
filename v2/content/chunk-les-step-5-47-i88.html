Step 5.47 — The Full DeepSeek Distributed-Training Stack

Plan node: A5 · chat order #88

We have now reached the point where the architecture itself is understood. The next question is:

\boxed{\text{How do we train this enormous model efficiently across many GPUs?}}

The source builds this progressively:

\boxed{ \text{Gradient Accumulation} \rightarrow \text{Data Parallelism} \rightarrow \text{Model/Pipeline Parallelism} \rightarrow \text{Expert Parallelism} \rightarrow \text{1F1B} \rightarrow \text{DualPipe} }

The central lesson is that each optimization solves one bottleneck and often exposes another. (Source: Build a DeepSeek Model (From Scratch))

5.47.1 First: one GPU is not enough

Our DeepSeek-style model contains:

\boxed{\text{MLA}}
\boxed{\text{MoE}}

and potentially hundreds of billions of parameters.

The source's DeepSeek-R1 example has:

671B

total parameters and:

37B

active per token. Yet the entire model weights still need to remain available. (Source: Build a DeepSeek Model (From Scratch))

So we need multiple GPUs.

But there are several ways to distribute the workload.

5.47.2 The first distinction: split data or split model?

There are two fundamental approaches in the source:

\boxed{\text{Data Parallelism}}

and:

\boxed{\text{Model Parallelism}}.

(Source: Build a DeepSeek Model (From Scratch))

The difference is extremely simple:

Data Parallelism

Keep copies of the model, split the data.

Model Parallelism

Split the model itself across GPUs.

5.47.3 Data Parallelism

Suppose you have:

4

GPUs.

Instead of processing one batch on one GPU:

Batch
  ↓
GPU 0

we split the batch:

             Batch
          /    |    |    \
         ↓     ↓    ↓     ↓
       GPU0  GPU1  GPU2  GPU3

Each GPU owns a replica of the model.

The source explicitly describes Data Parallelism this way: replicate the model and give each device a different shard of the batch. (Source: Build a DeepSeek Model (From Scratch))

5.47.4 Why data parallelism speeds training

Suppose one GPU takes:

100\text{ ms}

to process:

32

examples.

Four GPUs can process:

4\times32=128

examples approximately concurrently, subject to communication and scaling efficiency.

So throughput can approach:

\boxed{4\times}

in the ideal case.

But there is a major problem.

5.47.5 The data-parallel memory problem

Every GPU has a full copy of:

\boxed{\text{the model}}.

If the model is:

671B

parameters, replicating it on every GPU is obviously impossible.

The source explicitly says DDP does not solve the model-memory problem because every GPU contains the full model. (Source: Build a DeepSeek Model (From Scratch))

Thus:

\boxed{ \text{DDP solves throughput} }

but not:

\boxed{ \text{model-too-large} }.

5.47.6 Gradient accumulation

Before moving into model parallelism, the source introduces Gradient Accumulation.

Suppose your desired effective batch is:

B_{\text{eff}}=64

but your GPU can only fit:

B_{\text{physical}}=16.

Then:

N_{\text{acc}} = \frac{64}{16} = \boxed{4}.

The source derives this relationship explicitly. (Source: Build a DeepSeek Model (From Scratch))

5.47.7 Why gradient accumulation works

For a batch of B examples:

g_{\text{batch}} = \frac1B \sum_{i=1}^{B}g_i.

Instead of calculating all gradients at once, divide the batch into chunks.

Suppose:

g_1,g_2,g_3,g_4

are the gradients for four mini-batches.

Then accumulate:

g_{\text{acc}} = g_1+g_2+g_3+g_4

with appropriate normalization.

Then perform one optimizer update.

The source emphasizes that this lets a smaller physical batch simulate a larger effective batch without requiring all examples simultaneously in VRAM. (Source: Build a DeepSeek Model (From Scratch))

5.47.8 Numerical

Physical batch:

16

Accumulation steps:

4.

Effective batch:

16\times4 = \boxed{64}.

Another example:

B_{\text{physical}}=8

and:

N_{\text{acc}}=16.

Then:

\boxed{ B_{\text{effective}}=128. }

5.47.9 Important distinction

Gradient accumulation does not mean:

\boxed{\text{the GPU suddenly has more VRAM}}.

It means:

\boxed{ \text{process smaller pieces sequentially} }

instead of:

\boxed{ \text{process the entire effective batch simultaneously}. }

So:

\boxed{ \text{memory}\downarrow }

but:

\boxed{ \text{number of forward/backward iterations}\uparrow }.

5.47.10 Now model parallelism

Suppose the model itself is too large for one GPU.

Then:

\boxed{ \text{split the model}. }

The source describes this as Model Parallelism. (Source: Build a DeepSeek Model (From Scratch))

Two major forms in the source's discussion are:

\boxed{\text{Pipeline Parallelism}}

and other forms such as tensor/model splitting.

For the DeepSeek story, pipeline parallelism and expert parallelism are particularly important.

5.47.11 Pipeline Parallelism

Suppose there are:

8

Transformer stages.

Split them across:

8

GPUs:

GPU0 → Stage 0
GPU1 → Stage 1
GPU2 → Stage 2
GPU3 → Stage 3
GPU4 → Stage 4
GPU5 → Stage 5
GPU6 → Stage 6
GPU7 → Stage 7

A batch enters GPU 0.

Its activation flows:

GPU_0 \rightarrow GPU_1 \rightarrow GPU_2 \rightarrow\cdots\rightarrow GPU_7.

The source compares this to an assembly line. (Source: Build a DeepSeek Model (From Scratch))

5.47.12 Why micro-batches are necessary

Suppose the whole batch is treated as one unit.

Then the pipeline becomes:

GPU0: █████
GPU1:      █████
GPU2:           █████
GPU3:                █████
...

Most GPUs spend much of the time waiting.

To keep the pipeline active, split the batch into:

M

micro-batches.

Example:

B=64

could be split into:

M=8

micro-batches of:

8

samples each.

5.47.13 The pipeline idea

Instead of:

m_1

moving through all 8 stages before:

m_2

starts, we pipeline them:

Time →
GPU0: m1 m2 m3 m4 m5 ...
GPU1:    m1 m2 m3 m4 ...
GPU2:       m1 m2 m3 ...
GPU3:          m1 m2 ...
...

This is what makes pipeline parallelism useful.

5.47.14 The problem: Pipeline Bubble

At the beginning:

GPU_0

starts first.

Other GPUs must wait.

At the end:

later GPUs finish before earlier GPUs have fully drained.

This creates:

\boxed{\text{Pipeline Bubble}}.

The source defines this as idle time while stages wait for activations or gradients. (Source: Build a DeepSeek Model (From Scratch))

5.47.15 Bubble formula

In the simplified equal-time model used by the source:

\boxed{ \eta_{\text{pipeline}} = \frac{M}{M+(P-1)} }

where:

  • M = number of micro-batches,
  • P = number of pipeline stages.

The source gives the example:

M=8,\quad P=4.

Thus:

\eta= \frac8{8+3} = \frac8{11} \approx \boxed{72.7\%}.

(Source: Build a DeepSeek Model (From Scratch))

5.47.16 Numerical: increase micro-batches

Suppose:

P=4.
M=8
\eta= \frac8{11} = 72.7\%.
M=32
\eta= \frac{32}{35} = \boxed{91.4\%}.
M=128
\eta= \frac{128}{131} = \boxed{97.7\%}.

So:

\boxed{ M\uparrow \Rightarrow \text{bubble fraction}\downarrow. }

5.47.17 Why not just use enormous M?

Because each forward pass creates activations needed by backward.

The source explains that naive GPipe can require holding activations from many micro-batches, increasing memory usage. (Source: Build a DeepSeek Model (From Scratch))

So:

M\uparrow

helps:

\text{pipeline efficiency}

but can hurt:

\text{activation memory}.

5.47.18 1F1B

The source then introduces the 1F1B schedule.

The core principle:

\boxed{ \text{Don't run all forwards first.} }

Instead:

\boxed{ \text{Forward one micro-batch, then backward another as soon as dependencies allow.} }

The schedule has:

\boxed{\text{warm-up}}
\boxed{\text{steady state}}
\boxed{\text{cool-down}}.

(Source: Build a DeepSeek Model (From Scratch))

5.47.19 Why 1F1B matters

Suppose GPU 2 finishes the forward pass of:

m_3.

Rather than waiting for:

m_4,m_5,\ldots

to finish their forwards, it can begin useful backward work once the necessary downstream gradients are available.

Therefore the GPU spends less time holding unused activations.

This makes 1F1B much more memory-efficient than naive GPipe. (Source: Build a DeepSeek Model (From Scratch))

5.47.20 So far the progression is

\boxed{\text{Pipeline Parallelism}}

solves:

\text{model too large}.

But creates:

\boxed{\text{pipeline bubble}}.

Then:

\boxed{\text{1F1B}}

reduces the practical impact of that bubble and lowers activation-memory pressure.

But then DeepSeek adds:

\boxed{\text{MoE}}.

And now we discover another bottleneck.

5.47.21 Expert Parallelism

Remember our distributed experts:

GPU0 → E1,E2
GPU1 → E3,E4
GPU2 → E5,E6
GPU3 → E7,E8

A token may be on GPU 0 but select:

E_7.

Therefore:

\boxed{ \text{token must move across GPUs} }.

That is:

\boxed{\text{Expert Parallelism + All-to-All communication}}.

The source explicitly identifies distributed experts and this cross-GPU token exchange as the MoE scaling problem. (Source: Build a DeepSeek Model (From Scratch))

5.47.22 Why 1F1B is no longer enough

Imagine:

T_{\text{compute}}=8\text{ ms}

and:

T_{\text{All-to-All}}=10\text{ ms}.

Suppose 1F1B schedules compute normally.

A GPU can now spend:

10\text{ ms}

waiting for communication.

So even though we solved the traditional pipeline bubble, we have reintroduced idle time through communication.

The source explicitly states that MoE All-to-All communication can become more expensive than the pipeline bubble itself. (Source: Build a DeepSeek Model (From Scratch))

5.47.23 This is the central DeepSeek systems problem

We now have:

\boxed{ \text{Pipeline bubble} }

and:

\boxed{ \text{MoE communication} }.

We need a schedule that handles both.

This leads to:

\boxed{\text{DualPipe}}.

5.47.24 DualPipe's central idea

Suppose:

A = \text{communication}.

And:

B = \text{computation}.

Naive:

A\rightarrow B.

Time:

T_A+T_B.

DualPipe tries to arrange:

\boxed{ A\parallel B }

for operations belonging to different micro-batches.

Ideal time:

\boxed{ \max(T_A,T_B) }

rather than:

T_A+T_B.

The source describes exactly this fine-grained overlap of communication-heavy and compute-heavy operations. (Source: Build a DeepSeek Model (From Scratch))

5.47.25 Numerical

Suppose:

T_{\text{comm}}=12\text{ ms}

and:

T_{\text{compute}}=8\text{ ms}.

Sequential:

12+8 = \boxed{20\text{ ms}}.

Ideal overlap:

\max(12,8) = \boxed{12\text{ ms}}.

Potential speedup:

20/12 = \boxed{1.67\times}.

Potentially hidden communication:

20-12 = \boxed{8\text{ ms}}.

This is an idealized calculation.

5.47.26 What exactly is overlapped?

The source says DualPipe breaks large operations into finer pieces such as:

\boxed{\text{Attention}}
\boxed{\text{MLP / Expert}}
\boxed{\text{All-to-All}}

and schedules them against one another. (Source: Build a DeepSeek Model (From Scratch))

So the scheduler may conceptually arrange:

Micro-batch 1 → All-to-All
Micro-batch 2 → Expert compute
Micro-batch 3 → Attention
Micro-batch 4 → Backward

at overlapping times where dependencies permit.

5.47.27 Why “fine-grained” matters

Suppose the scheduler only knows:

\text{whole forward pass}

and:

\text{whole backward pass}.

It has relatively few opportunities to overlap communication.

Instead, break the computation into:

\text{Attention} \rightarrow \text{dispatch} \rightarrow \text{Expert} \rightarrow \text{combine}

and backward components.

Now the scheduler has much finer opportunities to place independent work in communication gaps.

This is the source's main scheduling insight. (Source: Build a DeepSeek Model (From Scratch))

5.47.28 Pipeline folding

DualPipe adds another idea:

\boxed{\text{pipeline folding}}.

Suppose there are:

8

stages.

Normal:

GPU0 → Stage 0
GPU1 → Stage 1
GPU2 → Stage 2
GPU3 → Stage 3
GPU4 → Stage 4
GPU5 → Stage 5
GPU6 → Stage 6
GPU7 → Stage 7

Folded:

GPU0 → Stage 0 + Stage 7
GPU1 → Stage 1 + Stage 6
GPU2 → Stage 2 + Stage 5
GPU3 → Stage 3 + Stage 4

The source gives exactly this 8-stage/4-rank example. (Source: Build a DeepSeek Model (From Scratch))

5.47.29 Why is this called V-shaped?

A micro-batch moves:

Stage0 \rightarrow Stage1 \rightarrow Stage2 \rightarrow Stage3

then:

Stage4

on the same device.

Then:

Stage4 \rightarrow Stage5 \rightarrow Stage6 \rightarrow Stage7.

So physically:

\boxed{ \text{down} \rightarrow \text{turn} \rightarrow \text{up} }

which forms a V.

The source calls this:

\boxed{\text{DualPipeV}}

or:

\boxed{\text{V-shape / cut-in-half schedule}}.

(Source: Build a DeepSeek Model (From Scratch))

5.47.30 Numerical — folded pipeline

Suppose:

N=16

stages.

Source-style DualPipeV:

N/2 = \boxed{8}

physical GPUs.

Each GPU holds:

\boxed{2\text{ stages}}.

Therefore parameter memory per GPU is approximately:

\boxed{2\times}

the one-stage-per-GPU arrangement.

This is an explicit trade-off described by the source. (Source: Build a DeepSeek Model (From Scratch))

5.47.31 Why accept 2× parameter memory?

Because we are getting:

\boxed{ \text{fewer physical GPUs} }

and:

\boxed{ \text{better utilization / communication hiding} }.

The source describes this as a deliberate engineering trade-off rather than an unconditional improvement. (Source: Build a DeepSeek Model (From Scratch))

5.47.33 Very important: these techniques are complementary

Don't think:

\text{Data Parallelism OR Pipeline Parallelism}.

\boxed{ \text{Data Parallelism} + \text{Model/Pipeline Parallelism} + \text{Expert Parallelism} }

5.47.34 A concrete 8-GPU mental model

Imagine:

8

GPUs.

The model is split into:

4

pipeline stages.

Each stage may span two GPUs or be further sharded, while experts are distributed separately.

Then:

\boxed{ \text{data} }

is divided across replicas,

while:

\boxed{ \text{layers} }

are distributed through pipeline parallelism,

while:

\boxed{ \text{experts} }

are distributed through expert parallelism.

This is a conceptual composition; actual production layouts depend on the particular parallelism dimensions.

5.47.35 Effective batch-size numerical

Suppose:

B_{\text{micro}}=4

samples per physical micro-batch.

There are:

8

micro-batches per data-parallel step.

And:

4

data-parallel replicas.

Then the effective examples represented in one synchronized update can be conceptualized as:

4\times8\times4 = \boxed{128}.

That combines:

\boxed{ \text{physical batch} \times \text{accumulation} \times \text{data-parallel replicas} }.

This is a derived bookkeeping formula; exact framework semantics depend on what is called a “step.”

5.47.36 Now add sequence length

For an LLM, each example may have:

S

tokens.

Suppose:

128

sequences and:

S=2048.

Then token count per effective batch is:

128\times2048 = \boxed{262,144\text{ tokens}}.

This matters because MoE routing and attention both operate over tokens, while communication volume grows with routed token representations.

5.47.37 MoE routing at cluster scale

Suppose:

T=262,144

tokens,

k=8.

Then total routed assignments:

T k = 262,144\times8
= \boxed{2,097,152}.

Suppose:

N=128

experts.

Ideal assignment count per expert:

2,097,152/128 = \boxed{16,384}.

That is the target around which load balancing tries to keep expert utilization.

5.47.38 Why balancing becomes increasingly important

Suppose one expert receives:

25,000

assignments rather than:

16,384.

That means the GPU hosting that expert may process much more data.

So at cluster scale:

\boxed{ \text{expert imbalance} \rightarrow \text{GPU imbalance} \rightarrow \text{communication imbalance} \rightarrow \text{throughput loss} }.

This is why the source's load-balancing mechanism is not just an abstract ML regularizer.

5.47.39 Full pipeline-bubble numerical

Suppose:

P=8

pipeline stages.

And:

M=64

micro-batches.

Using the source's simplified formula:

\eta= \frac{64}{64+7} = \frac{64}{71}.

Therefore:

\boxed{ \eta\approx90.14\% }.

Bubble fraction:

1-\frac{64}{71} = \boxed{9.86\%}.

So almost 10% of the theoretical schedule is bubble overhead under this simplified model.

5.47.40 What if M=512?

\eta= \frac{512}{512+7} = \frac{512}{519}
\approx \boxed{98.65\%}.

Excellent theoretical utilization.

But now activation-memory requirements and scheduling complexity become important.

Thus:

\boxed{ \text{high theoretical utilization} \neq \text{automatically optimal real system} }.

That is one of the source's most important practical lessons.

5.47.41 Full communication numerical

Suppose:

T=65,536

tokens,

k=8,
D=4096,

FP16.

Gross routed representation volume:

TkD(2).

Calculate:

65,536\times8 = 524,288.

Each token representation:

4096\times2 = 8192\text{ bytes}.

Therefore:

524,288\times8192 = \boxed{4,294,967,296\text{ bytes}}.

Approximately:

\boxed{4\text{ GB}}

of gross routed-token representation data.

Again, this is not automatically network traffic, because some assignments can be local and real implementations add protocol/padding/collective overhead.

5.47.42 Now combine communication and pipeline scheduling

Imagine:

T_{\text{attention}}=5\text{ ms}
T_{\text{expert}}=8\text{ ms}
T_{\text{All-to-All}}=10\text{ ms}
T_{\text{backward}}=9\text{ ms}.

A naive sequence might expose much of:

5+10+8+9 = \boxed{32\text{ ms}}.

A well-overlapped schedule can potentially arrange portions of:

10\text{ ms communication}

alongside:

8\text{ ms expert compute}

and:

9\text{ ms backward work}.

The achievable result depends on resource contention and dependencies; it is not simply:

\max(5,8,10,9)

in a real system.

But the optimization goal is to make as little communication as possible appear on the critical path.

That is the source's meaning of DualPipe's “hiding” of communication. (Source: Build a DeepSeek Model (From Scratch))

5.47.43 What DualPipe does NOT mean

It does not mean:

\boxed{ \text{communication becomes free} }

It means:

\boxed{ \text{communication overlaps with useful work} }.

Therefore:

\text{latency still exists},

but its contribution to:

\text{critical-path time}

can be reduced.

5.47.50 Final mental model

The entire engineering journey is:

\boxed{ \text{One GPU} }

↓

too little memory / too slow.

\boxed{\text{Gradient Accumulation}}

↓

larger effective batch.

\boxed{\text{Data Parallelism}}

↓

more throughput.

\boxed{\text{Pipeline Parallelism}}

↓

model can span GPUs.

\boxed{\text{Micro-batches + 1F1B}}

↓

reduce pipeline idle time.

\boxed{\text{MoE + Expert Parallelism}}

↓

massive parameter capacity with distributed experts.

But:

\boxed{\text{All-to-All}}

creates another bottleneck.

Finally:

\boxed{\text{DualPipe}}

uses:

\boxed{ \text{folded pipeline} + \text{fine-grained compute/communication overlap} }

to keep the hardware busy.

That is the complete distributed-systems story behind training the DeepSeek-style architecture described by the source. (Source: Build a DeepSeek Model (From Scratch))
