Step 5.27 — IndicCorp v2: Building the Indic Pretraining Corpus

Plan node: I10 · chat order #68

Now we go through IndicCorp v2 from raw web sources to the final 20.9B-token corpus, exactly in the order of the supplied deck.

The central pipeline is:

\boxed{ \text{Discover sources} \rightarrow \text{Human verify} \rightarrow \text{Crawl} \rightarrow \text{Language filter} \rightarrow \text{Script filter} \rightarrow \text{Punctuation/length filter} \rightarrow \text{Offensive-content filter} \rightarrow \text{Deduplicate} \rightarrow 20.9B\text{ tokens} }

The important idea is that large-scale web collection is not treated as “just scrape everything.” The corpus uses a quality gate before crawling and multiple automatic cleaning stages afterward. (Source: indicxtreme-slides)

5.27.1 First: what is IndicCorp v2?

IndicCorp v2 is the pretraining corpus component of the overall Indic work.

The deck describes it as:

\boxed{20.9\text{B tokens}}

across:

\boxed{24\text{ languages}}

and:

\boxed{4\text{ language families}}.

Its purpose is to provide substantially better Indic-language monolingual pretraining data. (Source: indicxtreme-slides)

Remember the separation:

\boxed{ \text{IndicCorp}=\text{training data} }
\boxed{ \text{IndicXTREME}=\text{evaluation benchmark} }
\boxed{ \text{IndicBERT v2}=\text{model trained on IndicCorp and evaluated on IndicXTREME} }

5.27.2 Step 1 — Find good source websites

The first question is:

Where should the text come from?

The deck says the corpus prioritizes clean, diverse text, and therefore chooses news articles as the primary source.

This is a deliberate departure from generic web corpora such as:

\boxed{\text{CC-100}}

and:

\boxed{\text{mC4}}.

(Source: indicxtreme-slides)

5.27.3 Why news?

Think about the alternatives.

A generic CommonCrawl-style dump may contain:

\text{forums} + \text{blogs} + \text{spam} + \text{machine-generated pages} + \text{duplicated pages} + \text{navigation text} + \text{advertising} + \text{clean articles}.

A news source is much more likely to provide structured natural-language prose.

So the corpus construction process deliberately prioritizes:

\boxed{ \text{high-quality source domains} }

rather than simply maximizing raw token count.

This is source-derived from the deck; the expanded list of typical web-noise categories is explanatory context.

5.27.4 Step 2 — Discover new sources

The researchers did not rely only on existing IndicCorp v1 sources.

The deck says new sources were found using:

\boxed{\text{news repositories}}

and:

\boxed{\text{automatic web search}}.

The search queries are generated from frequent words in the target language. Retrieved pages are then inspected to identify candidate source URLs. (Source: indicxtreme-slides)

5.27.5 Why use frequent words as search queries?

Suppose the target language is Hindi.

A corpus builder can obtain frequent Hindi words and use them as search queries.

Conceptually:

w_1,w_2,\ldots,w_k

are frequent words.

Then:

w_i \rightarrow \text{search engine} \rightarrow \text{candidate pages} \rightarrow \text{candidate source domains}.

This increases the chance of discovering websites that actually publish text in the target language.

The deck emphasizes that this discovery stage is noisy. (Source: indicxtreme-slides)

5.27.6 Why is source discovery noisy?

Because a page retrieved using a language-specific word does not guarantee:

\boxed{ \text{clean Indic-language text} }.

A retrieved URL might contain:

\text{offensive content}

or:

\text{machine-generated content}.

So the researchers need another stage:

\boxed{ \text{human verification} }.

(Source: indicxtreme-slides)

5.27.7 Step 3 — Human verification before crawling

This is one of the most important design decisions.

Before crawling a candidate site:

\boxed{ \text{a human checks the URL} }

The annotator visits the candidate URL and verifies that it is:

  1. a genuine website,
  2. containing clean data,
  3. in the language of interest.

Only verified URLs are then passed to the web-crawling system. (Source: indicxtreme-slides)

5.27.8 Why verify the URL before crawling?

Because crawling is expensive.

Imagine discovering:

100,000

candidate websites.

Suppose many are:

\text{spam}

or:

\text{wrong language}

or:

\text{machine-generated}.

If you crawl everything first and clean it later, you waste:

\boxed{\text{crawl bandwidth + storage + processing}}

on obviously bad sources.

So IndicCorp inserts a quality gate early:

\boxed{ \text{candidate URL} \rightarrow \text{human verification} \rightarrow \text{crawl} }

rather than:

\text{candidate URL} \rightarrow \text{crawl everything} \rightarrow \text{huge cleanup}.

The deck explicitly identifies this as the distinction in the “Verified source URLs” row compared with CC-100 and mC4. (Source: indicxtreme-slides)

5.27.9 How aggressive is this gate?

Across languages:

\boxed{1\%-33\%}

of candidate URLs are discarded as noisy.

So different languages have different source quality.

That itself is informative.

A language with:

1\%

rejection is very different from one with:

33\%

rejection.

The exact language-by-language values are not given on this slide, only the overall range. (Source: indicxtreme-slides)

5.27.10 Numerical example — URL verification

Suppose:

10,000

candidate URLs are collected.

If:

20\%

are rejected, then:

10,000\times0.20 = \boxed{2,000}

URLs are rejected.

Accepted:

10,000-2,000 = \boxed{8,000}.

This is an illustrative calculation; the actual slide gives a rejection range of 1–33%, not this specific 20% example. (Source: indicxtreme-slides)

5.27.11 Step 4 — Crawl the verified sources

Once URLs pass human review, they are handed to the:

\boxed{\text{open-source webcorpus toolkit}}

for crawling. (Source: indicxtreme-slides)

So the sequence is:

\boxed{ \text{Search} \rightarrow \text{Candidate URL} \rightarrow \text{Human verification} \rightarrow \text{Web crawl} }

This separation is very important.

5.27.12 Why not make the entire pipeline human?

Because the corpus is:

\boxed{20.9\text{ billion tokens}}

which is far too large for full manual inspection.

So the design is hybrid:

\boxed{ \text{human supervision at strategic quality gates} }

plus:

\boxed{ \text{automatic large-scale filtering} }.

This pattern appears repeatedly throughout the Indic work.

5.27.13 Step 5 — Language Identification (LID)

After crawling, the raw text needs to be checked for language.

The deck says paragraph-level language filtering is performed using:

\boxed{\text{cld3}}

and:

\boxed{\text{langdetect}}

in parallel. (Source: indicxtreme-slides)

So conceptually:

\text{paragraph} \rightarrow \begin{cases} \text{cld3}\\ \text{langdetect} \end{cases} \rightarrow \text{language decision}.

5.27.14 Why use two language-ID tools?

The deck's reason is practical rather than theoretical:

\boxed{ \text{one tool has language-specific limitations} }

It notes that cld3 misses:

\boxed{\text{Assamese and Oriya}}

and that neither of the two tools supports:

\boxed{\text{Bodo and Dogri}}.

Therefore LID filtering is skipped for Bodo and Dogri. (Source: indicxtreme-slides)

This is a very useful data-engineering lesson:

\boxed{ \text{automation is only as good as its coverage on the target population} }

5.27.15 Why is skipping LID for Bodo and Dogri not necessarily a contradiction?

Because a filter that cannot correctly recognize the language could be worse than not applying it.

Suppose the true language is:

L.

If the detector doesn't support L, then applying its output may cause systematic false rejection.

So:

\boxed{ \text{unsupported detector} \rightarrow \text{do not blindly trust detector output} }

The deck specifically says LID filtering is skipped for Bodo and Dogri. (Source: indicxtreme-slides)

5.27.16 Step 6 — Script-based cleaning

Language identification alone isn't enough.

A page can still contain:

\text{Indic text} + \text{English phrases} + \text{Latin transliteration}.

Therefore the next filter checks the proportion of characters written in the language's native script.

The deck uses a threshold:

\boxed{0.75}.

A sentence is dropped if:

\boxed{ \frac{\text{native-script characters}} {\text{total characters}} <0.75 }

(Source: indicxtreme-slides)

This formula is a direct expression of the threshold described by the slide.

5.27.17 Numerical example — script threshold

Suppose a sentence contains:

200

characters.

Of these:

150

are in the native script.

Then:

\frac{150}{200} = 0.75.

So it is:

\boxed{\text{not dropped under the stated }<0.75\text{ rule}}

because the fraction is exactly 0.75, not below 0.75.

5.27.18 Another example

Suppose:

200

characters total and:

140

native-script characters.

Then:

\frac{140}{200} = 0.70.

Because:

0.70<0.75,

the sentence is:

\boxed{\text{dropped}}.

Excellent exam-style threshold question.

5.27.19 Why use a script threshold?

Because a sentence can technically pass language identification while still being dominated by another script.

For example:

Indic-language words + English terminology + transliteration

could produce a misleadingly mixed corpus.

The script threshold therefore improves:

\boxed{ \text{language-pure text quality} }.

That is the purpose described by the slide. (Source: indicxtreme-slides)

5.27.20 Step 7 — Punctuation-based cleaning

Now punctuation is stripped from each sentence.

Then the system asks:

\boxed{ \text{How many words remain?} }

If the resulting content is shorter than:

\boxed{10\text{ words}}

the document is discarded entirely. (Source: indicxtreme-slides)

Notice the granularity:

  • sentence-level punctuation stripping,
  • document-level discard condition.

That's easy to miss.

5.27.21 Why strip punctuation?

Because punctuation and formatting can contribute noise to corpus statistics.

The deck's pipeline uses this cleaning stage before deciding whether the remaining textual content is substantial enough.

The specific 10-word threshold is source-derived. (Source: indicxtreme-slides)

5.27.22 Numerical example — 10-word threshold

Suppose after punctuation stripping a document contains:

8

remaining words.

Since:

8<10,

it is:

\boxed{\text{discarded}}.

If it contains:

10

words:

10<10

is false.

Therefore:

\boxed{\text{it survives this particular threshold}}

assuming it passes the other filters.

5.27.23 Why is this not just sentence filtering?

Because the slide explicitly says:

if what remains is shorter than 10 words, the document is discarded entirely. (Source: indicxtreme-slides)

This is a useful exam trap.

Do not accidentally write:

\text{discard sentence if <10 words}.

The stated operation is:

\boxed{ \text{discard document if remaining content <10 words} }.

5.27.24 Step 8 — Offensive-content filtering

Now comes another important cleaning stage.

Web-crawled Indic text can contain offensive material.

The deck uses two blacklists.

Blacklist A — In-house list

Native annotators create an in-house list covering:

\boxed{17\text{ languages}}

with about:

\boxed{90\text{ words/phrases per language}}

and including some borderline expressions identified as contextually offensive by native speakers. (Source: indicxtreme-slides)

Blacklist B — NLLB list

A second independently released blacklist covers:

\boxed{209\text{ languages}}.

This is merged with the in-house list to widen coverage. (Source: indicxtreme-slides)

5.27.25 Why use two lists?

Because one list has:

\boxed{\text{deep native/context coverage}}

for the 17 languages,

while the other provides:

\boxed{\text{much wider language coverage}}.

Thus:

\boxed{ \text{local expertise} + \text{broad external coverage} }

produces a stronger filtering mechanism.

That interpretation follows the stated purposes of the two lists. (Source: indicxtreme-slides)

5.27.26 How is the offensive filter applied?

The deck says:

For a blacklisted word

Remove the sentence if the word occurs.

For a blacklisted phrase

Remove the sentence if the whole phrase appears verbatim.

So conceptually:

\boxed{ \text{blacklisted word} \rightarrow \text{remove sentence} }

and:

\boxed{ \text{blacklisted phrase appears verbatim} \rightarrow \text{remove sentence} }

(Source: indicxtreme-slides)

5.27.27 The surprising scale effect

Before this offensive-content filter:

\boxed{23.1\text{B tokens}}

After:

\boxed{20.9\text{B tokens}}.

Reduction:

23.1-20.9 = \boxed{2.2\text{B tokens}}.

Percentage reduction:

\frac{2.2}{23.1}\times100 \approx \boxed{9.52\%}

which the deck reports as:

\boxed{9.5\%}.

(Source: indicxtreme-slides)

5.27.28 Exam question — filtering percentage

Question: A corpus contains 23.1B tokens before filtering and 20.9B after filtering. What percentage was removed?

\frac{23.1-20.9}{23.1}\times100
= \frac{2.2}{23.1}\times100
\approx \boxed{9.52\%}

So the reported:

\boxed{9.5\%}

is mathematically consistent.

5.27.29 Step 9 — Deduplication

After the cleaning pipeline, the resulting corpus is deduplicated.

This matters because web crawling often finds the same material multiple times.

For example:

D_1=D_2

could happen because:

  • multiple URLs mirror the same article,
  • syndication duplicates content,
  • crawlers encounter repeated copies.

If duplicated text remains, a language model effectively sees:

\boxed{ \text{same evidence repeatedly} }

which inflates the apparent dataset size.

The deck reports the final corpus as de-duplicated. (Source: indicxtreme-slides)

5.27.30 Final corpus

After these steps:

\boxed{ 20.9\text{B tokens} }

remain across:

\boxed{ 24\text{ languages} }.

This is IndicCorp v2. (Source: indicxtreme-slides)

5.27.31 Compare with IndicCorp v1

IndicCorp v1:

\boxed{ 8.79\text{B tokens} }

across:

\boxed{ 12\text{ languages} }.

IndicCorp v2:

\boxed{ 20.9\text{B tokens} }

across:

\boxed{ 24\text{ languages} }.

So the token-scale ratio is:

\frac{20.9}{8.79} \approx \boxed{2.38\times}.

The deck states that the paper rounds this to approximately:

\boxed{2.3\times}.

(Source: indicxtreme-slides)

5.27.32 And language coverage doubled

V1:

12

languages.

V2:

24.

So:

\frac{24}{12} = \boxed{2\times}.

This is a simple but useful observation from the reported figures.

So the improvement is not merely:

\boxed{\text{more text}}

but also:

\boxed{\text{broader language coverage}}.

5.27.33 Hindi growth

The deck reports that Hindi alone grew:

\boxed{3.28\times}

from v1 to v2, with the paper rounding it to:

\boxed{3.3\times}.

(Source: indicxtreme-slides)

This shows why simply saying “the corpus grew 2.38×” is incomplete.

Different languages experienced different growth.

5.27.34 Low-resource tail

This is an extremely important observation.

The bottom:

\boxed{11}

lowest-resource languages together contribute only:

\boxed{1.08\text{B tokens}}.

The deck explicitly contrasts this with Hindi alone. (Source: indicxtreme-slides)

So even within a corpus described as “Indic”:

\boxed{ \text{data distribution remains highly unequal} }

5.27.35 Numerical interpretation of the low-resource tail

The 11-language tail contributes:

1.08\text{B}

out of:

20.9\text{B}.

Fraction:

\frac{1.08}{20.9} \approx 0.0517.

Therefore:

\boxed{\approx5.17\%}

of the total corpus is contributed by those bottom 11 languages.

This is our derived calculation from the deck's reported numbers. (Source: indicxtreme-slides)

5.27.36 Why this is important for the later benchmark results

This connects directly to what we'll eventually see.

Even after creating a massive Indic corpus:

20.9\text{B tokens}

the data is still not evenly distributed.

Therefore we should expect:

\boxed{ \text{resource-rich languages} > \text{resource-poor languages} }

in many downstream tasks.

And indeed, later in the deck, the lowest-resource languages show sharp performance drops. (Source: indicxtreme-slides)

So the data-construction section isn't isolated.

It explains the benchmark results we will study later.

5.27.37 Complete IndicCorp pipeline

Now memorize the architecture:

Frequent-language words
        │
        ▼
News repositories / Web search
        │
        ▼
Candidate URLs
        │
        ▼
Human URL verification
        │
        ▼
Verified sources
        │
        ▼
Web crawling
        │
        ▼
Raw crawled text
        │

        │      cld3 + langdetect
        │

        │      >= 0.75
        │
        ├──► Punctuation stripping

        │
        ├──► Offensive-content filtering
        │      in-house + NLLB lists

        ▼
20.9B-token IndicCorp v2

The major stages and thresholds are directly from the supplied deck. (Source: indicxtreme-slides)

5.27.38 What is human and what is automatic?

This is another exam-important classification.

Human
\boxed{ \text{source URL verification} }

and:

\boxed{ \text{creation of the in-house offensive blacklist} }
Automatic
\boxed{ \text{web crawling} }
\boxed{ \text{LID} }
\boxed{ \text{script filtering} }
\boxed{ \text{punctuation/length filtering} }
\boxed{ \text{blacklist filtering} }
\boxed{ \text{deduplication} }

The in-house blacklist itself comes from human annotators, while its application to text is automatic.

5.27.39 The underlying engineering philosophy

IndicCorp v2 follows a pattern:

\boxed{ \text{Human judgment where semantic quality is difficult} }

and:

\boxed{ \text{automation where scale is essential} }.

Humans are good at answering:

“Is this website actually a trustworthy source in the language?”

Machines are good at applying:

\text{millions/billions of repetitive filtering operations}.

That hybrid architecture is one of the most important lessons from the corpus-construction section.

5.27.40 Exam-style Level 5 problem

Suppose a hypothetical crawl produces:

10\text{B tokens}.

After:

  • LID filtering: 85% remain
  • script filtering: 80% of the previous stage remains
  • punctuation/length filtering: 90% remain
  • offensive filtering: 90% remain
  • deduplication: 95% remain

Then final size is:

10 \times0.85 \times0.80 \times0.90 \times0.90 \times0.95
= \boxed{5.2334\text{B tokens approximately}}.

This is an illustrative multi-stage filtering problem, not an IndicCorp reported statistic.

The exam lesson is:

\boxed{ \text{successive percentages multiply; they do not simply add} }

5.27.41 Another exam trap

Suppose:

23.1\text{B}

becomes:

20.9\text{B}.

Do not say:

“The corpus lost 2.2%.”

It lost:

2.2\text{B tokens}

and the percentage loss is:

\boxed{9.5\%}.

Always distinguish:

\boxed{\text{absolute reduction}}

from:

\boxed{\text{relative percentage reduction}}.

5.27.42 Another exam trap: 0.75 threshold

The rule is:

\text{drop if native-script fraction}<0.75.

So:

0.749 \rightarrow \boxed{\text{drop}}

but:

0.750 \rightarrow \boxed{\text{keep under this particular rule}}.

Because the inequality is strictly less than.

5.27.43 Final mental model

You should now visualize IndicCorp v2 as:

\boxed{ \text{Discovery} }

find candidate sources.

\downarrow
\boxed{ \text{Human quality gate} }

verify sources before crawling.

\downarrow
\boxed{ \text{Web crawl} }

collect massive raw text.

\downarrow
\boxed{ \text{Automatic linguistic cleaning} }

LID + script + length.

\downarrow
\boxed{ \text{Safety/quality filtering} }

offensive-content filtering.

\downarrow
\boxed{ \text{Deduplication} }

remove repeated material.

\downarrow
\boxed{ 20.9\text{B tokens / 24 languages} }

(Source: indicxtreme-slides)

5.27.44 The deepest lesson

The most important thing about IndicCorp is not:

\boxed{20.9\text{B}}

It is the pipeline philosophy:

\boxed{ \text{More data is not automatically better data} }

A useful pretraining corpus must optimize:

\boxed{ \text{coverage} + \text{quality} + \text{language correctness} + \text{script purity} + \text{safety} + \text{deduplication} }

while still operating at billion-token scale.

And there is a fundamental tension:

\boxed{ \text{corpus-wide scale} \quad\text{vs}\quad \text{low-resource language balance} }

The final 20.9B-token corpus is much larger than v1, but the deck makes clear that its language distribution is still highly uneven. (Source: indicxtreme-slides)
