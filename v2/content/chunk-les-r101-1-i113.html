Continuation · checked fixture A05 — Gradient accumulation with unequal valid-token counts

Checked continuation mechanism and declared fixture; this is not certification of every inherited claim.

Fit a global batch in memory while preserving the intended token-mean objective.

Prerequisites: Matrix gradients from a scalar loss, Shifted next-token targets and masked loss

Notation and assumptions

Each microbatch supplies a gradient of its valid-token mean, plus its valid-token count. Accumulate sums and divide once by total valid tokens.

Derivation and mechanism

  1. Recover each microbatch token-sum gradient by multiplying its mean by its valid count.
  2. Add sums.
  3. Divide by the total count; update optimizer once for the global batch.
g={\sum_m n_mg_m\over\sum_m n_m}

Worked example

Mean gradients[1,3] and[5,1] with valid counts1 and3 combine to[4,1.5]. Unweighted mean[3,2] is wrong for this token-mean objective.

Limitations

  • Equal microbatch scaling is valid only under the corresponding denominator contract.
  • Clipping, scheduler steps, dropout and batch-dependent operations complicate full equivalence.

Connections to later concepts

  • A08 shards training state across ranks; neither operation automatically fixes unequal valid-token loss denominators.

R101.1 — Gradient Accumulation: Solving the GPU Memory Problem

Plan node: A5 · chat order #113

The source has now completed the single-GPU train.py pipeline and begins the next scaling problem:

What happens when the batch we would like to train with is too large to fit into one GPU?

The source introduces Gradient Accumulation before Data Parallelism because it establishes the fundamental memory constraint and its software-based solution. (Source: Build a DeepSeek Model (From Scratch))

1. First, remember the normal training loop

For one update, we normally do:

Mini-batch
   ↓
Forward
   ↓
Loss
   ↓
Backward
   ↓
Gradients
   ↓
Optimizer.step()
   ↓
zero_grad()

The source explicitly breaks this into six operations: obtain a mini-batch, forward pass, calculate loss, backward pass, update weights, and clear gradients. (Source: Build a DeepSeek Model (From Scratch))

The important constraint is:

\boxed{\text{the whole physical mini-batch must fit in GPU VRAM}}

That becomes a problem for large models or large batches.

2. Why do we want large batches?

Suppose we have 64 training examples.

A standard batch computes:

g_{\text{batch}} = \frac{1}{64} \left( g_1+g_2+\cdots+g_{64} \right)

where:

g_i=\nabla_\theta L(x_i).

The gradient is therefore an average over many examples.

The source explains that using more examples can give a more stable gradient and reduce the noise in individual updates. (Source: Build a DeepSeek Model (From Scratch))

But there is a problem:

64 examples
     ↓
Forward
     ↓
Backward

may require more VRAM than the GPU has.

3. The central insight

This is the key idea of gradient accumulation:

We don't necessarily need to have all 64 examples in GPU memory at the same time.

Instead, split them into smaller chunks.

For example:

64=4\times16.

So:

Effective batch = 64

     ┌────────┐
     │ 16     │
     ├────────┤
     │ 16     │
     ├────────┤
     │ 16     │
     ├────────┤
     │ 16     │
     └────────┘

Each physical batch has only 16 examples.

4. What changes?

Normally:

loss.backward()
optimizer.step()
optimizer.zero_grad()

happens every batch.

With gradient accumulation:

Batch 1 → backward
Batch 2 → backward
Batch 3 → backward
Batch 4 → backward
                       ↓
                 optimizer.step()
                       ↓
                 zero_grad()

The critical change is:

\boxed{ \text{do backward multiple times before step()} }

and:

\boxed{ \text{do not zero the gradients between accumulation steps}. }

PyTorch naturally adds new gradients to the existing .grad values when zero_grad() has not been called. (Source: Build a DeepSeek Model (From Scratch))

5. Why divide the loss?

The source's implementation uses:

loss = loss / accumulation_steps

For:

accumulation\_steps=4,

each loss is divided by 4.

Why?

Suppose the four physical batches produce gradients:

g_1,g_2,g_3,g_4.

We want the effective batch gradient to represent their average:

\boxed{ g_{\text{effective}} = \frac{g_1+g_2+g_3+g_4}{4} }

Dividing each loss by 4 causes its corresponding gradient to also be divided by 4:

\frac{g_1}{4} + \frac{g_2}{4} + \frac{g_3}{4} + \frac{g_4}{4} = \frac{g_1+g_2+g_3+g_4}{4}.

So the accumulated gradient corresponds to the desired effective batch average.

This normalization is explicitly shown in the source's gradient-accumulation code. (Source: Build a DeepSeek Model (From Scratch))

6. Source code

The source gives:

accumulation_steps = 4

for i, batch in enumerate(dataloader):

    outputs = model(batch)

    loss = loss_function(
        outputs,
        batch.labels
    )

    loss = loss / accumulation_steps

    loss.backward()

    if (i + 1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()

(Source: Build a DeepSeek Model (From Scratch))

Now let's trace it.

7. Iteration 1

First physical batch:

16\text{ samples}

We calculate:

\frac{g_1}{4}.

After:

loss.backward()

the model's .grad contains approximately:

\boxed{\frac{g_1}{4}}.

We do not call:

optimizer.step()

and we do not call:

optimizer.zero_grad()

yet. (Source: Build a DeepSeek Model (From Scratch))

8. Iteration 2

Second batch gives:

\frac{g_2}{4}.

PyTorch adds this to the existing gradient:

\frac{g_1}{4}+\frac{g_2}{4}.

Therefore:

\boxed{ \frac{g_1+g_2}{4} }

is now stored.

9. Iteration 3

Another backward pass adds:

\frac{g_3}{4}.

Stored gradient becomes:

\frac{g_1+g_2+g_3}{4}.

10. Iteration 4

Fourth batch adds:

\frac{g_4}{4}.

Now:

\boxed{ \frac{g_1+g_2+g_3+g_4}{4} }

is stored.

The condition:

(i + 1) % accumulation_steps == 0

becomes true because:

(3+1)\%4=0.

So now:

optimizer.step()

runs.

The source describes this as producing an update equivalent to using the effective batch of 64 while only having 16 examples resident at a time. (Source: Build a DeepSeek Model (From Scratch))

12. Effective batch size

This gives us an important formula:

\boxed{ \text{Effective Batch Size} = \text{Physical Batch Size} \times \text{Accumulation Steps} }

For the source example:

16\times4 = \boxed{64}.

So the GPU only needs memory for:

16

examples at once, while optimization behaves as though the update used:

64.

13. The trade-off

Gradient accumulation solves a memory problem.

But it does not magically create computation.

The source makes this trade-off explicit. (Source: Build a DeepSeek Model (From Scratch))

Without accumulation:

64 examples
→ 1 forward
→ 1 backward
→ 1 update

With accumulation:

16 examples × 4
→ 4 forwards
→ 4 backwards
→ 1 update

Therefore:

\boxed{ \text{less memory} \quad\Longleftrightarrow\quad \text{more computation time} }

The source summarizes this as a trade of time for memory. (Source: Build a DeepSeek Model (From Scratch))

14. Gradient accumulation vs increasing the GPU batch

These two are conceptually different:

Larger physical batch
GPU VRAM
   ↓
64 examples simultaneously

Requires enough memory.

Gradient accumulation
GPU VRAM
   ↓
16 examples
   ↓
16 examples
   ↓
16 examples
   ↓
16 examples

Requires much less memory.

But the total computation for an effective batch of 64 still has to happen.

15. Connection to our MiniDeepSeek

Our current train.py has:

batch\_size=24.

The source's baseline training script processes those 24 sequences directly.

Gradient accumulation would let us conceptually change the training behavior to something like:

24\times4=96

effective batch size, while retaining a physical batch of 24.

That is a derived application of the source's gradient-accumulation principle; the source itself gives the concrete 16→64 example rather than this MiniDeepSeek-specific modification. (Source: Build a DeepSeek Model (From Scratch))

16. Why this comes before distributed training

Now the architecture problem becomes clearer.

We have two different bottlenecks:

Bottleneck 1: Memory

A batch or model doesn't fit.

Gradient accumulation helps with batch-memory pressure:

\boxed{\text{Gradient Accumulation}}
Bottleneck 2: Time

Even if it fits, training is painfully slow.

Then we need:

\boxed{\text{Parallel Computing}}

The source explicitly uses this transition to introduce Data Parallelism. (Source: Build a DeepSeek Model (From Scratch))

17. The next key idea: Data Parallelism

Now imagine one GPU can process 16 samples.

What if we have four GPUs?

Instead of:

GPU 0:
16 samples

we can have:

GPU 0 → 16
GPU 1 → 16
GPU 2 → 16
GPU 3 → 16

all simultaneously.

The source calls this:

\boxed{\text{Data Parallelism}}

and this is the next stage of the chapter. (Source: Build a DeepSeek Model (From Scratch))

So remember the progression:

\boxed{ \text{Single GPU} \rightarrow \text{Gradient Accumulation} \rightarrow \text{Data Parallelism} \rightarrow \text{Model Parallelism} \rightarrow \text{DualPipe} }

That sequence is the important mental model for the rest of this section.
