R100.6 — DeepSeekMoE: ExpertFFN → Router → Top-k → Shared + Routed Output

Plan node: A6 · chat order #108

↩ Back to main text: Step 1.13 — Stacking Transformer Blocks → Final Norm → Unembedding → Log

We now move to the feed-forward half of the Transformer block.

Until now, inside attention we had:

x \rightarrow \text{MLA + RoPE} \rightarrow \text{attention output}.

The next question is:

What happens after attention?

In this Mini-DeepSeek implementation, the ordinary dense FFN is replaced with:

\boxed{\text{DeepSeekMoE}}

The source says this implementation combines three ideas:

\boxed{ \text{shared experts} + \text{routed experts} + \text{auxiliary-loss-free load balancing} }

and later the final Transformer block adds this MoE output through a residual connection. (Source: Build a DeepSeek Model (From Scratch))

1. First understand the architectural replacement

In a conventional Transformer block:

x
 │
 ├── Attention
 │
 └── Dense FFN

The FFN is applied to every token.

With MoE:

x
 │
 ├── Attention
 │
 └── MoE
      │
      ├── Shared expert path
      │
      └── Routed expert path
             │
             └── Router chooses top-k

So instead of one FFN:

\boxed{ \text{one token} \rightarrow \text{one dense FFN} }

we have:

\boxed{ \text{one token} \rightarrow \text{selected specialists} }

plus the shared path.

2. Why call them "experts"?

An expert is simply an FFN.

This is important because "expert" can sound like some completely different neural architecture.

It isn't.

The source explicitly defines:

class ExpertFFN(nn.Module):

as a simple two-layer MLP. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \text{Expert}=\text{small FFN} }

in this implementation.

3. The ExpertFFN

The source defines:

class ExpertFFN(nn.Module):
    def __init__(
        self,
        d_model: int,
        hidden: int,
        dropout: float = 0.0
    ):
        super().__init__()

        self.fc1 = nn.Linear(
            d_model,
            hidden,
            bias=False
        )

        self.fc2 = nn.Linear(
            hidden,
            d_model,
            bias=False
        )

        self.dropout = nn.Dropout(dropout)

    def forward(self, x):
        return self.fc2(
            self.dropout(
                F.gelu(
                    self.fc1(x)
                )
            )
        )

The source gives this structure in Listing 6.11. (Source: Build a DeepSeek Model (From Scratch))

4. What does one expert actually calculate?

Mathematically:

x \rightarrow W_1x \rightarrow \operatorname{GELU} \rightarrow \text{dropout} \rightarrow W_2

or:

\boxed{ E(x)=W_2\left(\operatorname{Dropout}(\operatorname{GELU}(W_1x))\right) }

So it is just an MLP.

5. Dimensions of one expert

For the source defaults:

d_{\text{model}}=512

and:

d_{\text{hidden}}=512.

Therefore:

\boxed{ 512\rightarrow512\rightarrow512. }

The source's moe_routed_hidden=512 feeds this hidden dimension. (Source: Build a DeepSeek Model (From Scratch))

6. Why have many experts?

Suppose we have:

8

routed experts.

Then we have:

Expert 1
Expert 2
Expert 3
Expert 4
Expert 5
Expert 6
Expert 7
Expert 8

Each one has its own parameters.

So they can learn different transformations.

The source describes them as routed specialists.

The important concept is:

\boxed{ \text{different tokens can activate different experts}. }

7. Shared experts

The source also creates:

self.shared_experts = nn.ModuleList([
    ExpertFFN(...)
    for _ in range(args.moe_n_shared_experts)
])

(Source: Build a DeepSeek Model (From Scratch))

The default is:

\boxed{1\text{ shared expert}}.

The shared expert is not selected by the router.

Every token goes through it.

So:

\boxed{ \text{shared path = dense} }

while:

\boxed{ \text{routed path = sparse}. }

8. Why have a shared expert at all?

The source's explanation is that shared experts provide a baseline transformation for every token, preserving common/foundational information, while routed experts specialize. (Source: Build a DeepSeek Model (From Scratch))

So you can think:

\boxed{ \text{Shared expert} = \text{common knowledge path} }

and:

\boxed{ \text{Routed experts} = \text{specialized knowledge paths}. }

9. The router

Now we need a mechanism to decide:

Which experts should process this token?

The source creates:

self.gate = nn.Linear(
    args.d_model,
    self.n_routed,
    bias=False
)

(Source: Build a DeepSeek Model (From Scratch))

So if:

d_{\text{model}}=512

and:

n_{\text{routed}}=8,

then:

512\rightarrow8.

10. What do those 8 outputs mean?

For one token representation x:

x\in\mathbb R^{512}.

The gate computes:

g(x)\in\mathbb R^8.

So we get:

[g_1,g_2,\ldots,g_8].

Each score represents how strongly the router prefers a particular expert.

These are called router logits in the source. (Source: Build a DeepSeek Model (From Scratch))

11. Important: logits are not probabilities yet

Suppose the router produces:

[2.1,\ 0.3,\ 1.7,\ -0.4,\ 3.0,\ 0.1,\ 1.0,\ 0.5].

These aren't probabilities.

They are raw scores.

The source first adds the dynamic bias and then performs top-k selection. (Source: Build a DeepSeek Model (From Scratch))

12. The dynamic bias

The source registers:

self.register_buffer(
    "bias",
    torch.zeros(self.n_routed)
)

and:

self.bias_lr = 0.01

(Source: Build a DeepSeek Model (From Scratch))

So each expert has a bias:

b_i.

Initially:

\boxed{ b_i=0. }

This bias isn't a normal trainable parameter.

The source updates it separately during training.

13. Why add bias to router logits?

Suppose expert 1 keeps receiving too many tokens.

Then we would like to make expert 1 less attractive.

Suppose expert 8 receives too few.

Then we would like to make expert 8 more attractive.

That is the purpose of the dynamic bias mechanism.

The source describes it as a way of influencing the top-k selection to achieve load balancing without adding an auxiliary balancing loss. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \text{router score} + \text{load-balancing bias} }

determines the final selection.

14. Flatten the tokens

The source begins its MoE forward pass with:

B, S, D = x.shape
x_flat = x.reshape(-1, D)

(Source: Build a DeepSeek Model (From Scratch))

Suppose:

B=24,\quad S=256,\quad D=512.

Then:

x:[24,256,512].

The number of tokens is:

24\times256=6144.

After flattening:

\boxed{ x_{\text{flat}}:[6144,512]. }

Why?

Because routing is performed token by token.

The router doesn't need the 2-D batch/sequence organization.

It just needs a collection of token representations.

15. Shared expert path

The source computes:

shared_out = torch.zeros_like(x)

for exp in self.shared_experts:
    shared_out += exp(x)

(Source: Build a DeepSeek Model (From Scratch))

For one shared expert:

shared\_out=E_{\text{shared}}(x).

Every token participates.

So if there are:

B\times S

tokens, all of them go through the shared expert.

16. Now the sparse routed path

The source calculates:

router_logits = self.gate(x_flat)

(Source: Build a DeepSeek Model (From Scratch))

Therefore:

[BS,D] \rightarrow [BS,N]

where:

N=n_{\text{routed}}.

With our example:

[6144,512] \rightarrow \boxed{[6144,8]}.

Each row contains the eight expert scores for one token.

17. Add the balancing bias

The source then does:

router_logits_with_bias =
    router_logits +
    self.bias.to(router_logits.dtype)

(Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ r_{i,j}'=r_{i,j}+b_j }

where i is the token and j is the expert.

The bias is broadcast over all tokens.

18. Top-k selection

Now:

top_k_logits, top_k_indices = torch.topk(
    router_logits_with_bias,
    self.top_k,
    dim=-1
)

(Source: Build a DeepSeek Model (From Scratch))

With:

N=8

and:

k=2,

each token selects its top two experts.

So:

[6144,8] \rightarrow [6144,2]

for the selected scores and:

[6144,2]

for the selected expert indices.

19. Example of top-k routing

Suppose a token gets:

[1.2,3.9,0.4,2.1,5.0,0.7,1.8,2.5].

The two highest are:

5.0

and:

3.9.

Therefore:

\boxed{ \text{selected experts}=(5,2) }

using one-based human-readable numbering.

The token will not be sent through experts 1, 3, 4, 6, 7, and 8 in the sparse path.

This is what makes the routed path sparse.

20. Convert the selected scores into routing weights

The source does:

gates = F.softmax(
    top_k_logits,
    dim=-1,
    dtype=torch.float
).type_as(x)

(Source: Build a DeepSeek Model (From Scratch))

Suppose the selected logits are:

[5.0,3.9].

Softmax produces:

w_1= \frac{e^{5.0}}{e^{5.0}+e^{3.9}}

and:

w_2= \frac{e^{3.9}}{e^{5.0}+e^{3.9}}.

Thus:

w_1+w_2=1.

So the selected experts don't just get selected.

They also receive weights.

21. Why softmax only after top-k?

This is important.

The source does:

\boxed{ \text{all expert logits} \rightarrow \text{top-k} \rightarrow \text{softmax selected logits} }

rather than softmax over all experts first.

That means the normalization happens only among the experts that were selected.

22. Sparse dispatch

The source initializes:

routed_out_flat = torch.zeros_like(x_flat)

Then loops through the routed experts.

For each expert i, it builds a mask:

mask = (top_k_indices == i)

and finds which tokens selected that expert. (Source: Build a DeepSeek Model (From Scratch))

So we effectively construct:

Expert 1 ← some tokens
Expert 2 ← some tokens
Expert 3 ← some tokens
...
Expert 8 ← some tokens

rather than feeding every token to every expert.

23. Why use row_idx?

The source uses:

row_idx, which_k = torch.where(mask)

This tells us two things:

row_idx

Which token selected this expert.

which_k

Whether this expert was that token's first or second selected expert.

For example:

Token 17 → Expert 3 → first selected expert
Token 17 → Expert 7 → second selected expert

Then the corresponding softmax routing weight can be recovered.

24. Process only selected tokens

The source then obtains:

exp_in = x_flat[row_idx]

and:

exp_out = self.routed_experts[i](exp_in)

(Source: Build a DeepSeek Model (From Scratch))

Therefore only tokens assigned to expert i are passed through expert i.

This is the essence of sparse computation.

25. Weight the expert output

The source computes:

w = gates[row_idx, which_k].unsqueeze(-1)

Then:

exp_out * w

So if a token has:

w_1=0.7

for expert 1 and:

w_2=0.3

for expert 2, the final routed contribution is:

\boxed{ 0.7E_1(x)+0.3E_2(x). }

That's the mixture in Mixture-of-Experts.

26. Put the routed results back together

The source uses:

routed_out_flat.index_add_(
    0,
    row_idx,
    exp_out * w
)

(Source: Build a DeepSeek Model (From Scratch))

Conceptually:

Multiple experts may contribute to the same token, so accumulate their weighted outputs into that token's output slot.

Thus:

\boxed{ routed\_out(x) = \sum_{i\in TopK(x)} g_i(x)E_i(x). }

That is the mathematical meaning of the sparse dispatch code.

27. Reshape back

Initially:

x:[B,S,D].

We flattened:

x_{\text{flat}}:[BS,D].

After routing, we have:

routed\_out_{\text{flat}}:[BS,D].

Then:

routed_out =
    routed_out_flat.view(B,S,D)

(Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ [BS,D]\rightarrow[B,S,D]. }

28. The final MoE output

The source returns:

return shared_out + routed_out

(Source: Build a DeepSeek Model (From Scratch))

Therefore:

\boxed{ MoE(x) = Shared(x) + Routed(x). }

This is the final output of this simplified DeepSeekMoE implementation.

29. But there's one important discrepancy to understand

The source's broader architectural explanation earlier describes the three contributions as:

\boxed{ x + shared\_out + routed\_out. }

That is the residual connection.

However, the MoE module itself returns:

\boxed{ shared\_out+routed\_out. }

The residual x is added later by TransformerBlock.

The source's TransformerBlock does:

x = x + self.feed_forward(self.norm2(x))

(Source: Build a DeepSeek Model (From Scratch))

So the complete block contribution is:

\boxed{ x_{\text{after MoE}} = x+ shared\_out+ routed\_out. }

This resolves the apparent difference cleanly.

30. Now the load-balancing mechanism

The source's special feature is that it attempts to balance expert load without an auxiliary balancing loss. (Source: Build a DeepSeek Model (From Scratch))

During training:

if self.training:
    with torch.no_grad():

the source calculates routing statistics. (Source: Build a DeepSeek Model (From Scratch))

31. Calculate the ideal average load

The source computes:

avg_load =
    x_flat.size(0) * self.top_k / self.n_routed

(Source: Build a DeepSeek Model (From Scratch))

Let's use:

BS=6144

tokens,

k=2

selected experts per token,

and:

N=8

experts.

Total routing assignments:

6144\times2 = 12288.

If perfectly balanced:

\frac{12288}{8} = \boxed{1536}.

So each routed expert ideally receives approximately 1536 assignments.

32. Count actual assignments

The source uses:

counts = torch.bincount(
    top_k_indices.flatten(),
    minlength=self.n_routed
)

(Source: Build a DeepSeek Model (From Scratch))

Suppose actual counts are:

Expert 1 → 2200
Expert 2 → 1600
Expert 3 → 1000
Expert 4 → 1400
Expert 5 → 1300
Expert 6 → 1500
Expert 7 → 1200
Expert 8 → 1588

The total will be approximately:

12288.

33. Calculate the violation

The source computes:

violation =
    (avg_load - counts) /
    (avg_load + 1e-6)

(Source: Build a DeepSeek Model (From Scratch))

The intuition is:

Underloaded expert
count_i<avg\_load

then:

avg\_load-count_i>0

so:

violation_i>0.
Overloaded expert
count_i>avg\_load

then:

violation_i<0.

So the sign tells us which direction the bias should move.

34. Update the bias

The source then does:

self.bias.add_(
    self.bias_lr *
    torch.tanh(violation)
)

(Source: Build a DeepSeek Model (From Scratch))

Therefore:

\boxed{ b_i \leftarrow b_i+ \eta\tanh(v_i) }

where:

\eta=0.01

in this implementation.

The important idea is not the exact formula alone.

It is the feedback loop:

\boxed{ \text{routing imbalance} \rightarrow \text{bias adjustment} \rightarrow \text{future routing changes}. }

35. Why torch.no_grad()?

Because this bias update is not intended to be part of gradient-based parameter learning.

The source explicitly wraps the update in:

with torch.no_grad():

so it doesn't contribute to the gradient computation. (Source: Build a DeepSeek Model (From Scratch))

Thus we have two mechanisms:

\boxed{ \text{gradient learning} }

for the actual neural-network parameters, and:

\boxed{ \text{explicit routing feedback} }

for the load-balancing bias.

36. Why no auxiliary loss?

A common MoE design can introduce another loss term to encourage balanced expert usage.

This source instead uses the dynamic bias.

So the training objective doesn't need an extra load-balancing loss in this implementation.

That's why the source refers to this as an auxiliary-loss-free load-balancing mechanism. (Source: Build a DeepSeek Model (From Scratch))

37. Complete MoE flow

Now compress everything into one picture:

                 x
                 │
          ┌──────┴──────┐
          │             │
          ▼             ▼
   Shared experts     Router
          │             │
          │       router logits
          │             │
          │       + dynamic bias
          │             │
          │          top-k
          │             │
          │       selected experts
          │             │
          │        softmax gates
          │             │
          │         sparse FFNs
          │             │
          │       weighted sum
          │             │
          └──────┬──────┘
                 ▼
          shared + routed
                 │
                 ▼
              MoE output

During training there is an additional feedback loop:

expert token counts
       ↓
load imbalance
       ↓
dynamic bias
       ↓
next routing decision

38. Numerical routing example

Suppose one token has eight router logits:

[1.0,2.0,0.5,4.0,1.5,3.0,0.2,2.5].

Let:

k=2.

The top two are:

4.0

and:

3.0.

Thus:

\text{experts}=(4,6).

The routing softmax is:

w_4= \frac{e^4}{e^4+e^3} \approx0.731

and:

w_6= \frac{e^3}{e^4+e^3} \approx0.269.

Therefore the routed output is approximately:

\boxed{ 0.731E_4(x)+0.269E_6(x). }

Then the shared expert contributes:

E_{\text{shared}}(x).

So the MoE result is approximately:

\boxed{ E_{\text{shared}}(x) + 0.731E_4(x) + 0.269E_6(x). }

And the Transformer residual later makes:

\boxed{ x+ E_{\text{shared}}(x) + 0.731E_4(x) + 0.269E_6(x). }

40. Why MoE is called sparse

The architecture contains:

8

routed experts.

But each token uses only:

2.

Thus the routing decision activates:

\frac{2}{8}=25\%

of the routed expert pool for a token.

That is the basic meaning of sparse activation.

The parameter pool can be much larger than the amount of routed computation per token.

41. Important: sparse does NOT mean fewer parameters

This is another common misunderstanding.

If there are 8 experts, all 8 contain parameters.

So:

\boxed{ \text{total model parameters} }

can be large.

But for each token, only a subset of those routed parameters is activated.

Thus MoE separates:

\boxed{ \text{parameter capacity} }

from:

\boxed{ \text{per-token active computation}. }

That distinction is central to the architecture.
