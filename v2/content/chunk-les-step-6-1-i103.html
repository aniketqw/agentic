6.1.1 What problem are we solving?

Up to now, most of our work has been:

\boxed{ \text{“How should the model work?”} }

Now the question becomes:

\boxed{ \text{“How do we feed real training data into it?”} }

The source defines the data preparation pipeline as four operations:

\boxed{ \text{download} \rightarrow \text{split} \rightarrow \text{tokenize} \rightarrow \text{store efficiently} }

(Source: Build a DeepSeek Model (From Scratch))

6.1.2 Why does the data pipeline matter?

A neural network does not train directly on raw text.

We ultimately need:

\boxed{ \text{text} \rightarrow \text{token IDs} \rightarrow \text{tensor batches} \rightarrow \text{model}. }

So the data pipeline is the bridge between:

\boxed{ \text{human-readable corpus} }

and:

\boxed{ \text{numerical computation}. }

This is why Chapter 6 starts with data rather than immediately constructing another attention layer.

6.1.3 Why TinyStories?

The source selects:

\boxed{\text{TinyStories}}

for the Mini-DeepSeek experiment.

The reason given is very practical:

  • it is simple and coherent English,
  • it is large enough to learn meaningful language patterns,
  • but it is still manageable on a single consumer GPU.

The source describes TinyStories as a collection of short stories generated by GPT-3.5 and GPT-4 and hosted as roneneldan/TinyStories. (Source: Build a DeepSeek Model (From Scratch))

So the design goal is not:

\boxed{\text{replicate DeepSeek-V3's real pretraining corpus}}

but:

\boxed{\text{create a small laboratory in which the architecture can actually be trained}.}

That distinction matters.

6.1.4 Why not use the real DeepSeek tokenizer?

The source explicitly addresses this.

DeepSeek's tokenizer has a vocabulary of:

\boxed{\text{100k+ tokens}}

and is designed for a much larger multilingual corpus.

For this small English-only TinyStories experiment, the source chooses:

\boxed{\text{GPT-2 tokenizer}}

through tiktoken.

Its vocabulary size is:

\boxed{50,257}.

(Source: Build a DeepSeek Model (From Scratch))

So this is a simplification for the mini-model, not a claim that GPT-2's tokenizer is DeepSeek-V3's production tokenizer.

6.1.5 What is a tokenizer actually doing?

This connects back to our Transformer foundations.

Take:

The cat sat.

The tokenizer converts the text into discrete token IDs:

[t_1,t_2,t_3,t_4,\ldots].

For the GPT-2 BPE tokenizer, the exact tokenization depends on the text.

What matters architecturally is:

\boxed{ \text{text} \rightarrow \text{integer IDs}. }

Those IDs are what ultimately index the model's embedding matrix.

So:

\boxed{ \text{tokenizer output} = \text{model input vocabulary indices}. }

6.1.6 Why BPE?

The source says the selected tokenizer is the standard GPT-2 tokenizer and describes it as a Byte-Pair Encoding (BPE) tokenizer. (Source: Build a DeepSeek Model (From Scratch))

We already learned why subword tokenization is useful:

A word need not have its own unique vocabulary entry.

Instead, recurring pieces can be reused.

So conceptually:

\boxed{ \text{large vocabulary of full words} \rightarrow \text{smaller reusable subword vocabulary}. }

That lets an unknown or rare word be represented through pieces.

For this response, the important point is simply:

\boxed{ \text{BPE turns text into integer token IDs that the model can process}. }

6.1.7 The source's configuration

The source's prepare.py defines:

DATASET_NAME = "roneneldan/TinyStories"
TOKENIZER_NAME = "gpt2"
OUTPUT_DIR = "data/tinystories_tokenized"
VAL_RATIO = 0.05

(Source: Build a DeepSeek Model (From Scratch))

So we have:

\boxed{ 95\%\rightarrow\text{training} }

and:

\boxed{ 5\%\rightarrow\text{validation}. }

because:

VAL\_RATIO=0.05.

6.1.8 Why do we need a validation split?

This is important conceptually.

Suppose training loss keeps falling:

L_{\text{train}}\downarrow.

That does not automatically mean the model is learning patterns that generalize.

We also want:

L_{\text{val}}.

The source explains that the validation split gives a measure of how well the model generalizes to unseen data. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \text{training set} \rightarrow \text{learn parameters} }

while:

\boxed{ \text{validation set} \rightarrow \text{measure generalization}. }

6.1.9 Numerical split example

Suppose, purely as an example, the dataset contains:

100,000

stories.

With:

VAL\_RATIO=0.05,

validation size is:

100,000\times0.05 = \boxed{5,000}.

Training size:

100,000-5,000 = \boxed{95,000}.

The source implements the split through:

split_index = int(len(dataset) * (1 - VAL_RATIO))

then selects the first portion for training and the remainder for validation. (Source: Build a DeepSeek Model (From Scratch))

6.1.10 One subtle source-specific limitation

The source uses:

train_dataset = dataset.select(range(split_index))
val_dataset = dataset.select(range(split_index, len(dataset)))

So it takes the first:

95\%

and the last:

5\%.

That is what the code actually does.

Do not silently replace that with a randomized split and claim that the source did so.

The source's implementation is the basis here. (Source: Build a DeepSeek Model (From Scratch))

6.1.11 Step 1: Load the raw dataset

The source uses:

dataset = load_dataset(DATASET_NAME)['train']

Therefore:

\boxed{ \text{Hugging Face dataset} \rightarrow \text{Python dataset object}. }

At this stage, we still have:

\boxed{\text{raw text}}

not token IDs.

6.1.12 Step 2: Initialize the tokenizer

The source then uses:

enc = tiktoken.get_encoding(TOKENIZER_NAME)

With:

TOKENIZER_NAME = "gpt2"

Then:

vocab_size = enc.n_vocab

which gives:

\boxed{50,257}.

(Source: Build a DeepSeek Model (From Scratch))

Why does the model need this?

Because the embedding/output layers depend directly on:

\boxed{V=\text{vocabulary size}}.

For example:

E\in\mathbb R^{V\times d}.

So:

V=50,257

becomes a model architecture parameter.

6.1.13 Step 3: Encode each story

The source defines:

def encode_corpus(texts, enc):
    all_ids = []
    eot_token = enc.eot_token

    for text in texts:
        ids = enc.encode(text)
        all_ids.extend(ids)
        all_ids.append(eot_token)

    return np.array(all_ids, dtype=np.uint16)

(Source: Build a DeepSeek Model (From Scratch))

Now there are two important ideas here:

\boxed{\text{tokenization}}

and:

\boxed{\text{document separation}}.

6.1.14 Why append an EOT token?

Suppose two stories are:

Story 1: The boy went home.
Story 2: A dog ran outside.

If we simply concatenate their token IDs:

[t_1,t_2,\ldots,t_n,\; u_1,u_2,\ldots,u_m],

the model sees one continuous token stream.

We need some indication that one document ended and another began.

The source therefore appends:

\boxed{ <|endoftext|> }

after each story. (Source: Build a DeepSeek Model (From Scratch))

Conceptually:

Story 1
   ↓
tokens
   ↓
EOT
   ↓
Story 2
   ↓
tokens
   ↓
EOT

6.1.15 Why not keep every story as a separate Python object during training?

Because the source wants a simple continuous numerical stream.

After encoding:

\boxed{ \text{many text examples} \rightarrow \text{one flat token stream}. }

This makes the training-data storage and later random window extraction straightforward.

The EOT markers preserve the document boundaries inside that stream. (Source: Build a DeepSeek Model (From Scratch))

6.1.16 Tiny example

Suppose:

Story 1 → [10, 20, 30]
Story 2 → [40, 50]

and suppose EOT has ID:

99.

Then:

\boxed{ [10,20,30,99,40,50,99]. }

This is the token stream saved for later training.

The specific ID 99 here is purely illustrative; the source uses enc.eot_token.

6.1.17 Why store token IDs as uint16?

This is a very good systems question.

The vocabulary is:

V=50,257.

A token ID therefore lies below:

65,535.

And the source notes:

\boxed{ 65535=\text{maximum value representable by uint16}. }

Therefore:

\boxed{ \text{uint16 is enough to store every token ID}. }

(Source: Build a DeepSeek Model (From Scratch))

6.1.18 Why does that save space?

Compare:

\boxed{\text{uint16}=16\text{ bits}=2\text{ bytes}}

versus:

\boxed{\text{uint32}=32\text{ bits}=4\text{ bytes}}.

For:

1,000,000,000

token IDs:

uint16
1B\times2 = \boxed{2\text{ GB}}

raw storage.

uint32
1B\times4 = \boxed{4\text{ GB}}.

So:

\boxed{ 2\text{ GB saved} }

for that illustrative billion-token stream.

That is exactly the kind of low-level data-engineering decision the source is making.

6.1.19 Important distinction: token IDs are not embeddings

This is worth reinforcing.

After tokenization:

\boxed{ t_i\in\mathbb Z }

is just an integer ID.

It is not:

\boxed{ h_i\in\mathbb R^d. }

The transformation happens later:

\boxed{ t_i \overset{\text{embedding lookup}}{\longrightarrow} e_i\in\mathbb R^d. }

So the dataset file should store IDs, not giant floating-point embedding vectors.

6.1.20 Step 4: Why binary files?

The source saves:

\boxed{ train.bin }

and:

\boxed{ val.bin. }

These are flat binary token files. (Source: Build a DeepSeek Model (From Scratch))

Why?

Because training repeatedly needs numerical token IDs.

There is no benefit in parsing raw text again every time the model asks for another training batch.

So we perform:

\boxed{ \text{text processing once} }

and then:

\boxed{ \text{reuse numerical data many times}. }

6.1.21 Why not save the token stream as JSON?

JSON would look conceptually like:

[10, 20, 30, 99, 40, 50, 99, ...]

but is verbose compared with packed binary integers.

The source instead stores:

\boxed{ \text{raw uint16 binary data}. }

This is much more suitable for very large sequential numeric arrays. The source explicitly calls the binary format an efficient representation for training. (Source: Build a DeepSeek Model (From Scratch))

6.1.22 Step 5: Why memmap?

This is probably the most important systems concept in this response.

Suppose the tokenized dataset contains:

100\text{ GB}

of token IDs.

Your GPU cannot load all of that.

Even your CPU RAM may not be enough.

But at each training step you may need only:

\boxed{\text{one small batch}}.

Therefore:

\boxed{ \text{store the complete dataset on disk} }

and:

\boxed{ \text{load only the portions needed}. }

This is where:

\boxed{\text{memory mapping}}

comes in.

The source explicitly explains that the operating system can treat the file as memory-like and load required portions as needed instead of reading the entire dataset into RAM. (Source: Build a DeepSeek Model (From Scratch))

6.1.23 What is a memory-mapped file?

Conceptually:

             TRAINING PROGRAM
                    │
                    ▼
               memmap object
                    │
                    ▼
          ┌───────────────────┐
          │  train.bin on SSD │
          └───────────────────┘
              │    │    │
              ▼    ▼    ▼
             small regions
             loaded when needed

Your code interacts with the file as an array.

But the entire file does not need to be physically loaded into RAM at once.

The operating system handles the underlying page loading. This is the source's stated reason for using memmap. (Source: Build a DeepSeek Model (From Scratch))

6.1.24 The source's implementation

arr = np.memmap(
    path,
    dtype=np.uint16,
    mode="w+",
    shape=(tokens.size,)
)

arr[:] = tokens
arr.flush()

(Source: Build a DeepSeek Model (From Scratch))

Let's decode it.

6.1.25 dtype=np.uint16

We already established why:

\boxed{ \text{token IDs fit inside uint16}. }

Therefore each token occupies:

\boxed{2\text{ bytes}}.

6.1.26 mode="w+"

This means the mapped file is opened/created for writing in this preparation step.

The source then fills it:

arr[:] = tokens

and:

arr.flush()

ensures the buffered data is written out.

The conceptual flow is:

\boxed{ \text{NumPy token array} \rightarrow \text{memory-mapped binary file}. }

6.1.27 Why flush()?

Imagine your program has written data through a mapped/buffered interface.

You want to make sure those changes are pushed appropriately to the file.

The source therefore calls:

\boxed{ arr.flush(). }

We don't need to turn this into an operating-systems lecture here; the purpose in this pipeline is simply:

\boxed{ \text{commit the written token data to the mapped file}. }

6.1.28 Step 6: Save metadata

The source also creates:

meta = {"vocab_size": vocab_size}

and writes:

\boxed{ meta.json. }

(Source: Build a DeepSeek Model (From Scratch))

Why?

Because the training script needs to know:

\boxed{ V=\text{vocabulary size} }

when constructing the model.

So instead of hardcoding that value again:

\boxed{ \text{data preparation writes metadata} \rightarrow \text{training reads metadata}. }

The source says the preparation script produces:

data/tinystories_tokenized/

(Source: Build a DeepSeek Model (From Scratch))

6.1.31 Why the order matters

Notice the sequence:

\boxed{ \text{split before tokenization}. }

The source does:

  1. load dataset,
  2. create train/validation split,
  3. tokenize each split,
  4. save each separately. (Source: Build a DeepSeek Model (From Scratch))

This means we maintain distinct:

\boxed{ \text{training corpus} }

and:

\boxed{ \text{validation corpus}. }

That is a clean separation in the pipeline.

6.1.32 One end-to-end numerical example

Suppose we have:

10,000

stories.

With:

VAL\_RATIO=0.05:

training:

10,000\times0.95 = \boxed{9,500}.

validation:

10,000\times0.05 = \boxed{500}.

Suppose after tokenization the training set contains:

5,000,000

tokens including EOT markers.

At uint16:

5,000,000\times2 = 10,000,000

bytes.

Approximately:

\boxed{10\text{ MB}}

of raw token storage.

This is an illustrative calculation; the source does not specify this toy dataset size.

6.1.33 Why EOT changes the token count

Suppose there are:

N_{\text{stories}}

stories.

The pipeline adds one EOT token per story.

So:

\boxed{ N_{\text{final tokens}} = N_{\text{text tokens}} + N_{\text{stories}} }

assuming one EOT per story and no other filtering.

That is a useful implementation-level formula derived directly from the source's encoding function. (Source: Build a DeepSeek Model (From Scratch))

6.1.34 Why this representation is ideal for the next stage

Soon we need to train with blocks of:

T

tokens.

For example, if:

T=1024,

we need to repeatedly extract windows:

[t_i,t_{i+1},\ldots,t_{i+1023}]

from the giant token stream.

A flat binary array is ideal for this because arbitrary contiguous regions can be accessed efficiently.

So the data structure is already being designed for the later training operation.

6.1.35 The deeper systems principle

This small chapter section teaches a general architecture pattern:

\boxed{ \text{expensive preprocessing once} }

then:

\boxed{ \text{cheap repeated access during training}. }

Specifically:

\text{raw text} \rightarrow \text{tokenization once}

rather than:

\text{raw text} \rightarrow \text{retokenize every training step}.

And:

\text{entire dataset on disk} \rightarrow \text{memmap small windows}.

Rather than:

\text{entire dataset} \rightarrow \text{load into RAM}.

6.1.36 What the source does NOT do here

We should be precise.

This section does not yet build:

\boxed{\text{training batches}}

in detail.

It creates the storage foundation that later allows training to read batches efficiently.

Nor does this section yet implement:

\boxed{\text{MLA}}
\boxed{\text{MoE}}
\boxed{\text{MTP}}

or:

\boxed{\text{FP8}}

again.

Those components are assembled in the next model-building section.

The source explicitly says that after the data preparation is complete, it moves to model.py, where MLA, Decoupled RoPE, MoE and MTP are integrated. (Source: Build a DeepSeek Model (From Scratch))
