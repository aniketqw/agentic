Step 5.32 — IndicGenBench: Task-by-Task Dataset Construction

Plan node: I11 · chat order #73

Now we go through how each IndicGenBench task is actually constructed.

The four construction ideas we just established are now going to become concrete:

\boxed{ \text{reuse} + \text{translate} + \text{preserve parallel structure} + \text{human quality control} }

We will go in the exact task order of the supplied deck:

\boxed{ \text{CrossSum-IN} \rightarrow \text{FLORES-IN} \rightarrow \text{XQuAD-IN} \rightarrow \text{XorQA-IN} }

with XorQA then splitting into two evaluation tasks. (Source: indicgenbench-slides)

5.32.1 Task 1 — CrossSum-IN

Start with:

\boxed{\text{CrossSum-IN}}

This is the cross-lingual summarization task.

Its source is:

\boxed{\text{CrossSum}}

which itself derives from:

\boxed{\text{XL-Sum}}

and contains BBC news articles paired with summaries in another language. (Source: indicgenbench-slides)

The model's task is ultimately:

\boxed{ \text{article} \rightarrow \text{compressed summary in target language} }

5.32.2 Step 1 — Start from English article-summary pairs

The benchmark first samples:

\boxed{700}

English article-summary pairs.

The split is:

100\text{ train}
100\text{ dev}
500\text{ test}.

Therefore:

100+100+500 = \boxed{700}.

(Source: indicgenbench-slides)

5.32.3 Step 2 — What about languages already covered by CrossSum?

CrossSum already has:

\boxed{9}

of the target languages.

For those 9 languages, the benchmark does not simply translate another 700 English pairs.

Instead, it resamples:

\boxed{100/100/500}

from the existing CrossSum data.

The reason is straightforward:

\boxed{ \text{keep every language at the same dataset size} }

so one language does not receive many more evaluation examples merely because an existing resource happened to be larger. (Source: indicgenbench-slides)

5.32.4 Step 3 — What about the remaining 20 languages?

There are:

29-9 = \boxed{20}

remaining target languages.

For these, professional human translators translate the English summaries into the target language. (Source: indicgenbench-slides)

So the construction is:

\boxed{ 9\text{ languages} \rightarrow \text{reuse existing CrossSum examples} }

while:

\boxed{ 20\text{ languages} \rightarrow \text{new human translation} }

5.32.5 Total size

Every language receives:

700

examples.

There are:

29

languages.

Therefore:

700\times29 = \boxed{20,300}

total examples.

This is explicitly confirmed in the supplied slide. (Source: indicgenbench-slides)

5.32.6 Exam numerical

Training:

100\times29 = \boxed{2,900}.

Development:

100\times29 = \boxed{2,900}.

Test:

500\times29 = \boxed{14,500}.

Total:

2900+2900+14500 = \boxed{20,300}.

5.32.7 What does a CrossSum-IN example look like?

Conceptually:

Input:
Long news article

Output:
Short summary in Hindi

The target is not another full article.

It is:

\boxed{ \text{compressed preservation of the important information} }

The deck's example highlights alignment between article information such as “Nasa,” “problem,” “launch,” “spacecraft,” and “scheduled” and corresponding content in a Hindi summary. (Source: indicgenbench-slides)

5.32.8 Why does the deck emphasize “never via an intermediate English summary”?

Because a poor multilingual system might conceptually do:

\text{article} \rightarrow \text{English summary} \rightarrow \text{target language}.

But the benchmark is testing whether the model can directly produce:

\boxed{ \text{article} \rightarrow \text{target-language summary} }

This matters because an intermediate-language step can hide weaknesses in direct target-language generation.

The supplied example specifically emphasizes direct target-language generation rather than an English intermediary. (Source: indicgenbench-slides)

5.32.9 CrossSum-IN metric

CrossSum-IN uses:

\boxed{\text{chrF}}

because it is a free-form generation task and the benchmark wants a character-level metric less dependent on tokenization. (Source: indicgenbench-slides)

We will later derive why chrF is particularly useful for low-resource languages.

5.32.10 Task 2 — FLORES-IN

Now:

\boxed{\text{FLORES-IN}}

is the machine-translation task.

Its source is:

\boxed{\text{FLORES-200}}

from the NLLB work. (Source: indicgenbench-slides)

The important feature here is that FLORES-200 already contains:

\boxed{ \text{human-annotated multi-way parallel translation data} }

for many languages.

Therefore IndicGenBench follows:

\boxed{ \text{reuse where possible} }

and:

\boxed{ \text{translate where necessary}. }

5.32.11 What does “multi-way parallel” mean?

Suppose one English sentence is:

x.

It has translations:

y_{\text{Hindi}}, y_{\text{Tamil}}, y_{\text{Punjabi}}, y_{\text{Bengali}}, \ldots

all corresponding to the same x.

So:

\boxed{ x \rightarrow \{y_1,y_2,\ldots,y_K\} }

where each y_i belongs to a different language.

This gives direct comparability across languages.

5.32.12 FLORES-IN source coverage

The source slide says FLORES-200 already covers:

\boxed{22\text{ of the 29 target languages}}.

Therefore:

29-22 = \boxed{7}

languages still need new human translations. (Source: indicgenbench-slides)

5.32.13 FLORES splits

The source dataset has:

\boxed{997\text{ dev}}
\boxed{1012\text{ devtest}}

and:

\boxed{992\text{ non-public test}}.

The benchmark uses:

997+1012 = \boxed{2009}

sentences per language.

It does not use the non-public test set in this construction. (Source: indicgenbench-slides)

5.32.14 Total FLORES-IN size

There are:

2009

sentences per language and:

29

languages.

Therefore:

2009\times29
= \boxed{58,261}.

The deck reports this as approximately:

\boxed{58.2K}.

(Source: indicgenbench-slides)

5.32.15 Exam calculation

Check:

2009\times30 = 60,270.

Subtract one language:

60,270-2,009 = \boxed{58,261}.

Useful mental-math approach.

5.32.16 Important special case: no training split

The supplied deck explicitly says:

\boxed{ \text{FLORES-IN is the only task with no training split}. }

(Source: indicgenbench-slides)

This is important to memorize because the other generation tasks have training/dev/test structures in the benchmark.

5.32.17 What does a FLORES-IN example look like?

It is extremely simple:

\boxed{ \text{source sentence} \rightarrow \text{target-language sentence} }

There is:

\text{no question}

and:

\text{no context passage}.

It is sentence-level translation. (Source: indicgenbench-slides)

5.32.18 Why is FLORES-IN especially useful experimentally?

Suppose English sentence x is translated independently into:

29

target languages.

Because all outputs correspond to the same source sentence:

\boxed{ \text{content is controlled} }

while:

\boxed{ \text{language changes}. }

This makes FLORES-IN particularly useful for comparing generation quality across languages.

5.32.19 Task 3 — XQuAD-IN

Now we move to:

\boxed{\text{XQuAD-IN}}.

This tests multilingual reading comprehension.

Its source is:

\boxed{\text{XQuAD}}

which itself derives from:

\boxed{\text{SQuAD}}.

The original structure is:

\boxed{ \text{passage} + \text{question} \rightarrow \text{short answer span} }.

(Source: indicgenbench-slides)

5.32.20 Step 1 — Reuse existing XQuAD data

The benchmark starts from:

\boxed{240\text{ passages}}

containing:

\boxed{1190\text{ QA pairs}}.

These are already human-translated into:

\boxed{10\text{ higher-resource languages}}

and Hindi is the only Indic language among them.

These are reused as the test component. (Source: indicgenbench-slides)

5.32.21 Step 2 — Create train/dev data

The benchmark additionally selects:

\boxed{20\text{ passages}/100\text{ QA pairs}}

from SQuAD's training set, and:

\boxed{20\text{ passages}/100\text{ QA pairs}}

from SQuAD's development set.

Thus:

20+20 = \boxed{40\text{ new passages}}

and:

100+100 = \boxed{200\text{ new QA pairs}}

for the train/dev construction. (Source: indicgenbench-slides)

5.32.22 Total XQuAD-IN source material

So overall:

240+20+20 = \boxed{280\text{ passages}}

and:

1190+100+100 = \boxed{1390\text{ QA pairs}}.

This is exactly what the slide reports. (Source: indicgenbench-slides)

5.32.23 Step 3 — Human translation into Indic languages

All:

280

passages and:

1390

QA pairs are professionally translated into:

\boxed{12\text{ Indic languages}}.

Therefore:

280\times12 = \boxed{3360}

passage-language instances.

And:

1390\times12 = \boxed{16,680}

QA-language instances.

The deck reports these as approximately:

\boxed{3.3K\text{ passages}}

and:

\boxed{16.6K\text{ QA pairs}}.

(Source: indicgenbench-slides)

5.32.24 Important distinction: passage count vs QA count

Do not confuse:

\boxed{3360}

with:

\boxed{16,680}.

The first counts:

\text{passage × language}

while the second counts:

\text{QA pair × language}.

There can be multiple questions per passage.

This is a classic exam-data-counting trap.

5.32.25 What makes XQuAD-IN “multilingual”?

Suppose:

\text{passage}=\text{Punjabi}
\text{question}=\text{Punjabi}
\text{answer}=\text{Punjabi}.

Then:

\boxed{ \text{everything matches in one language} }

for that example.

The deck emphasizes that this is what “multilingual” means here: the model handles one language at a time, repeated across 12 languages. (Source: indicgenbench-slides)

This is important because the next XorQA task is deliberately different.

5.32.26 XQuAD-IN versus XorQA-IN

XQuAD-IN
\boxed{ \text{Question: target language} }
\boxed{ \text{Passage: target language} }
\boxed{ \text{Answer: target language} }

Everything is within one language.

XorQA-IN
\boxed{ \text{Question: target language} }
\boxed{ \text{Passage: English} }
\boxed{ \text{Answer: English OR target language} }

That distinction is crucial.

5.32.27 Task 4/5 — XorQA-IN

Now we reach the most conceptually interesting construction.

\boxed{\text{XorQA-IN}}

comes from:

\boxed{\text{XOR-TyDi}}.

The original source contains:

\boxed{\text{non-English question}}

paired with:

\boxed{\text{English evidence passage}}

and an answer.

Its purpose already involves cross-lingual retrieval. (Source: indicgenbench-slides)

5.32.28 Initial Indic coverage

The original XOR-TyDi source covers two Indic languages:

\boxed{\text{Bengali}}

with:

302

examples,

and:

\boxed{\text{Telugu}}

with:

237

examples.

So total original Indic examples:

302+237 = \boxed{539}.

This is a useful source-derived numerical calculation. (Source: indicgenbench-slides)

5.32.29 The problem with pairwise translation

Suppose there are:

29

target languages.

If you independently translated every language pair, you'd face roughly:

29\times28 = 812

directed language pairs.

Or:

\frac{29\times28}{2} = 406

undirected pairs.

That becomes a huge translation-routing problem.

The source therefore uses a clever pivot.

5.32.30 Stage 1 — Normalize through English

First:

\boxed{ \text{Bengali/Telugu question} \rightarrow \text{English} }

Professional translators translate the original question into English.

Now every source question has a common English representation.

5.32.31 Stage 2 — Fan out from English

Then:

\boxed{ \text{English question} \rightarrow \text{all target languages} }

and independently:

\boxed{ \text{English answer} \rightarrow \text{all target languages} }.

This is far more scalable than pairwise translation among every language. (Source: indicgenbench-slides)

5.32.32 The pivot architecture

Think of English as a hub:

                 English
              /   / |   \
             /   /  |    \
         Hindi Tamil Telugu Bengali ...

instead of:

Hindi ↔ Tamil ↔ Telugu ↔ Bengali ↔ ...

The hub-and-spoke architecture dramatically simplifies the translation workflow.

5.32.33 Why is this called normalization?

Because all original questions are first mapped into the same intermediate representation:

\boxed{\text{English}}

before being expanded outward.

So:

q_{\text{Bengali}} \rightarrow q_{\text{English}} \rightarrow q_{\text{Hindi}},q_{\text{Tamil}},\ldots

and:

q_{\text{Telugu}} \rightarrow q_{\text{English}} \rightarrow q_{\text{Hindi}},q_{\text{Tamil}},\ldots

This creates a consistent multilingual source for the later benchmark variants.

5.32.34 Now the clever part: one dataset becomes two tasks

The same stage-2 translations provide:

\boxed{\text{question in every target language}}

and:

\boxed{\text{answer in every target language}}.

These are recombined into two different evaluation tasks.

5.32.35 XorQA-IN-EN

In:

\boxed{\text{XorQA-IN-EN}}

we have:

\boxed{ \text{Question = target language} }
\boxed{ \text{Passage = English} }
\boxed{ \text{Answer = English} }

So the model must understand a target-language question and find/produce the relevant answer using English evidence. (Source: indicgenbench-slides)

5.32.36 XorQA-IN-XX

In:

\boxed{\text{XorQA-IN-XX}}

we have:

\boxed{ \text{Question = target language} }
\boxed{ \text{Passage = English} }

but:

\boxed{ \text{Answer = target language} }.

So now the model must perform both:

\boxed{ \text{cross-lingual comprehension} }

and:

\boxed{ \text{target-language generation} }.

This makes XorQA-IN-XX harder in a different way than XorQA-IN-EN.

5.32.37 Why is XorQA-IN-XX particularly interesting?

Consider:

\text{Telugu question} \rightarrow \text{English evidence} \rightarrow \text{Telugu answer}.

The model must:

  1. interpret Telugu;
  2. retrieve relevant information from English;
  3. map the information back into Telugu;
  4. generate the answer correctly.

So it combines:

\boxed{ \text{cross-lingual understanding} + \text{cross-lingual retrieval} + \text{target-language generation} }.

The deck explicitly contrasts this with XorQA-IN-EN, where the answer is generated in English. (Source: indicgenbench-slides)

5.32.38 Compare all three QA designs

XQuAD-IN
\boxed{ L_q=L_c=L_a }

where all three are the same target language.

XorQA-IN-EN
\boxed{ L_q\neq L_c,\quad L_a=L_c=\text{English} }
XorQA-IN-XX
\boxed{ L_q=L_a\neq L_c }

where L_c is English.

This is a very useful symbolic way to memorize the difference.

5.32.39 Coverage across languages

The deck says:

CrossSum-IN
\boxed{29\text{ languages}}
FLORES-IN
\boxed{29\text{ languages}}
XQuAD-IN
\boxed{11\text{ languages}}
XorQA-IN
\boxed{28\text{ languages}}

with:

\boxed{\text{Nepali excluded}}

from the latter due to not being translated. (Source: indicgenbench-slides)

5.32.40 Why does XQuAD-IN have fewer languages?

The slide says its coverage is constrained by:

  1. which languages already had XQuAD translations;
  2. the three medium-resource languages selected for extension.

Therefore it reaches only:

\boxed{11}.

(Source: indicgenbench-slides)

This is another example of why benchmark coverage depends partly on the availability of usable source resources.

5.32.41 Numerical coverage comparison

CrossSum/FLORES:

29/29 = \boxed{100\%}

of the target language set in this benchmark.

XQuAD:

11/29 \approx \boxed{37.9\%}.

XorQA:

28/29 \approx \boxed{96.6\%}.

These percentages are our calculations from the deck's reported language counts. (Source: indicgenbench-slides)

5.32.42 Why are the benchmark tasks not equally broad?

Because the source datasets are different.

CrossSum has a route to 29 languages.

FLORES already has broad multilingual coverage.

XQuAD has more constrained existing translation coverage.

XOR-TyDi starts from only certain source-language questions and then expands them.

Therefore:

\boxed{ \text{benchmark coverage is constrained by source-resource structure} }

not just by the researchers' desired language count.

5.32.45 The deepest construction idea

The most interesting thing about IndicGenBench is that the researchers are not merely increasing:

\boxed{\text{number of languages}}

They are trying to control the experimental variables.

For example:

CrossSum

Same underlying article/task structure, different output languages.

FLORES

Same source sentence, many target languages.

XQuAD

Same passage/question structure, translated consistently into target language.

XorQA

Same evidence language, different question/output-language configurations.

Therefore:

\boxed{ \text{language} }

can be varied while holding much of the underlying task constant.

That is exactly what makes these datasets scientifically useful for cross-lingual comparison. (Source: indicgenbench-slides)

5.32.46 One final conceptual comparison

Imagine these two systems.

System A
\text{English question} \rightarrow \text{English answer}.
System B
\text{Telugu question} \rightarrow \text{English evidence} \rightarrow \text{Telugu answer}.

System B requires much more than ordinary generation.

It requires:

\boxed{ \text{language understanding} + \text{cross-lingual information retrieval} + \text{target-language generation} }.

This is why XorQA-IN-XX is an especially valuable task conceptually.

5.32.47 Exam-ready master structure

Memorize this:

\boxed{ \text{CrossSum-IN} = \text{summarization} }
\boxed{ \text{FLORES-IN} = \text{translation} }
\boxed{ \text{XQuAD-IN} = \text{same-language QA} }
\boxed{ \text{XorQA-IN-EN} = \text{target-question + English-evidence + English-answer} }
\boxed{ \text{XorQA-IN-XX} = \text{target-question + English-evidence + target-answer} }

and the key language counts are:

\boxed{ 29,\ 29,\ 11,\ 28,\ 28 }

respectively. (Source: indicgenbench-slides)

5.32.48 Final mental model

The construction can be summarized as:

\boxed{ \text{Existing benchmark} }
\downarrow
\boxed{ \text{reuse existing multilingual data where possible} }
\downarrow
\boxed{ \text{professionally translate missing Indic languages} }
\downarrow
\boxed{ \text{preserve parallel correspondence} }
\downarrow
\boxed{ \text{evaluate generation across resource levels} }

This is the core engineering philosophy of IndicGenBench.

And the most important distinction between the tasks is:

\boxed{ \text{XQuAD-IN keeps question, context, and answer in the same language} }

while:

\boxed{ \text{XorQA-IN deliberately separates the question language from the evidence language} }

and then tests both English and target-language answer generation. (Source: indicgenbench-slides)
