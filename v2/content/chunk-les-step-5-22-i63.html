Step 5.22 — ReTool Cold-Start SFT

Plan node: I9 · chat order #63

We now focus on one specific question:

\boxed{ \text{How does ReTool teach a normal LLM the basic ability to use the code-interpreter protocol before RL begins?} }

This is the cold-start SFT stage.

The central distinction is:

\boxed{ \text{SFT teaches the protocol} }

while:

\boxed{ \text{RL learns the strategy} }

The ReTool slides make this distinction explicitly. (Source: retool-slides)

5.22.1 Why can't we start PPO immediately?

Imagine taking an ordinary pretrained/instruction-tuned LLM and telling it:

You can use Python whenever useful.

Then give it PPO.

What should it generate?

It may produce:

Let me calculate this manually...

or malformed output such as:

<code
x = ...

or:

I will execute:
x = 5 * 7

without following the expected protocol.

The RL algorithm is now trying to discover two different things simultaneously:

\boxed{ \text{How do I use the protocol?} }

and:

\boxed{ \text{When should I use the tool?} }

That makes exploration harder.

ReTool therefore first gives the model examples of the mechanics. (Source: retool-slides)

5.22.2 The core principle

The training is split into:

\boxed{ \text{Cold-start SFT} \rightarrow \text{PPO} }

The cold start teaches:

\boxed{ \text{format + mechanics} }

The PPO stage discovers:

\boxed{ \text{strategic tool use} }

Think of it as:

SFT teaches how to operate the machine.

RL teaches when operating the machine is useful.

5.22.3 Step 1 — Start with verified reasoning traces

ReTool first collects existing reasoning traces.

Call this dataset:

\boxed{D_{\text{init}}}

The supplied slide describes these as existing verified text-only reasoning traces, filtered by human review and DeepSeek-R1. (Source: retool-slides)

So conceptually:

D_{\text{init}} = \{ (q_i,r_i,a_i) \}_{i=1}^{N}

where:

  • q_i = question,
  • r_i = reasoning trace,
  • a_i = final answer.

The important property is:

\boxed{ \text{the trace is already considered correct/verified} }

5.22.4 Why start from text-only reasoning?

Because the model already needs some reasoning ability.

Suppose the original reasoning says:

We need to evaluate several candidate values.

For x=1, ...
For x=2, ...
For x=3, ...

Therefore the answer is 699.

ReTool does not throw that reasoning away.

Instead, it asks:

\boxed{ \text{Which computational portions could be delegated to Python?} }

This preserves the surrounding reasoning while changing how computation is performed. (Source: retool-slides)

5.22.5 Step 2 — Convert manual computation into executable code

This is the key transformation.

Suppose original trace:

We need to compute the values.

17 × 41 = 697.

Then check the next candidate...

The answer is 699.

The transformed version might look conceptually like:

We need to compute the values.

<code>
print(17 * 41)
</code>

<interpreter>
697
</interpreter>

Then check the next candidate...

The answer is 699.

The important transformation is:

\boxed{ \text{manual calculation} \rightarrow \text{code} + \text{real execution result} }

The slide explicitly describes automatically rewriting each trace this way. (Source: retool-slides)

5.22.6 Why must the execution result be real?

Suppose we merely replaced:

17 × 41 = 697

with:

print(17 * 41)

but never actually ran the code.

Then the model would only see:

\text{code syntax}.

It would not learn what the tool actually returns.

ReTool therefore executes the generated code in a real sandbox and inserts the actual output.

Thus:

\boxed{ \text{code} \rightarrow \text{real execution} \rightarrow \text{real feedback} }

This is exactly what later makes the rollout a true model-environment interaction. (Source: retool-slides)

5.22.7 Why does the sandbox matter during dataset creation?

Because the cold-start example must teach the model the relationship:

\boxed{ \text{my code} \rightarrow \text{environment response} }

For example:

<code>
print(20 + 22)
</code>

followed by:

<interpreter>
42
</interpreter>

The model can therefore learn the protocol:

\boxed{ \text{code block} \rightarrow \text{pause} \rightarrow \text{feedback} \rightarrow \text{continue} }

5.22.8 What remains unchanged?

An important detail from the slide:

the surrounding reasoning remains, including failed attempts.

So transformation is not:

\text{replace the entire reasoning with code}.

Instead:

\boxed{ \text{preserve reasoning} + \text{insert computational tool use} }

This gives the model examples of a reasoning process in which code is only one component. (Source: retool-slides)

5.22.9 Example with a failed attempt

Suppose original reasoning:

I will first try candidate x=500.

That doesn't work.

Maybe we should search the entire range.

The augmented trace may retain:

I will first try candidate x=500.

<code>
...
</code>

<interpreter>
...
</interpreter>

That doesn't work.

Maybe we should search the entire range.

The important idea is:

\boxed{ \text{failure is not necessarily removed} }

because the resulting data can expose the model to realistic interaction patterns. (Source: retool-slides)

5.22.10 Step 3 — Filter the transformed examples

The slide says only examples that pass both:

\boxed{ \text{format check} }

and:

\boxed{ \text{answer-correctness check} }

are retained. (Source: retool-slides)

So:

D_{\text{init}} \rightarrow \text{rewrite} \rightarrow \text{execute} \rightarrow \text{verify} \rightarrow D_{\text{CI}}

where:

\boxed{D_{\text{CI}}}

is the code-augmented dataset.

5.22.11 Why do we need a format check?

Suppose a generated training example looks like:

<code>
x = 10

with no closing tag.

The protocol is malformed.

Or:

<interpreter>
42

appears before any code call.

Such an example teaches the wrong interaction structure.

Therefore:

\boxed{ \text{correctness of answer} \neq \text{correctness of protocol} }

We need both.

5.22.12 Why do we also need an answer-correctness check?

A beautifully formatted example can still contain a wrong answer.

For example:

<code>
print(17 * 41)
</code>

<interpreter>
697
</interpreter>

\boxed{699}

The protocol is valid, but the final answer is inconsistent.

That example should not become supervised training data.

Therefore:

\boxed{ \text{valid format} \land \text{correct answer} }

is the filtering condition. (Source: retool-slides)

5.22.13 Numerical example — filtering

Suppose we start with:

N=1000

candidate traces.

After format checking:

850

remain.

Of those, answer verification retains:

700.

Therefore:

\boxed{|D_{\text{CI}}|=700}

The retention rate is:

\frac{700}{1000}\times100 = \boxed{70\%}.

This is an illustrative numerical example; the slide does not provide these particular counts.

5.22.14 Step 4 — SFT on the code-augmented data

Now we have:

D_{\text{CI}}.

The base model is supervised-fine-tuned on these examples. (Source: retool-slides)

At this point, training is ordinary autoregressive SFT conceptually:

\boxed{ \mathcal L_{\text{SFT}} = -\sum_t \log P_\theta(y_t\mid y_{<t},q) }

where y_t is the target token.

The key difference is that the target sequences now contain the ReTool protocol.

5.22.15 What exactly does the model learn?

Suppose training repeatedly contains:

reasoning
<code>
...
</code>
<interpreter>
...
</interpreter>
continue reasoning
\boxed{answer}

Then the model learns statistical patterns such as:

\boxed{ \text{when code is written, an interpreter result follows} }

and:

\boxed{ \text{after interpreter feedback, continue reasoning} }

and:

\boxed{ \text{eventually produce a final answer} }.

This is protocol learning.

5.22.16 What SFT does NOT solve

This is perhaps the most important sentence in the ReTool deck:

\boxed{ \text{Cold-start SFT is not where good tool-use strategy is learned.} }

The strategy is learned during RL. (Source: retool-slides)

Why?

Because the SFT examples themselves already demonstrate the behavior.

The model is essentially asked:

Given this context, reproduce this successful example.

It is not being explicitly optimized to discover:

Was using code actually necessary here?

or:

Would another tool call have been better?

or:

Should I use the tool earlier?

Those decisions are what PPO can discover from reward.

5.22.17 Protocol learning vs strategy learning

This distinction deserves a clean table.

Cold-start SFT PPO
Learn syntax Learn decisions
Learn <code> format Learn whether to call code
Learn <interpreter> structure Learn when to call code
Learn how feedback appears Learn how useful tool calls are
Imitate examples Explore alternatives
Supervised signal Reward signal

The first column is directly supported by the ReTool deck; the second follows its explicit statement that strategy is what RL discovers. (Source: retool-slides)

5.22.18 This is exactly why the word “cold-start” is appropriate

The model is not learning the entire task from scratch.

It already has:

\boxed{ \text{language ability} + \text{reasoning ability} }

and the SFT stage adds:

\boxed{ \text{tool-interaction format} }.

Then RL adds:

\boxed{ \text{strategic tool use} }.

So conceptually:

\boxed{ \text{base capabilities} + \text{protocol SFT} + \text{RL exploration} }

5.22.19 Let's walk through one complete example

Suppose the task is:

Find the value of x satisfying a complicated constraint.

Original verified reasoning
We need to examine candidate values.

Trying to calculate everything manually would be tedious.

After checking the relevant condition, the answer is 699.

Now ReTool augments the computation:

We need to examine candidate values.

Trying to calculate everything manually would be tedious.

<code>
for x in range(1, 1000):
    ...
</code>

<interpreter>
699
</interpreter>

The search gives the valid candidate.

\boxed{699}

Now this becomes a supervised example.

The model learns:

\boxed{ \text{problem} \rightarrow \text{reason} \rightarrow \text{code} \rightarrow \text{feedback} \rightarrow \text{reason} \rightarrow \text{answer} }

5.22.20 But this still doesn't mean the model has learned optimal tool timing

Suppose a problem is:

What is 2+2?

A cold-start example might use:

print(2+2)

The model could therefore learn:

\text{math problem} \rightarrow \text{use code}.

But that's not necessarily optimal.

For a simple task, direct reasoning may be perfectly adequate.

ReTool's RL stage needs to discover:

\boxed{ \text{tool use has a cost} }

and should therefore be used strategically.

The slide explicitly says that nothing tells the model when to use the tool; timing is exactly what RL must teach. (Source: retool-slides)

5.22.21 Why this is an exploration problem

Suppose the model has two possible policies:

Policy A
Always use code.
Policy B
Use code only when computation is difficult.

The cold-start SFT dataset may contain successful examples of both kinds, depending on the source transformations.

SFT mainly learns:

P(\text{successful-looking sequence}).

RL instead evaluates:

\boxed{ \text{Did this strategy actually produce the correct answer?} }

That is much closer to discovering an optimal policy.

Memorize this diagram:

          │
          ▼
      D_init

This is the complete cold-start-to-RL transition described by the supplied ReTool material. (Source: retool-slides)

5.22.23 Why the distinction is important for interviews

Suppose an interviewer asks:

Why not simply fine-tune the model on tool-use examples and stop there?

A strong answer is:

\boxed{ \text{SFT gives imitation, while ReTool's RL stage optimizes the actual task outcome.} }

SFT can teach:

“Here is how a successful tool-use trajectory looks.”

RL can discover:

“Given this particular problem, using the tool here improves the probability of success.”

That is a more powerful learning signal for strategic behavior.

5.22.24 Numerical exam question

Suppose:

|D_{\text{init}}|=5000.

After automatic rewriting:

4700

examples have valid syntax.

After answer checking:

4200

remain.

Then:

\text{final retention} = \frac{4200}{5000}\times100 = \boxed{84\%}.

The number rejected after rewriting:

5000-4700 = \boxed{300}.

The number rejected by answer verification:

4700-4200 = \boxed{500}.

Total rejected:

300+500 = \boxed{800}.

5.22.25 Numerical exam question — SFT token prediction

Suppose one cold-start example has:

\boxed{1000}

target tokens.

The sequence contains:

  • 780 reasoning/code tokens generated by the model,
  • 150 interpreter-feedback tokens,
  • 70 final-answer/reasoning tokens.

If interpreter tokens are excluded from a policy-style loss:

1000-150 = \boxed{850}

tokens remain eligible for the model's token-level learning signal.

This is an illustrative calculation. The supplied ReTool deck explicitly says interpreter tokens are masked during RL; it does not give this particular numerical example. (Source: retool-slides)

5.22.26 A subtle point: SFT and RL have different data roles

Cold-start SFT uses:

\boxed{ \text{curated demonstrations} }

RL uses:

\boxed{ \text{new rollouts generated by the current policy} }

So:

\boxed{ \text{SFT = learn from examples} }

while:

\boxed{ \text{RL = generate, evaluate, update, repeat} }

That difference explains why RL can discover behavior that wasn't explicitly demonstrated in the SFT set.

The slides' later example of self-correcting after a NameError is presented as such an emergent behavior. (Source: retool-slides)

5.22.27 The three-stage logic of ReTool

You can compress the entire mechanism into:

\boxed{ D_{\text{init}} \overset{\text{rewrite + execute}}{\longrightarrow} D_{\text{CI}} \overset{\text{SFT}}{\longrightarrow} \pi_{\text{cold}} \overset{\text{PPO + reward}}{\longrightarrow} \pi_{\text{ReTool}} }

where:

D_{\text{init}}

Verified reasoning examples.

D_{\text{CI}}

Code/interpreter-augmented examples.

\pi_{\text{cold}}

Model capable of following the protocol.

\pi_{\text{ReTool}}

Model that learns strategically when/how to use the tool.

5.22.28 The deepest conceptual lesson

There are actually two different learning problems:

Problem 1 — Representation/protocol learning
\boxed{ \text{What does a tool interaction look like?} }

SFT is well suited to this.

Problem 2 — Decision/policy learning
\boxed{ \text{When should I invoke the tool to maximize final success?} }

RL is well suited to this.

Therefore:

\boxed{ \text{SFT teaches the language of tool use} }

while:

\boxed{ \text{RL teaches the economics of tool use} }

That is the central idea of ReTool's cold-start stage.

5.22.29 Final exam-ready picture

Remember the entire chain:

\boxed{ \text{Verified text reasoning} }
\downarrow
\boxed{ \text{Replace manual computation with executable code} }
\downarrow
\boxed{ \text{Run code in real sandbox} }
\downarrow
\boxed{ \text{Insert actual output} }
\downarrow
\boxed{ \text{Filter: format + correctness} }
\downarrow
\boxed{ D_{\text{CI}} }
\downarrow
\boxed{ \text{Cold-start SFT} }
\downarrow
\boxed{ \text{learn protocol} }
\downarrow
\boxed{ \text{PPO with correctness reward} }
\downarrow
\boxed{ \text{learn strategic tool use} }

(Source: retool-slides)

Step 5.22 checkpoint

Before proceeding, the following distinctions should be completely clear:

\boxed{ D_{\text{init}}\neq D_{\text{CI}} }

because D_{\text{CI}} contains actual tool interactions.

\boxed{ \text{SFT}\neq\text{RL} }

because SFT imitates curated demonstrations while RL optimizes reward through exploration.

\boxed{ \text{protocol}\neq\text{strategy} }

because knowing how to invoke a tool does not imply knowing when invocation is useful.

And finally:

\boxed{ \text{ReTool's central learning target} = \text{strategic tool use} }
