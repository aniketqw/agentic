Step 5.49.3 — Pillar 3: Increasing Accumulation Precision

We now reach the third pillar of DeepSeek's FP8 framework.

Pillar 1 asked:

\boxed{\text{Where should FP8 be used?}}

Pillar 2 asked:

\boxed{\text{How should FP8 values be scaled?}}

Pillar 3 asks:

\boxed{\text{After multiplying FP8 values, how do we safely add thousands of products together?}}

This is the accumulation problem.

The source's solution is:

\boxed{ \text{low-precision Tensor-Core computation} \rightarrow \text{periodic promotion} \rightarrow \text{FP32 accumulation}. }

(Source: Build a DeepSeek Model (From Scratch))

5.49.3.1 Start with matrix multiplication

Everything starts from:

\boxed{ Y=WX }

For one element of Y:

\boxed{ Y_{ij} = \sum_{r=1}^{K}W_{ir}X_{rj} }

or explicitly:

Y_{ij} = W_{i1}X_{1j} + W_{i2}X_{2j} +\cdots+ W_{iK}X_{Kj}.

The source writes this exact dot-product structure before introducing the accumulator problem. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.2 Multiplication is only half the problem

Suppose:

K=4096.

Then one output value requires:

\boxed{4096\text{ products}}

and then those products have to be added:

p_1+p_2+\cdots+p_{4096}.

So there are two separate numerical operations:

\boxed{\text{multiplication}}

and:

\boxed{\text{accumulation}}.

This distinction is absolutely central.

5.49.3.3 What is an accumulator?

Suppose:

p_1=W_{i1}X_{1j}.

Then:

a_1=p_1.

Next:

p_2=W_{i2}X_{2j}

and:

a_2=a_1+p_2.

Then:

a_3=a_2+p_3.

And so on:

\boxed{ a_r=\sum_{q=1}^{r}p_q. }

The register holding the running sum is called the:

\boxed{\text{accumulator}}.

The source explicitly introduces the accumulator this way. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.4 Why can't we just accumulate in FP8?

Because the running sum can involve thousands of terms.

Imagine:

p_1=1.2
p_2=-1.1
p_3=0.0004
p_4=0.0003

and many more.

The small contributions can matter to the final answer.

But low-precision accumulation may not preserve enough information to represent the running total accurately.

The source describes this as a hardware limitation of low-precision accumulators and connects it to underflow/precision loss for large inner dimensions. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.5 The source's hardware-specific framing

The source says that, for the hardware it discusses, the internal low-precision accumulator can have substantially less precision than FP32; it gives an example of roughly 14 bits and states that long reductions can therefore suffer significant numerical error, potentially around 2% in its discussion. (Source: Build a DeepSeek Model (From Scratch))

The source's Figure 5.31 illustration labels the Tensor Core side as 16 bit and the CUDA Core side as 32 bit, while the prose discusses an example of a lower-precision accumulator around 14 bits. (Source: Build a DeepSeek Model (From Scratch))

For our conceptual understanding, the important point is simply:

\boxed{ \text{Tensor-Core accumulator precision} < \text{FP32 precision}. }

The exact hardware width should be treated as source-specific, rather than as a universal property of every Tensor Core.

5.49.3.6 What happens when precision is too low?

Suppose the true sum is:

1000.0001.

But your low-precision representation can only distinguish values separated by, say, 0.1 at that magnitude.

Then:

1000.0001

may effectively become:

1000.0.

The tiny contribution:

0.0001

is lost.

So even if every individual multiplication is reasonable, information can disappear during repeated addition.

This is the key numerical lesson.

5.49.3.7 A simple accumulation example

Suppose the exact products are:

[0.25,\;0.25,\;0.25,\;0.25].

Then:

Y=1.0.

No problem.

Now suppose we have:

[1,\;1,\;-1,\;0.001].

Exact result:

1+1-1+0.001 = \boxed{1.001}.

A low-precision accumulator may lose part or all of that 0.001 contribution depending on the precision available.

The precise error depends on the numerical format and accumulation ordering, so the example is illustrative rather than a claim about one particular Tensor Core.

5.49.3.8 Why does the error get worse for large K?

Suppose:

K=4.

We add four products.

Now suppose:

K=4096.

We add:

4096

products.

More additions mean more opportunities for rounding/precision loss.

Therefore:

\boxed{ K\uparrow \Rightarrow \text{accumulation becomes more numerically demanding}. }

This is particularly relevant to LLMs because their matrix dimensions commonly involve thousands of elements. The source explicitly highlights inner dimensions such as 4096 or larger. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.9 The naive low-precision approach

Conceptually:

FP8 W ─┐
       ├──► Tensor Core ───► low-precision accumulator
FP8 X ─┘                           │
                                   ▼
                              final result

Everything remains inside the low-precision environment.

The source identifies this as the problem.

5.49.3.10 DeepSeek's idea

DeepSeek says:

Don't wait until the entire dot product is finished.

Instead:

\boxed{ \text{accumulate for a while} \rightarrow \text{promote} \rightarrow \text{continue accumulating in FP32}. }

The source calls this:

\boxed{\text{promotion to CUDA Cores}}.

(Source: Build a DeepSeek Model (From Scratch))

5.49.3.11 The hardware roles

The source distinguishes two kinds of GPU compute units.

Tensor Cores

Optimized for:

\boxed{\text{high-throughput matrix multiplication}}

especially low-precision operations.

CUDA Cores

More general-purpose and capable of:

\boxed{\text{full-precision operations}}

such as FP32 accumulation.

The source's strategy is to exploit both. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.12 The key architecture

Instead of:

\boxed{ \text{Tensor Core only} }

we get:

\boxed{ \text{Tensor Core} \rightarrow \text{CUDA Core}. }

More specifically:

\boxed{ \text{low-precision partial sum} \rightarrow \text{FP32 register} }

and the FP32 register becomes the reliable long-term running total.

(Source: Build a DeepSeek Model (From Scratch))

5.49.3.13 What is WGMMA?

The source introduces:

\boxed{\text{WGMMA}}

which stands for:

\boxed{\text{Warp-Group-level Matrix Multiply-Accumulate}}.

The source describes WGMMA as a low-level optimized GPU instruction used to perform chunks of the matrix multiplication. (Source: Build a DeepSeek Model (From Scratch))

For our purposes:

\boxed{ WGMMA = \text{perform a small piece of the large GEMM}. }

5.49.3.14 Think of WGMMA as chunks

Suppose the complete dot product is:

p_1+p_2+\cdots+p_{4096}.

Rather than doing all 4096 in one conceptual block, imagine:

\underbrace{p_1+\cdots+p_{128}}_{\text{WGMMA chunk 1}}

then:

\underbrace{p_{129}+\cdots+p_{256}}_{\text{WGMMA chunk 2}}

and so on.

This is the intuition behind the source's diagram showing:

WGMMA_1,\;WGMMA_2,\;WGMMA_3,\;WGMMA_4,\ldots

as sequential pieces of a longer dot product. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.15 Now introduce N_C

The source specifies a promotion interval:

\boxed{ N_C=128. }

After a fixed interval of approximately 128 element-wise operations, the partial sum is promoted from the low-precision environment to an FP32 register. (Source: Build a DeepSeek Model (From Scratch))

This is important because we already encountered the same:

\boxed{128}

in Pillar 2.

But the meanings are slightly different.

5.49.3.16 Why the same N_C=128 keeps appearing

Pillar 2

For activations:

\boxed{ 128\text{ channels per quantization group}. }

For weights:

\boxed{ 128\times128\text{ blocks}. }
Pillar 3

The source describes:

\boxed{ 128\text{ element-wise operations between promotions}. }

So the same scale of granularity appears across the design.

The source's Figure 5.31 specifically uses N_C as the promotion interval. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.17 Why promote periodically instead of after every multiplication?

Because that would destroy much of the efficiency advantage.

Imagine:

4096

products.

If we converted every single product to a high-precision path immediately, we'd spend much more overhead on precision management.

Instead:

\boxed{ \text{perform many fast low-precision operations} }

then:

\boxed{ \text{occasionally promote}. }

This gives a compromise:

\boxed{ \text{speed} + \text{numerical stability}. }

That is the source's central design philosophy. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.18 Numerical example with 4096 products

Suppose:

K=4096

and:

N_C=128.

Then the number of promotion intervals is:

\frac{4096}{128} = \boxed{32}.

So conceptually:

\boxed{32\text{ partial-sum promotions}}

are needed.

Each promotion represents roughly:

128

products.

There are:

\boxed{32}

such chunks for 4096/128.

5.49.3.20 The FP32 register

After promotion, the source says the partial result enters an:

\boxed{\text{FP32 Register}}.

That register holds the high-precision running total.

So if:

A_{FP32}

is the current accumulated value and:

P_k

is the newly promoted partial sum, then:

\boxed{ A_{new}=A_{old}+P_k. }

But now:

A

is held in:

\boxed{FP32}.

(Source: Build a DeepSeek Model (From Scratch))

5.49.3.21 Numerical FP32 accumulation example

Suppose four low-precision chunks produce:

P_1=12.345
P_2=7.891
P_3=-3.217
P_4=0.004.

The FP32 accumulator performs:

A_1=12.345
A_2=12.345+7.891=20.236
A_3=20.236-3.217=17.019
A_4=17.019+0.004 = \boxed{17.023}.

The point is that the final accumulation retains substantially more precision than if the long-running sum stayed entirely in a narrower accumulator.

5.49.3.22 What does the CUDA Core do with scaling factors?

This connects directly to Pillar 2.

The source explains that the CUDA Core stage can use the corresponding activation and weight scaling factors during dequantization. (Source: Build a DeepSeek Model (From Scratch))

Recall:

X\approx s_XQ_X

and:

W\approx s_WQ_W.

Therefore:

WX \approx s_Xs_W(Q_WQ_X).

So after Tensor-Core computation:

Q_WQ_X

the scale information is used to restore the magnitude.

Thus Pillars 2 and 3 work together:

\boxed{ \text{Pillar 2: local scaling} }

and:

\boxed{ \text{Pillar 3: safe accumulation}. }

5.49.3.24 Why is the promotion periodic?

This is a systems trade-off.

Let:

N_C

be the promotion interval.

Very small N_C

For example:

N_C=16.

Then promotions happen frequently.

Benefits:

\boxed{\text{more frequent precision protection}}

but:

\boxed{\text{more promotion overhead}}.
Very large N_C

For example:

N_C=1024.

Then:

\boxed{\text{fewer promotions}}

but:

\boxed{\text{more accumulation in low precision before protection}}.

The source specifies N_C=128 for its described mechanism. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.25 Exam numerical — promotion count

Suppose:

K=8192

and:

N_C=128.

Then:

N_{\text{promotions}} = \frac{8192}{128} = \boxed{64}.

So the reduction is divided into approximately:

\boxed{64}

promotion intervals.

5.49.3.26 Exam numerical — incomplete final block

Suppose:

K=1000

and:

N_C=128.

Then:

1000/128=7.8125.

So there are:

\boxed{8\text{ chunks}}

if the final incomplete chunk is handled separately.

The first seven contain:

7\times128=896

products.

Remaining:

1000-896 = \boxed{104}.

Thus:

7\times128+104=1000.

This is a derived implementation-style calculation; the source's conceptual discussion assumes fixed intervals but doesn't spell out the boundary handling for arbitrary K.

5.49.3.27 Why not just use FP32 for the whole matrix multiplication?

Because that would discard much of the performance advantage.

Recall:

\boxed{ FP8 }

provides extremely compact values and efficient low-precision matrix operations.

If everything becomes:

FP32,

we lose much of the benefit.

So the philosophy is:

\boxed{ \text{cheap low precision for the bulk} }

with:

\boxed{ \text{expensive high precision only where it matters}. }

This is exactly the recurring mixed-precision philosophy from Pillar 1. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.28 Why is this called “promotion”?

Because we move:

\boxed{ \text{lower precision} \rightarrow \text{higher precision}. }

Specifically:

\boxed{ \text{low-precision accumulator} \rightarrow \text{FP32 register}. }

The source calls this periodic movement a promotion. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.29 Promotion is not the same as quantization

This distinction matters.

Quantization

Moves:

\boxed{ \text{high precision} \rightarrow \text{low precision} }

for efficient computation.

Promotion

Moves:

\boxed{ \text{low precision} \rightarrow \text{high precision} }

to preserve numerical accuracy.

So DeepSeek's pipeline repeatedly performs:

\boxed{ \text{quantize} \rightarrow \text{compute} \rightarrow \text{promote/dequantize}. }

5.49.3.30 Numerical example: why accumulation precision matters

Suppose the true partial sums are:

P_1=1000.1
P_2=0.2
P_3=-0.1
P_4=0.003.

Exact result:

1000.1+0.2-0.1+0.003 = \boxed{1000.203}.

Suppose a toy low-precision accumulator rounds to one decimal place:

1000.1+0.2=1000.3

then:

1000.3-0.1=1000.2

and:

1000.2+0.003 \approx1000.2.

So we obtain:

\boxed{1000.2}

instead of:

\boxed{1000.203}.

The error is:

0.003.

This tiny toy example illustrates the basic mechanism. Real FP8/Tensor-Core behavior is format- and hardware-specific and should not be inferred from this decimal-rounding toy model.

5.49.3.31 Why does this matter to a language model?

A Transformer performs enormous numbers of matrix multiplications.

Suppose one layer performs:

Y=XW.

Then this occurs repeatedly across:

  • attention projections,
  • FFN/MoE projections,
  • MTP Transformer blocks,
  • many layers,
  • huge token batches.

A small numerical error repeated across enormous computation can affect the final model output.

Therefore:

\boxed{ \text{numerical stability becomes a systems-level problem}. }

The source explicitly frames accumulation precision as essential to avoiding instability during large-scale FP8 training. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.32 Connect to the earlier DeepSeek architecture

Remember MoE:

\boxed{ \text{many expert matrix multiplications} }

and MTP:

\boxed{ \text{additional Transformer blocks}. }

MLA:

\boxed{ \text{many matrix operations}. }

So the total system contains massive GEMM workloads.

That's exactly where:

\boxed{\text{FP8 Tensor-Core computation}}

can provide major efficiency.

But those GEMMs still need:

\boxed{\text{numerically reliable accumulation}}.

Hence Pillar 3.

5.49.3.33 The three FP8 pillars so far

Now we can distinguish them precisely.

Pillar 1 — Mixed Precision
\boxed{ \text{Choose the right precision for each component}. }
Pillar 2 — Fine-Grained Quantization
\boxed{ \text{Use local scaling so outliers do not destroy precision globally}. }
Pillar 3 — Increasing Accumulation Precision
\boxed{ \text{Do the bulk multiplication cheaply, but protect long reductions with FP32 accumulation}. }

So:

\boxed{ \text{where} \rightarrow \text{how} \rightarrow \text{how to accumulate}. }

Suppose:

K=4096

N_C=128.
Number of low-precision chunks
4096/128 = \boxed{32}.

Suppose each chunk produces a partial sum.

Then:

P_1,P_2,\ldots,P_{32}.

The final result is:

\boxed{ Y \approx \sum_{i=1}^{32} \text{Dequantize}(P_i,s_X,s_W) }

with the accumulated result retained in higher precision.

The exact hardware ordering and scaling implementation can be more elaborate, but this is the conceptual structure shown in the source. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.36 Why the source says this is a “best of both worlds” design

Because the two hardware units are optimized for different objectives.

Tensor Core:

\boxed{ \text{throughput} }

CUDA Core:

\boxed{ \text{precision/flexibility} }

So:

\boxed{ \text{Tensor Core} + \text{CUDA Core} = \text{speed + numerical stability}. }

The source explicitly describes the mechanism in those terms. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.37 Very important exam distinction

A common wrong answer is:

“DeepSeek performs FP32 matrix multiplication.”

No.

The source's design is:

\boxed{ \text{FP8 matrix multiplication} }

with:

\boxed{ \text{high-precision accumulation}. }

The multiplication and accumulation are different stages.

5.49.3.38 Another common wrong answer

“The low-precision partial sum is converted to FP32 only once, at the end.”

According to the source's Pillar 3:

\boxed{\text{No.}}

The distinctive idea is periodic promotion at a fixed interval N_C, rather than waiting until the entire dot product has been accumulated. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.39 Why periodic promotion is mathematically sensible

Suppose:

S_1=P_1+\cdots+P_{128}.

Then promote:

S_1\rightarrow FP32.

Then:

S_2=P_{129}+\cdots+P_{256}.

Then:

S_2\rightarrow FP32.

Final:

Y=S_1+S_2+\cdots.

Therefore the long reduction is decomposed into smaller local reductions followed by high-precision combination.

This limits how long the low-precision accumulator must retain the running sum.

5.49.3.40 Pillar 3 and Pillar 2 are designed together

This connection is extremely important.

Pillar 2 says:

\boxed{ \text{scale locally}. }

Pillar 3 says:

\boxed{ \text{accumulate safely}. }

So the overall computation is:

\boxed{ \text{local scaling} \rightarrow \text{FP8 GEMM} \rightarrow \text{periodic promotion} \rightarrow \text{FP32 accumulation}. }

The source's combined diagram makes exactly this connection. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.41 Exam-style problem

A matrix multiplication has inner dimension:

K=16384.

DeepSeek's described promotion interval is:

N_C=128.

How many promotion intervals?

\frac{16384}{128} = \boxed{128}.

So the computation can be thought of as:

\boxed{128\text{ local reduction chunks}}

before the corresponding high-precision accumulation of the promoted partial results.

5.49.3.42 Exam-style conceptual question

Why not simply use FP32 for everything?

Because:

\boxed{ \text{FP32 computation costs more memory/bandwidth and is slower for the massive GEMMs} }

while:

\boxed{ \text{FP8 provides much higher-throughput low-precision matrix computation}. }

DeepSeek therefore reserves higher precision for the parts where numerical accuracy matters most.

That is the unifying philosophy across all three pillars. (Source: Build a DeepSeek Model (From Scratch))

5.49.3.45 One final mental model

Think of a worker who must add:

4096

numbers.

You give them a tiny notebook and ask them to keep the running total there.

Eventually the notebook cannot preserve every tiny detail.

Instead, after every:

128

entries, they transfer the partial total into a much more precise ledger.

So:

\boxed{ \text{small notebook} = \text{low-precision accumulator} }
\boxed{ \text{large ledger} = \text{FP32 register}. }

The fast worker keeps doing the bulk arithmetic; the precise ledger protects the long-term accumulated result.

That is the intuition behind DeepSeek's Increasing Accumulation Precision. (Source: Build a DeepSeek Model (From Scratch))
