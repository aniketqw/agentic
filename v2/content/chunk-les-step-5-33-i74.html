Notation and assumptions

Toy whitespace tokens and multiset overlap; precision/recall use predicted/gold token counts. Actual benchmark normalization is language- and implementation-specific.

Derivation and mechanism

  1. Normalize/tokenize with the declared rules.
  2. Count multiset intersection, precision and recall.
  3. Take harmonic mean; define empty-answer behavior and multi-reference aggregation.

Step 5.33 — IndicGenBench: Metrics, Resource Gaps, Directionality, and In-Context Learning

Plan node: I11 · chat order #74

We now move from how IndicGenBench was constructed to:

\boxed{ \text{How do we score generation quality, and what do the results reveal?} }

This step contains some of the most important insights in the Indic material because the benchmark does more than rank models. It exposes why generation quality breaks down for lower-resource Indic languages.

The major chain is:

\boxed{ \text{metric choice} \rightarrow \text{model comparison} \rightarrow \text{resource-tier gap} \rightarrow \text{translation asymmetry} \rightarrow \text{few-shot behavior} \rightarrow \text{tokenizer bottleneck} }

5.33.1 First: why ordinary accuracy is not enough

For classification we had:

x\rightarrow y

so accuracy was natural.

But generation looks like:

x\rightarrow \hat y

where many different outputs can be valid.

Suppose gold:

The mission launched after several delays.

Model:

After being delayed several times, the mission finally launched.

The strings are different, but the meaning is very similar.

Therefore:

\boxed{ \text{exact string equality is too strict} }

for most generation tasks.

IndicGenBench therefore uses two major metric families:

\boxed{\text{chrF}}

for summarization/translation, and:

\boxed{\text{token-level F1}}

for QA. (Source: indicgenbench-slides)

5.33.2 chrF — Character-level F-score

The deck uses:

\boxed{\text{chrF}}

for:

\boxed{\text{CrossSum-IN}}

and:

\boxed{\text{FLORES-IN}}.

The important idea is:

\boxed{ \text{compare character-level n-gram overlap rather than token overlap} }

The deck specifically motivates this because token-level metrics such as BLEU and ROUGE can be unreliable for low-resource languages when tokenization itself is problematic. (Source: indicgenbench-slides)

5.33.3 Why character-level evaluation helps

Suppose the same word is tokenized differently.

Language A:

w\rightarrow[t_1]

Language B:

w\rightarrow[t_1,t_2,t_3,t_4].

A token-level metric now depends partly on the tokenizer.

At the character level, we instead compare something closer to:

\text{c-a-t}

against another string's character sequence.

Thus:

\boxed{ \text{evaluation becomes less tied to subword segmentation} }

The deck calls this important because tokenization is itself a weakness for some low-resource languages. (Source: indicgenbench-slides)

5.33.4 Why not say chrF is “perfect”?

We should be careful.

The deck says character-level scoring sidesteps the tokenization problem.

It does not claim that chrF perfectly captures semantics.

Two sentences can have high character overlap but different meanings, or low overlap while expressing the same meaning.

So the correct lesson is:

\boxed{ \text{chrF reduces one important low-resource evaluation problem} }

not:

\boxed{ \text{chrF completely solves generation evaluation} }.

That stronger statement is not supported by the slide.

5.33.5 Token-F1 for QA

For:

\boxed{\text{XQuAD-IN}}

and:

\boxed{\text{XorQA-IN-EN}}
\boxed{\text{XorQA-IN-XX}},

the benchmark uses SQuAD-style:

\boxed{\text{token-overlap F1}}.

(Source: indicgenbench-slides)

Recall:

P=\frac{TP}{TP+FP}
R=\frac{TP}{TP+FN}

and:

\boxed{ F1=\frac{2PR}{P+R} }.

5.33.6 Numerical QA example

Suppose:

P=0.8

and:

R=0.6.

Then:

F1= \frac{2(0.8)(0.6)}{0.8+0.6}
= \frac{0.96}{1.4}
= \boxed{0.6857}.

So:

\boxed{68.57\%}.

5.33.7 Why F1 is appropriate for short answers

Suppose gold answer:

[\text{New Delhi}]

and prediction:

[\text{Delhi}]

The model is partially correct.

Accuracy would force a binary:

0\text{ or }1.

F1 can reflect partial overlap.

That makes it much more useful for span-based QA.

The exact normalization/tokenization details are not specified on this deck page, so we shouldn't invent them.

5.33.8 Now: do bigger models actually do better?

The benchmark asks:

\boxed{ \text{Does IndicGenBench distinguish model quality?} }

The answer from the deck is:

\boxed{\text{Yes}}

and several patterns emerge. (Source: indicgenbench-slides)

5.33.9 Pattern 1 — Larger models within a family generally perform better

The deck states:

\boxed{ \text{larger models within a family consistently do better} }

The reported comparison includes models such as:

\text{PaLM-2-XXS}
\text{PaLM-2-XS}
\text{PaLM-2-S}
\text{PaLM-2-L}

and LLaMA variants.

(Source: indicgenbench-slides)

This is a classic scaling observation.

5.33.10 Why is the family comparison useful?

Suppose:

M_1<M_2<M_3

in model size.

If performance consistently follows:

P(M_1)<P(M_2)<P(M_3),

then the benchmark has some sensitivity to model capability.

That doesn't prove size is the only factor, because architecture, training data, and training procedure can also differ.

But within one model family, size comparisons become more informative.

5.33.11 PaLM-2-L

The deck reports that:

\boxed{\text{PaLM-2-L wins on 4 of the 5 tasks}}

among the listed comparisons. (Source: indicgenbench-slides)

So the largest model in that family is very strong, but notably:

\boxed{ \text{not necessarily the winner on all five} }.

Again:

\text{larger} \not\Rightarrow \text{automatic universal dominance}.

5.33.12 LLaMA result

The slide reports that open-source LLaMA models lag substantially in this benchmark setup.

It even notes that:

\boxed{ \text{LLaMA-65B underperforms the smallest PaLM-2-XXS} }

in the reported comparisons. (Source: indicgenbench-slides)

This is extremely important.

It tells us:

\boxed{ \text{parameter count alone does not determine multilingual generation quality} }

because a much larger model can still underperform a smaller model from another training family.

5.33.13 BLOOMZ

The deck reports:

\boxed{\text{BLOOMZ wins 3 of 5 tasks}}

among the listed models. (Source: indicgenbench-slides)

The deck describes BLOOMZ as:

\boxed{ \text{instruction-tuned + broad multilingual pretraining} }.

So multilingual training and instruction tuning can be particularly valuable for this benchmark.

Again, this doesn't establish a universal ranking outside the reported benchmark.

5.33.14 The biggest result: Indic performance trails English

The most important sentence on that results slide is:

\boxed{ \text{Every model, even the best, trails its own English performance by 20+ points.} }

(Source: indicgenbench-slides)

This is a very strong diagnosis.

The benchmark isn't merely showing:

\text{different models behave differently}.

It is showing:

\boxed{ \text{the same model is substantially weaker when generating Indic languages than when generating English} }.

5.33.15 Numerical illustration

Suppose a model scores:

85\%

on English.

If it trails English by 22 points on an Indic task:

85-22 = \boxed{63\%}.

The source says the gap is 20+ points across the reported models; 22 is just an illustrative example. (Source: indicgenbench-slides)

5.33.16 Now the resource-tier analysis

The next question is:

Is this degradation uniform across all Indic languages?

No.

The deck reports a clear ordering:

\boxed{ \text{High resource} > \text{Medium resource} > \text{Low resource} }

across every task. (Source: indicgenbench-slides)

This is one of the central findings.

5.33.17 What is being measured?

For every task, the benchmark groups languages into:

\boxed{H=\text{Higher}}
\boxed{M=\text{Medium}}
\boxed{L=\text{Low}}.

Then it computes performance by tier.

So rather than one number:

P_{\text{all}}

we look at:

\boxed{ P_H,\quad P_M,\quad P_L }.

The reported pattern is:

P_H>P_M>P_L.

(Source: indicgenbench-slides)

5.33.18 Why is this stronger than one overall average?

Suppose:

P_H=70
P_M=60
P_L=40.

Overall average could still look respectable:

\frac{70+60+40}{3} = \boxed{56.7}.

But that average hides the fact that the lowest-resource languages are far weaker.

This is why resource-tier breakdown is much more revealing.

5.33.19 Translation direction changes the story

Now comes one of the strongest findings in the entire deck.

Consider:

\boxed{\text{FLORES-IN}}.

The benchmark evaluates translation in both directions.

For PaLM-2-L:

English → target language

High:

56.9

Low:

41.9.

So the drop is:

56.9-41.9 = \boxed{15.0\text{ points}}.

(Source: indicgenbench-slides)

5.33.20 Now reverse the direction

Target language → English

High:

68.2

Low:

62.6.

Drop:

68.2-62.6 = \boxed{5.6\text{ points}}.

So:

\boxed{ 15.0\text{ points} }

vs:

\boxed{ 5.6\text{ points} }.

That is a huge difference.

5.33.21 Calculate the ratio

\frac{15.0}{5.6} \approx \boxed{2.68}.

So the resource-tier degradation reported for PaLM-2-L is roughly 2.7 times larger in the:

\boxed{ \text{English}\rightarrow\text{target} }

direction than in:

\boxed{ \text{target}\rightarrow\text{English} }.

This ratio is our calculation from the source numbers. (Source: indicgenbench-slides)

5.33.22 This reveals a major asymmetry

The deck's interpretation is:

\boxed{ \text{current LLMs are better at understanding low-resource languages than generating them} }

(Source: indicgenbench-slides)

Think about the direction:

Understanding low-resource language
\text{Low-resource language} \rightarrow \text{English}

The model receives the difficult language and produces English.

Generating low-resource language
\text{English} \rightarrow \text{Low-resource language}

Now the model has to produce target-language text.

The second is much more fragile.

5.33.23 Why is generation harder?

The source reports the empirical asymmetry, but does not give a single definitive mathematical cause.

A reasonable interpretation is:

\boxed{ \text{understanding requires recognizing patterns} }

whereas generation requires:

\boxed{ \text{reliably producing those patterns} }.

The model may have enough representation to understand some low-resource input but insufficient learned generation statistics to produce fluent target-language output.

This explanatory distinction is model reasoning/inference, not a direct formula from the slide.

5.33.24 Exam question: directionality

Suppose:

P_{H}^{EN\rightarrow Indic}=60
P_{L}^{EN\rightarrow Indic}=40.

Drop:

20.

For reverse direction:

P_H^{Indic\rightarrow EN}=70
P_L^{Indic\rightarrow EN}=65.

Drop:

5.

Then:

\boxed{ \text{generation-side resource sensitivity is }4\times\text{ larger} }

because:

20/5=4.

This is an illustrative exam problem modeled on the directionality finding.

5.33.25 Now the few-shot question

Suppose the model receives:

0

examples.

That is:

\boxed{\text{zero-shot}}.

What happens if we give:

1

worked example?

The deck reports that:

\boxed{ \text{every model family improves monotonically as in-context examples increase} }

and the biggest jump is often:

\boxed{0\rightarrow1\text{ shot}}.

(Source: indicgenbench-slides)

5.33.26 The striking example

For PaLM-2-XXS on FLORES-IN:

\boxed{0\text{-shot}=0.8}

and:

\boxed{1\text{-shot}=24.0}.

Improvement:

24.0-0.8 = \boxed{23.2\text{ points}}.

Relative increase:

\frac{23.2}{0.8}\times100 = \boxed{2900\%}.

This enormous percentage is mathematically correct, but because the original score is tiny, the more meaningful source-friendly statement is:

\boxed{+23.2\text{ points}}.

(Source: indicgenbench-slides)

5.33.27 Why does one example help so much?

The source reports the phenomenon but does not claim a single mechanism.

A reasonable interpretation is that one example gives the model:

\boxed{ \text{task format} + \text{translation style} + \text{expected output structure} }.

So the model does not need to infer the entire task from instructions alone.

This is an inference from general in-context learning, not a statement explicitly established as a theorem by the slide.

5.33.28 But “more examples” has a limit

The slide title is:

\boxed{ \text{More in-context examples help — up to a point} }

Why does the improvement stop being straightforward?

Because every example consumes context.

And for Indic languages:

\boxed{ \text{tokenization itself can become the bottleneck} }.

That takes us to the tokenizer section. (Source: indicgenbench-slides)

5.33.29 Language-specific exemplars

Now the benchmark asks:

Which language should the in-context examples be written in?

The reported ordering is:

\boxed{ \text{test language} > \text{Hindi} > \text{English} }

(Source: indicgenbench-slides)

This is a very elegant result.

5.33.30 Why is the ordering interesting?

Suppose the test language is Punjabi.

Then the model benefits most from:

\boxed{\text{Punjabi examples}}

then:

\boxed{\text{Hindi examples}}

then:

\boxed{\text{English examples}}.

The deck says this matches the order of linguistic relatedness to the test language. (Source: indicgenbench-slides)

So:

\boxed{ \text{similar-language demonstration} > \text{distant-language demonstration} }

in the reported experiments.

5.33.31 Especially important for smaller models

The deck says:

\boxed{ \text{for smaller models, Hindi exemplars can come extremely close to, and sometimes beat, test-language exemplars} }

(Source: indicgenbench-slides)

This suggests that Hindi can function as a useful bridge language in prompting.

Again, that is a reported empirical finding, not a universal guarantee for every Indic language.

5.33.32 Numerical example

Suppose a model scores:

50

with English exemplars,

56

with Hindi exemplars,

and:

60

with test-language exemplars.

Then:

\boxed{ 60>56>50 }

matching the reported ordering.

5.33.33 Now the biggest hidden bottleneck: tokenizer fertility

This is one of the most important technical concepts in the entire IndicGenBench deck.

The slide defines:

\boxed{ \text{Fertility} = \text{average number of subword tokens per word} }

(Source: indicgenbench-slides)

This connects directly to everything we learned earlier about tokenization.

5.33.34 Example of fertility

Suppose a language has 100 words.

After tokenization, those words become:

500

subword tokens.

Then:

\text{fertility} = \frac{500}{100} = \boxed{5}.

So on average:

\boxed{5\text{ tokens per word}}.

5.33.35 Reported fertility values

The deck says:

\boxed{\text{English}\approx1}

and among Indic languages:

\boxed{\text{Pashto}=4.1}

while:

\boxed{\text{Tibetan}=19.9}.

(Source: indicgenbench-slides)

The important consequence is:

one Tibetan word can consume roughly 20 tokens under the evaluated tokenizer.

5.33.36 Why is this not a statement about the language itself?

The slide makes this explicit.

High fertility is:

\boxed{ \text{a tokenizer artifact} }

and is not a measure of intrinsic language complexity.

So:

\boxed{ \text{language is not “hard” because fertility is high} }

Rather:

\boxed{ \text{the chosen tokenizer represents the language inefficiently} }.

This distinction is extremely important.

5.33.37 Context-window mathematics

Suppose the model has a context budget:

B=1920

tokens.

For English:

F_E\approx1.

Suppose an example requires:

100

words.

Approximate token cost:

100\times1 = 100.

Now suppose a target language has:

F=10.

The same 100 words consume approximately:

100\times10 = \boxed{1000}

tokens.

So the same semantic amount of text consumes:

\boxed{10\times}

more context.

This is a conceptual calculation directly based on the fertility definition.

5.33.38 Why does this hurt few-shot prompting?

Suppose each demonstration has:

200

words.

For a language with fertility:

F=1,

rough estimate:

200\text{ tokens}.

Five examples:

5\times200 = 1000.

Easy to fit in:

1920.

Now fertility:

F=8.

Each example costs:

200\times8 = 1600.

Even one demonstration consumes most of the budget.

So:

\boxed{ \text{high fertility} \rightarrow \text{fewer demonstrations fit} }.

That is the central mechanism highlighted by the deck. (Source: indicgenbench-slides)

5.33.39 The actual 1920-token result

At:

\boxed{1920\text{ tokens}}

of context budget:

English

The deck reports that English still fits:

\boxed{5\text{ in-context examples}}

for more than:

\boxed{80\%}

of its test set.

Oriya and Punjabi

The deck reports that these high-fertility languages fall to nearly:

\boxed{0\%}

of test cases being able to fit the required examples by only:

\boxed{2-3\text{ examples}}.

(Source: indicgenbench-slides)

5.33.40 This creates a hidden disadvantage

Suppose two languages have identical model reasoning capability.

Language A can fit:

5

examples.

Language B can fit:

1

example.

Then even if the model would benefit equally from demonstrations, language B receives less usable prompting support.

So:

\boxed{ \text{measured performance} = \text{model capability} + \text{context/tokenizer effects} }

conceptually.

The second equation is a general inference; the source's direct point is that fertility causes some languages to fit fewer worked examples. (Source: indicgenbench-slides)

5.33.41 Why this changes how we interpret low-resource performance

Earlier we might conclude:

Low-resource language models perform poorly because they understand the language poorly.

The tokenizer analysis adds another layer:

\boxed{ \text{they may also receive fewer effective in-context examples} }

because their text consumes more tokens.

So the gap may contain both:

\boxed{\text{representation/understanding difficulty}}

and:

\boxed{\text{context-budget inefficiency}}.

The deck explicitly connects the high-fertility result to the low-resource in-context performance gap. (Source: indicgenbench-slides)

5.33.42 Numerical exam question — fertility

A language has:

F=4.1.

A document contains:

500

words.

Approximate token cost:

500\times4.1 = \boxed{2050\text{ tokens}}.

If the context budget is:

1920,

the document alone exceeds the budget under this simplified calculation.

This is an illustrative estimate using the source's fertility concept and Pashto value; real token counts vary from word to word.

5.33.43 Numerical exam question — Tibetan

Suppose:

F=19.9

and:

200

words need to be included.

Approximate token count:

200\times19.9 = \boxed{3980}.

So a 1920-token context cannot even hold that 200-word text under this average-based approximation.

This illustrates why fertility can become a severe practical bottleneck.

5.33.44 The full causal chain now becomes visible

We began with:

\boxed{ \text{Low-resource language} }

Then:

\downarrow
\boxed{ \text{less training data} }

Then:

\boxed{ \text{weaker learned generation} }

But there is another path:

\boxed{ \text{high tokenizer fertility} }
\downarrow
\boxed{ \text{same content consumes more tokens} }
\downarrow
\boxed{ \text{fewer in-context examples fit} }
\downarrow
\boxed{ \text{less prompting support} }

Thus the low-resource challenge isn't only a data quantity problem.

5.33.45 Another surprising result: fine-tuning vs few-shot

The deck compares:

\boxed{\text{mT5}}

and:

\boxed{\text{PaLM-2}}

under fine-tuning and few-shot prompting. (Source: indicgenbench-slides)

The reported pattern is:

QA

mT5 performs very strongly because it is purpose-built for short-span generation.

CrossSum

PaLM-2 performs better on the longer-form generation task.

And:

\boxed{ \text{PaLM-2-XS few-shot} \approx \text{or exceeds its fine-tuned performance on QA} }

while:

\boxed{ \text{fine-tuning remains clearly better for long-form generation} }.

(Source: indicgenbench-slides)

5.33.46 Why is this distinction useful?

It tells us:

\boxed{ \text{there is no universally best adaptation method} }

The task structure matters.

For short-span QA:

\boxed{\text{few-shot prompting can be surprisingly competitive}}

For long-form summarization:

\boxed{\text{additional training data is more valuable}}

in the reported experiments.

5.33.47 Exam-style conceptual question

Question:

Why can few-shot prompting beat fine-tuning on some QA tasks but not on long-form summarization?

The reported benchmark suggests that short-span QA can be performed very effectively through in-context examples, while long-form generation benefits more strongly from task-specific fine-tuning. The result is task-dependent rather than a universal rule. (Source: indicgenbench-slides)

5.33.49 The deepest takeaway

The benchmark reveals that poor Indic generation is not one single problem.

There are multiple interacting factors:

\boxed{ \text{resource availability} }
+
\boxed{ \text{model/training quality} }
+
\boxed{ \text{generation direction} }
+
\boxed{ \text{tokenizer fertility} }
+
\boxed{ \text{available in-context demonstrations} }

all affect observed performance.

That is why a simple statement such as:

“The model is bad at low-resource languages”

is too coarse.

The deck gives us a more detailed diagnosis.

5.33.50 The most important chain for the exam

Remember this sequence:

\boxed{ \text{Low-resource language} \rightarrow \text{high fertility} \rightarrow \text{more tokens per word} \rightarrow \text{context budget fills faster} \rightarrow \text{fewer demonstrations fit} \rightarrow \text{lower few-shot support} }

and independently:

\boxed{ \text{low-resource training} \rightarrow \text{weaker generation} }

Together:

\boxed{ \text{data scarcity + generation difficulty + tokenizer inefficiency} }

help explain the benchmark's observed low-resource gap.

5.33.52 Final mental model

The complete IndicGenBench evaluation story is now:

\boxed{ \text{Generation quality} }

is measured with metrics adapted to low-resource conditions:

\boxed{ \text{chrF for translation/summarization} }

and:

\boxed{ \text{token-F1 for QA} }.

Then the benchmark reveals:

\boxed{ \text{larger models usually improve} }

but:

\boxed{ \text{every model still has a large Indic-vs-English gap} }.

Then:

\boxed{ \text{High resource}>\text{Medium}>\text{Low} }

and:

\boxed{ \text{understanding low-resource language} > \text{generating low-resource language} }

in the reported FLORES direction comparison. (Source: indicgenbench-slides)

Finally:

\boxed{ \text{few-shot examples help} }

but:

\boxed{ \text{tokenizer fertility controls how many examples can physically fit} }.

That last connection is particularly important because it links tokenization, which we studied at the beginning of the course, directly to multilingual benchmark performance.
