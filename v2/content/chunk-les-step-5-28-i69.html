Step 5.28 — IndicXTREME Benchmark Architecture

Plan node: I10 · chat order #69

We now move from “how was IndicCorp built?” to:

\boxed{ \text{How do we actually measure an Indic-language model?} }

This is the purpose of IndicXTREME.

The benchmark is designed around:

\boxed{ 9\text{ tasks} \quad+\quad 4\text{ task categories} }

The four categories are:

\boxed{ \text{Classification} }
\boxed{ \text{Structure Prediction} }
\boxed{ \text{Question Answering} }
\boxed{ \text{Retrieval} }

The supplied task-suite slide lists 5 classification tasks, 2 structure-prediction tasks, 1 QA task, and 1 retrieval task, for 105 evaluation sets across languages/tasks, with 52 being new contributions. (Source: indicxtreme-slides)

5.28.1 First understand why there are multiple tasks

Suppose a model gets:

90\%

on sentiment.

Does that mean the model understands an Indic language?

Not necessarily.

It could be good at:

\text{classification}

but weak at:

\text{NER}

or:

\text{question answering}

or:

\text{retrieval}

or:

\text{causal reasoning}.

So IndicXTREME intentionally evaluates multiple capabilities.

Conceptually:

\boxed{ \text{language ability} \approx \text{many different downstream capabilities} }

This is why the benchmark is a task suite, not one single test. (Source: indicxtreme-slides)

5.28.2 The 9 tasks

The benchmark table gives:

Classification — 5
\boxed{\text{IndicSentiment}}
\boxed{\text{IndicXNLI}}
\boxed{\text{IndicCOPA}}
\boxed{\text{IndicPara}}
\boxed{\text{M-Intent}}
Structure Prediction — 2
\boxed{\text{Naamapadam}}
\boxed{\text{M-SlotFill}}
QA — 1
\boxed{\text{IndicQA}}
Retrieval — 1
\boxed{\text{FLORES}}

(Source: indicxtreme-slides)

Let's understand them sequentially.

Step 5.28.3 Task 1 — IndicSentiment

The first task is:

\boxed{\text{IndicSentiment}}

Its purpose is sentiment classification.

The model receives a review and predicts its sentiment category.

For example:

"The product looks excellent and works perfectly."

The model might predict:

\boxed{\text{Positive}}

while:

"The material is poor and the product broke quickly."

might be:

\boxed{\text{Negative}}.

The benchmark table lists:

  • 13 languages,
  • 1,000 test examples,
  • accuracy as the metric,
  • product reviews as the domain. (Source: indicxtreme-slides)

5.28.4 Why is sentiment useful?

Sentiment appears simple, but multilingual sentiment is not merely:

\text{translate English words} \rightarrow \text{predict polarity}.

A model has to understand the actual Indic-language input.

The deck's later creation slide also deliberately makes IndicSentiment harder than ordinary polarized review datasets by constructing reviews around specific product aspects rather than using only strongly positive/negative generic reviews. (Source: indicxtreme-slides)

5.28.5 Important creation detail

The supplied deck says IndicSentiment was built by:

  1. curating products from 15 popular categories on Amazon, Flipkart, and Myntra;
  2. identifying product aspects;
  3. asking annotators to write positive/negative reviews around particular aspects;
  4. translating the English reviews into 13 Indic languages manually.

(Source: indicxtreme-slides)

This is important because it attempts to create a more nuanced sentiment task.

5.28.6 Metric: Accuracy

For classification:

\boxed{ \text{Accuracy} = \frac{\text{correct predictions}} {\text{total predictions}} }

Suppose:

N=1000

test examples.

If the model gets:

850

correct:

\text{Accuracy} = \frac{850}{1000} = \boxed{85\%}.

5.28.7 Exam numerical

A model gets 920 correct out of 1,000 IndicSentiment examples.

\frac{920}{1000}\times100 = \boxed{92\%}.

Very straightforward, but this type of calculation should be automatic for you.

Step 5.28.8 Task 2 — IndicXNLI

Next:

\boxed{\text{IndicXNLI}}

This is the Natural Language Inference (NLI) task.

The input is typically:

\boxed{ \text{Premise} + \text{Hypothesis} }

and the model determines their relationship.

Conceptually, the classes are:

\boxed{ \text{Entailment} }
\boxed{ \text{Contradiction} }
\boxed{ \text{Neutral} }

The benchmark table lists:

\boxed{12\text{ languages}}

and:

\boxed{5010\text{ test examples}}.

The table marks its construction as machine-translated (MT), while the later deck explains that the resulting test set is being manually re-verified and corrected. (Source: indicxtreme-slides)

5.28.9 Example of NLI

Premise:

“Rahul went to the market and bought vegetables.”

Hypothesis:

“Rahul bought vegetables.”

Then:

\boxed{\text{Entailment}}

because the premise supports the hypothesis.

Hypothesis:

“Rahul did not buy anything.”

Then:

\boxed{\text{Contradiction}}.

Hypothesis:

“Rahul went to the market on Sunday.”

Then:

\boxed{\text{Neutral}}

unless the premise supplies that information.

5.28.10 Why is IndicXNLI interesting for multilingual evaluation?

Because the original XNLI-style setup is based on cross-lingual transfer.

The important benchmark question becomes:

\boxed{ \text{Can a model learn the inference task from English and transfer it to an Indic language?} }

That question becomes central to the zero-shot evaluation protocol we'll study later.

5.28.11 Metric

Again:

\boxed{\text{Accuracy}}

Suppose 5,010 test cases exist and the model gets 3,758 correct.

Then:

\frac{3758}{5010}\times100 \approx \boxed{74. \! \ \text{?}}

Let's calculate carefully:

3758/5010\approx0.7501.

So:

\boxed{\approx75.0\%}.

5.28.12 Task 3 — IndicCOPA

Now we get to a much more reasoning-oriented task:

\boxed{\text{IndicCOPA}}

COPA stands for:

\boxed{\text{Choice of Plausible Alternatives}}

It tests causal commonsense reasoning.

The model receives:

\boxed{\text{premise}}

and two possible alternatives.

It must choose which alternative is the more plausible:

\boxed{\text{cause}}

or:

\boxed{\text{effect}}.

(Source: indicxtreme-slides)

5.28.13 Example

Premise:

“The road became extremely slippery.”

Question:

What was the likely cause?

Options:

A. It had rained heavily.

B. The shop opened late.

Correct:

\boxed{A}

The model needs causal commonsense rather than simple keyword matching.

5.28.14 How IndicCOPA was constructed

The deck gives a very interesting anti-bias procedure.

The English COPA test set is manually translated into:

\boxed{18\text{ Indic languages}}.

But before translation:

\boxed{ \text{premise + option 1 + option 2} }

are randomized and reassigned across translators.

That means one translator does not see the entire original item. (Source: indicxtreme-slides)

5.28.15 Why randomize the pieces?

Suppose a translator sees the whole item.

They might unconsciously preserve:

\text{sentence length}

or:

\text{word choice}

or:

\text{stylistic cues}

that reveal the answer.

Then the benchmark could contain a translation artifact.

The bias-guard procedure attempts to prevent this.

So:

\boxed{ \text{randomization} \rightarrow \text{reduced translation leakage} }

This is directly from the dataset-construction description. (Source: indicxtreme-slides)

5.28.16 Important training detail

COPA itself has no training split.

Therefore fine-tuning uses:

\boxed{\text{English Social IQA}}

according to the slide.

This is another example of the benchmark's cross-lingual transfer idea. (Source: indicxtreme-slides)

5.28.17 Task 4 — IndicPara

Next:

\boxed{\text{IndicPara}}

This is a paraphrase/equivalence classification task.

The question is:

\boxed{ \text{Do two sentences express essentially the same meaning?} }

The benchmark table lists:

\boxed{10\text{ languages}}

and:

\boxed{2002\text{ test instances}}.

Metric:

\boxed{\text{Accuracy}}.

(Source: indicxtreme-slides)

5.28.18 Example

Sentence A:

“The boy fell and injured himself.”

Sentence B:

“The boy was hurt when he fell.”

These can be:

\boxed{\text{Paraphrase}}

because the meaning is substantially equivalent.

But:

“The girl pushed the boy and he fell.”

is not equivalent.

5.28.19 How IndicXParaphrase was created

The deck says:

\boxed{1001}

English sentences of at least 10 words were machine-translated into:

\boxed{10\text{ languages}}.

Annotators then:

  • verified/corrected translations,
  • wrote one paraphrase,
  • wrote one non-paraphrase.

(Source: indicxtreme-slides)

5.28.20 The important anti-shortcut rule

For paraphrases, annotators were instructed to minimize word overlap.

They could use:

\text{synonyms}
\text{active/passive changes}
\text{temporal phrase restructuring}.

For non-paraphrases, they could change things like:

\text{named entities}
\text{pronouns}
\text{adjectives}
\text{adverbs}.

The goal is:

\boxed{ \text{meaning} > \text{surface word overlap} }

The deck explicitly contrasts this construction with PAWS-X and says it did not use back-translation or noisy alignment to manufacture non-paraphrases. (Source: indicxtreme-slides)

5.28.21 Task 5 — M-Intent

The fifth classification task is:

\boxed{\text{M-Intent}}

This is intent classification over spoken/user-query data.

The benchmark table lists:

\boxed{7\text{ languages}}

with:

\boxed{2974\text{ test examples}}

and:

\boxed{\text{Accuracy}}

as the metric.

Its domain is:

\boxed{\text{spoken queries}}.

(Source: indicxtreme-slides)

5.28.22 Example of intent classification

Suppose the user says:

“Set an alarm for seven tomorrow morning.”

Possible intents:

\text{weather}
\text{alarm}
\text{music}
\text{navigation}.

Correct:

\boxed{\text{alarm}}

This tests whether the model can map multilingual natural-language input to the correct user intent.

5.28.23 Why does this task matter?

Because intent recognition tests a practical capability:

\boxed{ \text{understand what the user wants} }

rather than just:

\boxed{ \text{understand what the sentence literally says} }.

It is particularly relevant to spoken-agent systems.

The dataset comes from the MASSIVE resource, whose 7-language Indic subset is taken as-is according to the deck. (Source: indicxtreme-slides)

5.28.24 Now classification is complete

We have:

\boxed{ \text{IndicSentiment} }

sentiment.

\boxed{ \text{IndicXNLI} }

inference.

\boxed{ \text{IndicCOPA} }

causal commonsense reasoning.

\boxed{ \text{IndicPara} }

semantic equivalence.

\boxed{ \text{M-Intent} }

intent recognition.

So the five tasks probe very different abilities.

Suppose we get:

Their individual accuracies are:

Step 5.28.26 Category 2 — Structure Prediction

Now classification ends.

We move to:

\boxed{\text{Structure Prediction}}

There are:

\boxed{2\text{ tasks}}

in this category:

\boxed{\text{Naamapadam}}

and:

\boxed{\text{M-SlotFill}}.

(Source: indicxtreme-slides)

The fundamental difference is:

Classification

One label for the whole example.

x\rightarrow y
Structure prediction

Labels are assigned to parts of the input.

x_1,x_2,\ldots,x_n \rightarrow y_1,y_2,\ldots,y_n.

This is a major conceptual shift.

5.28.27 Task 6 — Naamapadam

Naamapadam is the:

\boxed{\text{Named Entity Recognition (NER)}}

task.

Suppose:

Aniket studies at BITS Pilani.

The model should identify entities such as:

\boxed{\text{Aniket}}

and:

\boxed{\text{BITS Pilani}}.

This is not one label for the sentence.

Instead, we assign a label to each relevant token/span.

5.28.28 IOB2 representation

The deck says Naamapadam uses:

\boxed{\text{IOB2 format}}

after projecting tags and then having annotators verify/correct them. (Source: indicxtreme-slides)

IOB2 means:

B=\text{Beginning of entity}
I=\text{Inside entity}
O=\text{Outside entity}.

Example:

Aniket       B-PER
studies      O
at           O
BITS         B-ORG
Pilani       I-ORG

So:

\boxed{ \text{token sequence} \rightarrow \text{structured label sequence} }

5.28.29 How Naamapadam is constructed

The deck describes this pipeline:

\boxed{ \text{English sentence} \rightarrow \text{off-the-shelf NER} }

then:

\boxed{ \text{project tags onto Indic sentence using word alignment} }

then:

\boxed{ \text{human verification + correction} }

(Source: indicxtreme-slides)

This is a classic example of:

\boxed{ \text{automatic generation} + \text{human quality control} }

rather than blindly trusting projection.

5.28.30 Metric: F1

Because NER is structured prediction, the benchmark uses:

\boxed{F1}

rather than simple accuracy.

Recall:

Precision= \frac{TP}{TP+FP}
Recall= \frac{TP}{TP+FN}

and:

\boxed{ F1= \frac{2PR}{P+R} }

where P is precision and R is recall.

5.28.31 Numerical NER example

Suppose:

TP=80,\quad FP=20,\quad FN=10.

Then:

P=\frac{80}{80+20}=0.8.
R=\frac{80}{80+10} = 0.8889.

Therefore:

F1= \frac{2(0.8)(0.8889)} {0.8+0.8889}
\approx \boxed{0.8421}

or:

\boxed{84.21\%}.

This is an exam-style F1 calculation.

5.28.32 Task 7 — M-SlotFill

The second structure-prediction task is:

\boxed{\text{M-SlotFill}}

It comes from the MASSIVE family and evaluates slot filling.

Think:

\boxed{ \text{Intent} + \text{Slot values} }

For example:

“Play Arijit Singh songs tomorrow evening.”

Potential structure:

\text{intent}=\text{play music}
\text{artist}=\text{Arijit Singh}
\text{time}=\text{tomorrow evening}.

The model must identify spans and assign slot types.

The benchmark table lists:

\boxed{7\text{ languages}}

and evaluates it with:

\boxed{F1}.

(Source: indicxtreme-slides)

5.28.33 Why F1 again?

Because a slot-filling system can:

  • miss an entity,
  • produce an incorrect span,
  • assign the wrong slot.

Accuracy would be a poor fit because the output is structured.

So:

\boxed{ \text{Precision + Recall} \rightarrow F1 }

is more appropriate.

Step 5.28.34 Category 3 — Question Answering

Now:

\boxed{\text{QA}}

has one task:

\boxed{\text{IndicQA}}.

Its task type is:

\boxed{\text{Span Extraction}}

and its metric is:

\boxed{F1}.

The table lists:

\boxed{11\text{ languages}}.

(Source: indicxtreme-slides)

5.28.35 What is span extraction?

Suppose context says:

“Rabindranath Tagore was born in Kolkata.”

Question:

Where was Rabindranath Tagore born?

The answer is a span from the context:

\boxed{\text{Kolkata}}.

So the model must identify:

\boxed{ [start,end] }

of the answer span.

This is fundamentally different from classification.

5.28.36 IndicQA was built differently

This is a particularly important dataset-construction idea.

The deck says IndicQA was created from scratch, without an English-source translation pipeline. (Source: indicxtreme-slides)

The researchers first identify topics connected to Indic:

\text{history}
\text{monuments}
\text{authors}
\text{politicians}
\text{festivals}

etc.

They then rank topics according to the number of Indic-language Wikipedia articles available and remove topics whose articles average fewer than 10 sentences. (Source: indicxtreme-slides)

5.28.37 Why is this important?

Because the benchmark is trying to test:

\boxed{ \text{actual Indic-language reading comprehension} }

rather than:

\boxed{ \text{translation of an English QA task} }.

That is a crucial benchmark-design distinction.

5.28.38 The clever anti-leakage trick

IndicQA has a two-phase process.

Phase 1 — Write question

The context is split into:

\boxed{\text{larger first part}}

and:

\boxed{\text{smaller second part}}

of 2–3 sentences.

These are machine-translated into English, and the annotator writes Indic-language questions from the English translation.

Phase 2 — Mark answer

A different annotator sees only the original Indic first part and marks the answer span.

Questions based on the withheld second part become naturally:

\boxed{\text{unanswerable}}

for the visible context. (Source: indicxtreme-slides)

This is a very clever way of generating both:

\boxed{\text{answerable}}

and:

\boxed{\text{unanswerable}}

questions.

5.28.39 IndicQA annotation rules

The deck specifies:

\boxed{\ge 2\text{ questions per paragraph}}

answer span:

\boxed{\le5\text{ continuous words}}

and:

  • answer must be in one sentence;
  • never use an entire sentence as an answer;
  • never use a pronoun;
  • minimize phrase overlap;
  • choose the relevant occurrence if the answer string appears more than once.

(Source: indicxtreme-slides)

These constraints are designed to make the 11 independently annotated languages comparable.

5.28.40 Numerical QA example

Suppose the gold answer span is:

[\text{Kolkata}]

and the model outputs:

[\text{Kolkata city}].

Token overlap:

1

of:

1

gold token.

Precision:

P=\frac{1}{2}=0.5

Recall:

R=\frac{1}{1}=1.

Therefore:

F1= \frac{2(0.5)(1)}{0.5+1} = \boxed{0.667}.

So:

\boxed{66.7\%}.

The benchmark's reported metric is F1, though the exact implementation details of tokenization/normalization are not specified on this slide.

Step 5.28.41 Category 4 — Retrieval

The final category is:

\boxed{\text{Retrieval}}

with:

\boxed{\text{FLORES}}.

The task is:

\boxed{\text{Sentence Retrieval}}

with:

\boxed{1012}

test sentences and:

\boxed{18\text{ Indic languages}}.

The table lists:

\boxed{\text{Accuracy}}

as the metric. (Source: indicxtreme-slides)

5.28.42 What does sentence retrieval mean?

Conceptually, suppose we have:

q

a query sentence.

And a collection:

D=\{d_1,d_2,\ldots,d_N\}.

The model must find the correct corresponding sentence:

\boxed{ d^* }

for the query.

A retrieval system therefore computes some notion of:

\text{similarity}(q,d_i)

and selects the best candidate.

The exact retrieval model architecture is not specified by this slide; this is the general retrieval formulation.

5.28.43 Why FLORES is useful

The deck says FLORES is already an:

\boxed{n\text{-way parallel, human-translated dataset}}

and the benchmark directly incorporates it for sentence-retrieval evaluation. (Source: indicxtreme-slides)

So unlike some newly constructed datasets:

\boxed{ \text{no new translation creation pipeline is required here} }

because the resource already exists.

5.28.44 Complete task-suite map

Now we can finally see the whole benchmark:

\boxed{ \text{IndicXTREME} }
Classification
\boxed{ \begin{aligned} &\text{IndicSentiment}\\ &\text{IndicXNLI}\\ &\text{IndicCOPA}\\ &\text{IndicPara}\\ &\text{M-Intent} \end{aligned} }
Structure Prediction
\boxed{ \begin{aligned} &\text{Naamapadam}\\ &\text{M-SlotFill} \end{aligned} }
QA
\boxed{ \text{IndicQA} }
Retrieval
\boxed{ \text{FLORES} }

(Source: indicxtreme-slides)

5.28.45 Why the metrics differ

This is very important for the exam.

Classification
\boxed{\text{Accuracy}}

because the output is a class.

NER / slot filling / QA
\boxed{F1}

because outputs involve structured spans/tags.

Retrieval
\boxed{\text{Accuracy}}

in the benchmark table because the correct retrieval target is evaluated as a discrete outcome.

Thus:

\boxed{ \text{Metric depends on output structure} }

not simply on whether the task is “hard” or “easy.”

5.28.46 Human annotation vs machine translation

Another key table dimension is:

\boxed{HA=\text{Human Annotated}}

and:

\boxed{MT=\text{Machine Translated}}.

The benchmark table marks, for example:

\text{IndicSentiment}\rightarrow HA
\text{IndicXNLI}\rightarrow MT
\text{IndicCOPA}\rightarrow HA

and other tasks accordingly. (Source: indicxtreme-slides)

But don't misinterpret MT.

It does not mean:

\boxed{ \text{“No humans involved.”} }

The later slide explicitly emphasizes:

\boxed{ \text{every IndicXTREME evaluation set contains a human-supervision step} }

through translation, post-editing, creation, verification, or correction. (Source: indicxtreme-slides)

5.28.47 The four construction pathways

The deck summarizes four broad paths:

\boxed{\text{translated from scratch}}
\boxed{\text{built without any English source}}
\boxed{\text{machine-translated then verified}}
\boxed{\text{tag-projected then corrected}}

Yet all retain human supervision. (Source: indicxtreme-slides)

This is a fundamental benchmark-quality principle.

5.28.48 Why benchmark construction itself matters

Suppose benchmark translations contain systematic artifacts.

Then a model can exploit:

\boxed{\text{translation artifacts}}

instead of:

\boxed{\text{actual language understanding}}.

Therefore benchmark design is itself part of model evaluation.

This is why IndicXTREME spends so much attention on:

\text{human verification}
\text{bias guards}
\text{anti-overlap rules}
\text{natural Indic-language content}.

The individual examples of these mechanisms are documented across the dataset-construction slides. (Source: indicxtreme-slides)

Suppose the benchmark has:

Then:

5+2+1+1 = \boxed{9}.

Exactly as stated by the deck. (Source: indicxtreme-slides)

5.28.50 Another exam numerical

There are:

105

evaluation sets in total.

Of these:

52

are brand-new contributions.

Then reused/adapted evaluation sets:

5.28.51 The key structural difference among tasks

This is an excellent way to organize the material:

\boxed{ \text{Classification} }

asks:

Which label?

x\rightarrow y
\boxed{ \text{Structure prediction} }

asks:

What label/span belongs to each piece?

x_1,\ldots,x_n \rightarrow y_1,\ldots,y_n
\boxed{ \text{QA} }

asks:

Which span answers the question?

(q,c)\rightarrow[a,b]
\boxed{ \text{Retrieval} }

asks:

Which candidate is the correct match?

q\rightarrow d^*.

This is the conceptual framework to remember.

5.28.52 Why IndicXTREME is more than a leaderboard

The benchmark is simultaneously testing:

\boxed{ \text{semantic understanding} }
\boxed{ \text{reasoning} }
\boxed{ \text{sequence labeling} }
\boxed{ \text{reading comprehension} }
\boxed{ \text{retrieval} }

across languages with different resource levels.

So a model's performance is a profile, not a single scalar capability.

5.28.54 The deeper lesson

IndicXTREME isn't designed merely to ask:

\boxed{ \text{“Can a model process Hindi?”} }

Instead it asks:

\boxed{ \text{“Can a model transfer multiple NLP capabilities into many Indic languages?”} }

That is a much more demanding question.

And this is why the benchmark must combine:

\boxed{ \text{many tasks} + \text{many languages} + \text{careful data construction} + \text{controlled transfer protocol} }.

The final piece—controlled transfer protocol—is what we study next.
