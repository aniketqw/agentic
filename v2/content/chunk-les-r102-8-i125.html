R102.8 — Master Integration: From Transformer to DeepSeek-R1-Distill

Plan node: B4 · chat order #125

↩ Back to main text: Step 1.13 — Stacking Transformer Blocks → Final Norm → Unembedding → Log · Step 5.19 — Limits of Distillation + Future Directions

We have learned every major component separately. Now we need to connect them into one system.

The source itself organizes the DeepSeek journey into four broad stages:

\boxed{ \text{KV Cache} \rightarrow \text{MLA + MoE} \rightarrow \text{MTP + FP8 + training} \rightarrow \text{RL + Distillation} }

with the post-training path ultimately producing reasoning models and distilled students. (Source: Build a DeepSeek Model (From Scratch))

This is the point where memorizing individual definitions stops being enough. You should be able to answer:

Why was each component introduced, what bottleneck does it solve, and what component comes next because of it?

1. Start with an ordinary Transformer

We begin with:

\text{tokens} \rightarrow \text{embeddings} \rightarrow \text{Transformer blocks} \rightarrow \text{logits} \rightarrow \text{next token}.

The problem is that scaling a normal Transformer creates several different bottlenecks.

Think of them as four separate engineering problems:

\boxed{ \begin{array}{ll} \text{Inference:} & \text{KV-cache memory}\\ \text{Model scaling:} & \text{parameter/compute cost}\\ \text{Training:} & \text{memory + communication + throughput}\\ \text{Post-training:} & \text{reasoning + deployment} \end{array}}

DeepSeek's innovations are easier to remember when attached to those problems.

2. Problem 1 — Autoregressive inference

Suppose we have generated:

The student studied machine learning ...

and want the next token.

At every step, the query for the new token has to attend to all previous tokens.

Without caching, we would repeatedly recompute old keys and values.

So:

\boxed{ \text{KV Cache} }

stores information from previous positions.

Instead of:

\text{recompute old K,V every step},

we do:

\text{compute new K,V once} + \text{reuse cache}.

That is the foundation for efficient autoregressive inference.

3. But KV Cache creates another scaling problem

For conventional multi-head attention, the cache contains:

K,V

for every layer, every head, every previous token.

Therefore, for long contexts:

\boxed{\text{KV-cache memory grows with sequence length}}

This leads directly to the next architectural idea.

4. Problem 2 — Make the KV cache smaller

DeepSeek introduces:

\boxed{\text{MLA — Multi-Head Latent Attention}}

Instead of storing full key/value representations for every head, MLA compresses the content into a lower-dimensional latent representation.

Conceptually:

x \rightarrow c_{KV} \rightarrow \text{store latent}

and during attention the necessary representations are reconstructed.

Thus the key idea is:

\boxed{ \text{store a compact latent representation rather than full K,V} }

The source explicitly describes MLA as targeting the attention memory/speed bottleneck, especially for long sequences. (Source: Build a DeepSeek Model (From Scratch))

5. MLA has two kinds of information

This is one of the most important architectural ideas to retain.

The source implementation separates:

\boxed{\text{content}}

and:

\boxed{\text{position}}

paths.

So conceptually:

                     x
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
      content path          position path
          │                     │
      latent c_kv              RoPE
          │                     │
          └──────────┬──────────┘
                     ▼
                   scores
                     │
                     ▼
                  context

The source's Chapter 6 implementation caches:

(c_{kv},k_r)

rather than a conventional full K,V pair.

That is the actual implementation distinction we previously traced.

6. Problem 3 — Scaling model capacity

Suppose we want a much larger model.

A dense Transformer makes every token pass through the same large feed-forward network.

That is expensive.

DeepSeek-MoE changes the idea:

\boxed{ \text{many experts exist, but only a few are activated per token} }

For example:

N=8,\qquad k=2

means:

\boxed{\text{8 available routed experts, 2 selected per token}}

in our Mini-DeepSeek configuration.

7. What MoE gives us

A token x goes through the router:

g(x) \rightarrow \text{scores}

then top-k experts are selected.

Conceptually:

                 Token
                   │
                 Router
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        Expert   Expert   Expert ...
          │        │
          └── weighted ────┘
                   │
             Routed output

A shared expert can also process every token.

Therefore:

\boxed{ \text{model capacity can be large without activating every routed expert} }

The source identifies MoE as the solution to the scaling/model-capacity problem. (Source: Build a DeepSeek Model (From Scratch))

8. But MoE creates a new problem

Now tokens must travel to the GPUs containing their selected experts.

That creates:

\boxed{\text{All-to-All communication}}

So we traded one bottleneck for another:

\text{dense compute cost} \rightarrow \text{sparse compute + communication}.

This becomes extremely important when we reach distributed training.

9. Problem 4 — Improve learning and inference through future prediction

The next DeepSeek innovation is:

\boxed{\text{MTP — Multi-Token Prediction}}

Instead of training only:

t_{i+1}

from position i, MTP creates additional prediction objectives for future tokens:

t_{i+1},t_{i+2},t_{i+3},\ldots

depending on the number of MTP modules.

The source describes MTP as improving learning and inference speed by predicting multiple future tokens. (Source: Build a DeepSeek Model (From Scratch))

10. MTP is not simply “many independent heads”

This is important.

Our source implementation uses a sequential structure:

h^0 \rightarrow h^1 \rightarrow h^2 \rightarrow\cdots

where each MTP stage receives:

\text{previous hidden representation} + \text{future-token embedding}.

So:

\boxed{ \text{MTP = sequential refinement/prediction chain} }

in the implementation we studied.

11. Why does MTP connect to inference?

The interesting possibility is speculative decoding.

The main model predicts the next token, while MTP-trained modules can provide information about several future positions.

Conceptually:

\boxed{ \text{predict farther ahead} \rightarrow \text{propose multiple tokens} \rightarrow \text{verify} }

So an objective originally introduced during training can also have an inference-time interpretation.

12. Problem 5 — Training efficiency

Now imagine the model is too large for one GPU.

We need distributed training.

Start with:

\boxed{\text{Data Parallelism / DDP}}

Every GPU holds a copy of the model.

Different GPUs process different data.

Then gradients are synchronized using All-Reduce.

So:

\boxed{ \text{DDP increases throughput} }

but:

\boxed{ \text{DDP does not reduce model-replica memory} }

because every GPU still holds the full model.

13. Model too large? Move beyond DDP

Then we use:

\boxed{\text{model/pipeline parallelism}}

Instead of:

GPU 0 → full model
GPU 1 → full model
GPU 2 → full model
GPU 3 → full model

we can have:

GPU 0 → layers 0–N
GPU 1 → layers N–2N
GPU 2 → layers 2N–3N
GPU 3 → layers 3N–4N

Now the model itself is distributed.

This solves the:

\boxed{\text{model-doesn't-fit}}

problem.

14. But pipeline parallelism creates a bubble

Suppose there are 4 stages and 8 micro-batches.

Pipeline execution contains fill and drain periods.

The source's simplified GPipe example gives:

\text{bubble}=8-4=4?

Careful: in the source's stated example, the reported bubble is:

\boxed{4-1=3}

and theoretical efficiency:

\frac{8}{8+3} \approx73\%.

The important thing is not memorizing this one numerical example but understanding the idle time created while the pipeline fills/drains.

15. 1F1B improves the memory behavior

Instead of doing:

FFFF...
BBBB...

the schedule interleaves:

F B F B F B ...

after warm-up.

This is:

\boxed{\text{1F1B}}

and reduces activation-memory pressure.

However, with MoE we now face another problem:

\boxed{\text{All-to-All communication}}

can become expensive.

16. DualPipe enters

DeepSeek therefore uses a more sophisticated pipeline schedule.

The source describes the key principle as:

\boxed{ \text{overlap communication with computation} }

Instead of:

communication
   ↓
wait
   ↓
computation

we try:

communication ──────────┐
                        │
                        ▼
                 computation

so GPU resources remain occupied.

The source emphasizes this especially for MoE's expensive token shuffling. (Source: Build a DeepSeek Model (From Scratch))

17. Problem 6 — Numerical efficiency

Even if the model fits and communication is handled, computation and memory traffic are expensive.

So the training pipeline introduces:

\boxed{\text{FP8}}

The central idea:

\text{higher numerical efficiency}

through 8-bit floating-point computation/representation in appropriate parts of the training system.

We previously separated:

\text{format} \rightarrow \text{scaling} \rightarrow \text{range} \rightarrow \text{clipping/outliers} \rightarrow \text{training implications}.

That is why FP8 belongs to the training-efficiency portion of the graph rather than being an architectural attention mechanism.

18. So now we have a trained foundation model

Put the architecture + training components together:

\boxed{ \text{Transformer} + \text{KV Cache} + \text{MLA} + \text{MoE} + \text{MTP} + \text{FP8} + \text{distributed training} }

produces the foundation-model stage.

In the book's framing, this is the path toward:

\boxed{\text{DeepSeek-V3 Base}}

which then enters post-training. (Source: Build a DeepSeek Model (From Scratch))

19. Now comes post-training

This is where the knowledge graph changes direction.

Before:

\text{How do we efficiently train a powerful model?}

Now:

\boxed{\text{How do we change what the model does?}}

We enter:

\boxed{\text{SFT → RL → Distillation}}

20. SFT comes first

Supervised fine-tuning gives the model demonstrations of desirable behavior.

Conceptually:

(x,y) \rightarrow \text{cross-entropy} \rightarrow \text{parameter update}.

In R1's cold-start stage, curated reasoning examples provide an initial reasoning format. (Source: Build a DeepSeek Model (From Scratch))

21. Then RL changes the optimization regime

LLM RL mapping:

\boxed{ \begin{aligned} state &= \text{prompt + generated tokens}\\ action &= \text{next token}\\ transition &= \text{append token}\\ reward &= \text{response score}\\ policy &= \text{LLM} \end{aligned}}

Then:

\text{reward} \rightarrow \text{advantage} \rightarrow \text{policy update}.

22. PPO and GRPO

Our knowledge graph becomes:

\boxed{ \text{Policy Gradient} \rightarrow \text{Advantage} \rightarrow \text{PPO / GRPO} }

PPO uses a learned value baseline.

GRPO replaces that learned value model with a group-relative baseline:

A_i= \frac{r_i-\mu_r}{\sigma_r+\epsilon}.

The source's DeepSeek-R1 framing uses GRPO as the central RL algorithm. (Source: deepseek-r1-slides)

23. DeepSeekMath is the bridge

This is where the earlier index matters.

Your learning spine had:

I_7=\boxed{\text{DeepSeekMath}}

before:

I_8=\boxed{\text{DeepSeek-R1}}.

Why?

Because DeepSeekMath introduces GRPO, which R1 then uses.

So:

\boxed{ \text{DeepSeekMath} \rightarrow \text{GRPO} \rightarrow \text{R1} }

The R1 slides explicitly state that GRPO comes from DeepSeekMath. (Source: deepseek-r1-slides)

24. R1-Zero asks the fundamental question

The slide's central design question is:

Can reasoning emerge from RL alone without SFT first?

The experimental setup begins from DeepSeek-V3-Base and applies GRPO with reward based on final-answer correctness, without human reasoning demonstrations or a learned reward model. (Source: deepseek-r1-slides)

So:

\boxed{ V3\text{-Base} \rightarrow GRPO + verifiable reward \rightarrow R1\text{-Zero} }

This is the reasoning discovery experiment.

25. But R1-Zero is not the final assistant

The problems we already studied lead to:

\boxed{ \text{R1-Zero} \rightarrow \text{R1 staged pipeline} }

with:

\text{cold-start SFT} \rightarrow \text{reasoning RL} \rightarrow \text{rejection sampling} \rightarrow \text{mixed-data SFT} \rightarrow \text{final hybrid RL}.

(Source: Build a DeepSeek Model (From Scratch))

Notice how all our previously separate concepts now appear in one line.

26. Where ReTool fits

Your original index has:

I_9=\boxed{\text{ReTool / tool-using reasoning}}.

ReTool extends the reasoning loop:

\text{reason} \rightarrow \text{call tool} \rightarrow \text{observe result} \rightarrow \text{continue reasoning}.

So reasoning isn't necessarily:

\text{LLM}\rightarrow\text{answer}.

It can become:

\boxed{ \text{LLM} \rightarrow \text{tool} \rightarrow \text{environment feedback} \rightarrow \text{LLM} }

This is the natural bridge from reasoning models toward agentic systems.

27. Then comes distillation

R1 is powerful but very large.

So:

\boxed{ R1 \rightarrow \text{generate reasoning traces} \rightarrow \text{rejection sampling} \rightarrow \text{student SFT} }

This gives the distilled models.

The key transition is:

\boxed{ \text{discover} \rightarrow \text{demonstrate} \rightarrow \text{imitate} }

rather than asking the small student to independently rediscover the teacher's reasoning strategy.

30. The most important dependency chain

For an interview, remember this:

\boxed{ \text{Transformer} \rightarrow \text{efficient inference} \rightarrow \text{efficient scaling} \rightarrow \text{efficient training} \rightarrow \text{reasoning} \rightarrow \text{distillation} }

And each stage answers one bottleneck:

\boxed{ \begin{array}{rcl} KV/MLA &\rightarrow& \text{memory}\\ MoE &\rightarrow& \text{capacity/compute}\\ MTP &\rightarrow& \text{prediction efficiency}\\ FP8 &\rightarrow& \text{numerical efficiency}\\ DDP/Pipeline/DualPipe &\rightarrow& \text{scale}\\ GRPO/RLVR &\rightarrow& \text{reasoning}\\ Distillation &\rightarrow& \text{deployment} \end{array}}

That is far more useful than memorizing eight isolated definitions.

31. One important source distinction

There is a subtle difference between the lecture slide framing and the more detailed book implementation.

The R1 slide presents R1-Zero very cleanly as:

V3\text{-Base} + GRPO + \text{final-answer correctness reward}

with no human reasoning demonstrations and no learned reward model. (Source: deepseek-r1-slides)

The book then expands the later engineering story, including formatting/language-consistency considerations and the hybrid rewards of final R1. (Source: Build a DeepSeek Model (From Scratch))

So don't collapse all these into one reward definition.

Use:

\boxed{\text{R1-Zero experimental setup}}

and:

\boxed{\text{full R1 production-oriented pipeline}}

as separate concepts.

32. What you should now be capable of doing

At this point, an interview question such as:

“Why does DeepSeek use MLA, MoE, MTP, FP8, DualPipe, GRPO and distillation?”

should not produce seven disconnected definitions.

You should answer:

MLA addresses attention/KV-memory efficiency; MoE increases model capacity with sparse activation; MTP provides additional future-token prediction objectives and can support faster inference; FP8 improves training efficiency; distributed/pipeline/DualPipe techniques make large-scale training practical, especially under MoE communication; GRPO provides the reasoning-oriented RL mechanism used by R1; and distillation transfers the resulting reasoning behavior into smaller models.

That is the architectural story.
