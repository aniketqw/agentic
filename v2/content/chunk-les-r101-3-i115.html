R101.3 — Model Parallelism: When the Model Itself Does Not Fit

Plan node: A5 · chat order #115

We now hit the limitation of DDP.

DDP solved:

\boxed{\text{“training is too slow”}}

by using multiple GPUs.

Gradient accumulation solved:

\boxed{\text{“my desired batch is too large”}}

But DDP makes a complete copy of the model on every GPU. So if the model itself cannot fit on one GPU, DDP cannot solve the problem. The source gives the example of a 671B-parameter DeepSeek-V3-class model, whose half-precision weights alone require hundreds of GB of memory. (Source: Build a DeepSeek Model (From Scratch))

That leads to:

\boxed{\text{Model Parallelism}}

Instead of splitting the data, we split the model across GPUs.

1. Data Parallelism vs Model Parallelism

This distinction must be absolutely clear.

Data Parallelism
             Same full model
        ┌────────┬────────┬────────┐
        ▼        ▼        ▼        ▼
      GPU 0    GPU 1    GPU 2    GPU 3
       data     data     data     data
       A        B        C        D

Every GPU stores the whole model.

Model Parallelism
         One model
            │
       ┌────┼────┬────┐
       ▼    ▼    ▼    ▼
     GPU0 GPU1 GPU2 GPU3
     part part part part

The model itself is divided.

The source frames this as the fundamental distinction: Data Parallelism accelerates by splitting data; Model Parallelism bypasses hardware memory limits by splitting the model. (Source: Build a DeepSeek Model (From Scratch))

2. Why can the model exceed GPU memory?

The VRAM requirement isn't only the model's parameters.

During training we may need memory for:

\text{weights} + \text{gradients} + \text{optimizer states} + \text{activations}.

The source specifically emphasizes that parameters, gradients, and optimizer states can collectively exceed one GPU's VRAM. (Source: Build a DeepSeek Model (From Scratch))

So imagine:

\text{required memory}=200\text{ GB}

but:

\text{one GPU}=80\text{ GB}.

Then:

200>80.

No amount of ordinary DDP replication fixes this.

3. The key idea: split the computation

The source next introduces Pipeline Parallelism, the most intuitive form of model parallelism discussed here.

Instead of splitting the inside of one layer, we split the model between layers.

Suppose our Transformer has 80 layers:

Layer 1
Layer 2
...
Layer 80

We can partition it into stages:

GPU 0 → Layers 1–20
GPU 1 → Layers 21–40
GPU 2 → Layers 41–60
GPU 3 → Layers 61–80

The source describes these groups as stages, with activations flowing from one stage to the next like an assembly line. (Source: Build a DeepSeek Model (From Scratch))

4. Why is it called Pipeline Parallelism?

Because data moves through the stages sequentially.

For one micro-batch:

x \rightarrow Stage_0 \rightarrow Stage_1 \rightarrow Stage_2 \rightarrow Stage_3.

Visually:

Micro-batch
    │
    ▼
┌─────────┐
│ GPU 0   │ Stage 0
│ layers  │
└────┬────┘
     │ activation
     ▼
┌─────────┐
│ GPU 1   │ Stage 1
└────┬────┘
     │
     ▼
┌─────────┐
│ GPU 2   │ Stage 2
└────┬────┘
     │
     ▼
┌─────────┐
│ GPU 3   │ Stage 3
└─────────┘

So the model can be larger than one GPU because no single GPU has to hold all the layers.

5. Three terms you must know

The source defines several terms before discussing schedules. (Source: Build a DeepSeek Model (From Scratch))

Communication

Whenever GPUs exchange tensors.

For example:

GPU_0\rightarrow GPU_1.

The source identifies communication as a major source of overhead.

Micro-batch

A large batch can be divided into smaller chunks.

For example:

32 \rightarrow 4+4+4+4+4+4+4+4.

Those chunks are micro-batches.

They become especially important for pipeline parallelism.

Stage

A portion of the model assigned to a GPU.

For example:

Stage_0=\text{Layers 1–20}.

6. The most important term: Pipeline Bubble

This is the concept you should remember most strongly.

Imagine four GPUs:

GPU 0 → Stage 0
GPU 1 → Stage 1
GPU 2 → Stage 2
GPU 3 → Stage 3

A micro-batch starts at GPU 0.

GPU 1 cannot work until GPU 0 sends its activation.

GPU 2 must wait for GPU 1.

GPU 3 must wait for GPU 2.

Therefore, at the beginning:

Time →

GPU 0   █████
GPU 1      █████
GPU 2         █████
GPU 3            █████

The blank spaces are GPUs doing nothing.

That idle region is the:

\boxed{\text{Pipeline Bubble}}

The source defines the bubble as GPU idle time while waiting for data from a previous stage during forward propagation or for gradients from a later stage during backward propagation. (Source: Build a DeepSeek Model (From Scratch))

7. Why micro-batches are necessary

Suppose we have one large batch.

We don't want:

GPU 0 → entire batch
       ↓
GPU 1
       ↓
GPU 2
       ↓
GPU 3

because then downstream GPUs sit idle for too long.

Instead, break the batch into micro-batches:

m_1,m_2,m_3,m_4,\ldots

Then pipeline them:

           GPU0      GPU1      GPU2      GPU3

m1          F         F         F         F
m2                    F         F         F
m3                              F         F
m4                                        F

Eventually, several GPUs are simultaneously processing different micro-batches.

That is the point of pipeline parallelism.

8. The naive schedule: GPipe

The source next discusses the original GPipe-style schedule.

The basic process has a fill phase.

All micro-batches are sent forward through the pipeline.

For example:

Time →
GPU0    m1F  m2F  m3F  m4F
GPU1         m1F  m2F  m3F  m4F
GPU2              m1F  m2F  m3F  m4F
GPU3                   m1F  m2F  m3F  m4F

Notice what happens.

GPU 3 is initially doing nothing.

GPU 2 is initially doing nothing.

GPU 1 is initially doing nothing.

This is the fill bubble. (Source: Build a DeepSeek Model (From Scratch))

9. Then comes the backward pass

Once all forward passes have happened, the pipeline must perform backward propagation.

Conceptually:

Forward:
GPU0 → GPU1 → GPU2 → GPU3

Backward:
GPU3 → GPU2 → GPU1 → GPU0

This creates another period where some GPUs are idle.

The source calls this the drain phase.

So GPipe effectively has:

\boxed{ \text{fill bubble} + \text{drain bubble} }

(Source: Build a DeepSeek Model (From Scratch))

10. Why is the bubble bad?

Suppose you have expensive GPUs.

During the bubble:

GPU 0 → WORK
GPU 1 → IDLE
GPU 2 → IDLE
GPU 3 → IDLE

You paid for four GPUs, but only one is doing useful computation.

The source emphasizes that this makes the naive pipeline inefficient, especially as the number of pipeline stages increases. (Source: Build a DeepSeek Model (From Scratch))

11. A numerical example from the source

The source gives:

8\text{ micro-batches}

and:

4\text{ stages}.

The bubble size is:

4-1=3.

The theoretical pipeline efficiency is:

\frac{8}{8+3} \approx \boxed{73\%}.

(Source: Build a DeepSeek Model (From Scratch))

This means, in this simplified analysis, only about 73% of the schedule is useful pipeline computation.

The remaining fraction corresponds to pipeline overhead/bubble.

12. A very useful intuition

The number of stages hurts us.

Suppose:

S=4.

Then the bubble component is:

S-1=3.

If:

S=8,

the corresponding fill/drain overhead becomes larger.

Therefore:

\boxed{ \text{more stages} \rightarrow \text{larger relative bubble} }

unless we use better scheduling and enough micro-batches.

The source explicitly states that the naive bubble grows with the number of pipeline stages. (Source: Build a DeepSeek Model (From Scratch))

13. The clever idea: 1F1B

Now the source asks the natural question:

Why run all forwards first and only then do backwards?

Once a micro-batch has completed enough forward computation and its gradient becomes available later in the pipeline, we can start doing its backward work while other micro-batches are still moving forward.

That gives:

\boxed{ \text{1F1B = One Forward, One Backward} }

(Source: Build a DeepSeek Model (From Scratch))

14. The 1F1B intuition

Instead of:

FFFF FFFF FFFF
then
BBBB BBBB BBBB

we do something like:

F → B → F → B → F → B

during the steady state.

The source describes the core intuition exactly this way: why wait to finish all forwards before starting backward? Start backward as soon as an appropriate gradient is available. (Source: Build a DeepSeek Model (From Scratch))

15. 1F1B has three phases

The source describes three phases. (Source: Build a DeepSeek Model (From Scratch))

Phase 1 — Warm-up

The pipeline is being filled.

Some GPUs still have to wait.

GPU0: F
GPU1: idle → F
GPU2: idle → idle → F
...

This is the initial bubble.

Phase 2 — Steady state

Now things become much denser.

A GPU alternates between forward and backward work:

\boxed{ F\rightarrow B\rightarrow F\rightarrow B\rightarrow\cdots }

This keeps the GPUs occupied for much more of the training step. (Source: Build a DeepSeek Model (From Scratch))

Phase 3 — Cool-down

Eventually all forward passes are finished, but some backward work remains.

So the pipeline drains.

There is a smaller ending bubble.

16. GPipe vs 1F1B

Conceptually:

GPipe:

F F F F F F F F
B B B B B B B B


1F1B:

F F F B F B F B
    B F B F B

The exact timeline depends on stage and micro-batch, but the critical difference is:

\boxed{ \text{1F1B interleaves forward and backward work} }

instead of separating them into long uninterrupted phases.

(Source: Build a DeepSeek Model (From Scratch))

17. A subtle but important point

The source makes an excellent distinction:

For a fixed number of stages and micro-batches, GPipe and 1F1B can have the same theoretical pipeline efficiency.

Yet 1F1B is practically superior.

Why?

\boxed{\text{Memory}}

(Source: Build a DeepSeek Model (From Scratch))

18. Why 1F1B uses memory better

During forward propagation, intermediate activations must be retained because backward propagation needs them.

In GPipe:

Forward m1 → store activation
Forward m2 → store activation
Forward m3 → store activation
...
Forward mn → store activation

So many activations may remain in memory simultaneously.

In 1F1B:

Forward mi
   ↓
store activation
   ↓
Backward mi
   ↓
discard activation

The source describes this as a first-in, first-out pattern that reduces peak activation memory. (Source: Build a DeepSeek Model (From Scratch))

Therefore 1F1B can often fit more micro-batches within the same VRAM budget.

And more micro-batches means:

\boxed{ \text{smaller relative bubble} }

because the steady-state portion becomes longer.

19. This is the engineering progression

Look at what has happened.

We started with:

DDP

Problem:

\text{training too slow}

Solution:

\text{more GPUs + replicated model}.

But:

\text{model must fit on every GPU}.

So we move to:

Pipeline Parallelism

Problem:

\text{model too large for one GPU}.

Solution:

\text{split layers across GPUs}.

But:

\text{pipeline bubble}.

So we move to:

1F1B

Problem:

\text{pipeline bubble}.

Solution:

\text{interleave forward/backward}.

But now the DeepSeek-specific issue appears:

\boxed{\text{MoE All-to-All communication}}

which becomes the next major bottleneck. (Source: Build a DeepSeek Model (From Scratch))

20. Why MoE changes everything

We already learned that in DeepSeek-style MoE, different tokens can be routed to different experts.

When experts are distributed across GPUs, tokens may need to move between devices.

Conceptually:

GPU 0
 experts A B

GPU 1
 experts C D

GPU 2
 experts E F

GPU 3
 experts G H

A token currently on GPU 0 might be routed to an expert on GPU 3.

So we need cross-GPU communication:

\boxed{\text{All-to-All}}

The source explains that this token shuffling can become so expensive for huge MoE models that its cost can exceed the pipeline bubble itself. (Source: Build a DeepSeek Model (From Scratch))

And this is precisely where the next innovation enters:

\boxed{\textbf{DualPipe}}

That is the exact engineering story the source is building toward. (Source: Build a DeepSeek Model (From Scratch))
