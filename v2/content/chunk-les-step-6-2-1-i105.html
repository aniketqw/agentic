Plan node: A6 · chat order #105

↩ Back to main text: Step 1.13 — Stacking Transformer Blocks → Final Norm → Unembedding → Log

We now move from data preparation into model construction.

The source explicitly says that model.py translates the architectural theory from the previous chapters into a single functional PyTorch nn.Module, integrating MLA, Decoupled RoPE, MoE, and MTP. (Source: Build a DeepSeek Model (From Scratch))

Before constructing those components, the book introduces one important idea:

\boxed{\texttt{ModelArgs}}

Think of this as the configuration contract of the entire Mini-DeepSeek model.

6.2.1.1 Why do we need ModelArgs?

A model has many architectural parameters:

d_model
number of layers
number of attention heads
latent dimension
RoPE dimension
number of experts
top-k experts
MTP modules
maximum sequence length
...

We could write a constructor like:

MiniDeepSeek(
    d_model,
    n_layers,
    vocab_size,
    num_heads,
    d_latent,
    d_rope,
    moe_n_routed_experts,
    moe_n_shared_experts,
    moe_top_k,
    moe_routed_hidden,
    n_mtp_modules,
    dropout,
    max_seq_len
)

That becomes difficult to manage.

Instead, the source creates one configuration object and passes it around:

\boxed{ \texttt{ModelArgs} \rightarrow \text{all model components} }

The book explicitly describes this as a cleaner way to manage the numerous hyperparameters and to make it easy to define different model sizes. (Source: Build a DeepSeek Model (From Scratch))

6.2.1.2 The source configuration

The source gives:

@dataclass
class ModelArgs:
    # Architecture
    d_model: int = 512
    n_layers: int = 8
    vocab_size: int = 50257

    # Attention (MLA)
    num_heads: int = 8
    d_latent: int = 128
    d_rope: int = 32

    # MoE
    moe_n_routed_experts: int = 8
    moe_n_shared_experts: int = 1
    moe_top_k: int = 2
    moe_routed_hidden: int = 512

    # MTP
    n_mtp_modules: int = 1

    # General
    dropout: float = 0.1
    max_seq_len: int = 1024

(Source: Build a DeepSeek Model (From Scratch))

Now let's understand why each group exists.

6.2.1.3 Group 1 — Core architecture

d_model
\boxed{d_{\text{model}}=512}

This is the hidden representation size.

So after token embedding, each token becomes a vector of length:

512.

For a batch:

X\in\mathbb Z^{B\times T}

becomes approximately:

H\in\mathbb R^{B\times T\times512}.

So d_model controls the width of the model's internal representation.

n_layers
\boxed{n_{\text{layers}}=8}

This determines how many TransformerBlocks are stacked.

Conceptually:

Embedding
   ↓
TransformerBlock 1
   ↓
TransformerBlock 2
   ↓
...
   ↓
TransformerBlock 8
   ↓
Final Norm
   ↓
LM Head

The source later constructs exactly this stack with:

self.blocks = nn.ModuleList(
    [TransformerBlock(args) for _ in range(args.n_layers)]
)

(Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ n_{\text{layers}} = \text{depth of the Transformer trunk}. }
vocab_size

The default is:

\boxed{50,257}.

This corresponds to the GPT-2 tokenizer used for this Mini-DeepSeek project. (Source: Build a DeepSeek Model (From Scratch))

It determines the size of the vocabulary space.

Therefore the output head ultimately produces:

\boxed{ V=50,257 }

logits per token position.

So if:

H\in\mathbb R^{B\times T\times d_{\text{model}}},

the language-model head produces:

\boxed{ Z\in\mathbb R^{B\times T\times V}. }

6.2.1.4 Group 2 — MLA parameters

The next three parameters belong to the Multi-head Latent Attention / MLA implementation.

num_heads
\boxed{8}

This determines how many attention heads are used.

So with:

d_{\text{model}}=512

the source's implementation uses:

d_{\text{head}} = \frac{512}{8} = \boxed{64}.

This division is also reflected later in DeepSeekAttention, where the query is reshaped into:

[\text{batch},\text{heads},\text{sequence},d_{\text{head}}].

The source's attention code uses num_heads and derives the per-head dimension accordingly. (Source: Build a DeepSeek Model (From Scratch))

d_latent
\boxed{d_{\text{latent}}=128}

This is the compressed latent dimension used in the content path of MLA.

The source creates:

self.W_dkv_content = nn.Linear(
    args.d_model,
    args.d_latent,
    bias=False
)

So:

\boxed{ d_{\text{model}} \rightarrow d_{\text{latent}} }

for the compressed KV representation. (Source: Build a DeepSeek Model (From Scratch))

Numerically:

512\rightarrow128.

This is the core compression idea that makes the KV cache smaller.

We already learned the mathematical motivation for MLA earlier; here ModelArgs simply provides the dimensions needed to implement it.

d_rope
\boxed{d_{\text{rope}}=32}

This controls the dimensionality of the separate positional pathway.

The source's implementation constructs:

self.W_k_pos = nn.Linear(
    args.d_model,
    args.d_rope * args.num_heads,
    bias=False
)

self.W_q_pos = nn.Linear(
    args.d_model,
    args.d_rope * args.num_heads,
    bias=False
)

and applies RoPE to those projections. (Source: Build a DeepSeek Model (From Scratch))

So MLA is conceptually split into:

                hidden state
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     Content path        Position path
       MLA latent             RoPE
          │                   │
          └─────────┬─────────┘
                    ▼
             attention scores

This is the decoupled MLA + RoPE architecture we previously derived.

6.2.1.5 Group 3 — MoE parameters

Now we configure the feed-forward part.

Routed experts
moe_n_routed_experts = 8

So there are:

\boxed{8}

specialist experts available to the router.

Shared experts
moe_n_shared_experts = 1

So there is:

\boxed{1}

shared expert through which every token passes.

The source explicitly separates:

shared_experts

from:

routed_experts

in the DeepSeekMoE implementation. (Source: Build a DeepSeek Model (From Scratch))

moe_top_k
moe_top_k = 2

For each token, the router chooses:

\boxed{2}

routed experts out of:

8.

Therefore a token does not go through all eight routed experts.

It goes through the selected top-2.

Conceptually:

Token
  │
  ▼
Router
  │
  ├── Expert 1   ← selected
  ├── Expert 2
  ├── Expert 3
  ├── Expert 4
  ├── Expert 5   ← selected
  ├── Expert 6
  ├── Expert 7
  └── Expert 8

The source implements this using torch.topk(..., self.top_k, ...). (Source: Build a DeepSeek Model (From Scratch))

moe_routed_hidden
moe_routed_hidden = 512

Each expert's FFN expands to a hidden size of:

\boxed{512}.

The source's ExpertFFN is:

d_{\text{model}} \rightarrow d_{\text{hidden}} \rightarrow d_{\text{model}}

implemented as:

fc1: d_model → hidden
fc2: hidden → d_model

with GELU between them. (Source: Build a DeepSeek Model (From Scratch))

Thus the source's expert is conceptually:

512\rightarrow512\rightarrow512.

6.2.1.6 Group 4 — MTP

n_mtp_modules = 1

means the model creates:

\boxed{1}

MTP module.

Remember what MTP does from our earlier derivation:

main representation
       ↓
 predict next token

MTP 1
       ↓
 predict further future token

The source later constructs:

self.mtp_modules = nn.ModuleList(
    [MTPModule(args) for _ in range(args.n_mtp_modules)]
)

(Source: Build a DeepSeek Model (From Scratch))

So n_mtp_modules literally determines the depth of the MTP chain.

6.2.1.7 Group 5 — General parameters

dropout
\boxed{0.1}

This is used as a regularization mechanism in the source implementation.

For example, dropout is attached to the expert FFN and attention components. (Source: Build a DeepSeek Model (From Scratch))

max_seq_len
\boxed{1024}

This defines the maximum positional sequence length for the model components by default.

It is particularly relevant to the RoPE frequency table.

6.2.1.8 An important distinction: default configuration vs actual training configuration

This is easy to miss.

The source's ModelArgs defaults are:

d_{\text{model}}=512
n_{\text{layers}}=8

but later train.py deliberately creates a larger flagship configuration:

d_{\text{model}}=768
n_{\text{layers}}=12
num\_heads=12.

The source describes this later model as approximately 130M parameters. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \texttt{ModelArgs defaults} \neq \text{final training configuration}. }

The defaults are a convenient baseline configuration.

6.2.1.9 Another important distinction: max_seq_len vs block_size

We just saw:

max\_seq\_len=1024.

But train.py uses:

block\_size=256.

The training configuration later passes:

max_seq_len=block_size

when constructing the model. (Source: Build a DeepSeek Model (From Scratch))

Therefore, in that actual training run:

\boxed{ max\_seq\_len=256. }

So do not memorize “1024” as an immutable property of the model.

It is the default in the configuration class.

6.2.1.10 What ModelArgs really accomplishes

Every major component reads from this same configuration.

For example:

ModelArgs
   │
   ├── d_model
   │      ├── Embedding
   │      ├── Attention
   │      ├── MoE
   │      ├── MTP
   │      └── LM Head
   │
   ├── num_heads
   │      └── MLA
   │
   ├── d_latent
   │      └── MLA compression
   │
   ├── d_rope
   │      └── RoPE position path
   │
   ├── MoE parameters
   │      └── DeepSeekMoE
   │
   └── n_mtp_modules
          └── MTP chain

That is why the source calls it an organized configuration object rather than passing independent arguments everywhere. (Source: Build a DeepSeek Model (From Scratch))

6.2.1.11 The architecture we are about to build

Now the whole model can be viewed from the outside:

                    ModelArgs
                        │
                        ▼
              ┌─────────────────┐
              │   MiniDeepSeek   │
              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Embedding       Transformer      MTP chain
                      stack
                       │
                 ┌─────┴─────┐
                 ▼           ▼
              MLA           MoE
                 │           │
              RoPE      Routed + Shared
                       experts
                       │
                       ▼
                   final norm
                       │
                       ▼
                    LM head
                       │
                       ▼
                    logits

The source's top-level MiniDeepSeek class later implements exactly this organization: shared embedding, a stack of Transformer blocks, final normalization, shared LM head, and an MTP module list. (Source: Build a DeepSeek Model (From Scratch))

6.2.1.12 The key mental model

Do not think of ModelArgs as doing computation.

It does not.

It is more like the blueprint handed to the construction workers.

\boxed{ \texttt{ModelArgs} = \text{architecture specification} }

while:

\boxed{ \texttt{MiniDeepSeek} = \text{actual neural network constructed from that specification}. }

For example:

d_{\text{model}}=512

tells the model how wide to make its internal representations.

n_{\text{layers}}=8

tells it how deep to make the Transformer.

num\_heads=8

tells MLA how many attention heads to create.

d_{\text{latent}}=128

tells MLA how small the compressed latent KV representation is.

moe\_top\_k=2

tells MoE how many routed experts each token should use.

n\_mtp\_modules=1

tells the model how many extra MTP stages to construct.

6.2.1.13 One exam-style numerical

Given:

d_{\text{model}}=512,\qquad num\_heads=8

what is the head dimension?

d_{\text{head}} = \frac{d_{\text{model}}}{num\_heads}
= \frac{512}{8}
\boxed{64}.

Now compare the MLA dimensions:

d_{\text{model}}=512

while:

d_{\text{latent}}=128.

So the content pathway compresses:

\boxed{ 512\rightarrow128 }

before reconstructing the per-head key/value representations.

That is the dimensional intuition behind the cache-efficiency motivation we studied earlier.
