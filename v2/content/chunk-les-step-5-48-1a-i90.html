Step 5.48.1A — DeepSeek Causal MTP Module: Inside One Prediction Step

Plan node: A3 · chat order #90

↩ Back to main text: Step 1.1 — What Exactly Is a Language Model? · Step 2.5 — Putting the Decoding Strategies Together

We now open the black box of one MTP head.

This is the most important part of MTP because the phrase

\boxed{\text{“predict multiple future tokens”}}

is easy to understand superficially, but the actual DeepSeek mechanism is more interesting:

\boxed{ \text{previous hidden state} + \text{future-token embedding} \rightarrow \text{projection} \rightarrow \text{Transformer block} \rightarrow \text{new hidden state} }

and then:

\boxed{ \text{new hidden state} \rightarrow \text{shared unembedding} \rightarrow \text{future-token logits} }

The source explicitly says that every MTP head has two jobs: predict a future token and produce a refined hidden state for the next MTP head. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.1 The complete internal picture

Suppose we want:

D=3

prediction depths.

The source's architecture is:

                         h⁰
                          │
                          ▼
                    ┌───────────┐
Embedding(t+1) ───► │   MTP 1   │
                    └─────┬─────┘
                          │
                         h¹
                          │
                          ▼
                    ┌───────────┐
Embedding(t+2) ───► │   MTP 2   │
                    └─────┬─────┘
                          │
                         h²
                          │
                          ▼
                    ┌───────────┐
Embedding(t+3) ───► │   MTP 3   │
                    └─────┬─────┘
                          │
                         h³

          h¹ ───────► shared unembedding ───► logits
          h² ───────► shared unembedding ───► logits
          h³ ───────► shared unembedding ───► logits

The critical feature is:

\boxed{ h^1\rightarrow\text{MTP 2} }

and:

\boxed{ h^2\rightarrow\text{MTP 3} }.

So this is a chain, not three independent heads. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.2 What enters one MTP module?

For MTP depth k, the source says the module receives two inputs.

Input 1 — Previous hidden state
\boxed{h_i^{k-1}}

For the first module:

\boxed{h_i^0}

comes from the main Transformer trunk.

For the second module:

h_i^1

comes from MTP 1.

For the third:

h_i^2.

The source explicitly describes this recursive dependency. (Source: Build a DeepSeek Model (From Scratch))

Input 2 — Future-token embedding

The source denotes this conceptually as:

\boxed{\operatorname{Emb}(t_{i+k})}.

So the MTP module also receives an embedding associated with a future token.

During training, the source implementation uses the ground-truth future-token embedding. (Source: Build a DeepSeek Model (From Scratch))

This is an important detail because MTP is a training objective/mechanism here, not simply a normal inference-time generation loop.

5.48.1A.3 Why use the future-token embedding?

The previous hidden state contains:

\boxed{\text{contextual understanding}}

while the future token embedding carries:

\boxed{\text{semantic/token information}}

about the future position being processed.

The source describes the merged representation as containing both contextual information from the previous step and semantic information associated with the future token. (Source: Build a DeepSeek Model (From Scratch))

So conceptually:

\boxed{ \text{What I already understand} + \text{information about the future position} }

is given to the MTP Transformer.

5.48.1A.4 Step 1 — RMSNorm the two inputs separately

This is subtle.

We do not concatenate the raw vectors immediately.

First:

\tilde h_i^{k-1} = \operatorname{RMSNorm}(h_i^{k-1})

and:

\tilde e_{i+k} = \operatorname{RMSNorm} \left( \operatorname{Emb}(t_{i+k}) \right).

The source explicitly says the two vectors go through separate RMSNorm layers. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.5 What is RMSNorm doing?

Recall:

\boxed{ \operatorname{RMSNorm}(x) = \frac{x} {\sqrt{ \frac1d\sum_{j=1}^{d}x_j^2+\epsilon }} \odot g }

where:

  • d = hidden dimension,
  • \epsilon = small numerical constant,
  • g = learnable scale vector,
  • \odot = elementwise multiplication.

The source's implementation is:

norm_x = x * torch.rsqrt(
    x.pow(2).mean(-1, keepdim=True) + self.eps
)
return self.weight * norm_x

(Source: Build a DeepSeek Model (From Scratch))

The reason for normalizing before merging is to put the two sources of information into a controlled numerical scale before concatenation and projection.

5.48.1A.6 Step 2 — Concatenate them

Now concatenate along the hidden dimension:

\boxed{ u_i^k = \left[ \tilde h_i^{k-1}; \tilde e_{i+k} \right] }

where [a;b] means concatenation.

Suppose:

d=512.

Then:

h_i^{k-1}\in\mathbb R^{512}

and:

e_{i+k}\in\mathbb R^{512}.

After concatenation:

\boxed{ u_i^k\in\mathbb R^{1024}. }

In general:

\boxed{ d\rightarrow 2d. }

The source explicitly emphasizes that the merged vector has twice the normal dimension. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.7 Tensor-shape example

Suppose:

B=2,\quad S=20,\quad d=128.

Then:

H^{k-1}\in\mathbb R^{2\times20\times128}.

Future embeddings:

E_{future}\in\mathbb R^{2\times20\times128}

before accounting for the shrinking valid sequence length.

After concatenation:

\boxed{ 2\times20\times256. }

That doubling is intentional.

5.48.1A.8 Step 3 — Projection back to d

The model does not keep the dimension at 2d.

The merged vector goes through a linear projection:

\boxed{ h_i^{\prime k} = M_k \left[ \operatorname{RMSNorm}(h_i^{k-1}); \operatorname{RMSNorm}(\operatorname{Emb}(t_{i+k})) \right] }

This is the source's Equation 21, represented in the source text as the projection of the concatenated normalized representations back to the standard model dimension. (Source: Build a DeepSeek Model (From Scratch))

The source denotes the projection matrix by:

\boxed{M_k}.

Its conceptual shape is:

\boxed{ M_k\in\mathbb R^{d\times2d}. }

Therefore:

(2d) \rightarrow d.

5.48.1A.9 Numerical projection example

Let:

d=4.

Then:

h^{k-1}\in\mathbb R^4

and:

e_{future}\in\mathbb R^4.

After concatenation:

u\in\mathbb R^8.

Therefore:

M_k\in\mathbb R^{4\times8}.

Matrix multiplication:

(4\times8)(8\times1) = 4\times1.

So:

\boxed{ 8\rightarrow4 }

and the MTP Transformer receives a normal d=4-dimensional hidden representation.

5.48.1A.10 Why project back down?

Because the next component is an ordinary Transformer block whose model dimension is still:

d.

Keeping 2d would change the architecture of the Transformer block.

So the projection acts as an information bottleneck:

\boxed{ 2d\text{ combined information} \rightarrow d\text{ usable Transformer representation}. }

The source calls this output the Transformer Input. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.11 Step 4 — A full Transformer block

Now comes the part that makes DeepSeek MTP much more powerful than a simple linear prediction head.

We take:

h_i^{\prime k}

and pass it through a dedicated Transformer block:

\boxed{ h_i^k = \operatorname{TRM}_k(h_i^{\prime k}) }

which is the source's Equation 22. (Source: Build a DeepSeek Model (From Scratch))

The important word is:

\boxed{\text{full}}.

The source says this is not merely a linear transformation. It involves Transformer computation including attention and a feed-forward network. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.12 What does the Transformer block do?

At a conceptual level:

h' \rightarrow \text{Norm} \rightarrow \text{Attention} \rightarrow \text{Residual} \rightarrow \text{Norm} \rightarrow \text{FFN} \rightarrow \text{Residual} \rightarrow h.

For a decoder-style implementation, this includes causal attention.

Therefore the MTP module is effectively saying:

\boxed{ \text{“Given what I knew before, plus information about the next future position, update my internal representation.”} }

The source uses essentially this interpretation when explaining the purpose of the Transformer block. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.13 Why not just use the projection output directly?

Because the projection only merges information.

The Transformer block can then process relationships between those representations.

So:

\text{Projection} \neq \text{reasoning/feature transformation}.

Instead:

\boxed{ \text{Projection} = \text{combine + resize} }

while:

\boxed{ \text{Transformer} = \text{deep contextual processing}. }

This distinction is central to the source's explanation. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.14 The result is h^k

After the Transformer block:

\boxed{ h_i^k }

is the new hidden state.

It has the same model dimension:

\boxed{ h_i^k\in\mathbb R^d. }

And now something very important happens.

This one hidden state has two destinations.

5.48.1A.15 Destination 1 — Next MTP head

The source states:

\boxed{ h^1\rightarrow\text{Head 2} }
\boxed{ h^2\rightarrow\text{Head 3} }

and so on. (Source: Build a DeepSeek Model (From Scratch))

So:

h_i^{k}

becomes:

h_i^{(k)} = \boxed{\text{previous hidden state for the next MTP stage}}.

This creates:

\boxed{ h^0\rightarrow h^1\rightarrow h^2\rightarrow h^3\rightarrow\cdots }

which is the causal refinement chain.

5.48.1A.16 Destination 2 — Shared unembedding

The second destination is:

\boxed{ \text{Shared Un-Embedding Matrix}. }

The source says this is the same output/logits layer shared with the main model and the other MTP heads. (Source: Build a DeepSeek Model (From Scratch))

Suppose:

h_i^k\in\mathbb R^d

and:

W_{out}\in\mathbb R^{d\times V}.

Then:

z_i^k = h_i^kW_{out}

and therefore:

\boxed{ z_i^k\in\mathbb R^V. }

These are the logits for that prediction depth.

5.48.1A.17 Why “shared” matters

Suppose:

V=50,000

and:

d=4096.

One output projection contains:

4096\times50,000 = 204,800,000

weights.

If every MTP head had its own copy, three MTP heads would require roughly:

614.4\text{ million}

output weights.

Instead, the source shares the output head.

Thus:

\boxed{ W_{out}^{(1)} = W_{out}^{(2)} = W_{out}^{(3)} = W_{out}^{main}. }

The source's implementation actually ties the embedding and LM head as well:

self.shared_lm_head.weight = self.shared_embed.weight

(Source: Build a DeepSeek Model (From Scratch))

So there is extensive parameter sharing.

5.48.1A.18 Equation 23 — producing the probability distribution

The source's equation is shown as:

\boxed{ P_{i+k+1}^{k} = \operatorname{OutHead}(h_i^k) }

in the figure. (Source: Build a DeepSeek Model (From Scratch))

The exact indexing is worth paying attention to.

The source's surrounding prose sometimes calls a head the predictor for the k-th future token, while the displayed Equation 23 indexes the probability at i+k+1. So when working through the source, keep the equation's index alignment separate from the informal “Head 1 = token 1” naming. The important architectural fact is unchanged: h_i^k is projected through the shared output head to produce the probability distribution associated with that MTP depth. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.19 Add softmax

Logits are not probabilities.

We still need:

\boxed{ p_i^k = \operatorname{softmax}(z_i^k) }

where:

p_i^k\in\mathbb R^V.

For token j:

p_{i,j}^k = \frac{e^{z_{i,j}^k}} {\sum_{m=1}^{V}e^{z_{i,m}^k}}.

The correct future token then contributes a cross-entropy term:

\boxed{ L_i^k = -\log p_i^k(y_i^k). }

5.48.1A.20 One complete MTP module

We can now write the entire operation:

\boxed{ h_i^{\prime k} = M_k \left[ \operatorname{RMSNorm}(h_i^{k-1}); \operatorname{RMSNorm}(e_{i+k}) \right] }

then:

\boxed{ h_i^k = \operatorname{TRM}_k(h_i^{\prime k}) }

then:

\boxed{ z_i^k = h_i^kW_{out} }

then:

\boxed{ p_i^k = \operatorname{softmax}(z_i^k). }

And simultaneously:

\boxed{ h_i^k \rightarrow \text{next MTP module}. }

That is the entire causal MTP mechanism in four equations.

5.48.1A.21 Tensor-shape flow

Let:

B=\text{batch size}
L_k=\text{valid sequence length at depth }k
d=\text{model dimension}
V=\text{vocabulary size}.

Then:

Previous hidden state
\boxed{ [B,L_k,d] }
Future-token embeddings
\boxed{ [B,L_k,d] }
Separate RMSNorm

still:

[B,L_k,d].
Concatenation
\boxed{ [B,L_k,2d] }
Projection
\boxed{ [B,L_k,d] }
MTP Transformer
\boxed{ [B,L_k,d] }
Shared unembedding
\boxed{ [B,L_k,V]. }

This shape progression is one of the most useful things to memorize for exam numericals:

\boxed{ d+d \rightarrow 2d \rightarrow d \rightarrow V. }

5.48.1A.22 Why does the sequence length shrink?

This is another excellent exam point.

Suppose:

S=20.

At MTP depth 1, we don't have all 20 positions available because we need future-token information.

So the source implementation uses:

L = S - depth_k

For:

k=1:
L=19.

For:

k=2:
L=18.

For:

k=3:
L=17.

The source's verification output confirms:

Main : [2, 20, 1000]
MTP k=1 : [2, 19, 1000]
MTP k=2 : [2, 18, 1000]
MTP k=3 : [2, 17, 1000]

(Source: Build a DeepSeek Model (From Scratch))

5.48.1A.23 Let's derive those shapes

Source configuration:

B=2
S=20
V=1000
D=3.

Main model:

\boxed{ [2,20,1000]. }

MTP 1:

L=20-1=19

so:

\boxed{ [2,19,1000]. }

MTP 2:

L=20-2=18

so:

\boxed{ [2,18,1000]. }

MTP 3:

L=20-3=17

so:

\boxed{ [2,17,1000]. }

This is not accidental. Every deeper prediction has fewer valid positions because progressively more future context is required. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.24 The source's actual implementation logic

The source uses:

h_prev = h_main

for depth_k in range(1, self.num_mtp_heads + 1):

    L = S - depth_k

    h_prev_sliced = h_prev[:, :L, :]

    future_token_ids = input_ids[:, depth_k:depth_k + L]

    future_token_embeds = self.get_embedding(
        future_token_ids
    )

    h_curr = self.mtp_modules[depth_k - 1](
        h_prev_sliced,
        future_token_embeds
    )

    logits_k = self.get_output_logits(h_curr)

    all_logits.append(logits_k)

    h_prev = h_curr

(Source: Build a DeepSeek Model (From Scratch))

Now let's understand this line by line.

5.48.1A.25 Line 1 — start with main hidden state

h_prev = h_main

So:

\boxed{ h_{\text{prev}}=h^0. }

The initial state comes from the normal Transformer backbone.

5.48.1A.26 Line 2 — select prediction depth

for depth_k in range(1, D+1):

Suppose:

D=3.

The loop executes:

k=1,2,3.

Thus:

\boxed{ \text{three sequential MTP modules}. }

5.48.1A.27 Line 3 — shrink the valid sequence

L = S - depth_k

For:

S=20,D=3:
L_1=19,\quad L_2=18,\quad L_3=17.

5.48.1A.28 Line 4 — slice the previous hidden state

h_prev_sliced = h_prev[:, :L, :]

Why?

Because only the first L positions have enough future-token context for that depth.

So:

[B,S,d]

becomes:

[B,L,d].

5.48.1A.29 Line 5 — obtain future-token IDs

future_token_ids = input_ids[:, depth_k:depth_k + L]

This performs the sequence shift.

For:

k=1

it selects positions beginning at index 1.

For:

k=2

it starts at index 2.

For:

k=3

it starts at index 3.

This is how the implementation aligns the hidden-state positions with increasingly future token information. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.30 Line 6 — convert IDs to embeddings

future_token_embeds = self.get_embedding(future_token_ids)

The result is:

\boxed{ [B,L,d]. }

Now the MTP module has exactly the two required inputs:

\boxed{ h_{prev}\in\mathbb R^{B\times L\times d} }

and:

\boxed{ E_{future}\in\mathbb R^{B\times L\times d}. }

5.48.1A.31 Line 7 — run the MTP module

h_curr = self.mtp_modules[depth_k - 1](
    h_prev_sliced,
    future_token_embeds
)

Inside:

h_normed = self.norm_hidden(h_prev)
embed_normed = self.norm_embed(future_token_embeds)

concatenated = torch.cat(
    [h_normed, embed_normed],
    dim=-1
)

h_prime = self.projection_matrix(concatenated)

h_output = self.transformer_block(h_prime)

return h_output

(Source: Build a DeepSeek Model (From Scratch))

Now you can map the code directly onto the mathematics:

\boxed{ \text{RMSNorm} \rightarrow \text{RMSNorm} \rightarrow \text{Concat} \rightarrow M_k \rightarrow TRM_k }.

5.48.1A.32 Line 8 — obtain MTP logits

logits_k = self.get_output_logits(h_curr)

Thus:

\boxed{ [B,L,d] \rightarrow [B,L,V]. }

And because the same output head is shared:

W_{out}

is reused across the main model and MTP modules. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.33 Line 9 — pass refined state to the next head

h_prev = h_curr

This one line creates the entire causal chain.

After Head 1:

h_{prev}=h^1.

After Head 2:

h_{prev}=h^2.

After Head 3:

h_{prev}=h^3.

Therefore:

\boxed{ h^0\rightarrow h^1\rightarrow h^2\rightarrow h^3. }

That is the defining feature of DeepSeek's causal MTP design. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.34 The loss

For one input position, suppose we have:

L_1,L_2,L_3.

The source says the total MTP loss is the sum of the individual cross-entropy losses. (Source: Build a DeepSeek Model (From Scratch))

For the complete implementation, the source uses:

\boxed{ L = L_{\text{main}} + \frac{\lambda}{D} \sum_{k=1}^{D} L_{\text{MTP}}^{(k)}. }

(Source: Build a DeepSeek Model (From Scratch))

Here:

  • L_{\text{main}} = ordinary next-token loss,
  • L_{\text{MTP}}^{(k)} = MTP loss at depth k,
  • D = number of MTP modules,
  • \lambda = overall MTP loss weight.

5.48.1A.35 Numerical loss example

Suppose:

L_{\text{main}}=0.40

and:

L_1=0.50,\quad L_2=0.70,\quad L_3=0.90.

Let:

D=3

and:

\lambda=0.1.

Then:

\sum L_k = 0.50+0.70+0.90 = 2.10.

Average:

\frac{2.10}{3} = 0.70.

MTP contribution:

0.1\times0.70 = 0.07.

Total:

\boxed{ L=0.40+0.07=0.47. }

So the main loss remains the foundation, while MTP contributes an additional training signal.

5.48.1A.36 Why divide by D?

Because otherwise increasing the number of MTP heads would automatically increase the magnitude of the auxiliary MTP contribution.

With:

\frac{\lambda}{D} \sum_{k=1}^{D}L_k,

you are effectively taking the mean MTP loss and then scaling it by \lambda.

Thus:

\boxed{ \text{MTP contribution} = \lambda\times \text{average MTP loss}. }

That makes \lambda easier to interpret when changing D.

5.48.1A.38 The most important conceptual distinction

There are three different representations involved:

1. Token ID
t_i

Example:

1742.

This is an integer.

2. Token embedding
e_i=\operatorname{Emb}(t_i)

This is:

d\text{-dimensional}.
3. Hidden state
h_i^k

This is also:

d\text{-dimensional},

but it is a contextual representation transformed by the network.

So:

\boxed{ \text{Token ID} \rightarrow \text{Embedding} \rightarrow \text{Hidden Representation} }

and MTP injects future-token embedding information into a refined hidden representation.

5.48.1A.39 Why pass h^k, not the predicted token ID, to the next head?

This is perhaps the most beautiful part.

Suppose Head 1 predicts:

\text{“the”}.

One possibility would be to take:

"the" → token ID → embedding → Head 2

But the source instead passes:

\boxed{h^1}

to Head 2.

Why?

Because h^1 contains a rich contextualized representation, whereas a single token ID contains only the identity of one token.

The source explicitly highlights this as a key advantage of causal MTP. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ h^1 \gg \text{one discrete token ID} }

in terms of information carried about the evolving state.

5.48.1A.40 MTP vs independent prediction heads

Now compare the two designs.

Independent heads
             h
          /  |  \
         /   |   \
       H1   H2   H3
       ↓    ↓    ↓
      t1   t2   t3

The heads don't refine one another.

DeepSeek causal MTP
h⁰
 │
 ▼
MTP1 ───► prediction 1
 │
 ▼
h¹
 │
 ▼
MTP2 ───► prediction 2
 │
 ▼
h²
 │
 ▼
MTP3 ───► prediction 3
 │
 ▼
prediction 3

Thus:

\boxed{ \text{prediction depth} \rightarrow \text{hidden-state refinement} \rightarrow \text{next prediction}. }

That is why the source describes the mechanism as cascaded latent refinement. (Source: Build a DeepSeek Model (From Scratch))

5.48.1A.41 Full mathematical chain

For one position i:

Initial state
\boxed{ h_i^0 = \text{main Transformer hidden state} }
MTP stage k
\boxed{ u_i^k = \left[ RMSNorm(h_i^{k-1}); RMSNorm(E(t_{i+k})) \right] }
Projection
\boxed{ h_i^{\prime k}=M_k u_i^k }
Dedicated Transformer
\boxed{ h_i^k=TRM_k(h_i^{\prime k}) }
Shared output projection
\boxed{ z_i^k=h_i^kW_{out} }
Probability
\boxed{ p_i^k=\operatorname{softmax}(z_i^k) }
Loss
\boxed{ L_i^k = -\log p_i^k(y_i^k) }
Total training objective
\boxed{ L = L_{\text{main}} + \frac{\lambda}{D} \sum_{k=1}^{D}L_{\text{MTP}}^{(k)} }

This is the mathematical skeleton you should retain.

5.48.1A.42 Parameter-count numerical

Suppose:

d=4096.

The projection matrix is:

M_k\in\mathbb R^{4096\times8192}.

Therefore its parameter count is:

4096\times8192
= \boxed{33,554,432}

parameters.

So one MTP projection alone has about:

\boxed{33.55M}

parameters, ignoring bias because the source implementation uses:

bias=False

(Source: Build a DeepSeek Model (From Scratch))

This is a good example of why MTP is not “just another output head.” Each MTP module contains an actual Transformer block plus projection layers.

5.48.1A.43 Parameter sharing vs unique parameters

Within the source implementation:

Shared
\boxed{ \text{token embedding} }
\boxed{ \text{output/unembedding} }
Per-MTP-module
\boxed{ M_k }

and:

\boxed{ TRM_k }

because each MTP module is independently instantiated in the ModuleList. (Source: Build a DeepSeek Model (From Scratch))

Therefore:

\boxed{ \text{MTP heads share output vocabulary projection} }

but:

\boxed{ \text{each MTP depth has its own processing module}. }

5.48.1A.45 The single most important insight

MTP is not simply:

\boxed{ \text{“attach 3 classifiers to the Transformer.”} }

Instead:

\boxed{ \text{Main Transformer} \rightarrow h^0 }

then:

\boxed{ h^0+\text{future embedding} \rightarrow \text{MTP Transformer} \rightarrow h^1 }

then:

\boxed{ h^1+\text{next future embedding} \rightarrow \text{MTP Transformer} \rightarrow h^2 }

and so forth.

So the core innovation is:

\boxed{ \textbf{future-conditioned hidden-state refinement} }

rather than merely:

\boxed{ \textbf{multiple independent prediction heads}. }
