Step 5.44 — Dense FFN vs MoE: Complete Parameter, Compute, and Scaling Derivation

Plan node: A2 · chat order #85

↩ Back to main text: Step 1.10 — Position-Wise Feed-Forward Network (FFN / MLP)

We now take everything from Steps 5.38–5.43 and answer the quantitative question:

\boxed{\text{Exactly what do we gain by replacing a dense FFN with MoE?}}

The source motivates MoE by noting that the FFN is a major parameter and computational component of a Transformer, and that sparsely activating experts lets the model grow in capacity without a proportional increase in per-token computation. (Source: Build a DeepSeek Model (From Scratch))

The parameter and arithmetic-count formulas below are derived from the matrix shapes; the source itself explains the computational motivation but does not give one universal FLOP-accounting convention. I will therefore distinguish source-derived facts from these mathematical derivations.

5.44.1 Start from the dense FFN

The source's expert is a two-layer expansion-contraction MLP with GELU:

x \rightarrow W_1 \rightarrow GELU \rightarrow W_2 \rightarrow y.

Let:

x\in\mathbb R^D

and:

W_1\in\mathbb R^{D\times H}, \qquad W_2\in\mathbb R^{H\times D}.

Then:

h=xW_1
z=GELU(h)
y=zW_2.

The source explicitly describes this expansion-contraction structure. (Source: Build a DeepSeek Model (From Scratch))

5.44.2 Dense FFN parameter count

Ignoring biases:

|W_1|=DH

and:

|W_2|=HD.

Therefore:

\boxed{ P_{\text{FFN}}=2DH }

This is one of the most useful formulas in this entire topic.

5.44.3 Example

Take:

D=4096

and:

H=16384.

Then:

P_{\text{FFN}} = 2(4096)(16384)
= \boxed{134,217,728}

parameters.

So one dense FFN already contains:

\boxed{134.2M}

weights, ignoring biases.

5.44.4 Why the source often talks about “4× expansion”

The source's standard-FFN discussion uses the familiar example:

768\rightarrow3072\rightarrow768.

That is:

H=4D.

(Source: Build a Large Language Model (From Scratch))

If:

H=4D,

then:

P_{\text{FFN}} = 2D(4D) = \boxed{8D^2}.

So a 4× expansion gives roughly:

\boxed{8D^2}

weights.

5.44.5 Dense FFN compute for one token

For:

xW_1,

we compute D\times H multiply-accumulates.

So:

\boxed{DH\text{ MACs}}

for the first projection.

The second projection costs another:

\boxed{HD\text{ MACs}}.

Therefore:

\boxed{ C_{\text{FFN}}\approx2DH }

MACs per token, ignoring the small activation cost.

If you count one multiply and one add as approximately two floating-point operations, then:

\boxed{ F_{\text{FFN}}\approx4DH }

FLOPs per token.

This is a derived arithmetic estimate, not a source-stated FLOP formula.

5.44.6 Dense FFN numerical

Using:

D=4096,\qquad H=16384,

we have:

2DH = 134,217,728

MACs.

So approximately:

\boxed{134.2M\text{ MACs/token}}

or:

\boxed{268.4M\text{ FLOPs/token}}

under the 2-FLOPs-per-MAC convention.

5.44.7 Now replace one FFN with MoE

Instead of one FFN:

FFN

we create:

N

experts.

Each expert has hidden size:

H_e.

Each expert therefore has:

2DH_e

parameters.

Total expert parameters:

\boxed{ P_{\text{MoE-experts}} = 2NDH_e }

ignoring biases.

The source describes exactly this conceptual replacement of one dense FFN with multiple smaller expert FFNs. (Source: Build a DeepSeek Model (From Scratch))

5.44.8 Dense vs MoE parameter count

Dense:

\boxed{ 2DH }

MoE:

\boxed{ 2NDH_e }

Now ask:

What happens when total capacity is supposed to remain comparable?

Set:

NH_e=H.

Then:

P_{\text{MoE-experts}} = 2ND\left(\frac HN\right)
= \boxed{2DH}.

So:

\boxed{ \text{same total expert parameters} }

This is exactly the mathematical principle behind the source's:

16\times4096

versus:

64\times1024

example. (Source: Build a DeepSeek Model (From Scratch))

5.44.9 Verify the source's example

Conventional:

16\times4096 = 65,536.

Fine-grained:

64\times1024 = 65,536.

Therefore:

\boxed{ 16\times4096=64\times1024 }.

The source says the total capacity can therefore remain the same while the knowledge is divided into many smaller experts. (Source: Build a DeepSeek Model (From Scratch))

5.44.10 Now the important part — activation

Suppose only:

k

experts are selected for each token.

One expert costs approximately:

2DH_e

MACs.

So selected expert computation is:

\boxed{ C_{\text{active-MoE}} \approx 2kDH_e }

MACs per token.

Compare with executing all N experts:

2NDH_e.

The fraction is:

\boxed{ \frac{2kDH_e}{2NDH_e} = \frac{k}{N} }.

So under equal-size experts:

\boxed{ \text{active routed-expert compute fraction} = \frac{k}{N} }

This is a mathematical consequence of sparse Top-K routing.

5.44.11 Numerical example

Suppose:

N=64

and:

k=8.

Then:

\frac8{64} = \boxed{12.5\%}.

So compared with executing all 64 expert networks, only 12.5% of the expert computations are selected for a token.

This is the core computational benefit of sparse MoE.

5.44.12 But compare it against a dense FFN carefully

Here is where people make mistakes.

Suppose the dense FFN has hidden size:

H=4096.

Suppose fine-grained MoE uses:

N=64,\quad H_e=1024.

Then:

NH_e = 64(1024) = 65,536.

This is 16× the dense hidden size:

65,536/4096=16.

So if you compare only:

k=8

active experts, active hidden capacity is:

8\times1024 = 8192.

That means the active expert capacity is:

8192/4096 = \boxed{2\times}

the dense FFN's hidden capacity.

Therefore this particular setup would have roughly 2× the dense FFN arithmetic, not half.

This is why you cannot simply say:

“Only 8 of 64 experts are active, so MoE is automatically 8× cheaper than the dense model.”

The correct comparison depends on:

\boxed{kH_e}

versus:

\boxed{H}.

5.44.13 The fundamental compute-preservation condition

To make the active MoE computation comparable to one dense FFN:

kH_e\approx H.

Because:

C_{\text{dense}}\approx2DH

and:

C_{\text{MoE}}\approx2DkH_e.

Therefore:

\boxed{ kH_e=H }

is the important condition.

This is a very powerful exam formula.

5.44.14 Example

Dense:

H=4096.

MoE:

k=4.

To keep comparable active computation:

4H_e=4096.

Therefore:

\boxed{H_e=1024}.

So:

4

active experts ×

1024

hidden width gives:

4096.

Hence the active FFN arithmetic is approximately comparable.

5.44.15 Now combine parameter and compute conditions

Suppose we want:

Same total expert capacity
NH_e=H_{\text{total-capacity-equivalent}}

and:

Same active computation
kH_e=H_{\text{dense}}.

Divide the equations:

\frac{N}{k} = \frac{H_{\text{total-capacity-equivalent}}} {H_{\text{dense}}}.

If total expert capacity is 16\times the dense FFN's hidden width:

H_{\text{total-capacity-equivalent}} = 16H_{\text{dense}},

then:

\boxed{ \frac Nk=16 }.

For example:

N=64,\quad k=4.

This would provide roughly:

16\times

the routed expert capacity while keeping active capacity equivalent to one dense FFN.

That is the central mathematical idea behind large-capacity sparse models.

5.44.16 Parameter capacity vs active compute

Let's make it explicit.

Suppose:

H=4096

dense.

Fine-grained MoE:

N=64,\quad H_e=1024,\quad k=4.

Total expert hidden capacity:

64\times1024 = 65,536.

Dense hidden capacity:

4096.

So total capacity ratio:

\frac{65,536}{4096} = \boxed{16\times}.

Active capacity:

4\times1024 = 4096.

Active ratio:

\frac{4096}{4096} = \boxed{1\times}.

Therefore:

\boxed{ 16\times\text{ total expert capacity} \quad\text{at roughly}\quad 1\times\text{ dense active capacity} }

in this idealized calculation.

That is an excellent way to understand sparse scaling.

5.44.17 Why this is different from simply making a 16× larger dense FFN

A 16× larger dense FFN would activate all that capacity for every token.

That would make:

\text{compute}\approx16\times.

The MoE version stores the larger capacity but activates only:

k

experts.

So conditional computation lets us approach:

\boxed{ \text{large capacity without proportional per-token compute} }.

This is exactly the scaling motivation emphasized by the source. (Source: Build a DeepSeek Model (From Scratch))

5.44.18 Now add the router cost

The router scores all experts.

Let:

X_f\in\mathbb R^{T\times D}

and:

W_R\in\mathbb R^{D\times N}

in mathematical notation.

Then:

L=X_fW_R

has:

T\times N

outputs.

The router therefore performs approximately:

\boxed{ TDN }

MACs.

Again, this is our matrix-multiplication derivation.

5.44.19 Complete idealized MoE compute

Ignoring communication and nonlinear activation costs:

\boxed{ C_{\text{MoE}} \approx TDN + 2TkDH_e }

MACs for a batch/sequence of T tokens.

Per token:

\boxed{ C_{\text{MoE/token}} \approx DN+2kDH_e }.

This is a useful derived formula.

5.44.20 Compare against dense

Dense:

\boxed{ C_{\text{dense/token}} \approx 2DH }

MoE:

\boxed{ C_{\text{MoE/token}} \approx DN+2kDH_e }.

Therefore MoE is not guaranteed to be cheaper.

You must compare:

\boxed{ DN+2kDH_e }

against:

\boxed{ 2DH }.

In practice, real hardware efficiency additionally depends on dispatch, batching, communication, kernel efficiency, memory bandwidth, and other costs.

5.44.21 Router cost often looks tiny relative to the experts

Suppose:

D=4096

and:

N=64.

Router cost:

DN = 4096\times64 = \boxed{262,144}

MACs/token.

Now suppose:

H_e=1024,\quad k=4.

Expert cost:

2(4)(4096)(1024) = \boxed{33,554,432}

MACs/token.

So in this illustrative setup:

\frac{262,144}{33,554,432} \approx \boxed{0.78\%}.

Thus the router arithmetic itself can be much smaller than the expert computation.

However, distributed communication is a different matter and can become a major bottleneck. The source later discusses All-to-All communication and DualPipe for precisely this reason. (Source: Build a DeepSeek Model (From Scratch))

5.44.22 Why All-to-All can dominate even when router FLOPs are small

Imagine 8 GPUs.

Experts are distributed:

GPU 0 → E1 ... E8
GPU 1 → E9 ... E16
GPU 2 → E17 ... E24
...
GPU 7 → E57 ... E64

A token currently on GPU 0 might select:

E_{60}.

Its representation must travel to GPU 7.

So:

\boxed{ \text{small router arithmetic} }

can still result in:

\boxed{ \text{large communication overhead} }.

Therefore:

\boxed{ \text{FLOPs alone do not determine MoE performance}. }

This is why the source's later systems discussion focuses on overlapping MoE communication with computation. (Source: Build a DeepSeek Model (From Scratch))

5.44.23 Now add shared experts

DeepSeek-style architecture has:

N_s

shared experts.

Each shared expert has hidden dimension:

H_s.

Every token passes through every shared expert.

Therefore shared computation is approximately:

\boxed{ 2N_sDH_s }

MACs/token.

The routed computation is:

\boxed{ 2kDH_r }

MACs/token.

So:

\boxed{ C_{\text{total}} \approx DN_r + 2N_sDH_s + 2kDH_r }

per token, ignoring communication and other overhead.

This is a derived expression combining the source's shared/routed architecture with matrix multiplication costs.

5.44.24 Parameter count with shared experts

Routed experts:

2N_rDH_r.

Shared experts:

2N_sDH_s.

Router:

DN_r

parameters, ignoring a possible router bias.

Thus:

\boxed{ P_{\text{MoE}} \approx 2N_rDH_r + 2N_sDH_s + DN_r }

under the source's simplified architecture.

5.44.25 Example with shared experts

Suppose:

D=4096
N_r=64
H_r=1024
N_s=2
H_s=1024.
Routed parameters
2(64)(4096)(1024) = \boxed{536,870,912}.
Shared parameters
2(2)(4096)(1024) = \boxed{16,777,216}.
Router parameters
4096\times64 = \boxed{262,144}.

Total:

536,870,912 + 16,777,216 + 262,144
= \boxed{553,910,272}

approximately.

5.44.26 Active parameters for one token

Suppose:

k=4.

Active routed parameters:

2(4)(4096)(1024) = \boxed{33,554,432}.

Shared experts are dense, so:

16,777,216

shared parameters participate.

Thus approximate expert parameters involved for the token:

33,554,432 + 16,777,216
= \boxed{50,331,648}.

This does not include attention parameters, embeddings, output head, normalization, etc.

So we must call this:

\boxed{\text{active expert parameters}}

rather than “active model parameters.”

5.44.27 This distinction is exam-critical

Suppose the total model has:

100B

parameters.

Suppose:

20B

are active per token.

Do not say:

“The model is a 20B model.”

It is a:

\boxed{100B\text{ total-parameter model}}

with:

\boxed{20B\text{ active parameters/token}}

under the specified routing behavior.

This distinction is central to understanding the source's DeepSeek-R1 example. (Source: Build a DeepSeek Model (From Scratch))

5.44.28 Parameter-count numerical: dense vs MoE

Suppose:

D=4096

and dense FFN:

H=4096.

Dense parameters:

2(4096)(4096) = \boxed{33,554,432}.

Now create:

N=64

experts:

H_e=1024.

Total MoE expert parameters:

2(64)(4096)(1024) = \boxed{536,870,912}.

Ratio:

536,870,912/33,554,432 = \boxed{16}.

So the MoE has:

\boxed{16\times}

the total expert parameter capacity.

If:

k=4,

active routed parameters:

2(4)(4096)(1024) = 33,554,432.

Therefore:

\boxed{ \text{16× capacity} \quad\text{with}\quad 1×\text{ active routed parameters} }

in this designed example.

This is perhaps the single best numerical example for understanding MoE scaling.

5.44.29 Why fine-grained segmentation makes sense here

Now suppose we instead had:

N=16

with:

H_e=4096.

Total expert capacity:

16\times4096 = 65,536.

Fine-grained:

N=64, \quad H_e=1024.

Total:

64\times1024 = 65,536.

Same aggregate hidden capacity.

But now the router can choose among:

64

specialized units rather than:

16.

This is the exact conceptual argument given by the source. (Source: Build a DeepSeek Model (From Scratch))

5.44.30 A very important condition

Suppose the number of experts increases by a factor:

r.

To preserve total capacity:

H_e'=\frac{H_e}{r}.

To preserve active computation:

k'H_e'=kH_e.

Substitute:

k'\frac{H_e}{r}=kH_e.

Cancel H_e:

\frac{k'}r=k.

Therefore:

\boxed{ k'=rk }

if you insist on preserving the same active hidden capacity while increasing the expert count by factor r.

For example:

16\rightarrow64

means:

r=4.

If:

k=2,

then:

k'=8.

That gives:

2(4096) = 8(1024) = 8192.

Again, this is a mathematical design relationship, not a claim that every DeepSeek configuration uses these exact numbers.

5.44.31 Why this matters for DeepSeek's fine-grained idea

You can now see the architecture mathematically:

\boxed{ \text{More experts} \rightarrow \text{smaller expert size} }

can preserve:

\text{total capacity}.

Then adjusting k appropriately can preserve:

\text{active computation}.

Therefore the architecture can gain:

\boxed{ \text{finer specialization} }

without simply scaling compute proportionally.

This is exactly the motivation the source gives for fine-grained expert segmentation. (Source: Build a DeepSeek Model (From Scratch))

5.44.32 Dense vs conventional MoE vs DeepSeek-MoE

Architecture Total expert capacity Per-token routed compute Common knowledge
Dense FFN 1× 1× Inside same FFN
Conventional MoE N expert units k experts Learned within routed experts
Fine-grained MoE Many smaller experts k' smaller experts Routed
DeepSeek-style Many fine-grained routed + shared sparse routed + dense shared Explicit shared path

The source specifically motivates the DeepSeek version as fine-grained routed specialists plus dense shared generalists. (Source: Build a DeepSeek Model (From Scratch))

5.44.33 Exam numerical — determine whether compute is actually saved

A dense FFN uses:

D=4096,\qquad H=4096.

MoE:

N=32,\qquad H_e=1024,\qquad k=4.
Dense
2DH = 2(4096)(4096) = \boxed{33.55M}

MACs.

MoE routed
2kDH_e = 2(4)(4096)(1024) = \boxed{33.55M}

MACs.

Therefore:

\boxed{ \text{same idealized active expert compute} }.

But MoE stores:

2(32)(4096)(1024) = \boxed{268.44M}

expert parameters.

Dense stores:

\boxed{33.55M}.

Capacity ratio:

268.44/33.55 = \boxed{8\times}.

Thus:

\boxed{ 8\times\text{ total expert capacity} \quad\text{at roughly}\quad 1\times\text{ active expert compute} }.

This is an excellent exam problem.

5.44.34 Add router cost to that example

Router:

DN = 4096\times32 = \boxed{131,072}

MACs/token.

So total MoE arithmetic is approximately:

33,554,432+131,072
= \boxed{33,685,504}

MACs/token.

That is only slightly above the dense FFN's:

33,554,432.

Again, real performance can differ because of communication and kernel efficiency.

5.44.35 Why hardware can still prefer the MoE

The mathematical operation count may be comparable, but the model has:

\boxed{8\times}

the expert parameter capacity in this example.

So the model can potentially learn richer, more differentiated transformations without requiring every token to pass through all of that capacity.

That is conditional computation.

5.44.36 But why isn't the MoE infinitely scalable?

Because increasing N causes:

\boxed{\text{router cost}\uparrow}
\boxed{\text{number of parameters}\uparrow}

and, in distributed systems:

\boxed{\text{dispatch/communication complexity}\uparrow}.

And you still need enough tokens to keep the larger expert pool usefully trained.

Hence there is no free lunch.

5.44.37 This brings us back to load balancing

Suppose:

N=32

and:

k=4.

For:

T=1024

tokens:

Tk = 4096

total assignments.

Ideal average:

4096/32 = \boxed{128}.

If actual routing becomes:

[300,250,200,180,\ldots]

with several experts overloaded and others nearly unused, then your theoretical compute savings are not necessarily your actual hardware savings.

The source's load-balancing discussion emphasizes exactly this problem and gives the dynamic bias mechanism as its solution.

5.44.38 Final quantitative model

For a simplified DeepSeek-style MoE:

Parameters
\boxed{ P \approx 2N_rDH_r + 2N_sDH_s + DN_r }
Per-token arithmetic
\boxed{ C \approx DN_r + 2kDH_r + 2N_sDH_s }
Ideal routed active fraction
\boxed{ \frac{k}{N_r} }
Ideal compute-preservation condition
\boxed{ kH_r\approx H_{\text{dense}} }
Fine-grained total-capacity preservation
\boxed{ N_rH_r\approx\text{constant} }
Fine-grained active-capacity preservation
\boxed{ kH_r\approx\text{constant} }

These last two equations explain the mathematics behind dividing large experts into many smaller ones.

5.44.39 Now return to the source's DeepSeek-R1 numbers

The source states:

\boxed{671B\text{ total}}

and:

\boxed{37B\text{ active/token}}.

(Source: Build a DeepSeek Model (From Scratch))

The active fraction is:

\frac{37}{671} \approx \boxed{5.51\%}.

The ratio is:

\frac{671}{37} \approx \boxed{18.1\times}.

And the source explicitly warns that all 671B model weights still need to remain available, even though only a subset is active for an individual token. (Source: Build a DeepSeek Model (From Scratch))

5.44.40 Why this is the perfect example of conditional computation

Think of the model as a huge library:

\boxed{671B\text{ parameters}}

but for one token the router says:

“Use this subset.”

So:

\boxed{37B\text{ active}}

for that token.

For the next token:

\boxed{\text{another subset may be selected}}.

Thus over an entire generated sequence, the model can exploit a broad parameter pool even though each individual token uses only part of it.

That is the essence of:

\boxed{ \text{conditional computation} }.

5.44.41 Exam master problem

Given

A dense FFN has:

D=2048,\qquad H=4096.

An MoE has:

N=32,\qquad H_e=1024,\qquad k=4.

Find:

  1. Dense parameter count.
  2. Total MoE expert parameters.
  3. Active MoE expert parameters.
  4. Capacity ratio.
  5. Active-compute ratio.
1. Dense
P_D=2(2048)(4096)
=\boxed{16,777,216}.
2. Total MoE
P_M = 2(32)(2048)(1024)
=\boxed{134,217,728}.

Capacity ratio:

134,217,728/16,777,216 = \boxed{8\times}.
3. Active MoE
P_A = 2(4)(2048)(1024)
=\boxed{16,777,216}.

So:

\boxed{ P_A=P_D }.
4. Capacity ratio
\boxed{8\times}.
5. Active compute ratio

Dense:

2DH

MoE:

2kDH_e.

So:

\frac{2kDH_e}{2DH} = \frac{kH_e}{H}.
= \frac{4(1024)}{4096} = 1.

Therefore:

\boxed{1\times}.
Final interpretation
\boxed{ 8\times\text{ total expert capacity} }

with approximately:

\boxed{ 1\times\text{ active expert compute} }

for this idealized configuration.

That is the mathematical heart of sparse MoE.

5.44.42 The one formula you should never forget

When comparing a dense FFN with an MoE, don't start with:

\boxed{\frac{k}{N}}

alone.

Start with:

\boxed{ \text{Dense active capacity}=H }

and:

\boxed{ \text{MoE active capacity}=kH_e }.

Then:

\boxed{ \text{compute ratio} \approx \frac{kH_e}{H} }

for the expert MLP portion.

This prevents most MoE numerical mistakes.

5.44.43 And the second formula

For total expert capacity:

\boxed{ \text{MoE total capacity}=NH_e }

relative to dense:

\boxed{ \frac{NH_e}{H} }.

Therefore the two key ratios are:

\boxed{ \text{Capacity ratio}=\frac{NH_e}{H} }

and:

\boxed{ \text{Active compute ratio}=\frac{kH_e}{H}. }

Their ratio is:

\boxed{ \frac{\text{Capacity ratio}} {\text{Active compute ratio}} = \frac Nk }

which measures how much larger the total expert pool is relative to the active expert subset.

5.44.44 Final mental model

For dense FFN:

\boxed{ \text{one big network} \rightarrow \text{all capacity used} }.

For MoE:

\boxed{ \text{many networks} \rightarrow \text{few selected} }.

For DeepSeek-MoE:

\boxed{ \text{many small specialists} + \text{few shared generalists} + \text{balanced sparse routing} }.

Quantitatively:

\boxed{ \text{Total capacity}\propto NH_e }

while:

\boxed{ \text{Active routed compute}\propto kH_e. }

That is the central mathematical reason MoE can scale model capacity much faster than per-token expert computation.

The source's fine-grained example,

16\times4096 \leftrightarrow 64\times1024,

and its DeepSeek-R1 example,

671B\text{ total} \leftrightarrow 37B\text{ active/token},

are concrete illustrations of this broader principle. (Source: Build a DeepSeek Model (From Scratch))
