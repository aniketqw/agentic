Motivation

Hide MoE communication using dependency-aware work scheduling and distinguish DualPipe from folded DualPipeV.

Prerequisites

  • Mini-batch SGD and weighted means
  • GPU state versus activation memory
  • MoE top-k routing
  • Critical paths and collective communication

Notation and units

  • B_micro: sequences/replica; R: DP replicas; A: accumulation count
  • P: pipeline stages; M: microbatches; F/B: forward/backward chunk duration
  • T: tokens; k: top-k; d: representation width; s: bytes/element
  • N_experts: expert count; rho: remote assignment fraction

Assumptions

  • All toy numerical inputs and normalization conventions are stated explicitly.
  • The teaching companion requires NumPy and runs on CPU; it claims no production backend execution.
  • Schedule formulas assume equal-duration stages and declared independent communication; traffic counts exclude unstated overhead.

Step-by-step derivation

  1. Split compute into attention, expert GEMMs, input backward and weight backward; schedule independent work while dispatch/combine or stage communication is active.
  2. Independent compute/network timing has ideal lower bound max(C,N), compared with serial C+N. Resource contention, shared SMs and dependency barriers can prevent this bound.
  3. DualPipe uses bidirectional streams. DualPipeV folds early/late stages onto one physical rank: with 8 stages, rank 0 owns 0/7, rank 1 owns 1/6, rank 2 owns 2/5, and rank 3 owns 3/4.
  4. The official bubble expression (PP/2-1)*(F&B+B-3W) requires its named chunk times and an implemented overlap schedule; generic compute/network times of 8 ms/6 ms are insufficient.

Continuation · checked fixture A09 — Pipeline bubbles: a model, not a measured DualPipe result

Checked continuation mechanism and declared fixture; this is not certification of every inherited claim.

Explain why filling and draining a pipeline consumes slots without useful steady-state work.

Prerequisites: Gradient accumulation with unequal valid-token counts

Notation and assumptions

Simplified balanced schedule with p stages and m microbatches; bubble fraction(p-1)/(m+p-1). This assumes equal stage time and no communication stalls.

Derivation and mechanism

  1. Count useful microbatch slots m.
  2. Add fill/drain overhead p-1 under this schedule model.
  3. Divide overhead by total slots; then assess where real scheduling violates assumptions.
f_{bubble}=(p-1)/(m+p-1)

Worked example

p4,m8 gives3/11≈27.27%;m32 gives3/35≈8.57%. More microbatches reduce this idealized fraction, while memory and scheduling costs may rise.

Limitations

  • DualPipe uses a more complex bidirectional overlap schedule.
  • Unequal stages, backward work, communication and expert dispatch require a measured timing trace.

Connections to later concepts

  • A02 expert routing adds dispatch/communication that invalidates a simple balanced-stage timing model.

R101.4 — DualPipe: How DeepSeek Tackles the MoE Communication Bottleneck

Plan node: A5 · chat order #116

We have reached the most important part of the scaling story.

So far:

\text{Gradient Accumulation} \rightarrow \text{batch-memory problem}
\text{DDP} \rightarrow \text{training-throughput problem}
\text{Pipeline Parallelism} \rightarrow \text{model-too-large problem}
\text{1F1B} \rightarrow \text{pipeline-bubble problem}

But DeepSeek is an MoE model.

And MoE introduces a new problem:

\boxed{\text{expensive All-to-All communication}}

The source's central claim is that this communication can become more expensive than the original pipeline bubble. (Source: Build a DeepSeek Model (From Scratch))

1. Why 1F1B is no longer enough

Recall what 1F1B does:

Forward → Backward → Forward → Backward

This keeps the pipeline busy.

But now imagine an MoE layer.

A token arrives at GPU 0, but its selected expert may live on GPU 3:

GPU 0
 token
   │
   │ routed to Expert 7
   ▼
GPU 3
 Expert 7

The token must physically move.

So the system has to perform communication such as:

\boxed{\text{All-to-All}}

across the GPUs.

The source describes this as dynamically reorganizing and moving tokens to the devices hosting their selected experts. (Source: Build a DeepSeek Model (From Scratch))

2. The new idle-time problem

Suppose the computation has finished but the required tokens have not arrived:

Compute
  ↓
WAIT FOR COMMUNICATION
  ↓
Expert computation

The GPU may have powerful compute hardware sitting idle while networking/communication finishes.

So now we have:

Old problem:
GPU idle because pipeline isn't filled.

New problem:
GPU idle because MoE communication hasn't finished.

Thus:

\boxed{ \text{1F1B solves pipeline bubble} \neq \text{1F1B solves communication latency} }

The source explicitly says vanilla 1F1B cannot hide this MoE communication cost. (Source: Build a DeepSeek Model (From Scratch))

3. DeepSeek's question

The source essentially asks:

Can we schedule computation so that while communication is happening for one piece of work, useful computation happens for another?

That is the key idea.

Instead of:

Communication
    ↓
wait
    ↓
Compute

we want:

Communication ───────────────
         Compute ────────────

at the same time.

This is:

\boxed{ \text{computation–communication overlap} }

and this is the central innovation of DualPipe. (Source: Build a DeepSeek Model (From Scratch))

4. First innovation: Pipeline Folding

The first structural change is called pipeline folding in the source's explanation.

A normal pipeline has stages assigned sequentially:

GPU 0 → Stage 0
GPU 1 → Stage 1
GPU 2 → Stage 2
GPU 3 → Stage 3
GPU 4 → Stage 4
GPU 5 → Stage 5
GPU 6 → Stage 6
GPU 7 → Stage 7

Every GPU has one contiguous portion.

DualPipe rearranges this.

One physical GPU holds:

\boxed{\text{one early stage + one late stage}}

The source gives this example for 8 stages and 4 physical GPUs. (Source: Build a DeepSeek Model (From Scratch))

5. The folded mapping

The source's mapping is:

Rank 0:
Stage 0 + Stage 7

Rank 1:
Stage 1 + Stage 6

Rank 2:
Stage 2 + Stage 5

Rank 3:
Stage 3 + Stage 4

So instead of:

0 → 1 → 2 → 3 → 4 → 5 → 6 → 7

being eight separate physical devices, we have:

GPU 0: [0 ............... 7]
GPU 1: [1 ........... 6]
GPU 2: [2 ....... 5]
GPU 3: [3 ... 4]

This is why the pipeline looks folded.

(Source: Build a DeepSeek Model (From Scratch))

6. Why is this useful?

Because now the physical device near one end of the pipeline also owns a stage from the opposite end.

This creates much more flexibility in scheduling.

The model is no longer simply:

GPU0 → GPU1 → GPU2 → GPU3 → GPU4 → ...

Instead, execution can be arranged around a folded topology.

That is the structural foundation for the later V-shape schedule.

7. Full DualPipe is more than folding

There is an important source distinction here.

The source says the DeepSeek paper's full DualPipe uses a true bidirectional schedule with two data streams.

But the book chooses to focus on a more intuitive variant:

\boxed{\text{DualPipeV}}

also called:

\boxed{\text{V-shape / cut-in-half}}

schedule. (Source: Build a DeepSeek Model (From Scratch))

So don't treat the names as completely interchangeable.

For our learning sequence:

\boxed{ \text{DualPipe idea} \rightarrow \text{DualPipeV practical/intuitive variant} }

8. The second innovation: Fine-Grained Scheduling

This is perhaps the most important conceptual part.

1F1B essentially thinks in fairly large units:

Forward
Backward
Forward
Backward

DualPipe breaks those operations into smaller pieces.

The source explicitly identifies components such as:

  • Attention
  • MLP / Expert computation
  • All-to-All communication

and schedules them more finely. (Source: Build a DeepSeek Model (From Scratch))

So rather than treating:

\text{Forward}

as one indivisible block, the scheduler can reason about its internal components.

9. Why this matters

Suppose micro-batch m_1 is waiting on:

\text{All-to-All}.

Instead of leaving the GPU idle, the scheduler can perform:

\text{Attention computation for }m_2

or another useful computation.

So:

Timeline →

m1:  All-to-All  ───────────
m2:       Attention ────────
m3:                 Expert ──

The communication for one workload is hidden underneath computation from another.

The source describes this as the key mechanism for hiding the large MoE communication cost. (Source: Build a DeepSeek Model (From Scratch))

10. Think of it like CPU + network overlap

A useful conceptual analogy is:

Task A:
Network transfer ───────────────

Task B:
               Computation ─────

If the hardware can make progress on both resources simultaneously, total wall-clock time can be much lower than:

Network
   ↓
finish
   ↓
Computation
   ↓
finish

DualPipe is applying this idea at extremely fine granularity to distributed LLM training.

The source's specific emphasis is:

\boxed{ \text{keep compute resources and communication resources busy simultaneously} }

11. What does "overlap" actually mean?

Suppose:

T_{\text{communication}}=5

and:

T_{\text{computation}}=5.

If done sequentially:

T_{\text{total}}=5+5=10.

If they can be perfectly overlapped:

T_{\text{total}}\approx5.

This is an idealized illustration of the reason overlap is valuable; it is not a performance number stated by the source.

Real systems have dependencies and imperfect overlap.

But the engineering goal is exactly this:

\boxed{ \text{hide communication behind useful computation} }

12. Now understand DualPipeV

The source calls DualPipeV the more intuitive "cut-in-half" or V-shape schedule. (Source: Build a DeepSeek Model (From Scratch))

Use the earlier example:

8\text{ stages}

on:

4\text{ physical GPUs}.

The stage assignment is:

GPU 0 → Stage 0 + Stage 7
GPU 1 → Stage 1 + Stage 6
GPU 2 → Stage 2 + Stage 5
GPU 3 → Stage 3 + Stage 4

Now follow one micro-batch.

13. The Downstroke

The micro-batch first travels:

Stage_0 \rightarrow Stage_1 \rightarrow Stage_2 \rightarrow Stage_3.

So physically:

GPU 0
  ↓
GPU 1
  ↓
GPU 2
  ↓
GPU 3

The source calls this the downstroke. (Source: Build a DeepSeek Model (From Scratch))

14. The Turnaround

Here comes the clever part.

GPU 3 contains:

Stage_3

and

Stage_4.

So after the micro-batch finishes Stage 3:

Stage_3\rightarrow Stage_4

does not require another GPU.

The pipeline effectively turns around on the same physical device.

The source calls this the turnaround. (Source: Build a DeepSeek Model (From Scratch))

15. The Upstroke

After Stage 4, the micro-batch moves:

Stage_4 \rightarrow Stage_5 \rightarrow Stage_6 \rightarrow Stage_7.

Physically:

GPU 3
  ↓
GPU 2
  ↓
GPU 1
  ↓
GPU 0

So the overall forward path is:

GPU0
 ↓
GPU1
 ↓
GPU2
 ↓
GPU3
 ↘
  Stage4
 ↗
GPU2
 ↑
GPU1
 ↑
GPU0

which visually forms:

\boxed{V}

Hence V-shape schedule.

(Source: Build a DeepSeek Model (From Scratch))

16. Why "cut-in-half"?

Normally, 8 pipeline stages might imply:

8\text{ physical devices}

for one stage per device.

DualPipeV can place those 8 stages onto:

\boxed{4\text{ physical devices}}

because each device stores two stages.

That is the source's "cut-in-half" idea. (Source: Build a DeepSeek Model (From Scratch))

17. But there is a price

Nothing is free.

Each GPU now owns:

\boxed{2\text{ stages}}

instead of:

1\text{ stage}.

So each physical GPU must store more model parameters.

The source states the trade-off as approximately:

\boxed{ 2\times\text{ parameter memory per GPU} }

compared with the corresponding standard 1F1B folded-stage arrangement described there. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \text{less hardware / better bubble behavior} \quad\leftrightarrow\quad \text{more parameter memory per GPU} }

18. Why this trade-off can be worthwhile for DeepSeek

This is especially relevant to an MoE architecture.

We already learned that DeepSeek uses other mechanisms such as:

\text{FP8}

and:

\text{Expert Parallelism}

to reduce or manage per-device memory and communication pressure.

The source argues that these techniques make the extra parameter-memory cost of the folded arrangement more favorable. (Source: Build a DeepSeek Model (From Scratch))

19. DualPipeV + interleaving

DualPipeV does not simply fold the network and stop there.

The source says the schedule also interleaves forward and backward passes of different micro-batches.

Therefore we combine two ideas:

\boxed{ \text{folded topology} + \text{interleaved execution} }

This reduces the pipeline bubble similarly to 1F1B while using half as many physical devices for the N-stage example. (Source: Build a DeepSeek Model (From Scratch))

22. One subtle but crucial distinction

Do not say in an interview:

"DualPipe removes the pipeline bubble completely."

That is too strong.

The source says DualPipe/DualPipeV dramatically reduces the bubble and, more importantly for MoE, hides expensive communication through overlap. (Source: Build a DeepSeek Model (From Scratch))

The better mental statement is:

\boxed{ \text{DualPipe minimizes wasted time by overlapping useful computation and communication} }

23. What happened to our MiniDeepSeek?
