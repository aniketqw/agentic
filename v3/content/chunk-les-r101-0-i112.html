Motivation

Turn correct forward/loss mechanics into reproducible parameter learning with controlled schedules, evaluation and recovery state.

Prerequisites

  • Gradient descent and AdamW
  • Batch/target alignment
  • Train/eval and automatic differentiation

Notation and units

  • B*T positions/update
  • K microbatches per optimizer update
  • eta_t: scheduled learning rate
  • g_t: gradient of declared mean loss

Assumptions

  • Source ordinary loop performs one update per batch
  • Companion demonstrates actual head-only SGD, not full-model AdamW
  • Equal-size microbatches in accumulation example

Step-by-step derivation

  1. Read data metadata, validate vocabulary and context against model configuration, instantiate model and optimizer.
  2. At step t set eta_t: linear warmup eta_peak*t/200; then cosine interpolate eta_peak to eta_peak/10 between200 and5000.
  3. Zero stale gradients, compute aligned main/MTP loss, backpropagate, and update parameters with optimizer state.
  4. If accumulating K equal-size microbatches, divide each mean loss by K before backward and step once. Unequal valid-token counts need token-count weighting instead.
  5. For AdamW use moving averages of gradients/squared gradients plus decoupled weight decay; schedule state, moment buffers and bias-correction count belong to recovery.
  6. Evaluation uses eval mode and disabled gradients on held-out data; estimate mean loss with specified token/batch weighting.
  7. A best-validation checkpoint and periodic recovery checkpoint have different selection criteria. Reproducible resume also needs RNG/sampler/scaler/schedule/best-loss state in addition to listed weights and optimizer.
  8. Mixed precision must be chosen for the actual device: source GPU BF16/FP16 autocast is not a complete production FP8 pipeline.

4. get_batch() is the bridge from disk to model

The source's get_batch() opens:

np.memmap(
    os.path.join(data_dir, f'{split}.bin'),
    dtype=np.uint16,
    mode='r'
)

Then it randomly selects starting positions:

ix = torch.randint(
    len(data) - block_size,
    (batch_size,)
)

(Source: Build a DeepSeek Model (From Scratch))

This is important.

We do not load all of train.bin into GPU memory.

Instead, we randomly sample windows from the large flat token stream.

5. Constructing X

For every random starting index i:

x = data[i:i+block_size]

So if:

block\_size=256,

we take:

t_i,t_{i+1},...,t_{i+255}.

This becomes one training input.

6. Constructing Y

The target is shifted by one position:

y = data[i+1:i+1+block_size]

So:

X:
t₁ t₂ t₃ t₄ t₅ ...

Y:
t₂ t₃ t₄ t₅ t₆ ...

Therefore the model learns:

P(t_{j+1}\mid t_1,\ldots,t_j).

This is the core next-token prediction objective.

7. A tiny example

Suppose the token sequence is:

[10, 25, 91, 7, 42]

and:

block\_size=4.

Then:

X = [10, 25, 91, 7]
Y = [25, 91, 7, 42]

The model is therefore trained on four predictions:

10\rightarrow25
25\rightarrow91
91\rightarrow7
7\rightarrow42.

That's why the target is shifted exactly one position.

8. Batch shape

The source uses:

batch\_size=24

block\_size=256.

Therefore:

\boxed{ X:[24,256] }

and:

\boxed{ Y:[24,256]. }

There are:

24\times256 = \boxed{6144}

token prediction positions in one training batch.

np.uint16

But when PyTorch uses token IDs for embeddings and cross-entropy, the source converts the slices:

So the flow is:

\boxed{ disk:\ uint16 \rightarrow PyTorch:\ int64 }

This is a storage representation versus computation representation distinction.

12. Phase 1 — Warmup

The source sets:

warmup\_iters=200.

For:

it<200,

the learning rate is:

\boxed{ LR(it) = learning\_rate \times \frac{it}{200} }

learning\_rate=3\times10^{-4}.

So approximately:

At iteration 100:

13. Why warmup?

The source's explanation is:

Early in training, the weights are still random.

A large update immediately can be unstable.

So instead:

0 \rightarrow small \rightarrow medium \rightarrow peak.

Conceptually:

learning rate
    ↑
    │           ______
    │          /
    │         /
    │        /
    │_______/________________→ iteration
            200
          warmup

14. Phase 2 — Cosine decay

After warmup, the source computes:

decay\_ratio = \frac{it-warmup\_iters} {lr\_decay\_iters-warmup\_iters}.

Then:

coeff = \frac12 \left( 1+\cos(\pi\cdot decay\_ratio) \right).

Finally:

\boxed{ LR = min\_lr + coeff (learning\_rate-min\_lr) }

with:

min\_lr=\frac{learning\_rate}{10}.

(Source: Build a DeepSeek Model (From Scratch))

15. What does cosine decay do?

At the beginning of decay:

coeff\approx1

so:

LR\approx learning\_rate.

Near the end:

coeff\approx0

so:

LR\approx min\_lr.

Thus:

LR
↑
│       ────────╮
│               ╲
│                ╲
│                 ╲
│                  ╲____
│
└────────────────────────→ iteration
       warmup       decay

The source describes this as allowing larger updates earlier and smaller updates as training approaches a good solution. (Source: Build a DeepSeek Model (From Scratch))

16. A subtle source detail: min_lr branch

The source explicitly notes something interesting.

It sets:

lr\_decay\_iters=max\_iters.

The main loop stops at max_iters, so:

if it > lr_decay_iters:

normally never fires.

Thus that branch is mainly a defensive guard for possible later extension/resumption.

The source also notes that setting:

lr\_decay\_iters\approx0.9\cdot max\_iters

would make the cooldown actually occur before the main loop ends. (Source: Build a DeepSeek Model (From Scratch))

       ↓
4. Get loss
       ↓

Therefore:

X:[24,256]
Y:[24,256].

The source uses:

(Source: Build a DeepSeek Model (From Scratch))

targets=Y

\boxed{\text{training path}}

rather than the cached inference path.

26. What happens inside the model?

We already derived this:

X \rightarrow Embedding \rightarrow 12\times TransformerBlock \rightarrow h_{\text{main}}

then:

h_{\text{main}} \rightarrow LM\ head \rightarrow L_{\text{main}}

and:

h_{\text{main}} \rightarrow MTP_1 \rightarrow MTP_2 \rightarrow\cdots \rightarrow L_{\text{MTP}}.

The model returns:

outputs['loss']

which is the combined training objective.

27. Step 5 — Zero gradients

The source uses:

optimizer.zero_grad(set_to_none=True)

(Source: Build a DeepSeek Model (From Scratch))

We need this because gradients accumulate in PyTorch by default.

Without clearing them:

g_t

would accumulate with previous iterations' gradients.

We instead want the gradient corresponding to the current batch.

28. Step 6 — Backpropagation

Then:

loss.backward()

(Source: Build a DeepSeek Model (From Scratch))

This computes:

\boxed{ \nabla_\theta L }

for the trainable parameters.

So gradients flow backward through:

total loss
   ↓
MTP losses + main loss
   ↓
LM head
   ↓
Transformer blocks
   ↓
MoE / Attention / RoPE-related operations
   ↓
Embedding

The important conceptual point is that the loss does not directly change the parameters.

It first produces gradients.

29. Step 7 — AdamW update

Finally:

optimizer.step()

(Source: Build a DeepSeek Model (From Scratch))

Now AdamW uses the gradients and its optimizer state to modify:

\theta.

Therefore:

\boxed{ \theta_{t+1} = Optimizer( \theta_t,\nabla_\theta L_t ) }

and the model has learned a tiny amount from this batch.

Then the loop starts again.

30. Why repeat 5000 times?

One batch only contains:

6144

token positions.

The dataset is much larger.

So training repeatedly draws different random windows:

Iteration 1 → random windows
Iteration 2 → different random windows
Iteration 3 → different random windows
...
Iteration 5000

Over many iterations, the parameters gradually encode statistical patterns in the dataset.

31. Validation is different from training

Every:

250

iterations, the source evaluates the model. (Source: Build a DeepSeek Model (From Scratch))

It calls:

model.eval()

and:

with torch.no_grad():

The purpose is to measure performance on:

\boxed{\text{validation data}}

rather than update the model.

32. Why model.eval()?

Training mode may activate training-specific behavior.

Evaluation mode tells PyTorch:

\boxed{ \text{evaluate rather than train}. }

Again, this is a framework-level behavior distinction.

33. Why torch.no_grad()?

During validation, we don't need:

\nabla_\theta L.

We're not updating the model.

Therefore keeping the computational graph would be unnecessary overhead.

So:

with torch.no_grad():

prevents gradient tracking during validation. (Source: Build a DeepSeek Model (From Scratch))

34. Why average 100 validation batches?

The source sets:

eval\_iters=100.

It computes a loss for each validation batch:

L_1,L_2,\ldots,L_{100}

and then:

\boxed{ L_{\text{val}} = \frac1{100} \sum_{i=1}^{100}L_i. }

This gives a more stable estimate than relying on one random validation batch.

35. Training loss vs validation loss

These answer different questions.

Training loss
\boxed{ \text{How well is the model fitting the training data?} }
Validation loss
\boxed{ \text{How well does the learned model perform on held-out data?} }

A useful conceptual pattern is:

training loss  ↓
validation loss ↓

which suggests learning and generalization.

But if:

training loss  ↓↓↓
validation loss ↑

that suggests the model is increasingly fitting training data while generalization worsens.

The source uses validation loss specifically as the criterion for its best checkpoint. (Source: Build a DeepSeek Model (From Scratch))

39. Why save optimizer state?

Suppose we only save:

model.state_dict()

and restart training later.

We would recover the model's parameters, but not necessarily the optimizer's internal state.

The source therefore saves:

optimizer.state_dict()

as part of the checkpoint. (Source: Build a DeepSeek Model (From Scratch))

This is important for resuming training rather than merely loading a model for inference.

41. The complete learning equation

Everything we've done can be compressed into:

\boxed{ \theta_{t+1} = \operatorname{AdamW} \left( \theta_t, \nabla_\theta \left[ L_{\text{main}} + L_{\text{MTP}} \right] \right) }

with a learning rate:

LR_t= \begin{cases} \text{linear warmup}, & t<200\\ \text{cosine decay}, & 200\le t\le5000. \end{cases}

That is the engine that turns the architecture into a trained model.

42. One very important distinction

At this point, we have a complete single-GPU training system.

The source explicitly says that this is enough to train the MiniDeepSeek model, but real DeepSeek-V3 was trained on a massive multi-GPU cluster. The text therefore transitions next to:

\boxed{\text{DualPipe Parallelism}}

and first introduces the core ideas of distributing deep-learning workloads across multiple GPUs. (Source: Build a DeepSeek Model (From Scratch))

So the conceptual transition is:

\boxed{ \text{single GPU} \rightarrow \text{distributed training} }

and that is where parallelism becomes the next major layer of the system.
