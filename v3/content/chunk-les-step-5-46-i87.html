Motivation

Translate sparse MoE routing into remote payloads, expert-device load and scheduling constraints.

Prerequisites

  • Mini-batch SGD and weighted means
  • GPU state versus activation memory
  • MoE top-k routing
  • Critical paths and collective communication

Notation and units

  • B_micro: sequences/replica; R: DP replicas; A: accumulation count
  • P: pipeline stages; M: microbatches; F/B: forward/backward chunk duration
  • T: tokens; k: top-k; d: representation width; s: bytes/element
  • N_experts: expert count; rho: remote assignment fraction

Assumptions

  • All toy numerical inputs and normalization conventions are stated explicitly.
  • The teaching companion requires NumPy and runs on CPU; it claims no production backend execution.
  • Schedule formulas assume equal-duration stages and declared independent communication; traffic counts exclude unstated overhead.

Step-by-step derivation

  1. Top-k assignment count A=T*k. A two-matrix expert requires approximately 2*k*d*h_expert MACs per token; the router requires approximately d*N MACs. SwiGLU adds a third matrix and changes this count.
  2. Dispatch copies or communicates each token representation to selected expert devices; weighted combine sums selected expert outputs back at the origin.
  3. Gross one-way payload T*k*d*s counts assignment bytes. Remote-routing fraction, duplicate expert locations, metadata, protocols and network hops change physical traffic.
  4. Average expert load A/N does not certify balance; latency often depends on maximum load and stragglers. Overlap preserves routing → dispatch → expert → combine dependencies.

Step 5.46 — Distributed MoE: Expert Parallelism, All-to-All Communication, Pipeline Bubbles, and DualPipe

Plan node: A5 · chat order #87

We have finished the single-GPU mathematical view of MoE.

Now we have to answer the much harder systems question:

What happens when the 64, 128, or hundreds of experts do not live on the same GPU?

This is where MoE changes from primarily a neural-network idea into a distributed-systems problem.

The source explicitly explains that large MoE models introduce an expensive All-to-All token exchange, because selected experts are distributed across devices. It then motivates DeepSeek's DualPipe as a scheduling strategy that overlaps this communication with useful computation. (Source: Build a DeepSeek Model (From Scratch))

5.46.1 First understand the problem

Suppose we have four GPUs:

GPU 0 → Experts E1 E2
GPU 1 → Experts E3 E4
GPU 2 → Experts E5 E6
GPU 3 → Experts E7 E8

Now suppose a token is currently on:

GPU_0

but the router selects:

E_7.

Expert 7 is on:

GPU_3.

Therefore the token representation must move:

\boxed{ GPU_0\rightarrow GPU_3 }

before Expert 7 can process it.

After Expert 7 computes the result, the result must be associated with the original token again.

That is the fundamental communication problem.

5.46.2 Why can't every GPU simply contain every expert?

It could, conceptually.

But then each GPU would store:

\boxed{\text{the entire MoE expert pool}}

which largely defeats the memory advantage of distributing experts.

Remember the DeepSeek-R1 example:

671B

total parameters.

A single GPU cannot simply replicate all of those weights.

So we distribute the experts across devices.

This is the motivation for:

\boxed{\text{Expert Parallelism}}

in large MoE systems.

The source explicitly identifies the combination of Expert Parallelism + DualPipe-style scheduling as the approach used to train massive MoE systems efficiently. (Source: Build a DeepSeek Model (From Scratch))

5.46.3 What is Expert Parallelism?

The basic idea is:

\boxed{ \text{different GPUs own different experts} }

For example:

N=64

experts and:

P=8

GPUs.

If distributed evenly:

64/8 = \boxed{8}

experts per GPU.

So:

GPU 0 → E1 ... E8
GPU 1 → E9 ... E16
GPU 2 → E17 ... E24
...
GPU 7 → E57 ... E64

The exact production mapping can be more sophisticated, but this is the core concept.

5.46.4 Why expert parallelism is attractive

Without expert parallelism:

\text{every GPU} \rightarrow \text{all experts}.

With expert parallelism:

\text{GPU} \rightarrow \text{its local subset of experts}.

Therefore expert weights can be partitioned across GPUs.

So:

\boxed{ \text{model memory per GPU decreases} }

for the expert portion.

But the price is:

\boxed{ \text{communication between GPUs}. }

This is the recurring pattern of distributed deep learning:

\boxed{ \text{split memory} \Rightarrow \text{introduce communication}. }

The source explicitly describes communication as a primary source of overhead in parallel computing. (Source: Build a DeepSeek Model (From Scratch))

5.46.5 Let's return to our token routing example

Suppose the current GPU has four tokens:

T_1,T_2,T_3,T_4.

Router decisions:

T_1\rightarrow E_1,E_3
T_2\rightarrow E_5,E_6
T_3\rightarrow E_2,E_8
T_4\rightarrow E_7,E_8.

Suppose:

E1,E2 → GPU 0
E3,E4 → GPU 1
E5,E6 → GPU 2
E7,E8 → GPU 3

Then:

T_1

local:

E_1

remote:

E_3
T_2

remote:

E_5,E_6
T_3

local:

E_2

remote:

E_8
T_4

remote:

E_7,E_8.

So many token activations need to leave the current GPU.

5.46.6 The communication happens because routing is dynamic

The router computes:

TopK(x_t).

The selected experts depend on:

x_t.

Therefore the system does not know in advance that every token belongs to GPU 2 or GPU 3.

The dispatch pattern changes with the data.

So communication is:

\boxed{\text{dynamic}}

rather than a fixed tensor partition.

That makes MoE more complicated than ordinary layer-based model parallelism.

5.46.7 What does All-to-All mean?

Suppose we have:

P

GPUs.

Each GPU may hold tokens that need experts on multiple other GPUs.

So one communication phase logically looks like:

\boxed{ \text{every GPU sends data to every other relevant GPU} }

and each GPU receives token representations destined for its local experts.

This is an All-to-All communication pattern.

The source identifies MoE token shuffling between expert devices as an expensive cross-GPU data exchange and specifically calls out All-to-All communication. (Source: Build a DeepSeek Model (From Scratch))

5.46.8 Two-stage mental model

Think of distributed MoE as:

\boxed{ \text{Dispatch All-to-All} }

followed by:

\boxed{ \text{Local expert computation} }

followed by:

\boxed{ \text{Combine / return communication} }

So:

Tokens
  ↓
Router
  ↓
Top-K
  ↓
DISPATCH
All-to-All
  ↓
Tokens grouped by destination GPU
  ↓
Local Expert FFNs
  ↓
COMBINE
Return results to original token locations

This is the distributed extension of the index_add_ logic we learned earlier.

5.46.9 Communication is not the same as router computation

This is important.

Router computation:

XW_R

is arithmetic.

Communication:

GPU_i\leftrightarrow GPU_j

is data movement.

You can have a very cheap router and still have a very expensive MoE system because:

\boxed{ \text{communication latency/bandwidth} }

can dominate.

The source explicitly says the MoE All-to-All operation can be more time-consuming than the pipeline bubble itself. (Source: Build a DeepSeek Model (From Scratch))

5.46.10 A simple communication-volume derivation

Suppose:

T

tokens are processed.

Each token has hidden dimension:

D.

Each token selects:

k

experts.

So the total number of routed token representations is:

Tk.

Each representation contains:

D

numbers.

If each number occupies:

s

bytes, then the total volume of routed representation data is approximately:

\boxed{ TkDs }

bytes.

This is the gross routed-data volume before accounting for whether some expert assignments are local, and before accounting for communication protocol overhead.

This formula is derived from the tensor dimensions.

5.46.11 Numerical communication example

Suppose:

T=8192

tokens,

k=8,
D=4096,

and FP16:

s=2\text{ bytes}.

Then:

T k = 8192\times8 = 65,536

routed representations.

Each is:

4096\times2 = 8192

bytes.

Therefore gross data volume:

65,536\times8192
= \boxed{536,870,912\text{ bytes}}

approximately:

\boxed{512\text{ MiB}}.

That is a lot of data movement for one routing event in this illustrative example.

5.46.12 Important qualification

The:

512\text{ MiB}

is not automatically the exact amount sent across the network.

Some assignments may remain on the same GPU.

So:

\boxed{ \text{network volume} \le TkDs }

in an ideal accounting.

Actual traffic can also include:

\text{metadata} + \text{headers} + \text{padding} + \text{collective-operation overhead}

depending on implementation.

The source does not provide a single universal communication-volume formula, so this calculation is our systems derivation.

5.46.13 Why load balancing suddenly becomes even more important

Previously, load imbalance meant:

\boxed{ E_1\text{ has too many tokens} }

while:

E_2\text{ has too few}.

In distributed MoE, it additionally means:

\boxed{ \text{GPU containing }E_1\text{ becomes a communication/computation hotspot} }.

So bad routing causes:

\text{expert imbalance}
\Downarrow
\text{GPU imbalance}
\Downarrow
\text{communication/compute bottleneck}.

That's why load balancing is both a machine-learning and systems concern.

The source's figures explicitly contrast hotspot experts in standard MoE with more balanced DeepSeek-MoE routing. (Source: Build a DeepSeek Model (From Scratch))

5.46.14 Example

Suppose four GPUs receive routed token assignments:

[4000,4000,4000,4000].

Perfect.

Now suppose:

[7000,5000,2000,2000].

GPU 0 and GPU 1 carry significantly more expert work.

Even if total work remains:

16,000,

the system's throughput can become limited by the busiest devices.

This is why:

\boxed{ \text{average load} }

is not enough.

We also care about:

\boxed{ \text{maximum load} }.

5.46.15 Now connect to the pipeline

Suppose the Transformer has:

8

pipeline stages.

These stages are spread across GPUs.

The source calls a group of layers on one GPU a stage and describes activations flowing from one stage to the next like an assembly line. (Source: Build a DeepSeek Model (From Scratch))

For example:

GPU 0 → Layers 1–10
GPU 1 → Layers 11–20
GPU 2 → Layers 21–30
GPU 3 → Layers 31–40
GPU 4 → Layers 41–50
GPU 5 → Layers 51–60
GPU 6 → Layers 61–70
GPU 7 → Layers 71–80

That's pipeline parallelism.

5.46.16 What is the pipeline bubble?

At the beginning:

GPU_0

starts computing.

But:

GPU_1

cannot compute until GPU 0 sends its activation.

Then GPU 2 waits for GPU 1.

And so on.

Likewise at the end, GPUs may become idle while the remaining gradients drain through the pipeline.

That idle region is:

\boxed{\text{pipeline bubble}}.

The source defines the bubble as GPU idle time while waiting for required data or gradients. (Source: Build a DeepSeek Model (From Scratch))

5.46.17 Naive GPipe

Suppose:

P=4

pipeline stages and:

M=8

micro-batches.

GPipe essentially fills the pipeline with forward passes and then drains it with backward passes.

The source explains that this creates significant idle time at fill/drain boundaries. (Source: Build a DeepSeek Model (From Scratch))

5.46.18 Pipeline efficiency formula

The source gives the illustrative theoretical efficiency:

\boxed{ \eta_{\text{pipeline}} \approx \frac{M}{M+(P-1)} }

for the simplified equal-time setting used in its discussion.

For:

M=8,\quad P=4:
\eta= \frac8{8+3} = \frac8{11}
\approx \boxed{72.7\%}.

The source explicitly gives this example as approximately 73%. (Source: Build a DeepSeek Model (From Scratch))

5.46.19 What reduces the bubble?

Increase:

M

the number of micro-batches.

For example:

M=8

gives:

8/11\approx72.7\%.

If:

M=32,

then:

\frac{32}{32+3} = \frac{32}{35} \approx \boxed{91.4\%}.

So:

M\uparrow \Rightarrow \text{bubble fraction}\downarrow.

The source explicitly explains this relationship. (Source: Build a DeepSeek Model (From Scratch))

5.46.20 Why not simply increase micro-batches forever?

Because activations must be stored for backward computation.

The source explains:

  • GPipe holds activations for many micro-batches during the forward phase.
  • 1F1B reduces this memory pressure by running backward sooner and freeing activations earlier. (Source: Build a DeepSeek Model (From Scratch))

Thus:

\boxed{ \text{more micro-batches} }

helps efficiency but can increase activation-memory requirements.

5.46.21 1F1B schedule

The idea is:

Don't wait until all forwards finish before starting backwards.

Instead:

\boxed{ 1F1B = \text{one forward, one backward} }

in the steady state.

The source describes the three phases:

\boxed{\text{warm-up}}
\boxed{\text{steady state}}
\boxed{\text{cool-down}}.

(Source: Build a DeepSeek Model (From Scratch))

5.46.22 Why 1F1B is better for memory

Suppose a micro-batch's forward activation is stored.

Under naive GPipe:

\text{many micro-batches} \rightarrow \text{many stored activations}.

Under 1F1B:

\text{forward}(m_i) \rightarrow \text{soon backward}(m_i) \rightarrow \text{free activation}.

So peak activation memory is lower.

This is why 1F1B allows more micro-batches in practice even though its theoretical bubble efficiency for a fixed M,P can be similar to GPipe. (Source: Build a DeepSeek Model (From Scratch))

5.46.23 But 1F1B meets a new problem with MoE

Here's the critical chain:

\boxed{ 1F1B }

solves:

\text{pipeline bubble}.

Then we add:

\boxed{\text{MoE}}

which introduces:

\boxed{\text{All-to-All communication}}.

Therefore:

\boxed{ \text{GPU can still become idle while waiting for expert communication} }.

The source explicitly says the All-to-All communication can be even more time-consuming than the pipeline bubble. (Source: Build a DeepSeek Model (From Scratch))

5.46.24 This is the engineering progression

Think:

\boxed{ \text{Pipeline parallelism} }

solves:

\text{model too large}.

↓

\boxed{ \text{GPipe} }

but creates:

\text{bubble}.

↓

\boxed{ 1F1B }

reduces:

\text{bubble}.

↓

\boxed{ \text{MoE} }

introduces:

\text{All-to-All communication}.

↓

\boxed{ \text{DualPipe} }

tries to hide:

\boxed{\text{communication inside computation}}.

This is one of the most important engineering stories in the entire DeepSeek architecture.

5.46.25 Now understand DualPipe

The key idea is:

\boxed{ \text{Don't let communication happen while compute waits} }

Instead:

\boxed{ \text{communication for one micro-batch} \parallel \text{computation for another} }.

The source explicitly says DualPipe schedules communication-heavy All-to-All operations alongside compute-heavy attention/expert operations. (Source: Build a DeepSeek Model (From Scratch))

5.46.26 Simple timeline

Imagine:

Time →
────────────────────────────────────────────

Micro-batch A:
        All-to-All

Micro-batch B:
               Expert Compute

Micro-batch C:
                      Attention

Micro-batch D:
                             All-to-All

Instead of:

All-to-All
    ↓
WAIT
    ↓
Expert
    ↓
WAIT
    ↓
Attention

we try to overlap them:

All-to-All A
      +
Expert B
      +
Attention C

The GPU's compute resources and communication/network resources can work concurrently.

That is the central DualPipe idea in the source. (Source: Build a DeepSeek Model (From Scratch))

5.46.27 Why this works

Different operations stress different resources.

Conceptually:

Expert/attention computation

uses:

\boxed{\text{GPU compute}}
Network communication

uses:

\boxed{\text{network/interconnect}}

If the hardware can progress them concurrently, then:

T_{\text{total}}

can approach the larger of the two costs rather than their sum.

Suppose:

T_C=8\text{ ms}

computation,

and:

T_{Comm}=6\text{ ms}

communication.

Sequential:

8+6 = \boxed{14\text{ ms}}.

Perfect overlap:

\max(8,6) = \boxed{8\text{ ms}}.

Potential hidden communication:

14-8 = \boxed{6\text{ ms}}.

The source uses the qualitative idea of “hiding” communication rather than providing this exact numerical formula. This is our systems derivation.

5.46.28 What does “hide communication” actually mean?

It does not mean:

\boxed{\text{communication takes zero time}}.

It means:

\boxed{ \text{communication time overlaps with useful computation} }

so less of its latency appears on the critical path.

This distinction is extremely important in interviews.

5.46.29 Fine-grained scheduling

The source says DualPipe doesn't merely interleave whole forward and backward passes.

It breaks computation into smaller components such as:

\boxed{\text{Attention}}
\boxed{\text{MLP/Expert}}
\boxed{\text{All-to-All communication}}

and schedules them carefully. (Source: Build a DeepSeek Model (From Scratch))

Therefore:

\boxed{ \text{fine-grained overlap} }

is a major part of the innovation.

5.46.30 Why the scheduler is complicated

Because dependencies must still be respected.

For example:

\text{routing} \rightarrow \text{dispatch} \rightarrow \text{expert compute}

must occur in the correct logical order.

You cannot arbitrarily reorder:

\text{Expert compute}

before the token has arrived.

So the scheduler has to identify operations that are:

\boxed{\text{independent enough to overlap}}

while preserving:

\boxed{\text{data dependencies}}.

5.46.31 DualPipe and backward computation

The source describes blocks such as:

\boxed{\text{Forward}}

and:

\boxed{\text{Backward for weights}}

being overlapped with communication and with computation from another micro-batch. (Source: Build a DeepSeek Model (From Scratch))

So a simplified picture is:

Micro-batch A:
    communication

Micro-batch B:
    forward compute

Micro-batch C:
    backward compute

Micro-batch D:
    expert compute

The scheduler interleaves these at a fine granularity.

5.46.32 Pipeline folding

DualPipe introduces another idea:

\boxed{\text{folding the pipeline}}

Instead of:

GPU 0 → Stage 0
GPU 1 → Stage 1
GPU 2 → Stage 2
GPU 3 → Stage 3
GPU 4 → Stage 4
GPU 5 → Stage 5
GPU 6 → Stage 6
GPU 7 → Stage 7

the folded arrangement puts two distant stages on each GPU.

For eight stages and four GPUs, the source gives:

GPU_0:\ Stage\ 0,\ Stage\ 7
GPU_1:\ Stage\ 1,\ Stage\ 6
GPU_2:\ Stage\ 2,\ Stage\ 5
GPU_3:\ Stage\ 3,\ Stage\ 4.

(Source: Build a DeepSeek Model (From Scratch))

5.46.33 Why this creates a V-shape

Suppose a micro-batch travels:

Stage\ 0 \rightarrow Stage\ 1 \rightarrow Stage\ 2 \rightarrow Stage\ 3

then turns:

Stage\ 4

on the same physical GPU that owns Stage 3.

Then:

Stage\ 4 \rightarrow Stage\ 5 \rightarrow Stage\ 6 \rightarrow Stage\ 7.

So physically it travels:

\boxed{ Down \rightarrow Turn \rightarrow Up }

forming a:

\boxed{V}.

The source calls this:

\boxed{\text{DualPipeV / V-shape / cut-in-half}}.

(Source: Build a DeepSeek Model (From Scratch))

5.46.34 Why is this useful?

The source says the V-shaped variant can run an:

N\text{-stage pipeline}

using only:

\boxed{N/2}

physical GPUs.

So:

8\text{ stages} \rightarrow 4\text{ GPUs}.

But there is an explicit trade-off:

each GPU holds:

\boxed{2\times}

the parameter memory of a conventional one-stage-per-GPU layout.

(Source: Build a DeepSeek Model (From Scratch))

5.46.35 Numerical: folded pipeline

Suppose:

N=16

stages.

DualPipeV can, in the source's simplified description, use:

16/2 = \boxed{8\text{ physical GPUs}}.

But each GPU holds two stages.

Therefore parameter memory per GPU is approximately:

\boxed{2\times}

the standard one-stage-per-GPU arrangement.

So:

\boxed{ \text{GPU count}\downarrow \quad\text{but}\quad \text{per-GPU parameter memory}\uparrow }.

This is a deliberate trade-off.

5.46.36 Why would DeepSeek accept that trade-off?

Because the source says other techniques already help reduce per-GPU parameter memory, including:

\boxed{\text{FP8}}

and:

\boxed{\text{Expert Parallelism}}.

So the system can trade additional parameter memory for:

\boxed{ \text{better utilization} + \text{better communication hiding} }.

The source explicitly frames this as an engineering trade-off. (Source: Build a DeepSeek Model (From Scratch))

5.46.37 Full distributed-training stack

At this point we can see several parallelism mechanisms.

Gradient Accumulation

Splits a large effective batch into smaller physical batches.

Problem solved:

\boxed{\text{batch memory}}

The source derives:

B_{\text{effective}} = b_{\text{physical}}\times N_{\text{accumulation}}.

(Source: Build a DeepSeek Model (From Scratch))

Data Parallelism

Replicates the model across GPUs and splits the data.

Problem solved:

\boxed{\text{training time}}

but the whole model must fit on every GPU. (Source: Build a DeepSeek Model (From Scratch))

Pipeline Parallelism

Splits model layers across GPUs.

Problem solved:

\boxed{\text{model too large}}

but creates pipeline bubbles. (Source: Build a DeepSeek Model (From Scratch))

Expert Parallelism

Splits MoE experts across GPUs.

Problem solved:

\boxed{\text{expert parameter memory}}

but creates:

\boxed{\text{All-to-All communication}}.
1F1B

Interleaves forward/backward work.

Problem solved:

\boxed{\text{pipeline bubble}}

but MoE communication remains problematic. (Source: Build a DeepSeek Model (From Scratch))

DualPipe

Overlaps:

\boxed{ \text{communication} + \text{computation} }

and uses a folded/V-shaped organization.

Problem solved:

\boxed{\text{MoE communication bottleneck + pipeline utilization}}

with a parameter-memory trade-off. (Source: Build a DeepSeek Model (From Scratch))

5.46.38 One very useful table

Technique What is split/replicated? Main problem
Gradient accumulation Batch VRAM for large batch
Data parallelism Data Training throughput
Pipeline parallelism Layers Model memory
Expert parallelism Experts MoE model memory
1F1B Schedule Pipeline bubble
DualPipe Schedule + folded stages MoE communication / idle time

The source presents these techniques as complementary rather than mutually exclusive. (Source: Build a DeepSeek Model (From Scratch))

5.46.39 An important conceptual distinction

A common mistake is to say:

“Pipeline parallelism and expert parallelism are alternatives.”

Not necessarily.

They solve different dimensions of the problem.

A real large-scale system can combine:

\boxed{ \text{Data Parallelism} + \text{Pipeline Parallelism} + \text{Expert Parallelism} }

plus:

\boxed{\text{tensor/model sharding and scheduling}}.

The source explicitly emphasizes that modern LLM training uses these techniques in combination to overcome both time and hardware constraints. (Source: Build a DeepSeek Model (From Scratch))

Suppose:

T=4096,
k=2,
D=2048,

FP16:

Gross routed-data volume:

= 4096\times2\times2048\times2.

Compute:

Approximately:

pipeline stages and:

Suppose:

T_{\text{compute}}=10\text{ ms}

T_{\text{communication}}=7\text{ ms}.
Sequential

Ideal full overlap
\max(10,7) = \boxed{10\text{ ms}}.

17/10 = \boxed{1.7\times}.

This assumes perfect overlap and no additional synchronization or resource contention.

5.46.44 Exam numerical — DualPipeV GPU count

Suppose a pipeline has:

N=20

stages.

Source-style DualPipeV:

N/2 = 20/2 = \boxed{10\text{ GPUs}}.

Each GPU holds two stages.

So if a normal layout used one stage per GPU:

20\text{ GPUs},

the folded layout uses:

\boxed{10\text{ GPUs}}

but approximately doubles per-GPU parameter storage.

5.46.45 The critical trade-off graph in your mind

You should now mentally understand this progression:

\boxed{ \text{Less GPU memory per model replica} }

often comes from:

\text{more partitioning}.

But:

\boxed{ \text{more partitioning} \Rightarrow \text{more communication} }.

Then:

\boxed{ \text{more communication} \Rightarrow \text{need better scheduling} }.

Then:

\boxed{ \text{better scheduling} \Rightarrow \text{overlap communication with computation} }.

That is the systems philosophy behind DualPipe.

DualPipe addresses the interaction between those constraints.

5.46.49 The deepest takeaway

At the algorithm level:

\boxed{ \text{MoE says “don't compute every expert.”} }

At the hardware level:

\boxed{ \text{Expert Parallelism says “don't store every expert on every GPU.”} }

But that creates:

\boxed{ \text{“move the token to the expert.”} }

That creates:

\boxed{ \text{All-to-All communication.} }

And then DeepSeek's scheduling insight becomes:

\boxed{ \text{Don't wait for communication—do useful computation while communication is happening.} }

That is the conceptual bridge from MoE mathematics to large-scale distributed training.
