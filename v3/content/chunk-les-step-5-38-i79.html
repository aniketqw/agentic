Motivation

Replace always-active FFN capacity with learned conditional expert execution.

Prerequisites

  • Two-layer FFN matrix shapes and parameter counts
  • Stable softmax, top-k, integer indices and gather/scatter accumulation
  • Expert parallelism, load/importance distinction and non-gradient feedback

Notation and units

  • T=B×S flattened tokens, D model width, N routed experts, k selected per token
  • Row score matrix[T, N]; selected indices and gates[T, k]; final stream[T, D]
  • Book bias is a persistent nontrainable buffer; gate weights come from softmax selected biased logits
  • V3: si=sigmoid(x·ei); select by si+bi; normalize original si within selected set

Assumptions

  • Bias-free educational two-matrix GELU experts use2DHparameters; gated/SwiGLUuses3DH
  • Per-tokenk/N is routed expert activation fraction, notcomplete-model storage or latency ratio
  • The Transformer owns the residual unless a standalone MoE explicitly returns x+transform; neveraddit twice
  • Tie behavior and normalization must be explicit; expert choices are learned, not manual domain labels

Step-by-step derivation

  1. A dense FFN executes both matrices for every token. Create N expert FFNs and a linear router WR[D, N] that produces T×N scores.
  2. Select k distinct experts per row; stable ties must be frozen for reproducible toy outputs. Apply declared gates and combine y_i=sum_i gate_ti Ei(x_t).
  3. Top-k selection is discrete; gradients can flow through selected gate values and expert transformations, but not through an ordinary hard arg-topk index change. Near a tie weight updates can abruptly change routes.
  4. When k=1and softmax only the selected score, gate is exactly1and has zero derivative with respect to that logit. Without another router learning mechanism, this gating path provides no router gradient; do not assume any top1implementation learns as intended.
  5. Separate expert pool parameters N×2DH from active experts k×2DH, then add router DN, shared experts, and other dense model components.
  6. Sparse expert computation is not necessarily cheaper vs a much smaller dense FFN; compare kHr with Hdense and system overhead explicitly.

Plan node: A2 · chat order #79

We now start the second major DeepSeek architectural innovation:

\boxed{\text{Mixture-of-Experts (MoE)}}

The source presents MoE as the mechanism that allows the model to have a very large total parameter count while activating only a small subset of those parameters for each token. (Source: Build a DeepSeek Model (From Scratch))

The core progression is:

\boxed{ \text{Dense FFN} \rightarrow \text{many expert FFNs} \rightarrow \text{router} \rightarrow \text{Top-K} \rightarrow \text{weighted expert outputs} }

Today we will build the basic MoE mechanism first. The harder problems—expert imbalance, fine-grained segmentation, shared experts, and auxiliary-loss-free balancing—come after the foundation is solid.

5.38.1 First: remember where FFN sits in a Transformer

A Transformer block has roughly:

\boxed{ \text{Attention} \rightarrow \text{FFN} }

The attention layer lets tokens exchange information.

The FFN performs nonlinear transformation independently at each token position.

A standard dense FFN is:

\boxed{ x \rightarrow W_1 \rightarrow \text{activation} \rightarrow W_2 \rightarrow y }

The source describes the FFN as an expansion-contraction MLP. (Source: Build a DeepSeek Model (From Scratch))

5.38.2 Standard dense FFN mathematically

Let:

x\in\mathbb R^{d_{\text{model}}}.

Choose hidden dimension:

d_{\text{hidden}}.

Then:

h=xW_1

where:

W_1\in \mathbb R^{d_{\text{model}}\times d_{\text{hidden}}}.

Apply activation:

z=\operatorname{GELU}(h).

Then:

y=zW_2

with:

W_2\in \mathbb R^{d_{\text{hidden}}\times d_{\text{model}}}.

Therefore:

\boxed{ y= \operatorname{GELU}(xW_1)W_2 }

in the simplified source-style representation.

5.38.3 Why does a dense FFN become expensive?

Suppose:

d_{\text{model}}=4096

and:

d_{\text{hidden}}=16384.

Then W_1 alone contains:

4096\times16384 = \boxed{67,108,864}

parameters.

W_2 contains the same number.

Total:

2(67,108,864) = \boxed{134,217,728}

parameters.

And every token activates all of them.

The source identifies exactly this issue: dense FFNs activate all of their parameters for every token and therefore become a major computational bottleneck. (Source: Build a DeepSeek Model (From Scratch))

5.38.4 The natural idea

Instead of one giant FFN:

\boxed{ FFN }

create many smaller FFNs:

\boxed{ E_1,E_2,\ldots,E_N }

where each:

E_i

is called an:

\boxed{\text{expert}}.

The source explicitly defines each expert as essentially a standard two-layer FFN/MLP. (Source: Build a DeepSeek Model (From Scratch))

5.38.5 Why call them “experts”?

The intuition is:

\boxed{ \text{different experts can specialize} }

during training.

For example, the source gives conceptual examples such as:

\text{punctuation expert}
\text{verb expert}
\text{Python/code expert}.

These examples are illustrative descriptions of specialization, not a claim that every trained MoE literally develops exactly those named experts. (Source: Build a DeepSeek Model (From Scratch))

5.38.6 The apparent problem

Suppose we replace one FFN with:

8

experts.

It may seem that computation becomes:

8\times

more expensive.

But this ignores the key idea:

\boxed{\text{sparsity}}.

We don't execute every expert for every token.

5.38.7 Sparse activation

For each token, only:

\boxed{k}

experts are activated.

Usually:

k\ll N.

For example:

N=8,\qquad k=2.

Then each token sees:

\boxed{2}

experts instead of:

8.

The source's basic example uses:

\boxed{k=2}

out of three available experts. (Source: Build a DeepSeek Model (From Scratch))

5.38.8 Computational intuition

Dense model:

\boxed{ 1\text{ token} \rightarrow 8\text{ experts} }

Sparse MoE:

\boxed{ 1\text{ token} \rightarrow 2\text{ experts} }

So approximately:

\frac{2}{8} = \boxed{25\%}

of the expert computations are activated per token, ignoring router/dispatch overhead and shared components.

This is why we can have:

\boxed{ \text{large total parameter capacity} }

without paying the full dense computation for every token.

5.38.9 Total parameters vs active parameters

This distinction is fundamental.

Suppose:

N=16

experts, each with:

100\text{M}

parameters.

Then total expert parameters:

16\times100M = \boxed{1.6B}.

But suppose:

k=2.

Then a token activates:

2\times100M = \boxed{200M}

expert parameters.

So:

\boxed{ 1.6B\text{ total} \quad\text{but}\quad 200M\text{ expert parameters active for a token} }

under this simplified model.

This is one of the most important MoE ideas.

5.38.10 Important caveat

“Active parameters” does not mean:

\boxed{\text{the rest of the model doesn't exist}}

The inactive experts still have parameters stored somewhere.

They simply are not involved in that token's expert computation.

So:

\boxed{ \text{total model memory} \neq \text{per-token active compute} }

This distinction will become extremely important when we later connect MoE to DeepSeek-R1's:

671B

total parameters but approximately:

37B

active parameters per token.

5.38.11 Now we need a router

We have many experts.

But who decides which experts receive a token?

Answer:

\boxed{\text{Router}}

The source calls the router a small learnable linear mechanism that generates scores for the experts. (Source: Build a DeepSeek Model (From Scratch))

5.38.12 Router input and output

Suppose:

x\in\mathbb R^{d_{\text{model}}}

and there are:

N

experts.

The router has parameters:

W_R\in \mathbb R^{d_{\text{model}}\times N}.

Then:

\boxed{ r=xW_R }

where:

r\in\mathbb R^N.

So for each token, the router produces one score per expert.

5.38.13 Example

Suppose:

N=4.

The router outputs:

\boxed{ r=[1.2,\;0.3,\;2.1,\;1.4] }

for a token.

Interpretation:

E_1:1.2
E_2:0.3
E_3:2.1
E_4:1.4.

These are raw router scores/logits.

They are not yet expert weights.

5.38.14 Why aren't they weights yet?

Because they can be:

\text{negative}

or:

>1.

For example:

[1.2,0.3,2.1,1.4]

does not sum to:

1.

We need normalized gating weights.

The basic source pipeline is:

\boxed{ \text{router logits} \rightarrow \text{Top-K} \rightarrow \text{softmax} }

(Source: Build a DeepSeek Model (From Scratch))

5.38.15 Step 1 — Router logits

Formally:

\boxed{ L=xW_R }

For an entire batch:

X\in\mathbb R^{T\times d_{\text{model}}}

gives:

\boxed{ L\in\mathbb R^{T\times N} }

where T is the number of tokens being routed.

This tensor-shape question is extremely exam-important.

5.38.16 Numerical shape question

Suppose:

B=4

sequences,

S=128

tokens each.

Then:

T=B\times S = 4\times128 = \boxed{512}.

Suppose:

d_{\text{model}}=4096

and:

N=64

experts.

Then:

X\in\mathbb R^{512\times4096}.

Router matrix:

W_R\in\mathbb R^{4096\times64}.

Therefore:

L=XW_R

has shape:

\boxed{ 512\times64 }.

So we have:

\boxed{ 512\text{ tokens}\times64\text{ expert scores}. }

5.38.17 Step 2 — Top-K expert selection

Now suppose:

k=2.

Our logits:

[1.2,0.3,2.1,1.4].

The two largest values are:

2.1

and:

1.4.

Therefore selected experts are:

\boxed{E_3,E_4}.

The others:

E_1,E_2

are dormant for this token.

This is the source's core sparse-routing operation. (Source: Build a DeepSeek Model (From Scratch))

5.38.18 Important: Top-K happens before softmax

This ordering matters.

We do:

\boxed{ \text{logits} \rightarrow \text{Top-K} \rightarrow \text{softmax on selected logits} }

not:

\text{softmax all experts} \rightarrow \text{Top-K}.

The source implementation explicitly does:

topk_logits, topk_idx = torch.topk(...)
gate = softmax(topk_logits)

(Source: Build a DeepSeek Model (From Scratch))

5.38.19 Step 3 — Softmax the selected logits

Our selected logits are:

[2.1,1.4].

Compute:

e^{2.1}\approx8.166

and:

e^{1.4}\approx4.055.

Sum:

8.166+4.055 = 12.221.

Therefore:

w_3= \frac{8.166}{12.221} \approx \boxed{0.668}.

And:

w_4= \frac{4.055}{12.221} \approx \boxed{0.332}.

Check:

0.668+0.332=1.

So:

\boxed{ E_3:66.8\% }

and:

\boxed{ E_4:33.2\% }.

5.38.20 Why softmax after Top-K?

The model is not saying:

“Use two experts equally.”

Instead:

\boxed{ \text{which experts} }

and:

\boxed{ \text{how much each selected expert contributes} }

are two separate decisions.

Top-K answers:

\boxed{\text{WHO?}}

Softmax answers:

\boxed{\text{HOW MUCH?}}

This is a very useful mental model.

5.38.21 Step 4 — Send the token to selected experts

Suppose the token representation is:

x.

It is sent only to:

E_3

and:

E_4.

So:

y_3=E_3(x)

and:

y_4=E_4(x).

The other outputs:

E_1(x),E_2(x)

are never computed.

That is the actual source of sparse computation.

5.38.22 Step 5 — Weighted aggregation

Now compute:

\boxed{ y= w_3y_3+w_4y_4 }

with:

w_3=0.668

and:

w_4=0.332.

The source gives exactly this concept: selected expert outputs are multiplied by their gate weights and summed. (Source: Build a DeepSeek Model (From Scratch))

5.38.23 Complete vector example

Suppose:

y_3= \begin{bmatrix} 2\\ 4 \end{bmatrix}

and:

y_4= \begin{bmatrix} 6\\ 1 \end{bmatrix}.

Then:

y = 0.668 \begin{bmatrix} 2\\ 4 \end{bmatrix} + 0.332 \begin{bmatrix} 6\\ 1 \end{bmatrix}.

First component:

0.668(2)+0.332(6)
= 1.336+1.992
= \boxed{3.328}.

Second:

0.668(4)+0.332(1)
= 2.672+0.332
= \boxed{3.004}.

So:

\boxed{ y= \begin{bmatrix} 3.328\\ 3.004 \end{bmatrix}. }

5.38.24 Why is the output shape unchanged?

Suppose:

x\in\mathbb R^{d}.

Each expert maps:

\mathbb R^d\rightarrow\mathbb R^d.

Therefore:

y_i\in\mathbb R^d.

The weighted sum:

\sum_{i\in TopK}w_i y_i

also belongs to:

\boxed{\mathbb R^d}.

Thus the MoE layer preserves the Transformer residual-stream dimension.

The source demonstrates this with a toy input/output matrix of shape:

\boxed{4\times8}.

(Source: Build a DeepSeek Model (From Scratch))

5.38.25 Batch-level shape

Suppose:

X\in\mathbb R^{B\times S\times D}.

Flatten:

X_{\text{flat}} \in \mathbb R^{(BS)\times D}.

Router:

L= X_{\text{flat}}W_R

gives:

\boxed{ (BS)\times N. }

After selecting k experts:

\boxed{ (BS)\times k }

expert indices and gating weights are retained.

After dispatch and aggregation:

\boxed{ (BS)\times D }

is restored.

Then reshape:

\boxed{ B\times S\times D. }

This is exactly the structure visible in the source implementation. (Source: Build a DeepSeek Model (From Scratch))

5.38.26 Now we can write the complete basic MoE equation

For token x:

L=Wx+b

router logits.

Then:

I(x)=TopK(L,k)

selected experts.

Then:

w_i= \frac{e^{L_i}} {\sum_{j\in I(x)}e^{L_j}}, \qquad i\in I(x).

Then:

\boxed{ MoE(x)= \sum_{i\in I(x)} w_iE_i(x) }

This compactly captures the entire basic sparse-routing mechanism.

The exact source implementation additionally contains DeepSeek's dynamic bias; we will add that in the load-balancing step. (Source: Build a DeepSeek Model (From Scratch))

5.38.27 Compare dense FFN and sparse MoE

Dense FFN
\boxed{ y=FFN(x) }

Every token executes the entire FFN.

MoE
\boxed{ y=\sum_{i\in TopK(x)}w_iE_i(x) }

Only selected experts execute.

So:

\boxed{ \text{Dense} = \text{all parameters active} }

while:

\boxed{ \text{MoE} = \text{large total capacity + sparse activation} }.

(Source: Build a DeepSeek Model (From Scratch))

5.38.28 Parameter-count numerical

Suppose a dense FFN has:

100M

parameters.

Now create:

16

experts, each with:

25M

parameters.

Total expert parameters:

16\times25M = \boxed{400M}.

If:

k=2,

then each token activates:

2\times25M = \boxed{50M}

expert parameters.

So compared with the dense model:

\boxed{4\times}

the total expert parameter capacity exists:

400/100=4.

Yet only half the dense FFN's parameters are activated per token:

50/100=0.5.

This illustrates the core MoE scaling idea.

These numbers are illustrative.

5.38.29 Compute intuition

Ignoring routing overhead, suppose one expert costs:

C.

Dense equivalent with one FFN:

C.

An MoE with N=16 experts and k=2:

\boxed{ 2C }

expert compute per token.

But the model stores:

16\times

the number of expert networks.

Thus:

\boxed{ \text{total capacity}\uparrow }

much faster than:

\boxed{ \text{per-token expert computation}\uparrow }.

That is the fundamental sparsity advantage.

5.38.30 But there is a hidden danger

Suppose the router always chooses:

E_1,E_2.

Then:

E_1,E_2

receive enormous amounts of training.

The other experts receive almost nothing.

This creates:

\boxed{\text{imbalanced routing}}.

The source describes exactly this failure mode. (Source: Build a DeepSeek Model (From Scratch))

5.38.31 Why does imbalance create a feedback loop?

Suppose early in training:

E_1

happens to perform slightly better.

Then the router favors:

E_1.

So:

E_1 \rightarrow \text{more tokens} \rightarrow \text{more training} \rightarrow \text{becomes even better} \rightarrow \text{router favors }E_1\text{ even more}.

This is:

\boxed{ \text{positive feedback} }

The source explicitly describes this self-reinforcing behavior. (Source: Build a DeepSeek Model (From Scratch))

5.38.32 Why are unused experts a problem?

An expert that is rarely selected receives few updates.

So:

\boxed{ \text{expert utilization}\downarrow }

leads to:

\boxed{ \text{expert learning}\downarrow. }

Eventually it can become effectively:

\boxed{\text{dead weight}}.

The source uses exactly this idea. (Source: Build a DeepSeek Model (From Scratch))

5.38.33 Why are overloaded experts a problem?

Suppose:

E_1

receives almost all tokens.

Then even though the other experts are idle:

E_1

becomes a computational bottleneck.

So:

\boxed{ \text{some hardware/expert capacity overloaded} }

while:

\boxed{ \text{other capacity wasted} }.

This is both a utilization and systems problem.

5.38.34 Numerical routing example

Suppose:

T=12

tokens,

N=4

experts,

and:

k=2.

Total routed assignments:

T\times k = 12\times2 = \boxed{24}.

Perfectly balanced load would be:

\frac{24}{4} = \boxed{6}

assignments per expert.

Suppose actual counts are:

[10,8,4,2].

Total:

10+8+4+2 = 24.

So Expert 1 is heavily overloaded, while Expert 4 is underused.

5.38.35 This is why “tokens per expert” matters

The raw token count is not enough.

For top-k routing, each token can contribute:

k

assignments.

So if:

T=1000

and:

k=2,

then total expert assignments are:

\boxed{2000}.

With:

N=8,

ideal average:

2000/8 = \boxed{250}

assignments per expert.

That is the baseline against which imbalance can be judged.

5.38.36 The source's simple example

The book gives a three-expert example where:

  • Expert 1 receives 2 tokens,
  • Expert 2 receives 2,
  • Expert 3 receives 4.

Thus:

2+2+4 = \boxed{8}

total routed assignments.

Average:

8/3 = \boxed{2.67}.

(Source: Build a DeepSeek Model (From Scratch))

So relative to the average:

E_1:2-2.67=-0.67
E_2:2-2.67=-0.67
E_3:4-2.67=+1.33.

This tells us:

\boxed{ E_1,E_2\text{ underloaded} }

and:

\boxed{ E_3\text{ overloaded}. }

5.38.37 Another key concept: expert capacity

Before we discuss DeepSeek's balancing method, understand the older hard constraint.

Each expert can be given a maximum number of tokens it is allowed to process in a batch.

The source calls this:

\boxed{\text{Expert Capacity}}.

If more tokens are routed to an expert than its capacity:

\boxed{\text{excess tokens are dropped for that forward pass}}

in the traditional scheme. (Source: Build a DeepSeek Model (From Scratch))

5.38.38 Capacity formula

The source describes capacity conceptually as:

\boxed{ \text{capacity} = \text{fair-share tokens} \times \text{capacity factor} }

where fair share is:

\frac{\text{tokens per batch}\times k} {\text{number of experts}}.

So:

\boxed{ C = \frac{T\,k}{N} \times CF }

where CF is the capacity factor.

The exact details can vary by implementation; this is the formula structure given in the source discussion.

5.38.39 Numerical capacity example

Suppose:

T=1000
k=2
N=8

and:

CF=1.25.

Fair share:

\frac{1000\times2}{8} = 250.

Capacity:

250\times1.25 = \boxed{312.5}.

In an implementation requiring integer capacity, this would need an appropriate rounding convention.

The important idea is:

\boxed{ \text{capacity factor gives a buffer above ideal balance} }.

The source specifically emphasizes that CF>1 gives flexibility for moderate imbalance. (Source: Build a DeepSeek Model (From Scratch))

5.38.40 Why is capacity only a partial solution?

Because it says:

“Don't process more than this many tokens.”

It does not directly teach the router:

“Please distribute tokens more evenly.”

So capacity is:

\boxed{\text{hard guardrail}}

whereas load-balancing losses/biases are:

\boxed{\text{routing-control mechanisms}}.

The source explicitly distinguishes these. (Source: Build a DeepSeek Model (From Scratch))

5.38.41 Complete basic MoE forward pass

Now we can finally write it as one sequence.

Given:

X\in\mathbb R^{B\times S\times D}
Step 1 — Flatten
X_f\in \mathbb R^{BS\times D}.
Step 2 — Router
L=X_fW_R

giving:

BS\times N.
Step 3 — Select
I=TopK(L,k).
Step 4 — Normalize
G=\operatorname{softmax}(L_I).
Step 5 — Dispatch

Send each token only to its selected experts.

Step 6 — Expert computation
Y_i=E_i(X_i).
Step 7 — Weighted combine
Y_t= \sum_{i\in I_t} G_{t,i}Y_{t,i}.
Step 8 — Reshape
Y\in \mathbb R^{B\times S\times D}.

This is the complete basic sparse MoE mechanism described in the source. (Source: Build a DeepSeek Model (From Scratch))

5.38.42 Where DeepSeek's architecture will eventually modify this

The basic MoE is not yet DeepSeek-MoE in its full form.

The source adds three major innovations:

\boxed{ \text{1. Fine-Grained Expert Segmentation} }
\boxed{ \text{2. Shared Expert Isolation} }
\boxed{ \text{3. Auxiliary-Loss-Free Load Balancing} }

The source identifies these as the three main DeepSeek innovations, with the third introduced in DeepSeek-V3.

We will derive each separately rather than mixing them into the basic routing mechanism.

5.38.43 Why the first innovation is necessary: knowledge hybridity

Suppose we only have:

8

experts.

The training data contains:

\text{Python} + \text{law} + \text{history} + \text{mathematics} + \text{conversation}.

One expert may receive tokens from all of these domains.

So its parameters have to become a mixture of:

\boxed{ \text{many unrelated competencies} }.

The source calls this:

\boxed{\text{Knowledge Hybridity}}.

(Source: Build a DeepSeek Model (From Scratch))

5.38.44 Why the second problem is the opposite: redundancy

Suppose:

E_1

specializes in Python and:

E_2

specializes in medicine.

Both still need:

\text{basic language grammar}

and:

\text{common foundational knowledge}.

So both experts may redundantly learn the same common knowledge.

The source calls this:

\boxed{\text{Knowledge Redundancy}}.

Therefore the two problems are:

\boxed{ \text{too much mixing} }

and:

\boxed{ \text{too much duplication}. }

This motivates the next DeepSeek-MoE innovations.

5.38.45 One very important systems-level interpretation

A dense model asks:

\boxed{ \text{How do I give every token the same computational pathway?} }

An ordinary MoE asks:

\boxed{ \text{Which specialized pathway should this token use?} }

DeepSeek-MoE goes further and asks:

\boxed{ \text{How do I make experts truly specialized while still preserving common knowledge and balanced hardware utilization?} }

That is the research problem behind the next stage.

5.38.48 Final mental model

The entire basic MoE mechanism is:

\boxed{ x }
\downarrow
\boxed{ \text{Router} }

produces:

\boxed{ \text{one score per expert} }
\downarrow
\boxed{ \text{Top-K} }

decides:

\boxed{\text{which experts}}
\downarrow
\boxed{ \text{Softmax} }

decides:

\boxed{\text{how much each selected expert contributes}}
\downarrow
\boxed{ \text{Sparse dispatch} }

only selected experts execute.

\downarrow
\boxed{ \text{Weighted sum} }

produces the token's output.

So the central equation is:

\boxed{ MoE(x) = \sum_{i\in TopK(x)} g_iE_i(x) }

(Source: Build a DeepSeek Model (From Scratch))

But the basic mechanism creates a critical problem:

\boxed{ \text{Who keeps the experts balanced?} }

Because if one expert receives most of the tokens:

\boxed{ \text{training becomes inefficient} + \text{some experts become under-trained} + \text{hardware becomes imbalanced}. }
