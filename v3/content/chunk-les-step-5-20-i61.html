Step-by-step derivation

Step 5.20 — ReTool: Reinforcement Learning for Strategic Tool Use

Plan node: I9 · chat order #61

We now move to the next major topic in your supplied material:

\boxed{\text{ReTool — Reinforcement Learning for Strategic Tool Use in LLMs}}

This is a very natural continuation of the DeepSeek-R1 story.

We just studied:

\boxed{ \text{text-only reasoning} }

with DeepSeek-R1.

ReTool asks a more advanced question:

What happens when the model is allowed to leave the text stream, execute real code, read the result, and then continue reasoning?

The supplied ReTool slides frame this as the transition from reasoning in text to reasoning with external computational feedback. (Source: retool-slides)

5.20.1 First understand the problem ReTool is solving

DeepSeek-R1 can reason for a long time using text:

Let me calculate...
3 × 17 = 51
51 + 29 = 80
...

This can work well.

But consider a problem requiring:

\boxed{ \text{exact arithmetic over 1000 cases} }

or:

\boxed{ \text{solving a complicated system of equations} }

or:

\boxed{ \text{geometric computation} }

or:

\boxed{ \text{searching many candidate values} }.

The model has to perform all of this through token generation.

The slides point out the key weakness:

\boxed{ \text{one arithmetic mistake can contaminate everything afterward} }

because the model is effectively performing computation through its own token stream. (Source: retool-slides)

5.20.2 The fundamental distinction

Text reasoning:

\boxed{ \text{reason} \rightarrow \text{write answer} }

ReTool reasoning:

\boxed{ \text{reason} \rightarrow \text{call tool} \rightarrow \text{observe real result} \rightarrow \text{continue reasoning} }

This is the key conceptual jump.

5.20.3 Why a code interpreter helps

Suppose the model needs:

1234567\times891011.

A text-only model might internally generate:

1234567 × 891011 = ...

and potentially make a bookkeeping error.

With a code interpreter:

1234567 * 891011

the external environment computes the result.

Then the model receives:

109950...

and continues reasoning.

So the computation has moved from:

\boxed{\text{LLM token prediction}}

to:

\boxed{\text{deterministic external execution}}.

5.20.4 But ReTool is NOT simply “give the model a calculator”

This distinction is extremely important.

The goal is not:

Always call the calculator.

The goal is:

Learn when using a tool is worth it.

The slides explicitly state that nothing tells the model when to use code; the timing itself is something RL must teach. (Source: retool-slides)

Therefore the target behavior is:

\boxed{ \text{sometimes use code} }

and:

\boxed{ \text{sometimes do not use code} }.

5.20.5 Tool use becomes a decision problem

Imagine two questions.

Question A

What is the capital of South Korea?

The model already knows:

\boxed{\text{Seoul}}

No computation is necessary.

Question B

What is 1234\times5678?

The model can invoke:

\boxed{\text{calculator/code}}

because exact computation is useful.

The related agent/tool-use material shows exactly this kind of selective tool choice: answer directly when the model has the needed information, call a tool when external computation is beneficial. (Source: Build an AI Agent (From Scratch))

ReTool takes that idea and trains the decision itself through RL.

5.20.6 The most important change: what is a rollout?

This is where ReTool becomes mathematically interesting.

Earlier, in text-only GRPO/RL, a rollout was approximately:

\boxed{ o_1,o_2,\ldots,o_T }

all produced by the language model.

Now the rollout becomes an interleaved trajectory.

For example:

\boxed{ t_1 \oplus c_1 \oplus f_1 \oplus t_2 \oplus c_2 \oplus f_2 \oplus o }

where:

  • t_i = model-generated reasoning text,
  • c_i = model-generated code,
  • f_i = interpreter feedback,
  • o = final answer.

The slides explicitly describe the rollout this way. (Source: retool-slides)

5.20.7 Let's make that concrete

Suppose the task is:

Find a number satisfying some complicated condition.

The model might generate:

I should search the candidate space.
<code>
for x in range(1,10000):
    ...
</code>

Generation pauses.

The sandbox executes the code and returns:

<interpreter>
candidate = 699
</interpreter>

Then the model continues:

The computation gives 699. I should verify the condition...

Then perhaps:

<code>
...
</code>

followed by another interpreter result.

Finally:

\boxed{699}

The entire thing is treated as one trajectory.

That is the core ReTool idea. (Source: retool-slides)

5.20.8 Three kinds of content now exist inside the trajectory

This is an exam-important distinction.

Type 1 — Model reasoning
\boxed{\text{generated by policy}}
Type 2 — Model code
\boxed{\text{generated by policy}}
Type 3 — Interpreter feedback
\boxed{\text{generated by environment}}

So unlike ordinary text-only RL:

\boxed{ \text{not every token in the trajectory is generated by the policy} }

That fact drives several important engineering decisions later.

5.20.9 Why does generation have to pause?

Suppose the model generates:

<code>
print(2+2)
</code>

The model cannot generate the output itself, because that output is supposed to come from the external interpreter.

So when:

\boxed{\texttt{</code>}}

is detected:

\boxed{ \text{generation pauses} }

and the code is sent to the sandbox.

The returned result is then inserted into the context, and generation resumes. (Source: retool-slides)

5.20.10 This produces a turn-by-turn rollout

Think of it like:

\boxed{ \text{LLM turn} \rightarrow \text{environment turn} \rightarrow \text{LLM turn} \rightarrow \text{environment turn} \rightarrow\cdots }

This is already very close to the structure of an agent-environment interaction.

That is why the slides connect ReTool to the broader concept of agentic RL. (Source: retool-slides)

5.20.11 ReTool vs DeepSeek-R1

This is one of the most important comparisons in the course.

DeepSeek-R1

Trajectory:

\boxed{ \text{long text reasoning} }

External environment:

\boxed{ \text{none during the reasoning trace} }

Reward:

\boxed{ \text{final correctness} }

Optimization:

\boxed{ \text{GRPO} }
ReTool

Trajectory:

\boxed{ \text{text} + \text{code} + \text{interpreter feedback} }

External environment:

\boxed{ \text{real code sandbox} }

Reward:

\boxed{ \text{final correctness} }

Optimization:

\boxed{ \text{PPO} }

The ReTool slides explicitly emphasize that ReTool uses plain PPO rather than GRPO. (Source: retool-slides)

5.20.12 Why is ReTool using PPO rather than GRPO?

Recall from our GRPO lessons:

GRPO avoids a learned value model by estimating a baseline from multiple sampled responses.

PPO normally uses:

\boxed{ V_\phi(s_t) }

a learned value function.

The ReTool slides explicitly say:

\boxed{\text{NOT GRPO}}

and state that ReTool uses standard PPO with a learned value function. (Source: retool-slides)

5.20.13 PPO review

For a policy:

\pi_\theta

the probability ratio is:

\boxed{ r_t(\theta) = \frac{ \pi_\theta(o_t\mid q,o_{<t};CI) }{ \pi_{\text{old}}(o_t\mid q,o_{<t};CI) } }

The CI denotes the code-interpreter interaction context.

The policy objective uses:

\boxed{ \min \left( r_tA_t, \operatorname{clip}(r_t,1-\epsilon,1+\epsilon)A_t \right) }

which is the same basic clipping mechanism we learned for PPO/GRPO. (Source: retool-slides)

5.20.14 What changes is not the ratio formula

This is a crucial conceptual point.

The PPO ratio itself is not fundamentally new.

What changes is:

\boxed{\textbf{the trajectory on which the ratio is evaluated}}

Previously:

o_t

was just another generated token.

Now the trajectory contains:

\boxed{ \text{text} + \text{code} + \text{environment feedback} }

So ReTool expands the meaning of the rollout without fundamentally replacing the PPO machinery. (Source: retool-slides)

5.20.15 Why does credit assignment become harder?

Suppose the final answer is correct:

R=+1.

The model may have taken this path:

reason
→ write code
→ code executes
→ read result
→ revise reasoning
→ write second code block
→ correct answer

Which model action deserves credit?

Was it:

  • writing the first code block?
  • deciding to call the tool?
  • reading the interpreter output correctly?
  • correcting an error?
  • the final reasoning?

ReTool must propagate the success signal through this longer trajectory.

The slides explicitly highlight that credit must flow through the turns where the model decided to use the sandbox, not merely through ordinary text tokens. (Source: retool-slides)

5.20.16 This is the key difference from ordinary reasoning RL

Text-only RL:

\boxed{ \text{good final answer} \rightarrow \text{credit reasoning tokens} }

ReTool:

\boxed{ \text{good final answer} \rightarrow \text{credit a strategy containing tool decisions} }

So the model is learning:

\boxed{ \textbf{when and how to use computation} }

not merely:

\boxed{ \textbf{how to write reasoning}. }

5.20.17 Before RL, ReTool needs a “cold start”

This is a very important engineering step.

A pretrained model does not automatically know the protocol:

<code>...</code>

followed by:

<interpreter>...</interpreter>

and then continued reasoning.

The slides say RL works by exploring variations of behavior the model already has, so the base model first needs the ability to use the protocol at all. (Source: retool-slides)

Therefore:

\boxed{ \text{Cold-start SFT} \rightarrow \text{RL} }

5.20.18 What does cold-start SFT teach?

Very important:

\boxed{ \text{protocol mechanics} }

not necessarily:

\boxed{ \text{optimal tool-use strategy} }.

The slides explicitly distinguish these.

The cold-start stage teaches things like:

  • where code goes,
  • when interpreter output appears,
  • how to continue after feedback,
  • how the formatting protocol works.

Then RL learns:

\boxed{ \text{when using the tool is actually useful} }.

(Source: retool-slides)

5.20.19 Where does the cold-start data come from?

The slides describe:

Step A

Collect verified text-only reasoning traces:

D_{\text{init}}.

These can be filtered by human review and by DeepSeek-R1.

Step B

Automatically transform those traces by replacing appropriate manual calculations with executable code and its real output.

This produces:

\boxed{ D_{\text{CI}} }

the code-augmented dataset.

Step C

Keep traces passing:

\boxed{ \text{format check} \land \text{answer correctness} }.
Step D

SFT the base model on this data.

(Source: retool-slides)

5.20.20 A crucial idea: failed tool attempts can remain

The slides specifically state that the transformation can leave surrounding reasoning, including failed attempts, untouched.

This matters because the eventual RL policy can learn what happens after failure.

For example:

<code>
greedy(...)
</code>

then:

NameError

then:

Oops, I need to define the function.

then corrected code.

This sets up exactly the kind of environment interaction that later RL can exploit. (Source: retool-slides)

5.20.21 ReTool's reward is surprisingly simple

You might expect:

R= R_{\text{correct}} + R_{\text{code}} + R_{\text{format}} + R_{\text{efficiency}}.

But the slides say the reward is deliberately much simpler.

For final answer \hat a and ground truth a:

\boxed{ R(a,\hat a) = \begin{cases} +1,&\text{if correct}\\ -1,&\text{otherwise} \end{cases} }

The correctness check is rule-based. (Source: retool-slides)

5.20.22 Why isn't successful code execution rewarded?

Suppose the reward gave:

+0.2

whenever code successfully executed.

The model could exploit this.

It could generate useless code like:

print("hello")

which executes successfully.

Then:

R_{\text{code}}=+0.2

without helping solve the problem.

That creates a reward-hacking opportunity.

The slides therefore deliberately omit a separate “successful execution” reward. (Source: retool-slides)

5.20.23 The principle behind this reward design

The rule is:

\boxed{ \text{Don't reward tool use for its own sake.} }

Instead:

\boxed{ \text{tool use only receives indirect credit if it helps produce a correct answer.} }

So the model must learn:

\boxed{ \text{useful tool calls} }

rather than:

\boxed{ \text{many tool calls}. }

5.20.24 This is very similar to our earlier format-reward lesson

Previously, we studied why adding:

R_{\text{format}}

can create undesirable optimization pressure.

Here the same principle appears in another form.

If we reward:

\text{code execution}

directly, the model may optimize for:

\text{code execution}

rather than:

\text{problem solving}.

Therefore:

\boxed{ \text{reward should measure the desired outcome, not an easy-to-game proxy} }.

5.20.25 Numerical example: reward hacking

Suppose:

R_{\text{correct}}= \begin{cases} +1\\ -1 \end{cases}

and someone adds:

R_{\text{code}}=+0.2

for executable code.

Then a wrong answer with successful code receives:

-1+0.2 = \boxed{-0.8}.

A model can improve average reward by learning to generate executable code even when it does not solve the problem.

That is precisely why ReTool avoids this additional reward.

5.20.26 The rollout now becomes a hybrid trajectory

Let's write one formally.

Suppose:

\tau= [t_1,t_2,c_1,f_1,t_3,c_2,f_2,o].

The policy generates:

t_1,t_2,c_1,t_3,c_2,o

while the environment produces:

f_1,f_2.

So:

\boxed{ \tau = \tau_{\text{policy}} \oplus \tau_{\text{environment}} }

conceptually.

This is different from ordinary language-model RL, where essentially the whole token trajectory comes from the policy.

5.20.27 Exam numerical: trajectory length

Suppose the model generates:

1200

reasoning/code tokens.

The interpreter produces:

300

feedback tokens.

The final answer contributes:

20

model-generated tokens.

Then total context/trajectory tokens:

1200+300+20 = \boxed{1520}.

The important insight is that:

\boxed{300}

tokens are environment-generated.

5.20.28 This creates a major training problem

Should the model be trained to predict the interpreter's output?

No.

Why?

Because:

\boxed{ \text{the model did not generate it} }

The interpreter generated it.

This leads to one of ReTool's most important engineering details:

\boxed{ \text{mask interpreter tokens from the loss} }

The slides explicitly state this. (Source: retool-slides)

5.20.29 Why must interpreter tokens be masked?

Suppose the sandbox outputs:

42

The student/policy did not choose:

42.

The environment did.

If the loss forced the model to predict that token, the model would be penalized or rewarded for something it did not actually control.

That corrupts the policy-learning signal.

So:

\boxed{ \text{loss applies to policy-generated tokens} }

and not:

\boxed{ \text{environment-generated tokens} }.

5.20.30 This is a very important exam question

Question:

Why are interpreter tokens masked in ReTool?

Answer:

Because those tokens come from the external sandbox rather than from the policy. Including them in the policy loss would train the model to predict environment-generated text and would interfere with the learning signal for the model's own actions. (Source: retool-slides)

5.20.31 Second engineering trick: KV-cache reuse

We already studied KV caching.

Normally, when the model continues generation, it can reuse:

K,V

for previous tokens.

ReTool exploits this.

When the code executes:

\boxed{ \text{everything generated so far is already cached} }

Then the interpreter returns new feedback.

Only the new feedback tokens need new KV computation before generation resumes. (Source: retool-slides)

5.20.32 Why is this especially important in ReTool?

Because otherwise every tool call would potentially force:

\boxed{ \text{recompute the entire prefix} }

which would be very expensive.

With KV reuse:

\boxed{ \text{old prefix cache} + \text{new feedback cache} }

allows generation to continue efficiently.

5.20.33 Numerical KV-cache intuition

Suppose before the code call the context has:

10,000

tokens.

Interpreter returns:

200

new tokens.

Without cache reuse, you might conceptually recompute attention-related states for roughly:

10,200

context tokens.

With reuse:

\boxed{ \text{reuse existing 10,000} }

and only process:

\boxed{200}

new tokens for the cache extension.

This is a conceptual efficiency illustration; actual implementation cost also depends on attention kernels and architecture.

5.20.34 There is a third engineering component: asynchronous sandbox execution

The interpreter may take time.

Suppose one model rollout executes:

300\text{ ms}

worth of code while another takes:

5\text{ s}.

If all rollouts share one synchronous execution path, the fast rollouts may sit idle waiting for the slow one.

The slides therefore describe an asynchronous sandbox pool so that slow executions do not stall the rest of training. (Source: retool-slides)

5.20.35 Why is this a distributed-systems problem?

Because ReTool has at least two computational systems:

\boxed{\text{policy inference}}

and:

\boxed{\text{code-execution environment}}.

They interact asynchronously.

You therefore care about:

  • scheduling,
  • queueing,
  • isolation,
  • failures,
  • timeout handling,
  • result routing,
  • cache state.

The source specifically mentions the asynchronous sandbox pool as a scale-enabling component. (Source: retool-slides)

Put everything together:

5.20.37 ReTool has changed the meaning of “reasoning”

Before:

\boxed{ \text{reasoning} = \text{generating useful text} }

After ReTool:

\boxed{ \text{reasoning} = \text{generating text + choosing actions + interpreting feedback} }

This is the beginning of tool-augmented reasoning.

5.20.38 The deeper RL interpretation

We can write:

\boxed{ s_t = \text{current problem + reasoning history + tool feedback} }

The action a_t can be:

\boxed{ \text{text token} }

or part of:

\boxed{ \text{code/tool invocation} }.

The environment then returns:

\boxed{ f_{t+1} = \text{interpreter feedback} }.

So:

\boxed{ (s_t,a_t) \rightarrow s_{t+1} }

now includes external computation.

This is much closer to classical environment-interaction RL than ordinary text-only generation.

5.20.39 The key difference from ordinary tool calling

Ordinary tool calling often works like:

\text{LLM} \rightarrow \text{tool} \rightarrow \text{answer}.

ReTool allows:

\boxed{ \text{reason} \rightarrow \text{tool} \rightarrow \text{observe} \rightarrow \text{reason} \rightarrow \text{tool} \rightarrow \text{observe} \rightarrow \text{answer} }

and crucially:

\boxed{ \text{RL decides whether and when to call the tool}. }

That timing is the learned skill.

5.20.44 Exam conceptual bank

Q1. What is novel about ReTool?

It makes the rollout a hybrid trajectory containing model-generated reasoning/code plus real external tool feedback, and uses RL to learn when and how to use the tool. (Source: retool-slides)

Q2. Why not reward successful code execution directly?

Because the model could generate arbitrary code that runs successfully without helping solve the task, creating reward hacking. (Source: retool-slides)

Q3. Why mask interpreter tokens?

Because the interpreter generated them, not the policy. Training the policy to predict them would corrupt the policy-learning signal. (Source: retool-slides)

Q4. Why does ReTool use PPO rather than GRPO?

The supplied deck explicitly specifies PPO with a learned value function rather than GRPO's group-relative baseline. (Source: retool-slides)

Q5. Why is cold-start SFT needed?

The model first needs to learn the mechanics of the code/interpreter protocol so that RL can explore the strategic question of when tool use is useful. (Source: retool-slides)

5.20.45 The deepest takeaway

DeepSeek-R1 taught us:

\boxed{ \text{spend more computation inside the model's reasoning process} }

ReTool adds:

\boxed{ \text{spend computation outside the model when that is advantageous} }

So the model learns a new decision:

\boxed{ \text{Should I continue reasoning in tokens, or should I invoke a computational tool?} }

That creates the transition:

\boxed{ \text{LLM reasoning} \rightarrow \text{tool-augmented reasoning} \rightarrow \text{agentic RL} }

and that is why ReTool is an important next step after DeepSeekMath and DeepSeek-R1. (Source: retool-slides)
