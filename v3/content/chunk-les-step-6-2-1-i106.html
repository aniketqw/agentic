Motivation

Preserve correct position information during both full-sequence training and cached generation.

Prerequisites

  • 2-D rotation matrices
  • Complex numbers
  • Broadcasting and cache offsets

Notation and units

  • theta_j=10000^(-2j/d_r)
  • p: absolute position
  • offset: number of cached positions

Assumptions

  • Adjacent coordinate-pair convention
  • Even rotating width
  • Offset+sequence length lies within the frequency table

Step-by-step derivation

  1. For pair (a,b), use complex z=a+ib and rotation exp(i*p*theta_j).
  2. Expand the product to obtain (a*cos(angle)-b*sin(angle),a*sin(angle)+b*cos(angle)); this is exactly a real rotation matrix.
  3. Construct theta for j=0..d_r/2-1; form the outer product of positions and theta.
  4. A precomputed [L,d_r/2] table becomes [1,1,S,d_r/2] after choosing offset:offset+S so it broadcasts over batch and heads.
  5. At cached offset P, a local row j must rotate using P+j, never simply j. Prefix-encoded keys are not rotated again.
  6. Orthogonal rotation preserves pair norms and creates relative-position dependence because R(p)^T R(q)=R(q-p).
  7. Pairing conventions can differ across implementations; adjacent pairing and split-half pairing require consistent weight interpretation.

    We now take the RoPE mathematics we already derived earlier and see exactly how the source turns it into executable PyTorch code.

    The source introduces RotaryPositionalEncoding as the first self-contained component of model.py. It precomputes the rotation frequencies and applies them to the Query/Key tensors. In the Mini-DeepSeek implementation, the important addition is position_offset, which allows the same RoPE module to work when inference is using a KV cache. (Source: Build a DeepSeek Model (From Scratch))

    1. First, remember what RoPE is doing

    We already know the mathematical idea.

    Instead of adding a positional vector to a token representation, RoPE rotates pairs of coordinates of Query and Key according to their position.

    For one 2-D pair:

    \begin{bmatrix} x_1'\\ x_2' \end{bmatrix} = \begin{bmatrix} \cos\theta &-\sin\theta\\ \sin\theta & \cos\theta \end{bmatrix} \begin{bmatrix} x_1\\ x_2 \end{bmatrix}.

    Equivalently:

    (x_1+i x_2)e^{i\theta}.

    That second form is exactly what this implementation exploits.

    So the key idea is:

    \boxed{ \text{2 real dimensions} \leftrightarrow \text{1 complex number} }

    and then:

    \boxed{ \text{rotation} = \text{complex multiplication}. }

    The source explicitly says that the implementation applies the rotations efficiently using complex-number multiplication. (Source: Build a DeepSeek Model (From Scratch))

    2. What shape reaches RoPE?

    This is important before reading the code.

    In DeepSeekAttention, the position-path Query and Key are reshaped as:

    [B,S,H,d_{\text{rope}}]

    and then transposed to:

    \boxed{ [B,H,S,d_{\text{rope}}] }

    before being passed to RoPE. The source's DeepSeekAttention code shows this exact reshape/transposition. (Source: Build a DeepSeek Model (From Scratch))

    So RoPE receives:

    x
shape = [B, H, S, d_rope]

    where:

    • B = batch size
    • H = number of heads
    • S = sequence length
    • d_{\text{rope}} = dimensions receiving positional rotation

    For the default ModelArgs:

    H=8,\qquad d_{\text{rope}}=32.

    So conceptually:

    \boxed{ x\in\mathbb R^{B\times8\times S\times32}. }

    4. Step A — Construct the frequency vector theta

    The source uses:

    theta = 1.0 / (
    10000 ** (
        torch.arange(0, d_head, 2).float()
        / d_head
    )
)

    (Source: Build a DeepSeek Model (From Scratch))

    Let's unpack this carefully.

    4.1 torch.arange(0, d_head, 2)

    Suppose:

    d_{\text{head}}=8.

    Then:

    torch.arange(0, 8, 2)

    produces:

    [0,2,4,6].

    Why every 2 dimensions?

    Because RoPE groups dimensions into pairs:

    (0,1)
(2,3)
(4,5)
(6,7)

    Each pair gets a rotation.

    Therefore there are:

    \frac{d_{\text{head}}}{2}

    rotation frequencies.

    For d_{\text{head}}=32:

    \frac{32}{2}=16.

    So:

    \boxed{\theta\in\mathbb R^{16}}.

    5. Why do different pairs need different frequencies?

    This comes from the original RoPE construction.

    We don't rotate every dimension pair at the same angular speed.

    Instead:

    \theta_j = 10000^{-2j/d_{\text{head}}}.

    The source expresses the same idea in reciprocal form:

    \boxed{ \theta_j = \frac{1} {10000^{2j/d_{\text{head}}}} }

    through:

    1.0 / (10000 ** (...))

    (Source: Build a DeepSeek Model (From Scratch))

    This gives multiple rotation frequencies.

    Intuitively:

    dimension pair
     ↓
frequency

pair 1  → relatively fast
pair 2  → slower
pair 3  → slower still
...

    This multi-frequency representation allows the positional encoding to represent different positional scales.

    That is the mathematical reason the frequency vector exists.

    self.register_buffer('theta', theta)

    (Source: Build a DeepSeek Model (From Scratch))

    This is a PyTorch implementation detail.

    theta is not a learnable parameter.

    It is fixed.

    Learnable:

    biases
    ...

    theta

    Using register_buffer makes theta part of the module's tensor state without making it trainable.

    That distinction is important:

    \boxed{ \theta\text{ is computed, not learned}. }

    7. Step B — Precompute all positions

    The source then creates:

    positions = torch.arange(max_seq_len)

    Suppose:

    max\_seq\_len=8.

    Then:

    positions=[0,1,2,3,4,5,6,7].

    These are the absolute token positions for which we will prepare rotations.

    8. Construct the phase matrix

    The source uses:

    freqs = torch.outer(positions, self.theta)

    (Source: Build a DeepSeek Model (From Scratch))

    This creates:

    \boxed{ freqs\in\mathbb R^{L\times d_{\text{head}}/2} }

    where:

    L=max\_seq\_len.

    For our example:

    8\times4.
    What does one element mean?

    The element:

    freqs[p,j]

    is:

    \boxed{ p\cdot\theta_j }

    where:

    • p = token position
    • j = rotary dimension pair.

    So position controls how far we rotate, while \theta_j determines the frequency for that dimension pair.

    Therefore:

    \boxed{ \text{rotation angle} = \text{position}\times\text{frequency}. }

    9. Why use an outer product?

    Suppose:

    positions= \begin{bmatrix} 0\\ 1\\ 2 \end{bmatrix}

    and:

    \theta= \begin{bmatrix} \theta_0&\theta_1 \end{bmatrix}.

    Then:

    positions\otimes\theta = \begin{bmatrix} 0\theta_0&0\theta_1\\ 1\theta_0&1\theta_1\\ 2\theta_0&2\theta_1 \end{bmatrix}.

    So every position gets every frequency.

    That produces the complete table of phases we need.

    10. Convert phase angles to complex rotations

    Now comes the clever implementation.

    The source writes:

    freqs_cis = torch.polar(
    torch.ones_like(freqs),
    freqs
)

    and registers it as:

    self.register_buffer(
    'freqs_cis',
    freqs_cis,
    persistent=False
)

    (Source: Build a DeepSeek Model (From Scratch))

    10.1 What does torch.polar mean?

    In complex-number mathematics:

    re^{i\theta}

    has:

    \text{magnitude}=r

    and:

    \text{angle}=\theta.

    The source uses magnitude:

    r=1.

    Therefore:

    \boxed{ e^{i\theta} = \cos\theta+i\sin\theta. }

    So torch.polar(1, theta) constructs exactly the complex-number rotation factor needed by RoPE.

    11. Therefore freqs_cis represents the rotation itself

    This is an important mental shortcut.

    We can think of:

    \boxed{ freqs = \text{angles} }

    then:

    \boxed{ freqs\_cis = e^{i\,freqs} = \text{actual complex rotation factors}. }

    So during initialization the model performs the expensive-looking trigonometric preparation once.

    Then the forward pass can simply multiply by the precomputed rotation factors.

    12. Why precompute?

    Suppose the model processes thousands of sequences.

    We don't need to repeatedly calculate:

    \cos(p\theta)

    and:

    \sin(p\theta)

    from scratch for every call.

    Instead:

    Initialization
     ↓
calculate theta
     ↓
calculate all position phases
     ↓
calculate complex rotation factors
     ↓
store them

    Then:

    Forward pass
     ↓
take required positions
     ↓
multiply

    This is an implementation optimization.

    The source explicitly describes the helper as pre-computing the necessary rotation frequencies. (Source: Build a DeepSeek Model (From Scratch))

    18. Why do we need position_offset?

    This connects directly to our earlier KV-cache discussion.

    Imagine the model has already generated:

    100

    tokens.

    Now it receives one new token.

    That new token is physically represented by a tensor of sequence length:

    S=1.

    But it is not position 0.

    It is position:

    100.

    So if we simply used:

    freqs_cis[:1]

    we would incorrectly rotate the new token using the position-0 rotation.

    Instead:

    position\_offset=100.

    Then:

    freqs_cis[100:101]

    is selected.

    Therefore the new token receives the positional rotation corresponding to absolute position 100.

    This is exactly why the source says position_offset is crucial for correctly applying positional encodings when cached inference processes a new token at a time. (Source: Build a DeepSeek Model (From Scratch))

    21. Step E — The actual RoPE operation

    Finally:

    x_rotated = x_complex * freqs_cis

    Remember:

    x_{\text{complex}} = a+ib

    and:

    freqs\_cis = e^{i\theta} = \cos\theta+i\sin\theta.

    Then:

    (a+ib)e^{i\theta}

    is exactly the RoPE rotation.

    So the whole complicated-looking implementation eventually reduces to:

    \boxed{ \text{complex multiplication} = \text{2-D rotation}. }

    \boxed{ q_r \rightarrow \operatorname{RoPE}(q_r) }

    and:

    \boxed{ k_r \rightarrow \operatorname{RoPE}(k_r). }

    The content path does not get this RoPE transformation.

    This is the "decoupled" part of the architecture.

    25. Why Query and Key, but not Value?

    The source's architecture separates the two roles:

    Content Path:
q_c, k_c, v_c
      │
      └── semantic/content information

Position Path:
q_r, k_r
      │
      └── positional information

    The two attention score components are then:

    \text{content\_scores} = \frac{q_c k_c^T}{\sqrt{d_{\text{head}}}}

    and:

    \text{position\_scores} = \frac{q_r k_r^T}{\sqrt{d_{\text{rope}}}}.

    Then:

    \boxed{ \text{attn\_scores} = \text{content\_scores} + \text{position\_scores}. }

    The source shows this combination in the attention implementation. (Source: Build a DeepSeek Model (From Scratch))

    So RoPE contributes specifically to the position-dependent part of the attention score.

    26. Training vs cached inference

    This is where the new position_offset becomes especially useful.

    Training

    The full sequence is processed at once:

    position\_offset=0.

    Therefore:

    token 0 → position 0
token 1 → position 1
token 2 → position 2
...
    Cached inference

    Suppose 256 tokens are already cached.

    Then:

    position\_offset=256.

    A new token with local sequence length:

    S=1

    gets:

    position=256.

    So the tensor may physically have only one token:

    [B,H,1,d_{\text{rope}}],

    but RoPE correctly interprets it as the 256th position.

    That is a subtle but critical distinction:

    \boxed{ \text{local tensor length} \neq \text{absolute position}. }

    position_offset bridges those two.

    27. A numerical mini-example

    Suppose:

    d_{\text{rope}}=4.

    Then we have two pairs:

    (x_0,x_1)

    and:

    (x_2,x_3).

    Suppose the rotation angles at a particular position are:

    \theta_0,\theta_1.

    The complex representation is:

    z_0=x_0+i x_1
    z_1=x_2+i x_3.

    RoPE creates:

    r_0=e^{i\theta_0}
    r_1=e^{i\theta_1}.

    Then:

    z_0'=z_0r_0

    and:

    z_1'=z_1r_1.

    Convert back to real values and we obtain the rotated 4-dimensional vector.

    Thus the implementation is mathematically identical to performing two separate 2\times2 rotation matrices.

    28. Why this implementation is elegant

    Instead of writing something like:

    \begin{bmatrix} \cos\theta &-\sin\theta\\ \sin\theta &\cos\theta \end{bmatrix}

    for every pair, every token, every head, the source uses:

    \boxed{ \text{pair dimensions} \rightarrow \text{complex numbers} \rightarrow \text{one multiplication} \rightarrow \text{real dimensions}. }

    So the code is compact while directly matching the mathematical derivation.

    29. The earlier Chapter 3 implementation vs the Chapter 6 version

    This is worth explicitly distinguishing.

    The earlier source implementation had:

    def forward(self, x):

    and simply selected:

    freqs_cis[:seq_len]

    (Source: Build a DeepSeek Model (From Scratch))

    The Chapter 6 Mini-DeepSeek version changes this to:

    def forward(
    self,
    x,
    position_offset=0
):

    and selects:

    self.freqs_cis[
    position_offset:
    position_offset + seq_len
]

    (Source: Build a DeepSeek Model (From Scratch))

    So the architecture has not changed mathematically.

    The implementation has been extended for cached inference.

    That is an excellent example of the distinction between:

    \boxed{ \text{algorithm} }

    and:

    \boxed{ \text{production-aware implementation}. }

    30. Final mental model

    When you see this:

    self.rope(q_r_unrotated, position_offset)

    think immediately:

    \boxed{ \text{specialized positional Query} \rightarrow \text{pair dimensions} \rightarrow \text{complex numbers} \rightarrow e^{i\theta} \rightarrow \text{rotate} }

    and when you see:

    self.rope(k_r_unrotated, position_offset)

    think the same process for the Key.

    The purpose is:

    \boxed{ \text{inject position into }q_r,k_r }

    while keeping the content pathway suitable for MLA's compressed KV-cache design. (Source: Build a DeepSeek Model (From Scratch))
