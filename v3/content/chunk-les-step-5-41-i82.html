Motivation

Implement gather, execute, weight and scatter with correct repeated-token accumulation.

Prerequisites

  • Two-layer FFN matrix shapes and parameter counts
  • Stable softmax, top-k, integer indices and gather/scatter accumulation
  • Expert parallelism, load/importance distinction and non-gradient feedback

Notation and units

  • T=B×S flattened tokens, D model width, N routed experts, k selected per token
  • Row score matrix[T, N]; selected indices and gates[T, k]; final stream[T, D]
  • Book bias is a persistent nontrainable buffer; gate weights come from softmax selected biased logits
  • V3: si=sigmoid(x·ei); select by si+bi; normalize original si within selected set

Assumptions

  • Bias-free educational two-matrix GELU experts use2DHparameters; gated/SwiGLUuses3DH
  • Per-tokenk/N is routed expert activation fraction, notcomplete-model storage or latency ratio
  • The Transformer owns the residual unless a standalone MoE explicitly returns x+transform; neveraddit twice
  • Tie behavior and normalization must be explicit; expert choices are learned, not manual domain labels
  • Toycompanion useslinear illustrative experts for8-tokentrace; production experts are learned FFNs

Step-by-step derivation

  1. Flatten[B, S, D]to[T, D], preserving token order; router dot product produces[T, N]. Shared path can operate directly on all leading dimensions.
  2. Select[T, k]expert indices and gates. For experti, find(tokenrow, selectedslot)whereindices==i; both coordinates are needed to pick the correct gate.
  3. Gather selected token rows, execute expert FFN once as batch, weight by the corresponding gate, andscatter-add into original token rows. Assignment duplicates across experts must add, not overwrite.
  4. If expert i is unused, skip it and keep its contribution zero. Expert capacity padding is optional implementation overhead and must not be confused with actual tokens assigned.
  5. Restore[B, S, D]. Sumshared+routed transforms; add residual once at the block boundary. Check output shape even if zero assignments go to a particular expert.
  6. Collect Ci from indices actually used in the forward pass. Re-running router after optimizer updates can choose other experts; use collected assignments for consistent bias feedback.
  7. Book logit-plus-bias→selected softmax is a pedagogical variant. V3selection only uses bias with sigmoid norm gates; retain clear mode flag in companion.

Mastery answers and retained exercise context

  1. Why index_add? A token has multiple expert contributions which must accumulate at same token row.
  2. What does nonzero return? Token row and expert-slot coordinates.
  3. Should bias receive optimizer gradients? It is a separate persistent balancing buffer in these variants.
  4. Why not recompute routes after optimizer step? Updated weights may change selections; feedback must reflect actual forward work.

Edge cases and remaining gaps

Continuation · checked fixture A02 — MoE top-k routing and selected normalization

Checked continuation mechanism and declared fixture; this is not certification of every inherited claim.

Use a small selected subset of experts per token, while retaining a larger stored expert pool.

Prerequisites: Stable softmax and log-softmax, Matrix multiplication and shape contracts

Notation and assumptions

Linear two-feature experts in this fixture; full-softmax router then selected-probability renormalization. DeepSeek sigmoid/top-k/group variants are separate.

Derivation and mechanism

  1. Compute router scores and select k.
  2. Apply only selected experts.
  3. Weight selected outputs using the declared normalization; add shared expert output separately if present.

Worked example

Expert0=identity,expert1=2identity,expert2=3identity; x=[1,2]. Router[.6,.3,.1],k2→selected weights[2/3,1/3], output=[4/3,8/3]. Unnormalized selected scores would yield[1.2,2.4], a different result.

Limitations

  • Stored parameters and active-per-token parameters use different denominators.
  • This fixture has no nonlinear FFN, capacity overflow or distributed dispatcher.

Connections to later concepts

  • A03 controls expert concentration, and distributed expert dispatch introduces costs not represented by a linear weighted-output fixture.

Step 5.41 — Build the Complete DeepSeek-MoE Layer

Plan node: A2 · chat order #82

↩ Back to main text: Step 1.10 — Position-Wise Feed-Forward Network (FFN / MLP)

We now combine everything from Steps 5.38–5.40 into one working mechanism:

\boxed{ \text{Shared Experts} + \text{Dynamic Routing} + \text{Top-K} + \text{Sparse Dispatch} + \text{Weighted Aggregation} + \text{Residual} + \text{Loss-Free Bias Update} }

The source's implementation follows exactly this three-path architecture: a dense shared path, a sparse routed path, and a residual path. (Source: Build a DeepSeek Model (From Scratch))

5.41.1 First, the complete picture

For an input tensor:

X\in\mathbb R^{B\times S\times D}

we have:

                         X
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
       SHARED PATH              ROUTED PATH
       every token              router
              │                     │
              │                  + bias
              │                     │
              │                  Top-K
              │                     │
              │                 Softmax
              │                     │
              │             selected experts only
              │                     │
              │               weighted sum
              │                     │
              └──────────┬──────────┘
                         │
                         ▼
                    + residual X
                         │
                         ▼
                    final output

The source explicitly describes the same three paths and the final summation. (Source: Build a DeepSeek Model (From Scratch))

5.41.2 Step 1 — Input tensor

Let:

X\in\mathbb R^{B\times S\times D}

where:

  • B: batch size
  • S: sequence length
  • D: model dimension

Example:

B=2,\quad S=4,\quad D=8.

Then:

X\in\mathbb R^{2\times4\times8}.

There are:

2\times4= \boxed{8}

tokens.

5.41.3 Step 2 — Flatten the token dimension

The router works token-by-token.

So reshape:

X \rightarrow X_f

with:

\boxed{ X_f\in\mathbb R^{(BS)\times D} }

In PyTorch:

x_flat = x.reshape(-1, D)

The source uses exactly this approach. (Source: Build a DeepSeek Model (From Scratch))

For our example:

2\times4\times8

becomes:

\boxed{8\times8}.

Nothing about the token representations has changed; we've only rearranged them.

5.41.4 Why flatten?

Because now each row corresponds to one token:

row 0 → token 0
row 1 → token 1
row 2 → token 2
...
row 7 → token 7

So routing becomes a simple matrix operation.

5.41.5 Step 3 — Shared expert path

Suppose we have:

N_s=2

shared experts.

Each shared expert is an FFN:

S_1(x),S_2(x).

Every token goes through both.

So:

\boxed{ S(x)=S_1(x)+S_2(x) }

in the source's simplified implementation. (Source: Build a DeepSeek Model (From Scratch))

In code:

shared_out = torch.zeros_like(x)

for exp in self.shared:
    shared_out += exp(x)

Notice:

exp(x)

uses the entire original:

B\times S\times D

tensor.

There is no Top-K here.

5.41.6 Why don't we flatten this path?

We don't need to.

The shared experts naturally accept:

B\times S\times D.

The source implementation deliberately keeps the shared path in that shape. (Source: Build a DeepSeek Model (From Scratch))

5.41.7 Step 4 — Router parameters

Suppose:

N_r=4

routed experts.

The router weight is:

W_R\in\mathbb R^{N_r\times D}

when implemented with PyTorch's F.linear, whose weight is conventionally stored as:

[\text{out features},\text{in features}].

So here:

W_R\in\mathbb R^{4\times8}.

The source calls this learnable parameter matrix centroids. (Source: Build a DeepSeek Model (From Scratch))

5.41.8 Router computation

We calculate:

L=F.linear(X_f,W_R).

Equivalent mathematically to:

L=X_fW_R^\top.

Therefore:

(8\times8)(8\times4)

gives:

\boxed{8\times4}.

Interpretation:

\boxed{ 1\text{ row per token} \times 1\text{ score per routed expert} }

5.41.9 Concrete router matrix

Imagine the result is:

L= \begin{bmatrix} 1.2&0.3&2.1&1.4\\ 0.5&2.2&1.1&0.7\\ 1.8&1.6&0.2&2.0\\ 0.2&0.9&2.4&1.1\\ 1.7&1.5&1.3&0.4\\ 0.6&2.3&1.0&1.9\\ 1.1&0.8&2.0&1.2\\ 2.1&0.4&0.9&1.7 \end{bmatrix}.

There are:

8

tokens and:

4

routed experts.

5.41.10 Step 5 — Add dynamic bias

From Step 5.39, we maintain:

b\in\mathbb R^{N_r}.

Suppose:

b= \begin{bmatrix} 0.2&0.1&-0.3&0 \end{bmatrix}.

Then:

\boxed{ L'=L+b }

where the bias is broadcast across all tokens.

For token 1:

[1.2,0.3,2.1,1.4] + [0.2,0.1,-0.3,0]

gives:

\boxed{ [1.4,0.4,1.8,1.4] }.

This is exactly where the source puts the dynamic balancing bias: before Top-K. (Source: Build a DeepSeek Model (From Scratch))

5.41.11 Why before Top-K?

Suppose:

L=[2.0,1.9,1.8,1.7].

With:

k=2

we select:

E_1,E_2.

Now suppose Expert 1 is overloaded and its bias becomes:

b_1=-0.5.

Then:

L'=[1.5,1.9,1.8,1.7].

Top-2 becomes:

\boxed{E_2,E_3}.

So the bias can actually change which experts are selected.

That's why the placement matters.

5.41.12 Step 6 — Top-K

Suppose:

k=2.

For token 1:

[1.4,0.4,1.8,1.4]

Top-2:

\boxed{E_3,E_1}

with logits:

[1.8,1.4].

So:

top\_k\_idx=[3,1]

if using zero-based indexing.

The source uses:

topk_logits, topk_idx = torch.topk(
    logits,
    self.top_k,
    dim=-1
)

(Source: Build a DeepSeek Model (From Scratch))

5.41.13 Step 7 — Softmax only over selected experts

For token 1:

z=[1.8,1.4].

Softmax:

g_1= \frac{e^{1.8}}{e^{1.8}+e^{1.4}}

and:

g_3= \frac{e^{1.4}}{e^{1.8}+e^{1.4}}.

Using:

e^{1.8}\approx6.050
e^{1.4}\approx4.055,

we get:

g_1\approx \frac{6.050}{10.105} \approx \boxed{0.599}.

and:

g_3\approx \boxed{0.401}.

The source uses exactly this Top-K → softmax sequence. (Source: Build a DeepSeek Model (From Scratch))

5.41.14 Step 8 — Build the routing table

Now let's trace four tokens so we can see dispatch.

Assume:

N_r=4,\qquad k=2.

Suppose after bias and Top-K:

Token Expert 1 Expert 2 Expert 3 Expert 4
T_1 0.599 0 0.401 0
T_2 0 0.750 0 0.250
T_3 0.450 0 0 0.550
T_4 0 0.600 0.400 0

This is the sparse gate matrix.

Notice:

2

nonzero entries per token.

5.41.15 Why represent it this way?

Because now we immediately know:

Expert 1 receives
T_1,T_3
Expert 2 receives
T_2,T_4
Expert 3 receives
T_1,T_4
Expert 4 receives
T_2,T_3

So the router has created:

\boxed{ \text{token groups per expert} }.

5.41.16 Step 9 — Sparse dispatch

Now comes one of the most important implementation ideas.

We do not process:

Expert 1 → all tokens
Expert 2 → all tokens
Expert 3 → all tokens
Expert 4 → all tokens

That would destroy sparsity.

Instead:

Expert 1 → only T1,T3
Expert 2 → only T2,T4
Expert 3 → only T1,T4
Expert 4 → only T2,T3

The source implements exactly this idea by creating a mask for each expert and gathering only its assigned rows. (Source: Build a DeepSeek Model (From Scratch))

5.41.17 The mask

For Expert 1:

mask = (topk_idx == 0)

Suppose:

topk_idx =
[
  [2,0],
  [1,3],
  [0,3],
  [1,2]
]

Then:

mask =
[
  [False, True ],
  [False, False],
  [True,  False],
  [False, False]
]

So Expert 1 gets:

T_1,T_3.

5.41.18 nonzero() gives us the locations

The source uses:

row_idx, which_k = mask.nonzero(as_tuple=True)

(Source: Build a DeepSeek Model (From Scratch))

Conceptually:

  • row_idx: which token?
  • which_k: which Top-K slot?

For:

mask =
[
 [F,T],
 [F,F],
 [T,F],
 [F,F]
]

we get:

row\_idx=[0,2]

and:

which\_k=[1,0].

So:

  • token 0 chose Expert 1 in Top-K slot 1;
  • token 2 chose Expert 1 in Top-K slot 0.

5.41.19 Gather the actual token representations

Now:

exp_in = x_flat.index_select(0, row_idx)

If:

x_f\in\mathbb R^{4\times D}

and:

row\_idx=[0,2],

then:

exp\_in\in\mathbb R^{2\times D}.

So Expert 1 receives a mini-batch of only its assigned tokens.

This is sparse batching.

5.41.20 Execute the expert

Now:

out = self.routed[i](exp_in)

If the expert preserves model dimension:

2\times D \rightarrow 2\times D.

Suppose:

D=8.

Then:

2\times8 \rightarrow 2\times8.

Only two token representations went through Expert 1.

5.41.21 Retrieve their gate weights

We need the corresponding routing weights.

Source:

w = gate[row_idx, which_k].unsqueeze(-1)

Suppose:

gate= \begin{bmatrix} 0&0&0.401&0.599\\ 0&0.750&0&0.250\\ 0.450&0&0&0.550\\ 0&0.600&0.400&0 \end{bmatrix}

and Expert 1 selected rows are:

row\_idx=[0,2].

Then its weights are:

[0.599,0.450].

After unsqueeze(-1):

\boxed{ [2\times1] }.

This shape allows broadcasting when multiplying by expert outputs.

5.41.22 Weighted expert result

Suppose:

E_1(T_1)= \begin{bmatrix} 1&2 \end{bmatrix}

and:

E_1(T_3)= \begin{bmatrix} 3&4 \end{bmatrix}.

Weights:

0.599

and:

0.450.

Then Expert 1 contributes:

0.599[1,2]

for T_1, and:

0.450[3,4]

for T_3.

These results must go back to the correct original token positions.

5.41.23 The crucial index_add_

The source uses:

routed_out.index_add_(0, row_idx, out * w)

(Source: Build a DeepSeek Model (From Scratch))

This is extremely important.

Suppose:

routed\_out

has shape:

T\times D.

For our four-token example:

4\times D.

We don't want to overwrite positions.

We want:

routed\_out[0] \mathrel{+}=E_1(T_1)\times0.599

and:

routed\_out[2] \mathrel{+}=E_1(T_3)\times0.450.

Then Expert 2 adds its contribution to tokens 1 and 3.

Expert 3 adds its contribution to tokens 0 and 3.

Expert 4 adds its contribution to tokens 1 and 2.

Hence the same token may accumulate contributions from multiple experts.

That is exactly why index_add_ is useful.

Take token T_1.

Suppose:

Weights:

So:

\boxed{ R(T_1)=[3.203,2.203] }.

This is the sparse routed contribution.

Suppose the shared experts produce:

Then:

becomes:

5.41.29 Step 14 — Update the load-balancing bias

Now the forward computation is finished.

During training, the source performs a separate bias update.

It first gets the expert counts:

counts = torch.bincount(
    top_k_indices.flatten(),
    minlength=self.n_routed
)

So if:

top_k_indices =
[
 [2,0],
 [1,3],
 [0,3],
 [1,2]
]

flatten:

[2,0,1,3,0,3,1,2]

Counts:

E_1=2
E_2=2
E_3=2
E_4=2.

Perfectly balanced.

5.41.30 Another example of bincount

Suppose instead:

top_k_indices =
[
 [2,0],
 [2,3],
 [0,3],
 [2,3]
]

Flatten:

[2,0,2,3,0,3,2,3].

Counts:

\boxed{ [2,0,3,3] }.

So:

  • Expert 1: 2
  • Expert 2: 0
  • Expert 3: 3
  • Expert 4: 3

Expert 2 is effectively dead for this batch.

Experts 3 and 4 are relatively overloaded.

5.41.31 Average load

Suppose:

T=4,\quad k=2,\quad N_r=4.

Total assignments:

T\times k = 8.

Average:

\frac84 = \boxed{2}.

So:

\bar C=2.

This is exactly the source's logic. (Source: Build a DeepSeek Model (From Scratch))

5.41.32 Calculate violation

Use:

\boxed{ v_i= \frac{\bar C-C_i} {\bar C+\epsilon} }

as in the source implementation. (Source: Build a DeepSeek Model (From Scratch))

For:

C=[2,0,3,3]

and:

\bar C=2,

we get:

Expert 1
v_1= \frac{2-2}{2} = 0.
Expert 2
v_2= \frac{2-0}{2} = \boxed{1}.
Expert 3
v_3= \frac{2-3}{2} = \boxed{-0.5}.
Expert 4
v_4=-0.5.

So:

\boxed{ v=[0,1,-0.5,-0.5] }.

5.41.33 Apply the bounded update

Suppose:

\eta=0.01.

Then:

\Delta b_i = 0.01\tanh(v_i).

For Expert 2:

\tanh(1)\approx0.7616

so:

\Delta b_2 \approx \boxed{0.007616}.

For Experts 3 and 4:

\tanh(-0.5)\approx-0.4621

so:

\Delta b_3 = \Delta b_4 \approx \boxed{-0.004621}.

Thus:

b_2\uparrow

and:

b_3,b_4\downarrow.

Exactly the desired direction. (Source: Build a DeepSeek Model (From Scratch))

5.41.34 Why is Expert 2 now more attractive?

Because next time:

L'_2=L_2+b_2.

Since:

b_2

increased:

L'_2

also increases.

Therefore Expert 2 is more likely to enter Top-K.

Conversely, Expert 3:

b_3\downarrow

so:

L'_3\downarrow.

Thus Expert 3 becomes less likely to be selected.

This is the self-correcting loop emphasized by the source. (Source: Build a DeepSeek Model (From Scratch))

5.41.35 Important: the bias is persistent

The bias isn't simply:

\text{temporary computation}.

It is carried into later steps.

So:

b^{(t)} \rightarrow b^{(t+1)} \rightarrow b^{(t+2)} \rightarrow\cdots

The router gradually adapts its selection preferences.

5.41.36 Important: bias update isn't backpropagation

The source uses:

@torch.no_grad()

for the update. (Source: Build a DeepSeek Model (From Scratch))

So conceptually:

language loss
      ↓
backpropagation
      ↓
model parameters

separate load measurement
      ↓
bias update
      ↓
router preference next step

That separation is the heart of the:

\boxed{\text{loss-free}}

approach.

5.41.37 Full source-style code

Now let's put the pieces together.

import math
from typing import Optional

import torch
import torch.nn as nn
import torch.nn.functional as F


def _gelu(x: torch.Tensor) -> torch.Tensor:
    return 0.5 * x * (
        1.0
        + torch.tanh(
            math.sqrt(2.0 / math.pi)
            * (x + 0.044715 * torch.pow(x, 3))
        )
    )


class ExpertFFN(nn.Module):
    """
    Two-layer expert FFN.
    """

    def __init__(self, d_model: int, hidden: int):
        super().__init__()

        self.fc1 = nn.Linear(
            d_model,
            hidden,
            bias=False
        )

        self.fc2 = nn.Linear(
            hidden,
            d_model,
            bias=False
        )

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.fc2(
            _gelu(
                self.fc1(x)
            )
        )


class DeepSeekMoE(nn.Module):

    def __init__(
        self,
        d_model: int,
        n_routed_exp: int,
        n_shared_exp: int = 1,
        top_k: int = 8,
        routed_hidden: int = 2048,
        shared_hidden: Optional[int] = None,
        bias_lr: float = 0.01,
    ):
        super().__init__()

        assert top_k <= n_routed_exp

        self.d_model = d_model
        self.n_routed = n_routed_exp
        self.n_shared = n_shared_exp
        self.top_k = top_k
        self.bias_lr = bias_lr

        # Sparse routed experts
        self.routed = nn.ModuleList(
            [
                ExpertFFN(d_model, routed_hidden)
                for _ in range(n_routed_exp)
            ]
        )

        # Dense shared experts
        hidden_shared = shared_hidden or routed_hidden

        self.shared = nn.ModuleList(
            [
                ExpertFFN(d_model, hidden_shared)
                for _ in range(n_shared_exp)
            ]
        )

        # Router weights
        self.centroids = nn.Parameter(
            torch.empty(n_routed_exp, d_model)
        )

        nn.init.normal_(
            self.centroids,
            std=d_model ** -0.5
        )

        # Dynamic balancing bias
        self.register_buffer(
            "bias",
            torch.zeros(n_routed_exp)
        )

    def forward(self, x: torch.Tensor) -> torch.Tensor:

        B, S, D = x.shape

        # -------------------------------------------------
        # 1. SHARED PATH
        # -------------------------------------------------

        shared_out = torch.zeros_like(x)

        for expert in self.shared:
            shared_out += expert(x)

        # -------------------------------------------------
        # 2. FLATTEN TOKENS
        # -------------------------------------------------

        x_flat = x.reshape(-1, D)

        # -------------------------------------------------
        # 3. ROUTER
        # -------------------------------------------------

        logits = F.linear(
            x_flat,
            self.centroids
        )

        # -------------------------------------------------
        # 4. DYNAMIC LOAD-BALANCING BIAS
        # -------------------------------------------------

        logits = logits + self.bias.to(
            logits.dtype
        )

        # -------------------------------------------------
        # 5. TOP-K
        # -------------------------------------------------

        topk_logits, topk_idx = torch.topk(
            logits,
            self.top_k,
            dim=-1
        )

        # -------------------------------------------------
        # 6. SOFTMAX GATES
        # -------------------------------------------------

        gate = F.softmax(
            topk_logits,
            dim=-1,
            dtype=x.dtype
        )

        # -------------------------------------------------
        # 7. SPARSE DISPATCH
        # -------------------------------------------------

        routed_out = torch.zeros_like(x_flat)

        for i in range(self.n_routed):

            mask = (topk_idx == i)

            row_idx, which_k = mask.nonzero(
                as_tuple=True
            )

            if row_idx.numel() == 0:
                continue

            exp_in = x_flat.index_select(
                0,
                row_idx
            )

            out = self.routed[i](
                exp_in
            )

            w = gate[
                row_idx,
                which_k
            ].unsqueeze(-1)

            routed_out.index_add_(
                0,
                row_idx,
                out * w
            )

        routed_out = routed_out.view(
            B, S, D
        )

        # -------------------------------------------------
        # 8. RESIDUAL + SHARED + ROUTED
        # -------------------------------------------------

        return (
            x
            + shared_out
            + routed_out
        )

This is source-grounded pseudocode/implementation structure adapted directly from the book's listings rather than a claim that this is production DeepSeek code. The source itself describes its implementation as a scaled-down, educational implementation. (Source: Build a DeepSeek Model (From Scratch))

5.41.38 The forward() method in plain English

Let's translate the whole function:

Input X
  ↓
Every token → shared experts
  ↓
Flatten tokens
  ↓
Router computes scores
  ↓
Add balancing bias
  ↓
Choose top-k experts
  ↓
Softmax selected scores
  ↓
Group tokens according to destination expert
  ↓
Run each group through its expert
  ↓
Weight each expert output
  ↓
Scatter-add results back to token locations
  ↓
Reshape
  ↓
Add shared output
  ↓
Add residual X
  ↓
Final output

That is the complete MoE forward pass.

5.41.39 Why the code uses a loop over experts

This line:

for i in range(self.n_routed):

does not mean every expert processes every token.

The loop merely asks:

“Which tokens were assigned to expert i?”

Then:

mask = (topk_idx == i)

finds only those tokens.

Therefore:

\boxed{ \text{loop over experts} \neq \text{dense computation over all tokens} }

This is a very important code-reading point.

5.41.40 What happens if an expert receives zero tokens?

Then:

if row_idx.numel() == 0:
    continue

So the expert is skipped entirely for that batch.

No expert computation.

This is sparse execution.

But if this happens repeatedly, it indicates a routing problem—the “dead expert” issue discussed earlier. (Source: Build a DeepSeek Model (From Scratch))

5.41.46 Why shared experts are dense but routed experts are sparse

For every token:

\boxed{ \text{shared computation} }

always happens.

But:

\boxed{ \text{routed computation} }

depends on Top-K.

Therefore:

\boxed{ \text{Dense common computation} + \text{Sparse specialized computation} }

is the key DeepSeek-MoE structure.

The source explicitly frames the shared experts as dense generalists and routed experts as sparse specialists. (Source: Build a DeepSeek Model (From Scratch))

5.41.47 Production reality: dispatch is not free

This is important for systems/design questions.

Mathematically we say:

\text{only selected experts execute}.

But on distributed GPUs, tokens may need to move to the GPU that owns the selected expert.

That introduces:

\boxed{\text{communication overhead}}

often involving all-to-all communication in distributed MoE systems.

The source later discusses this as a major systems issue motivating DualPipe. (Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ \text{MoE efficiency} \neq \text{zero communication cost} }

The source's chapter 4 implementation is intentionally simplified and does not reproduce full production distributed execution.

5.41.48 Another critical distinction: educational code vs production DeepSeek

The source code is designed to make the mechanism understandable.

For example, the source says shared experts are processed sequentially in a simple for loop and notes that production systems would parallelize expert computation. (Source: Build a DeepSeek Model (From Scratch))

Therefore don't answer an interview question:

“DeepSeek production runs experts one by one in a Python loop.”

That would be wrong.

The correct distinction is:

\boxed{ \text{source implementation} = \text{educational reference implementation} }

versus:

\boxed{ \text{production system} = \text{distributed, parallel expert execution} }.

5.41.49 The entire DeepSeek-MoE formula

We can now express the whole thing in one equation.

Let:

L_t=W_Rx_t+b.

Select:

I_t=TopK(L_t,k).

Normalize:

g_{t,i} = \frac{e^{L_{t,i}}} {\sum_{j\in I_t}e^{L_{t,j}}}.

Then:

R(x_t) = \sum_{i\in I_t} g_{t,i}E_i(x_t).

Shared path:

S(x_t) = \sum_{j=1}^{N_s}S_j(x_t).

Final:

\boxed{ y_t = x_t + S(x_t) + R(x_t) }

with:

\boxed{ b_i \text{ updated separately from routing load}. }

(Source: Build a DeepSeek Model (From Scratch))

\boxed{ \text{Every token gets common knowledge} }

from the shared experts,

\boxed{ \text{Every token gets specialized knowledge} }

from only a small number of routed experts,

\boxed{ \text{the router controls specialization} }

and:

\boxed{ \text{the dynamic bias controls utilization}. }

5.41.53 What you should now understand, not memorize

You should now be able to explain why each operation exists:

\boxed{\text{Flatten}}

because routing is token-wise.

\boxed{\text{Router}}

because the model needs to choose specialists.

\boxed{\text{Bias}}

because some experts can become overloaded.

\boxed{\text{Top-K}}

because we want sparsity.

\boxed{\text{Softmax}}

because selected experts need normalized mixture weights.

\boxed{\text{Dispatch}}

because each expert should process only its assigned tokens.

\boxed{\text{index\_add}}

because multiple experts contribute back to the same token.

\boxed{\text{Shared experts}}

because common knowledge should not be redundantly relearned.

\boxed{\text{Residual}}

because the MoE sits in the Transformer residual stream.

\boxed{\text{Bias update}}

because routing balance is corrected over training without adding an auxiliary loss.

We have now completed the entire conceptual Chapter 4 architecture:

\boxed{ \text{Dense FFN} \rightarrow \text{MoE} \rightarrow \text{Load balancing} \rightarrow \text{Fine-grained experts} \rightarrow \text{Shared experts} \rightarrow \text{Loss-free balancing} \rightarrow \text{Complete DeepSeek-MoE layer} }
