Motivation

Turn a flat corpus into correctly aligned autoregressive examples while sampling only a small portion per update.

Prerequisites

  • Flat token storage
  • Zero-based half-open slicing
  • Causal attention

Notation and units

  • N: stream length
  • B: independent windows
  • T: input positions per window
  • i_b: start of batch row b

Assumptions

  • At least T+1 tokens are available
  • Starts are sampled with replacement unless specified
  • Target positions are predicted from their own causal prefixes

Step-by-step derivation

  1. For each b set X[b,j]=stream[i_b+j] and Y[b,j]=stream[i_b+j+1], for j=0..T-1.
  2. The last target uses stream[i_b+T], hence i_b <=N-T-1. torch.randint(N-T) has an exclusive upper bound and matches this condition exactly.
  3. Check N>T before random sampling; N=T contains no valid full pair, while N=T+1 has exactly start zero.
  4. Stack windows into [B,T] and expand compact IDs to int64 for the framework indexing/loss contract.
  5. The causal mask permits input indices <=j; the target shift defines what to predict and the mask prevents reading the target through future inputs.
  6. B*T counts prediction positions, not one giant context. Overlapping sampled windows also mean this is not necessarily B*T distinct corpus tokens.
  7. Pinned memory plus asynchronous transfer can reduce CPU waiting where the hardware/stream conditions allow it; these calls do not prove throughput gains.

    We are now at the exact bridge between:

    \boxed{\texttt{train.bin / val.bin}}

    and:

    \boxed{\text{the Transformer forward pass}}

    The source calls this the get_batch stage of train.py. Its job is to open the memory-mapped token file, choose random starting positions, construct input/target sequences, and move them to the GPU when appropriate. (Source: Build a DeepSeek Model (From Scratch))

    6.1.1.1 What does the model actually need?

    The language model was trained earlier conceptually with the objective:

    \boxed{ \text{predict the next token from previous tokens} }

    So we cannot simply give it:

    [10, 20, 30, 40, 50]

    and say “learn this.”

    We need two aligned sequences:

    \boxed{X}

    and:

    \boxed{Y}.

    The first is what the model sees.

    The second is what the model is supposed to predict.

    6.1.1.2 The crucial one-token shift

    Suppose the token stream is:

    [10,20,30,40,50,60].

    Choose a sequence length:

    T=5.

    Then the source constructs:

    X=[10,20,30,40,50]

    and:

    Y=[20,30,40,50,60].

    So:

    \boxed{ Y_t=X_{t+1} }

    for every valid position.

    This is the entire next-token prediction mechanism in its simplest form.

    6.1.1.3 Why is the shift necessary?

    Consider:

    Input:
10 20 30 40 50

Target:
20 30 40 50 60

    At position 1, the model receives:

    10

    and should predict:

    20.

    At position 2:

    10,20

    and should predict:

    30.

    At position 3:

    10,20,30

    and should predict:

    40.

    And so on.

    So the training pair is really:

    \boxed{ (X_1,\ldots,X_T) \rightarrow (Y_1,\ldots,Y_T) }

    where:

    \boxed{ Y_i=X_{i+1}. }

    This is the same causal language-model objective we established earlier; here Chapter 6 finally implements it.

    6.1.1.4 The source's exact mechanism

    The source uses:

    x = torch.stack([
    torch.from_numpy(
        (data[i:i+block_size]).astype(np.int64)
    )
    for i in ix
])

y = torch.stack([
    torch.from_numpy(
        (data[i+1:i+1+block_size]).astype(np.int64)
    )
    for i in ix
])

    (Source: Build a DeepSeek Model (From Scratch))

    Notice the difference:

    Input
    data[i : i + block_size]
    Target
    data[i + 1 : i + 1 + block_size]

    That single +1 is the heart of next-token training.

    6.1.1.5 Let's inspect it numerically

    Suppose:

    data= [100,101,102,103,104,105,106,107].

    Let:

    block\_size=4

    and:

    i=2.

    Then:

    Input
    data[2:6]

    gives:

    \boxed{[102,103,104,105]}.
    Target
    data[3:7]

    gives:

    \boxed{[103,104,105,106]}.

    Therefore:

    X = [102, 103, 104, 105]
Y = [103, 104, 105, 106]

    The model is trained to predict:

    102 → 103
103 → 104
104 → 105
105 → 106

    6.1.1.6 But our dataset is one giant stream

    Recall what we built previously:

    Story 1 tokens
EOT
Story 2 tokens
EOT
Story 3 tokens
EOT
...

    stored as:

    \boxed{\text{one flat array}}.

    So get_batch() does not need to know anything about stories at this point.

    It simply sees:

    \boxed{ [t_0,t_1,t_2,\ldots,t_{N-1}] }

    and extracts contiguous windows.

    The EOT tokens remain inside this stream and tell the model where document boundaries were encoded.

    6.1.1.7 Why use random starting positions?

    The source uses:

    ix = torch.randint(
    len(data) - block_size,
    (batch_size,)
)

    (Source: Build a DeepSeek Model (From Scratch))

    This means:

    \boxed{ \text{randomly choose }batch\_size\text{ starting locations}. }

    Suppose:

    batch\_size=4.

    We might get:

    i=[1032, 7811, 22501, 46290].

    Then four different chunks are extracted.

    6.1.1.8 Why not simply take the first 256 tokens every time?

    Because then every iteration would see almost the same training example.

    For example:

    Iteration 1:
tokens 0–255

Iteration 2:
tokens 0–255

Iteration 3:
tokens 0–255

    That would be extremely wasteful.

    Random starting offsets let the model see many different portions of the corpus across training steps.

    The source explicitly says get_batch randomly selects batch_size starting positions. (Source: Build a DeepSeek Model (From Scratch))

    6.1.1.9 What is block_size?

    This is one of the most important hyperparameters in the data loader.

    The source configuration uses:

    \boxed{ block\_size=256. }

    (Source: Build a DeepSeek Model (From Scratch))

    It means each training example contains:

    \boxed{ 256\text{ input tokens} }

    and:

    \boxed{ 256\text{ target tokens}. }

    So for one sample:

    X\in\mathbb Z^{256}

    and:

    Y\in\mathbb Z^{256}.

    6.1.1.10 Why block_size matters to the Transformer

    The Transformer does not normally process the whole corpus at once.

    It sees a context window:

    \boxed{ T=256 }

    in this source configuration.

    So the model operates on:

    X= [x_1,x_2,\ldots,x_{256}].

    The model produces logits for all positions:

    Z\in\mathbb R^{256\times V}.

    Then the targets are:

    Y= [y_1,y_2,\ldots,y_{256}].

    And cross-entropy compares:

    Z_t

    against:

    Y_t.

    6.1.1.11 What is batch_size?

    The source configuration uses:

    \boxed{ batch\_size=24. }

    (Source: Build a DeepSeek Model (From Scratch))

    So we don't train on just one sequence.

    We build:

    24

    different random sequences.

    Therefore:

    \boxed{ X\in\mathbb Z^{24\times256} }

    and:

    \boxed{ Y\in\mathbb Z^{24\times256}. }

    This is the first major tensor-shape checkpoint.

    6.1.1.12 The complete shape transformation

    We begin with:

    \boxed{ \text{1-D token stream} }

    of shape:

    [N].

    Randomly choose:

    B=24

    starting points.

    Extract:

    T=256

    tokens at each point.

    Therefore:

    \boxed{ [N] \rightarrow [B,T] }

    which becomes:

    \boxed{ [N] \rightarrow [24,256]. }

    And because targets are shifted by one:

    \boxed{ X:[24,256] }
    \boxed{ Y:[24,256]. }

    6.1.1.13 Why len(data) - block_size?

    Look closely at:

    torch.randint(len(data) - block_size, ...)

    Suppose:

    len(data)=1000

    and:

    block\_size=256.

    A starting position needs enough room for:

    256

    input tokens plus the next-token target.

    The source's indexing makes the valid-start constraint explicit through the len(data) - block_size bound.

    The important idea is:

    \boxed{ \text{don't choose a starting point so close to the end that a full training pair cannot be extracted}. }

    6.1.1.14 Why convert from uint16 to int64?

    This line is interesting:

    .astype(np.int64)

    The saved dataset is:

    \boxed{uint16}

    because that is an efficient storage representation.

    But before constructing the PyTorch training tensor, the source converts those token IDs to:

    \boxed{int64}.

    Why?

    Because token IDs are being prepared as integer indices for the model's embedding lookup and later loss computation.

    So we have an important distinction:

    \boxed{ \text{storage dtype} \neq \text{training tensor dtype}. }

    Storage:

    uint16

    Training token tensor:

    int64.

    6.1.1.15 Why not store everything as int64 from the beginning?

    Because that would waste storage.

    We already established:

    uint16=2\text{ bytes}.

    Whereas:

    int64=8\text{ bytes}.

    So a billion token IDs would require approximately:

    uint16
    1B\times2 = 2\text{ GB}.
    int64
    1B\times8 = 8\text{ GB}.

    Thus:

    \boxed{ \text{compact storage} \rightarrow \text{expand only when needed for computation}. }

    The source explicitly implements this distinction. (Source: Build a DeepSeek Model (From Scratch))

    6.1.1.16 torch.from_numpy

    The source wraps the NumPy slices with:

    torch.from_numpy(...)

    This converts the NumPy array representation into a PyTorch tensor representation.

    Then:

    torch.stack(...)

    combines the individual sequences into a batch.

    Conceptually:

    sequence 1 → [T]
sequence 2 → [T]
sequence 3 → [T]
...
sequence B → [T]

        ↓ stack

        [B,T]

    So:

    \boxed{ [T]\times B \rightarrow [B,T]. }

    6.1.1.17 Let's visualize the batch

    Suppose:

    B=3,\qquad T=5.

    We might obtain:

    X:

[ 10  20  30  40  50 ]
[ 72  91  33  14  18 ]
[201 202 203 204 205 ]

Y:

[ 20  30  40  50  60 ]
[ 91  33  14  18  19 ]
[202 203 204 205 206 ]

    Each row is an independent training example.

    The model processes all three in parallel.

    6.1.1.18 What does the Transformer see?

    The Transformer receives:

    \boxed{ X=[B,T] }

    of integer token IDs.

    For the source configuration:

    \boxed{ X=[24,256]. }

    The embedding layer then converts:

    [24,256]

    into:

    \boxed{ [24,256,d_{\text{model}}]. }

    For the flagship configuration later in the source:

    d_{\text{model}}=768.

    So conceptually:

    \boxed{ [24,256] \rightarrow [24,256,768]. }

    That is where the token IDs become continuous vectors.

    6.1.1.20 Now let's understand the causal relationship

    Suppose:

    X= [x_1,x_2,x_3,x_4].

    Because of causal masking:

    Position 1

    The model can use:

    x_1

    to predict:

    y_1=x_2.
    Position 2

    It can use:

    x_1,x_2

    to predict:

    y_2=x_3.
    Position 3

    It can use:

    x_1,x_2,x_3

    to predict:

    y_3=x_4.

    So the batch construction and the causal mask work together.

    \boxed{ \text{shifted targets} + \text{causal attention} = \text{next-token language modeling}. }

    This is a key connection.

    6.1.1.21 What would happen without the shift?

    Suppose:

    X=[10,20,30]

    and incorrectly:

    Y=[10,20,30].

    Then the model would be rewarded for reproducing the current token rather than predicting the next one.

    That would no longer implement the intended autoregressive next-token objective.

    Therefore:

    \boxed{ Y=X\text{ shifted left by one}. }

    6.1.1.22 What would happen without causal masking?

    This is equally important.

    Suppose:

    X = [10, 20, 30, 40]
Y = [20, 30, 40, 50]

    At position 1, if attention could see all tokens including:

    30,40,

    then the model could use future information to help predict 20.

    That creates information leakage.

    So the two mechanisms have different jobs:

    \boxed{ \text{batch shift} \rightarrow \text{defines the prediction target} }

    while:

    \boxed{ \text{causal mask} \rightarrow \text{prevents seeing future inputs}. }

    6.1.1.23 CPU → GPU

    if 'cuda' in device:
    return (
        x.pin_memory().to(device, non_blocking=True),
        y.pin_memory().to(device, non_blocking=True)

    (Source: Build a DeepSeek Model (From Scratch))

    This introduces another systems concept.

    We have:

    \boxed{ \text{CPU memory} \rightarrow \text{GPU VRAM}. }

    6.1.1.24 What is pinned memory?

    The source specifically describes pin_memory() as a performance optimization for transferring data from CPU RAM to GPU VRAM. (Source: Build a DeepSeek Model (From Scratch))

    So conceptually:

    Normal CPU memory
      │
      ▼
GPU transfer
      │
      ▼
GPU

Pinned CPU memory
      │
      │ optimized transfer path
      ▼
GPU

    It doesn't change the model's mathematical computation.

    It improves the data movement path.

    6.1.1.25 What does non_blocking=True mean here?

    The source uses:

    .to(device, non_blocking=True)

    together with pinned memory. (Source: Build a DeepSeek Model (From Scratch))

    The practical intention is to allow the transfer to be issued without unnecessarily forcing the CPU-side execution to wait synchronously at that point, when the underlying conditions permit asynchronous transfer.

    So this belongs to:

    \boxed{ \text{performance engineering} }

    rather than:

    \boxed{ \text{language-model mathematics}. }

    6.1.1.26 Why does this matter at scale?

    Imagine:

    1000

    training iterations.

    If each iteration spends excessive time waiting for:

    \text{CPU}\rightarrow\text{GPU}

    data transfer, the GPU can sit idle.

    The goal is therefore:

    \boxed{ \text{keep GPU computation busy}. }

    This is another recurring theme in large-scale ML:

    \boxed{ \text{computation isn't the only bottleneck; data movement matters too}. }

    \boxed{ X\in\mathbb Z^{24\times256} }

    6.1.1.29 But notice something subtle

    The batch contains:

    24\times256

    positions.

    That does not mean the model has:

    24\times256=6,144

    tokens in one giant sequence.

    Rather, it has:

    \boxed{24\text{ independent sequences}}

    each of length:

    \boxed{256}.

    So the tensor:

    [24,256]

    has two different meanings along its axes:

    \boxed{ B=\text{batch dimension} }
    \boxed{ T=\text{sequence dimension}. }

    6.1.1.30 Why random windows are useful

    Suppose the token stream is:

    [t_0,t_1,\ldots,t_{N-1}].

    A random batch might choose:

    i_1,i_2,\ldots,i_B.

    Then:

    X_b = [t_{i_b},\ldots,t_{i_b+T-1}]

    and:

    Y_b = [t_{i_b+1},\ldots,t_{i_b+T}].

    Thus each batch provides many different local contexts.

    This formula is a mathematical expression of the source's slicing code.

    6.1.1.34 One very important distinction

    There are three different lengths you must not confuse:

    Entire dataset
    \boxed{N}

    possibly millions/billions of tokens.

    \boxed{T=256}

    \boxed{B=24}.

    6.1.1.35 Why this is efficient

    We do not do:

    \text{entire dataset} \rightarrow \text{GPU}.

    Instead:

    \boxed{ \text{disk} \rightarrow \text{small slices} \rightarrow \text{CPU} \rightarrow \text{GPU} \rightarrow \text{model}. }

    That's why the earlier choice of memmap matters.

    The two responses are therefore one continuous design:

    \boxed{ \text{R100.1: efficient storage} }

    feeds directly into:

    \boxed{ \text{R100.2: efficient sampling}. }
