Motivation

Provide farther predictive objectives without leaking the very target being predicted, and maintain a genuine chain of refined hidden states.

Prerequisites

  • Next-token target shift
  • Causal blocks
  • Teacher forcing and concatenation

Notation and units

  • Base position i
  • MTP depth k>=1
  • Future input x[i+k]
  • Farther target x[i+k+1]
  • L_k=S-k-1 for targets restricted to input IDs

Assumptions

  • Explicit in-input target convention declared below
  • S must exceed k+1
  • Earlier refined hidden states retain their original base-position indexing

Step-by-step derivation

  1. The main hidden state at i predicts x[i+1]. At MTP depth1 combine h_i^0 with embedding x[i+1] and predict x[i+2].
  2. At depth k combine h_i^(k-1) with E(x[i+k]); never provide E(x[i+k+1]), which is the target itself.
  3. With targets restricted to an input of length S, valid base indices are0..S-k-2, so L_k=S-k-1. If separately shifted Y provides the extra final token, a different explicitly aligned convention can retain S-k positions.
  4. Slice the previously refined hidden tensor by desired PREFIX length L_k. Absolute-depth negative slicing of an already-short tensor compounds truncation incorrectly.
  5. Concatenate two d-vectors to2d; apply a2d-to-d projection and a dedicated causal Transformer block.
  6. Assign h_prev=h_curr after every stage; apply the shared final normalization/vocabulary head to its output and compare with targets x[:,k+1:k+1+L_k].
  7. Compute a mean CE per stage and choose either lambda/D times their sum or lambda times their sum; these coefficients are not interchangeable as D grows.
  8. The Chapter6 printed listing uses ellipses for CE and omits the h_prev reassignment; the chain and exact objective therefore need completion before it is executable.

R100.7 — MTPModule: Turning One Hidden State into a Causal Prediction Chain

Plan node: A6 · chat order #109

↩ Back to main text: Step 1.13 — Stacking Transformer Blocks → Final Norm → Unembedding → Log

We now build the final special component inside the Mini-DeepSeek architecture:

\boxed{\text{Multi-Token Prediction (MTP)}}

The important point is that this is not another ordinary output head.

Instead, the source constructs a sequential chain of dedicated Transformer blocks. Each MTP stage receives the refined hidden state from the previous stage together with an embedding of a future token, produces a new hidden state, and sends that hidden state to the next MTP stage. (Source: Build a DeepSeek Model (From Scratch))

1. Why do we need MTP?

A normal autoregressive Transformer primarily learns:

t_1,t_2,\ldots,t_i \rightarrow t_{i+1}.

So at each position it is trained for immediate next-token prediction.

The source's MTP idea asks the model to learn a longer predictive horizon.

For prediction depth:

D=3

we construct:

Main trunk
   │
   ▼
h⁰
   │
   ▼
MTP 1
   │
   ▼
h¹
   │
   ▼
MTP 2
   │
   ▼
h²
   │
   ▼
MTP 3
   │
   ▼
h³

The source emphasizes that this is a causal chain, not a set of independent heads. The hidden state produced by one MTP module becomes the input hidden state of the next. (Source: Build a DeepSeek Model (From Scratch))

2. The fundamental difference from independent prediction heads

Imagine we want to predict three future positions.

An independent-head design might do:

h⁰ ──→ Head 1
 │
 ├──→ Head 2
 │
 └──→ Head 3

Each head independently sees h^0.

DeepSeek's causal design instead does:

h⁰
 ↓
MTP 1
 ↓
h¹
 ↓
MTP 2
 ↓
h²
 ↓
MTP 3
 ↓
h³

So:

\boxed{ h^1=f_1(h^0,\text{future information}) }
\boxed{ h^2=f_2(h^1,\text{future information}) }
\boxed{ h^3=f_3(h^2,\text{future information}) }

The source describes this as cascaded latent refinement. (Source: Build a DeepSeek Model (From Scratch))

3. What exactly is inside one MTP module?

The Mini-DeepSeek implementation defines:

class MTPModule(nn.Module):
    def __init__(self, args):
        super().__init__()

        self.projection = nn.Linear(
            args.d_model * 2,
            args.d_model,
            bias=False
        )

        self.block = TransformerBlock(args)

(Source: Build a DeepSeek Model (From Scratch))

So there are only two major pieces:

\boxed{ \text{projection} }

and:

\boxed{ \text{dedicated TransformerBlock}. }

4. Why is the projection input 2d?

The module receives two vectors.

First

The hidden state from the previous MTP stage:

h^{k-1}.
Second

The embedding of a future token:

E(t_{i+k}).

The source explicitly describes these as the two inputs to each MTP stage. During training, that future-token embedding is the ground-truth embedding. (Source: Build a DeepSeek Model (From Scratch))

Each has dimensionality:

d.

So concatenating them gives:

\boxed{2d}.

5. Concatenation

The source does:

x = torch.cat(
    [h_prev, next_token_embeds],
    dim=-1
)

(Source: Build a DeepSeek Model (From Scratch))

Suppose:

h_{\text{prev}}\in\mathbb R^{B\times L\times d}

and:

E_{\text{future}}\in\mathbb R^{B\times L\times d}.

Concatenating along the final dimension gives:

\boxed{ [B,L,d] \rightarrow [B,L,2d]. }

So the module has combined:

\boxed{ \text{contextual state} + \text{future-token semantic representation}. }

6. Projection back to d

The source then applies:

x = self.projection(x)

The projection is:

M_k:\mathbb R^{2d}\rightarrow\mathbb R^d.

Therefore:

\boxed{ [B,L,2d] \rightarrow [B,L,d]. }

This is exactly the purpose described in the source's Chapter 5 derivation: concatenate the two normalized d-dimensional vectors, then use a linear projection to return to the model's normal dimension. (Source: Build a DeepSeek Model (From Scratch))

7. The mathematical form

The source's conceptual equation can be represented as:

\boxed{ h_i^{\prime k} = M_k \left[ \operatorname{Norm}(h_i^{k-1}); \operatorname{Norm}(E(t_{i+k})) \right] }

where:

  • [\,;\,] means concatenation,
  • M_k is the projection matrix,
  • h_i^{k-1} is the previous hidden state,
  • E(t_{i+k}) is the future token embedding.

The source explicitly gives this as its Equation 5.1 description. (Source: Build a DeepSeek Model (From Scratch))

Important source distinction

Chapter 5's conceptual implementation shows separate normalization of the hidden state and future embedding before concatenation using RMSNorm. (Source: Build a DeepSeek Model (From Scratch))

The simplified Chapter 6 MTPModule listing directly concatenates h_prev and next_token_embeds and does not show those separate normalization layers. (Source: Build a DeepSeek Model (From Scratch))

So for our Mini-DeepSeek implementation, we follow the Chapter 6 code rather than silently inserting the Chapter 5 normalization.

8. Why does the module contain a full TransformerBlock?

This is one of the most important ideas.

After projection:

h_i^{\prime k}

does not immediately go to the output head.

It goes through:

\boxed{ TRM_k }

a dedicated Transformer block.

The source explicitly stresses that this is a full Transformer computation, not merely a linear transformation. (Source: Build a DeepSeek Model (From Scratch))

In our Mini-DeepSeek code:

h_k, _ = self.block(
    x,
    attn_mask=...
)

(Source: Build a DeepSeek Model (From Scratch))

So:

\boxed{ h^k=TRM_k(h^{\prime k}). }

9. Why is that powerful?

The projection merely merges:

h^{k-1}

with:

E(t_{i+k}).

The Transformer block can then perform a much richer transformation over that representation.

The source explains this as asking, conceptually:

Given my current understanding and the future-token information, what is my updated understanding?

Thus the module doesn't merely generate a token.

It generates a new latent state.

That new state becomes useful to the next stage. (Source: Build a DeepSeek Model (From Scratch))

10. The causal chain

Now the entire process for three MTP stages is:

h_i^0

↓

\boxed{ [h_i^0;E(t_{i+1})] }

↓

M_1

↓

TRM_1

↓

h_i^1

↓

\boxed{ [h_i^1;E(t_{i+2})] }

↓

M_2

↓

TRM_2

↓

h_i^2

↓

\boxed{ [h_i^2;E(t_{i+3})] }

↓

M_3

↓

TRM_3

↓

h_i^3.

The source explicitly says the refined state from Head 1 becomes the input hidden state for Head 2, then Head 2 feeds Head 3. (Source: Build a DeepSeek Model (From Scratch))

11. Why does h_prev keep changing?

Look at the full-model logic from the source:

h_prev = h_main

for depth_k in range(1, self.num_mtp_heads + 1):
    ...
    h_curr = self.mtp_modules[
        depth_k - 1
    ](
        h_prev_sliced,
        future_token_embeds
    )

    ...
    h_prev = h_curr

(Source: Build a DeepSeek Model (From Scratch))

The critical line is:

h_prev = h_curr

That is what turns multiple modules into a chain.

Without it:

M_2(h^0,\cdot)

would be independent of:

M_1.

With it:

\boxed{ M_2(h^1,\cdot) }

depends on the refinement performed by MTP 1.

12. Now understand the sequence shrinking

Suppose:

S=20.

With three MTP stages, the source's conceptual verification example produces:

\boxed{ \begin{aligned} \text{Main} &: [2,20,1000]\\ \text{MTP 1} &: [2,19,1000]\\ \text{MTP 2} &: [2,18,1000]\\ \text{MTP 3} &: [2,17,1000]. \end{aligned} }

The source explicitly reports these shapes and says the shrinking middle dimension confirms the causal chain. (Source: Build a DeepSeek Model (From Scratch))

Why does it shrink?

Because a prediction k steps into the future cannot exist for the final k positions of the sequence.

For example, with:

S=20

you cannot ask for a 3-step future target from the last position because that token doesn't exist in the provided sequence.

So the valid prediction region gets shorter.

13. The indexing in the actual Chapter 6 code

Chapter 6 uses:

h_prev_shifted = h_prev[:, :-(k+1), :]

and:

next_tokens_embed = self.embed(
    input_ids[:, k:-1]
)

(Source: Build a DeepSeek Model (From Scratch))

For example, when:

k=1

the source removes the last two positions from h_prev:

S\rightarrow S-2.

And it extracts future embeddings over the same resulting length.

This is the specific indexing used by the Chapter 6 Mini-DeepSeek implementation.

14. Source-level caution about MTP indexing

There is an important source difference here.

The earlier Chapter 5 verification implementation uses:

L=S-k

for prediction depth k. (Source: Build a DeepSeek Model (From Scratch))

The Chapter 6 MiniDeepSeek implementation instead uses:

h_{\text{prev}}[:, :-(k+1),:]

which yields:

S-k-1

positions. (Source: Build a DeepSeek Model (From Scratch))

So the two source implementations are not identical in their indexing convention.

We should not silently "fix" one to match the other. For our current task, the Chapter 6 code is the implementation we are studying.

That distinction becomes important when you later write your own exact implementation.

15. The MTP output goes through the shared LM head

After obtaining:

h_k,

the source computes:

logits_k =
    self.lm_head(
        self.norm_f(h_k)
    )

(Source: Build a DeepSeek Model (From Scratch))

So:

[B,L,d] \rightarrow [B,L,V].

Each position now gets a vocabulary-sized prediction.

For vocabulary:

V=50,257,

we obtain:

\boxed{ logits_k\in\mathbb R^{B\times L\times50257}. }

16. Why is the LM head shared?

The source's broader MTP implementation explicitly says that the same output/unembedding layer is used by the main model and all MTP heads. (Source: Build a DeepSeek Model (From Scratch))

In the Mini-DeepSeek code, the same:

self.lm_head

is invoked for the main output and every MTP module. (Source: Build a DeepSeek Model (From Scratch))

So conceptually:

h_main ────────┐
               │
h¹ ────────────┤
               ├──→ shared LM head → vocabulary logits
h² ────────────┤
               │
h³ ────────────┘

This avoids creating a separate huge vocabulary projection for every MTP stage.

17. Why not use separate output heads?

Suppose:

d=768

and:

V=50,257.

One vocabulary projection already contains roughly:

768\times50,257

weights.

Creating a completely independent one for every MTP stage would multiply that cost.

The source instead uses a shared output layer, reducing redundant parameters and maintaining a common vocabulary projection. (Source: Build a DeepSeek Model (From Scratch))

18. Now the most important part: the loss

The main Transformer gives:

L_{\text{main}}.

Each MTP head gives:

L_{\text{MTP}}^{(1)}, L_{\text{MTP}}^{(2)}, \ldots, L_{\text{MTP}}^{(D)}.

The source combines them as:

\boxed{ L = L_{\text{main}} + \frac{\lambda}{D} \sum_{k=1}^{D} L_{\text{MTP}}^{(k)} }

(Source: Build a DeepSeek Model (From Scratch))

where:

  • D = number of MTP depths
  • \lambda = MTP loss weight.

This is the same formula we derived earlier, now appearing inside the actual model.

19. Why divide by D?

Suppose:

D=3.

Without normalization, we would add:

L_1+L_2+L_3.

The contribution from the MTP system grows automatically as we add more heads.

The source instead uses:

\frac{\lambda}{D} (L_1+L_2+L_3).

This gives a weighted average of the MTP losses, multiplied by \lambda.

So:

\boxed{ \lambda }

controls the overall importance of MTP relative to the main objective.

20. Why does this create a richer gradient?

Suppose the total loss is:

L= L_{\text{main}} + \frac{\lambda}{D} (L_1+L_2+L_3).

Then the shared early representations receive gradient contributions from multiple objectives.

Conceptually:

                    L_main
                       │
                       ▼
                    h⁰ / trunk
                       ▲
                       │
             ┌─────────┼──────────┐
             │         │          │
             L₁        L₂         L₃
             │         │          │
             ▼         ▼          ▼
           MTP1      MTP2       MTP3

But because the modules are chained:

h^0\rightarrow h^1\rightarrow h^2\rightarrow h^3,

the gradients from deeper MTP stages can propagate backward through earlier MTP stages and ultimately into the main trunk.

This connects directly to the gradient-flow discussion we completed earlier.

The source describes the resulting signal as a rich, multi-faceted gradient signal that improves both immediate prediction and longer-range forecasting. (Source: Build a DeepSeek Model (From Scratch))

21. A concrete chain example

Let's use a tiny sequence:

The   cat   sat   on   mat   .
 t0    t1    t2   t3   t4   t5

The main model produces hidden states:

h_0^0,h_1^0,h_2^0,\ldots

For a particular starting position i=0:

Main objective

Predict the next token:

t_1.
MTP stage 1

Use:

h_0^0

together with the appropriate future-token embedding specified by the MTP construction, then create:

h_0^1.
MTP stage 2

Use:

h_0^1

and the next future-token embedding to create:

h_0^2.
MTP stage 3

Use:

h_0^2

and another future-token embedding to create:

h_0^3.

Each stage produces vocabulary logits and contributes an MTP loss.

The source's conceptual description explicitly frames each stage as producing a refined hidden state that is passed onward. (Source: Build a DeepSeek Model (From Scratch))

22. One extremely important point: training vs inference

For this source implementation, MTP is primarily a training mechanism.

During training:

\boxed{ \text{future token embedding = ground truth} }

The source explicitly says this. (Source: Build a DeepSeek Model (From Scratch))

Therefore the model gets teacher-forced future embeddings while constructing the MTP chain.

This is different from ordinary generation, where the next token is not known in advance.

23. So are MTP predictions themselves used to generate the training input?

No.

During training, the source uses:

E(t_{i+k})

from the actual input sequence.

So the MTP chain gets the ground-truth future-token embedding, not the model's sampled prediction.

This is why the MTP training mechanism can provide a stable training signal.

24. What happens to MTP during normal model inference?

The Chapter 6 source makes an explicit split in MiniDeepSeek.forward():

targets provided
        ↓
training path
        ↓
main trunk + MTP

versus:

targets is None
        ↓
inference path
        ↓
KV-cache generation

The inference path returns the main logits and updated cache, while the MTP training path is entered when targets are supplied. (Source: Build a DeepSeek Model (From Scratch))

So for this implementation:

\boxed{ \text{MTP is part of the training path} }

while:

\boxed{ \text{ordinary autoregressive generation uses the cached main path}. }

The source also discusses MTP as something that can be leveraged for future-token prediction/speculative-style acceleration, but that is a later connection rather than the core Chapter 6 training path.

26. Why is the MTP block itself causal?

The Chapter 6 implementation creates:

mask = torch.triu(
    torch.ones(
        S, S,
        device=x.device,
        dtype=torch.bool
    ),
    diagonal=1
)

then:

attn_mask = torch.zeros(
    S, S,
    device=x.device
).masked_fill(
    mask,
    float('-inf')
)

and passes the resulting mask into the dedicated Transformer block. (Source: Build a DeepSeek Model (From Scratch))

So even within an MTP module, attention remains causal.

The architecture therefore preserves the principle:

\boxed{ \text{no future information beyond what the MTP construction intentionally provides}. }

27. Why is there no KV cache inside MTP?

The source explicitly states:

We don't use KV cache inside MTP during training

and the implementation calls the block without a cached state. (Source: Build a DeepSeek Model (From Scratch))

That makes sense in this training setup because the whole training sequence is already processed in parallel.

So:

\boxed{ \text{main trunk training: full sequence} }

and:

\boxed{ \text{MTP training: full available MTP sequence} }

rather than one-token-at-a-time cached generation.

30. The deepest conceptual point

The MTP system is not simply:

\boxed{ \text{"predict 3 tokens instead of 1"} }

The more useful interpretation is:

\boxed{ \text{repeatedly refine a latent representation toward increasingly distant future positions}. }

That is why the hidden state itself is passed through the chain:

\boxed{ h^0\rightarrow h^1\rightarrow h^2\rightarrow\cdots\rightarrow h^D. }

The source calls this sequential/cascaded latent refinement. (Source: Build a DeepSeek Model (From Scratch))
