Motivation

Keep weight storage, active arithmetic and measured runtime separate while interpreting large MoE models.

Prerequisites

  • Two-layer FFN matrix shapes and parameter counts
  • Stable softmax, top-k, integer indices and gather/scatter accumulation
  • Expert parallelism, load/importance distinction and non-gradient feedback
  • GB versus GiB and measurement denominators

Notation and units

  • T=B×S flattened tokens, D model width, N routed experts, k selected per token
  • Row score matrix[T, N]; selected indices and gates[T, k]; final stream[T, D]
  • Book bias is a persistent nontrainable buffer; gate weights come from softmax selected biased logits
  • V3: si=sigmoid(x·ei); select by si+bi; normalize original si within selected set
  • 671B/37B figures describe complete published model total/activated weights, not only one expert pool

Assumptions

  • Bias-free educational two-matrix GELU experts use2DHparameters; gated/SwiGLUuses3DH
  • Per-tokenk/N is routed expert activation fraction, notcomplete-model storage or latency ratio
  • The Transformer owns the residual unless a standalone MoE explicitly returns x+transform; neveraddit twice
  • Tie behavior and normalization must be explicit; expert choices are learned, not manual domain labels

Step-by-step derivation

  1. Total weights671×10^9times2bytesgive1.342×10^12bytes=1342decimal GB; binary GiB is about1249.83. Quantization and sharding change placement/representation but not published parameter total.
  2. 37/671=5.514157974%activated per-token by reported count. Its reciprocal18.1351iscapacity/activated ratio with no implied18×latencyclaim.
  3. Across multiple positions, the union of activated experts can be much larger than an individual token’sselection. Unused weights must remain available for future tokens.
  4. Compute examples use2DH for book experts, or3DH for gated SwiGLU experts. Add always-active attention, norm/router/shared weights and account separately for embedding/output head conventions.
  5. The book scaled experiment reports standard350iter/minversus428.6iter/min,14.29minversus11.67minandloss1.9854versus1.9451. Compute improvements using the baseline-denominator, then qualify hardware, seed, data and configuration.
  6. Measured throughput incorporates communication, load balance and kernel utilization; an ideal routed parameter fraction alone cannot predict it.

Step 5.42 — DeepSeek-MoE: End-to-End Numerical Analysis, Active Parameters, Compute, and Why 671B ≠ 671B Active

Plan node: A2 · chat order #83

↩ Back to main text: Step 1.10 — Position-Wise Feed-Forward Network (FFN / MLP)

We now have the complete DeepSeek-MoE mechanism. This step is about being able to calculate what actually happens, especially for exam numericals and system-design questions.

The source gives a scaled-down experiment comparing a standard MoE with its DeepSeek-style implementation, and later uses the DeepSeek-R1 figures of 671B total parameters and 37B active parameters per token to explain the deployment problem. (Source: Build a DeepSeek Model (From Scratch))

5.42.1 The most important MoE distinction

There are three numbers you must keep separate:

\boxed{\text{Total parameters}}
\boxed{\text{Active parameters per token}}
\boxed{\text{Parameters physically stored}}

For a dense model:

\text{total}\approx\text{active per token}.

For MoE:

\boxed{ \text{total}\gg\text{active per token} }

because only selected experts are used for each token.

5.42.2 Why MoE is powerful

Suppose we have:

64

routed experts.

Each has:

100M

parameters.

Then total routed-expert parameters are:

64\times100M = \boxed{6.4B}.

But if:

k=8,

only:

8\times100M = \boxed{800M}

routed-expert parameters participate for a token.

So:

\boxed{ 6.4B\text{ total expert capacity} }

but:

\boxed{ 800M\text{ active expert parameters/token} }

under this simplified equal-expert setup.

5.42.3 Active fraction

If all experts have equal size, and only k out of N are selected:

\boxed{ \text{active fraction} \approx \frac{k}{N} }

for the routed expert pool.

Example:

N=64,\qquad k=8.

Then:

\frac{8}{64} = \boxed{12.5\%}.

So approximately 12.5% of the routed-expert pool is active for each token.

This is a mathematical consequence of the sparse Top-K design, not a source-stated universal percentage.

5.42.4 But total memory does not shrink by 87.5%

This is one of the most common conceptual mistakes.

People often say:

“Only 12.5% is active, so the model only needs 12.5% of its memory.”

No.

The full expert weights are still part of the model.

Therefore:

\boxed{ \text{MoE reduces per-token computation much more directly than total weight storage} }

The source makes this explicit for DeepSeek-R1: 671B total parameters must be stored even though only 37B are activated per token. (Source: Build a DeepSeek Model (From Scratch))

5.42.5 DeepSeek-R1 numerical

The source gives:

\boxed{671B}

total parameters.

Active per token:

\boxed{37B}.

Compute the ratio:

\frac{671}{37} \approx \boxed{18.14}.

So the model has roughly:

\boxed{18.1\times}

as many total parameters as the number activated per token.

This does not mean the model is 18× faster than a dense 671B model; the actual runtime also depends on architecture, communication, memory bandwidth, attention, routing, hardware, and other factors.

The ratio simply quantifies total-vs-active parameter scale.

5.42.6 Active percentage

\frac{37}{671}\times100
\approx \boxed{5.51\%}.

So approximately:

\boxed{5.5\%}

of the total parameter count is active per token, using the source's rounded figures.

Again, this is not the same as saying only 5.5% of the model must be stored.

5.42.7 FP16 memory numerical

The source gives:

671B

parameters and assumes FP16.

FP16 uses:

2\text{ bytes/parameter}.

Therefore:

671\times10^9\times2 = 1.342\times10^{12}\text{ bytes}.

Using the source's decimal-style presentation:

\boxed{1342\text{ GB}}.

The source explicitly reports approximately 1342 GB. (Source: Build a DeepSeek Model (From Scratch))

So even though only:

37B

are active per token, the full model is still enormous in weight storage.

5.42.8 What would 37B parameters occupy in FP16?

This is a useful comparison.

37B\times2 = 74B\text{ bytes}.

Approximately:

\boxed{74\text{ GB}}

under the same decimal convention.

So conceptually:

\boxed{ 671B\text{ total}\rightarrow1342GB }

while:

\boxed{ 37B\text{ active}\rightarrow74GB }

under FP16 arithmetic.

This does not mean the system can simply delete the remaining 634B parameters during inference, because future tokens may route to different experts.

5.42.9 Why can a different token activate different parameters?

Token 1 might produce:

TopK(T_1)=\{E_2,E_7,E_{15},\ldots\}

while token 2 might produce:

TopK(T_2)=\{E_1,E_4,E_{12},\ldots\}.

So over a sequence:

\boxed{ \text{different tokens use different portions of the model} }.

That is the essence of conditional computation.

5.42.10 Sequence-level view

Suppose:

N=8,\quad k=2.

For five tokens:

T_1\rightarrow\{E_1,E_2\}
T_2\rightarrow\{E_3,E_4\}
T_3\rightarrow\{E_1,E_4\}
T_4\rightarrow\{E_5,E_6\}
T_5\rightarrow\{E_2,E_7\}.

The model activates only two experts per token, but across the sequence many experts may participate.

So:

\boxed{ \text{per-token sparsity} \neq \text{sequence-wide sparsity over the same fixed experts} }.

5.42.12 Ideal load

For:

T=5,\quad k=2,\quad N=8,

ideal average:

\bar C= \frac{Tk}{N} = \frac{10}{8} = \boxed{1.25}.

Actual:

[2,2,1,2,1,1,1,0].

This is why balancing is needed.

5.42.13 Bias update for this example

Use:

v_i= \frac{\bar C-C_i} {\bar C+\epsilon}.

Ignoring the tiny \epsilon for intuitive calculation:

Expert 1
v_1= \frac{1.25-2}{1.25} = \boxed{-0.6}.
Expert 8
v_8= \frac{1.25-0}{1.25} = \boxed{1}.

Therefore:

b_1\downarrow

and:

b_8\uparrow.

5.42.14 Now let's connect parameter count to compute

Suppose an expert FFN has:

D=4096

and:

Ignoring biases, one expert has:

2DH

parameters.

Therefore:

With:

64

64\times8,388,608 = \boxed{536,870,912}.

So:

\boxed{536.9M}

expert parameters exist in the routed pool.

5.42.15 Active expert parameters

If:

k=8,

Exactly matching:

Now compare:

Aggregate hidden capacity:

Fine-grained

Aggregate hidden capacity:

\boxed{ \text{same aggregate expert capacity} }.

This is the exact source example. (Source: Build a DeepSeek Model (From Scratch))

5.42.17 Activated capacity

Suppose conventional routing uses:

k=2.

Then activated hidden capacity is:

2\times4096 = \boxed{8192}.

Suppose fine-grained routing uses:

k=8.

Then:

8\times1024 = \boxed{8192}.

Therefore:

\boxed{ kH }

is preserved.

This is the mathematical reason one can split experts more finely without necessarily increasing the per-token expert capacity.

Again, this is a derived interpretation of the source's capacity-preserving example, not a claim that these exact k values define a specific DeepSeek production configuration.

5.42.18 Parameter memory vs active compute

This gives us a very important systems table:

Quantity Meaning
Total expert parameters All expert weights in the model
Active expert parameters Experts selected for a particular token
Expert load Number of token assignments to each expert
Expert capacity Maximum tokens an expert can accept in a batch

Do not mix these four.

5.42.19 Complexity — dense FFN

This section is a mathematical inference from matrix multiplication cost.

For:

X\in\mathbb R^{T\times D}

and:

W_1\in\mathbb R^{D\times H},

the first projection costs approximately:

O(TDH)

multiply-accumulate work.

The second projection is also approximately:

O(THD).

Therefore:

\boxed{ O(TDH) }

up to constant factors for the two projections.

5.42.20 Complexity — sparse MoE

Suppose there are:

N

experts, each with the same hidden dimension H, but only:

k

are activated.

Ignoring routing and communication overhead, the expert computation becomes approximately:

\boxed{ O(TkDH) }

rather than:

O(TNDH).

Thus the idealized expert-computation ratio is:

\boxed{ \frac{k}{N} }.

This is an inference from the Top-K sparse structure; the source emphasizes the sparsity benefit conceptually rather than giving this asymptotic formula. (Source: Build a DeepSeek Model (From Scratch))

5.42.21 But there is a router cost

The router itself computes:

L=XW_R.

If:

X\in\mathbb R^{T\times D}

and:

W_R\in\mathbb R^{D\times N},

then router computation is approximately:

\boxed{ O(TDN) }.

So MoE is not:

O(TkDH)

and nothing else.

More realistically, the conceptual cost is:

\boxed{ \text{router} + \text{selected expert compute} + \text{dispatch/communication} }.

For large distributed systems, the communication component becomes particularly important; the source later identifies MoE All-to-All communication as a bottleneck motivating DualPipe. (Source: Build a DeepSeek Model (From Scratch))

5.42.22 Why N can be large

The router has to score all routed experts.

So increasing:

N

increases router-side work:

O(TDN).

But expert computation only uses:

k

experts.

Therefore there is a trade-off:

\boxed{ N\uparrow \Rightarrow \text{more routing choices / specialization} }

but also:

\boxed{ \text{more router and dispatch complexity} }.

This is why MoE engineering is not simply:

“Use as many experts as possible.”

5.42.23 Complete end-to-end numerical problem

Now let's solve a full one.

Suppose:

B=2
S=4
D=8
N=4
k=2.

There are:

T=BS=8

tokens.

Step A — Router shape
X_f\in\mathbb R^{8\times8}.

Router:

W_R\in\mathbb R^{8\times4}.

Thus:

L=X_fW_R

has:

\boxed{8\times4}.
Step B — Top-K

Each of the 8 tokens selects 2 experts.

Total assignments:

8\times2 = \boxed{16}.
Step C — Ideal load
16/4 = \boxed{4}.

So ideal expert load is:

[4,4,4,4].
Step D — Suppose actual counts are
[6,2,5,3].

Check:

6+2+5+3 = 16.

So:

\boxed{ E_1,E_3\text{ are relatively overloaded} }

and:

\boxed{ E_2,E_4\text{ are relatively underloaded}. }
Step E — Violations
v_i= \frac{4-C_i}{4}.

Therefore:

v_1= \frac{4-6}{4} = \boxed{-0.5}
v_2= \frac{4-2}{4} = \boxed{0.5}
v_3= \frac{4-5}{4} = \boxed{-0.25}
v_4= \frac{4-3}{4} = \boxed{0.25}.

So:

\boxed{ v=[-0.5,0.5,-0.25,0.25]. }
Step F — Direction of bias correction
\boxed{ b_1\downarrow }
\boxed{ b_2\uparrow }
\boxed{ b_3\downarrow }
\boxed{ b_4\uparrow }.

That is exactly the balancing feedback.

5.42.24 What happens in the next batch?

Suppose before correction:

L_t=[2.0,1.9,2.2,1.8].

For a particular token.

Suppose dynamic bias after the previous batch is:

b=[-0.1,+0.1,-0.05,+0.05].

Adjusted:

L'= [1.9,2.0,2.15,1.85].

Top-2:

\boxed{E_3,E_2}.

Before balancing, perhaps it was:

E_3,E_1.

So the bias has changed the routing decision itself.

That is why DeepSeek modifies the logits before Top-K. (Source: Build a DeepSeek Model (From Scratch))

5.42.25 End-to-end pipeline as equations

Now all the mathematics is connected:

Input
X\in\mathbb R^{B\times S\times D}
Flatten
X_f\in\mathbb R^{BS\times D}
Router
L=X_fW_R
Bias
L'=L+b
Top-K
I_t=TopK(L'_t,k)
Gating
g_{t,i} = \frac{e^{L'_{t,i}}} {\sum_{j\in I_t}e^{L'_{t,j}}}
Routed expert output
R_t = \sum_{i\in I_t} g_{t,i}E_i(x_t)
Shared output
S_t= \sum_jS_j(x_t)
Residual
Y_t= x_t+S_t+R_t
Load measurement
C_i= \#\{\text{tokens routed to }E_i\}
Average
\bar C= \frac{Tk}{N}
Violation
v_i= \frac{\bar C-C_i} {\bar C+\epsilon}
Bias update
\boxed{ b_i \leftarrow b_i+ \eta\tanh(v_i) }

(Source: Build a DeepSeek Model (From Scratch))

5.42.31 Systems interpretation

Suppose four experts have:

[100,100,100,100]

tokens.

Perfect.

Each expert gets:

100

units of work.

Now suppose:

[180,20,0,200].

The total work is still:

400.

But the system is terrible.

One worker processes:

200,

another:

180,

one:

20,

and one:

0.

This is why:

\boxed{ \text{balanced routing} }

is not merely a machine-learning concern.

It is also a:

\boxed{ \text{systems utilization problem}. }

5.42.32 Why All-to-All appears in distributed MoE

Suppose:

GPU 0 owns E1,E2
GPU 1 owns E3,E4
GPU 2 owns E5,E6
GPU 3 owns E7,E8

A token on GPU 0 might be routed to:

E_7.

Therefore the token representation must move:

GPU_0\rightarrow GPU_3.

After computation, the result must return to the correct token location.

So the architecture creates communication:

\boxed{ \text{token dispatch} \rightarrow \text{remote expert} \rightarrow \text{result combine} }

This is the distributed-MoE challenge.

The source later describes All-to-All communication as a major bottleneck and motivates DeepSeek's DualPipe scheduling to overlap communication with computation. (Source: Build a DeepSeek Model (From Scratch))

5.42.33 Therefore, MoE efficiency has three layers

Think of it as:

\boxed{ \text{Algorithmic sparsity} }

↓

only k experts.

Then:

\boxed{ \text{Load balance} }

↓

those k-expert assignments are distributed properly.

Then:

\boxed{ \text{Distributed execution} }

↓

tokens must be moved efficiently between hardware.

This is why a good MoE architecture is both:

\boxed{\text{ML design}}

and:

\boxed{\text{systems design}}.

Suppose someone says:

The inactive expert parameters remain part of the model and must remain available, while routing determines which subset participates for each token. (Source: Build a DeepSeek Model (From Scratch))

Because the architecture first determines:

5.42.38 Exam trap #4

Question

Because the DeepSeek-style auxiliary-loss-free method is specifically designed to avoid adding a competing balancing objective to the primary language-learning objective. Instead, it modifies router scores through the dynamic bias. (Source: Build a DeepSeek Model (From Scratch))

The total expert capacity can therefore remain comparable while the number of specialists increases. (Source: Build a DeepSeek Model (From Scratch))
