Motivation

Define zero-shot transfer precisely enough that model selection cannot leak target-test information.

Prerequisites

  • Train/dev/test separation and task-specific fine-tuning
  • Tokenizer, vocabulary, multilingual pretraining
  • Accuracy, precision/recall and F1; distinguish points from relative percent
  • Hyperparameter search, checkpoints and language-family transfer

Notation and units

  • L is a language; task and language jointly define an evaluation set
  • Scores are on a declared 0..100 scale; score differences are points
  • Corpus tokens depend on the counting tokenizer and release; a token is not necessarily a word
  • theta(task, h) denotes a checkpoint for one task/hyperparameter configuration
  • h*=argmax English-dev score; target test is evaluated once after selection

Assumptions

  • All historical counts are attributed to the supplied release/paper, not presented as live 2026 leaderboard facts
  • Translated parallel examples share content and are not statistically independent across languages
  • Reported scores require fixed checkpoint, preprocessing, split, prompt and metric implementation
  • Zero-shot is relative to labeled task adaptation in the target language; target-language text can occur in multilingual pretraining
  • Train, dev, test examples must not overlap through translation or duplicate source content

Step-by-step derivation

  1. For every model and task, fine-tune on English task training data; task-specific heads and losses differ. Search learning rate/weight decay using English development data only.
  2. Freeze selected configuration and checkpoint before evaluating Indic test sets. Looking at Indic test scores to choose a checkpoint converts testing into optimization and inflates results.
  3. Target-language development selection does not require target-language gradient updates, but it does use target-language supervised information for selection; report it as a different setting.
  4. Hindi/Tamil in-family development selection is an empirical alternative, not strict English-only selection. Gold Hindi transfer uses genuine Hindi task labels; silver Hindi transfer uses translated English labels.
  5. A model trained on English and Hindi but evaluated on Bengali can be zero-shot Bengali labeled-task transfer; it is not zero-shot Hindi and is not the same baseline as English-only fine-tuning.
  6. Interpret reported Hindi gains as points on fixed tasks, not universal language superiority. Translation noise can hurt commonsense alternatives and answer-span alignment.

    2. Can target-dev selection be called strict English-only zero-shot? No, even if no target gradient update occurs.
    3. Gold versus silver? Genuine Hindi labels versus translated English task data; both must be separately labeled.

Strict zero-shot requires: \boxed{ \text{no target Indic-language training data} } and the benchmark's main protocol uses English training only. (Source: indicxtreme-slides)

    • Using Hindi as a bridge cannot be assumed equally good for every script or language family.

    Step 5.29 — IndicXTREME Zero-Shot Fine-Tuning Protocol

    Plan node: I10 · chat order #70

    Now we reach one of the most important experimental-design concepts in the IndicXTREME material.

    We already know:

    \boxed{\text{IndicXTREME has many Indic-language test sets}}

    But that alone does not tell us whether the benchmark is measuring:

    \boxed{\text{cross-lingual transfer}}

    or simply:

    \boxed{\text{ordinary supervised learning in each Indic language}}.

    The solution is the benchmark's zero-shot fine-tuning protocol. (Source: indicxtreme-slides)

    5.29.1 First understand the problem

    Imagine a model is trained directly on Hindi data.

    Then we test it on Hindi.

    Suppose it gets:

    90\%.

    What have we learned?

    The model is good at Hindi.

    But we have not learned whether it can transfer knowledge from another language into Hindi.

    Now consider:

    \boxed{ \text{English training} \rightarrow \text{Hindi testing} }

    If the model succeeds, that is evidence of:

    \boxed{ \text{cross-lingual transfer} }.

    That is what IndicXTREME is designed to evaluate. (Source: indicxtreme-slides)

    5.29.2 What does “zero-shot” mean here?

    It means the model receives no Indic-language training examples for the target benchmark task.

    The supplied slide is very explicit:

    \boxed{ \text{Indic-language training data = none} }

    Instead:

    \boxed{ \text{training data = English} }

    and the target evaluation is performed directly on Indic-language test data.

    (Source: indicxtreme-slides)

    5.29.3 The exact pipeline

    The deck gives three steps.

    Step 1 — Fine-tune on English

    For each task:

    \boxed{ \text{pretrained LM} \rightarrow \text{English task training data} }

    This is done independently for the task.

    For example:

    \text{English sentiment training}

    for IndicSentiment.

    Or:

    \text{English NLI training}

    for IndicXNLI.

    (Source: indicxtreme-slides)

    5.29.4 Step 2 — Select hyperparameters using English development data

    Suppose we test:

    \text{learning rate}\in \{10^{-5},2\times10^{-5},5\times10^{-5}\}

    and:

    \text{weight decay}\in \{0,0.01\}.

    We evaluate candidate configurations on the:

    \boxed{\text{English development set}}

    and choose the best one.

    Crucially:

    \boxed{ \text{Indic test data is not used for model selection} }

    according to the protocol. (Source: indicxtreme-slides)

    5.29.5 Step 3 — Evaluate directly on Indic test sets

    After selecting the model/configuration:

    \boxed{ \text{English-trained model} \rightarrow \text{Indic-language test set} }

    No Indic-language examples were used during the task training or model-selection process.

    So if we write:

    \theta^* = \arg\max_\theta \text{Score}_{EN-dev}(\theta),

    then evaluation is:

    \boxed{ \text{Score}_{Indic-test}(\theta^*) }

    This equation is a conceptual formalization of the protocol; the source states the three-stage procedure rather than presenting this exact notation.

    5.29.6 Why is this powerful?

    Suppose:

    \text{English training accuracy}=95\%

    and:

    \text{Hindi test accuracy}=85\%.

    The model has transferred:

    \boxed{ \text{task knowledge from English to Hindi} }.

    The benchmark is therefore asking:

    Does the multilingual pretrained representation allow knowledge learned in English to transfer into an Indic language?

    That is the fundamental scientific question.

    5.29.7 Why not train on Hindi too?

    Because then we would be measuring something different.

    Consider:

    Setup A
    \text{English + Hindi training} \rightarrow \text{Hindi test}.
    Setup B
    \text{English training} \rightarrow \text{Hindi test}.

    Setup A measures:

    \boxed{ \text{in-language supervised performance} }

    while Setup B measures:

    \boxed{ \text{zero-shot cross-lingual transfer} }.

    IndicXTREME is specifically interested in Setup B. (Source: indicxtreme-slides)

    5.29.8 The most important anti-leakage condition

    The deck states:

    \boxed{ \text{no Indic data is seen during training or model selection} }

    This prevents a hidden source of information.

    Suppose the model is allowed to see 1000 Hindi development examples.

    Then choosing hyperparameters based on them could indirectly adapt the model to Hindi.

    The resulting performance would no longer represent a clean zero-shot evaluation.

    So the protocol creates:

    \boxed{ \text{training language} \neq \text{evaluation language} }

    5.29.9 Numerical example: why leakage matters

    Imagine two configurations.

    Model A

    English dev:

    82\%

    Hindi dev:

    77\%.
    Model B

    English dev:

    80\%

    Hindi dev:

    85\%.

    If we select using English dev:

    \boxed{\text{Model A wins}}

    because:

    82>80.

    If we select using Hindi dev:

    \boxed{\text{Model B wins}}

    because:

    85>77.

    Thus using Hindi development data changes model selection.

    That would introduce target-language information into the process.

    The actual deck uses English development selection specifically to avoid that issue. (Source: indicxtreme-slides)

    5.29.10 A subtle point: zero-shot does not mean zero training

    This is a common exam trap.

    Zero-shot here does not mean:

    \boxed{\text{the model receives no fine-tuning}}

    Instead:

    \boxed{ \text{the model is fine-tuned} }

    but:

    \boxed{ \text{not on the target Indic language} }.

    So:

    \boxed{ \text{zero-shot target-language transfer} }

    is more precise.

    5.29.11 Example: IndicSentiment

    Suppose the English training set contains:

    100,000

    English reviews.

    We fine-tune the multilingual model using those reviews.

    Then:

    \boxed{\text{NO Hindi reviews}}

    are used for training.

    Finally:

    \boxed{\text{Hindi reviews}}

    are used only for evaluation.

    If the model gets:

    88\%

    on Hindi, that result is evidence of transfer.

    5.29.12 Example: IndicXNLI

    English training:

    \text{Premise + Hypothesis} \rightarrow \text{English NLI labels}

    Then Hindi test:

    \text{Hindi Premise + Hypothesis} \rightarrow \text{prediction}.

    The model has to carry the NLI capability across languages.

    5.29.13 Why task-specific hyperparameter tuning matters

    The deck makes another methodological point.

    Many earlier approaches reused one fixed hyperparameter configuration across tasks.

    IndicXTREME instead performs a:

    \boxed{ \text{task-specific grid search} }

    for:

    \boxed{ \text{learning rate} }

    and:

    \boxed{ \text{weight decay} }.

    This is done for every model and task. (Source: indicxtreme-slides)

    5.29.14 Why is this fairer?

    Suppose:

    Task A

    works best with:

    LR=10^{-5}.
    Task B

    works best with:

    LR=5\times10^{-5}.

    If we force both to use:

    LR=10^{-5},

    Task B may be artificially weakened.

    Then we'd be measuring:

    \boxed{ \text{quality under a poor hyperparameter choice} }

    rather than:

    \boxed{ \text{quality of the underlying model} }.

    So task-specific tuning makes the comparison more informative.

    The source explicitly motivates this as part of fair comparison. (Source: indicxtreme-slides)

    5.29.15 But doesn't hyperparameter tuning introduce target information?

    The benchmark avoids that by selecting configurations on:

    \boxed{\text{English development data}}

    rather than the target Indic test data.

    So the target language remains hidden from model selection.

    This is a crucial experimental-design principle.

    5.29.16 Full experimental pipeline

    Keep this picture in your head:

                     Multilingual pretrained LM
                           │
                           ▼
                 English task training
                           │
                           ▼
                  English development
                           │
                     hyperparameter
                       selection
                           │
                           ▼
                    Final model θ*
                           │
                           ▼
          ┌────────────────┼─────────────────┐
          ▼                ▼                 ▼
       Hindi test       Tamil test       Bengali test
          │                │                 │
          ▼                ▼                 ▼
      zero-shot         zero-shot         zero-shot
      transfer          transfer          transfer

    No Indic-language training data enters before evaluation. (Source: indicxtreme-slides)

    5.29.17 Now comes the interesting extension

    The researchers ask:

    Does using an in-language development set help model selection?

    At first, the benchmark says:

    \boxed{\text{English dev}}

    is used.

    But they investigate alternatives.

    This produces an important distinction:

    \boxed{ \text{in-language} }

    versus:

    \boxed{ \text{in-family} }

    versus:

    \boxed{ \text{English} }.

    5.29.18 What is an in-language dev set?

    Suppose we're evaluating:

    \boxed{\text{Bengali}}.

    An in-language dev set is:

    \boxed{\text{Bengali development data}}.

    This gives direct feedback about the target language.

    But using it changes the strict zero-shot protocol because the target language now influences model selection.

    5.29.19 What is an in-family dev set?

    This is a very interesting intermediate idea.

    The deck uses:

    \boxed{\text{Hindi}}

    as a representative language for:

    \boxed{\text{Indo-European}}

    and:

    \boxed{\text{Tamil}}

    as a representative language for:

    \boxed{\text{Dravidian}}.

    (Source: indicxtreme-slides)

    So instead of having Bengali-specific dev data, one can potentially select using a related language.

    Conceptually:

    \boxed{ \text{Hindi dev} \rightarrow \text{select for other Indo-European languages} }

    and:

    \boxed{ \text{Tamil dev} \rightarrow \text{select for other Dravidian languages} }.

    5.29.20 Why might that work?

    Suppose two languages share some useful linguistic structure.

    Then a model configuration that works well on:

    L_1

    may also work reasonably well on:

    L_2

    within the same family.

    This can provide a compromise:

    \boxed{ \text{better than English-only selection} }

    without needing a separate development set for every target language.

    The source reports that these in-family dev sets perform on par with true in-language dev sets and clearly ahead of English-only selection. (Source: indicxtreme-slides)

    5.29.21 Let's inspect the reported table

    The slide compares:

    • English development selection,
    • in-language development selection,
    • in-family development selection.

    The table shows that for the reported tasks, in-family selection tends to be close to actual in-language selection and better than English-only selection. (Source: indicxtreme-slides)

    For example, on IndicSentiment, the table reports approximately:

    \text{mBERT: }72.9

    for in-language and:

    72.9

    for in-family, compared with a smaller English-dev-selected result.

    For IndicBERT, the reported numbers similarly show in-family selection tracking in-language performance closely. (Source: indicxtreme-slides)

    We should interpret the pattern rather than memorize every table cell.

    5.29.22 What does this tell us?

    There appears to be a useful hierarchy:

    \boxed{ \text{English dev} < \text{related-language dev} \approx \text{target-language dev} }

    for the reported experiments.

    The key lesson is:

    \boxed{ \text{language-aware model selection can matter} }

    even when actual target-language training remains absent.

    The precise numerical gains are task/model dependent; the deck's broad conclusion is the important point. (Source: indicxtreme-slides)

    5.29.23 Why is Hindi particularly interesting?

    Now the deck goes one step further.

    It asks:

    What happens if Hindi itself becomes the transfer language?

    The slide reports:

    \boxed{\text{Hindi is a better transfer language than English}}

    for the evaluated tasks. (Source: indicxtreme-slides)

    This is a major observation.

    5.29.24 “Gold zero-shot”

    The deck defines:

    \boxed{\text{gold zero-shot}}

    as using real Hindi training data for the tasks.

    So instead of:

    \text{English training} \rightarrow \text{Indic test},

    we have:

    \boxed{ \text{Hindi training} \rightarrow \text{other Indic-language test} }.

    This is not strict zero-shot with respect to Hindi, because the model sees Hindi training data.

    It is better understood as cross-Indic transfer from Hindi.

    The slide explicitly uses the term “gold zero-shot” for this setup. (Source: indicxtreme-slides)

    5.29.25 “Silver zero-shot”

    The deck also constructs:

    \boxed{\text{silver zero-shot}}

    by machine-translating the English training set into Hindi.

    So:

    \text{English training}

    becomes:

    \boxed{ \text{machine-translated Hindi training} }

    and then the model transfers from Hindi to the other Indic languages.

    This provides:

    \boxed{ \text{Hindi-language supervision without manually creating Hindi data} }

    although translation errors can be introduced.

    (Source: indicxtreme-slides)

    5.29.26 Reported Hindi transfer gains

    The deck reports that switching the transfer language from English to Hindi in the evaluated setup lifts:

    \boxed{\text{NER by }+3.5}
    \boxed{\text{Intent by }+3.1}
    \boxed{\text{Slot-filling by }+10.6}

    percentage points. (Source: indicxtreme-slides)

    These are source-derived results.

    5.29.27 Why might Hindi help?

    The deck's result supports the idea that:

    \boxed{ \text{English is not necessarily the optimal transfer language for Indic targets} }

    because Hindi may share more useful linguistic properties with other Indic languages than English does.

    We should be careful, though:

    \boxed{ \text{Hindi} \neq \text{equally close to every Indic language} }

    and the source does not establish a universal rule that Hindi must always be the best transfer language.

    The conclusion is specific to the experiments reported.

    5.29.28 Gold vs silver transfer

    Here is the distinction:

    Gold zero-shot
    \boxed{ \text{real Hindi task training data} }
    Silver zero-shot
    \boxed{ \text{machine-translated Hindi task training data} }

    The silver approach is cheaper/easier to construct, but introduces translation errors.

    The deck reports that silver transfer helps:

    \boxed{ \text{sentiment} }
    \boxed{ \text{XNLI} }
    \boxed{ \text{paraphrase} }

    similarly, but hurts:

    \boxed{ \text{IndicCOPA} }

    and:

    \boxed{ \text{IndicQA} }.

    (Source: indicxtreme-slides)

    5.29.29 Why would translation hurt COPA and QA?

    The source explicitly attributes this to the sensitivity of these tasks to small translation errors. (Source: indicxtreme-slides)

    This makes intuitive sense.

    For causal reasoning:

    \boxed{ \text{one subtle wording change} }

    can alter which cause is plausible.

    For QA:

    \boxed{ \text{small translation error} }

    can change:

    \text{answer span}

    or:

    \text{question/context relationship}.

    So:

    \boxed{ \text{translation noise} \rightarrow \text{task-dependent degradation} }

    is the important lesson.

    5.29.30 Numerical example — transfer improvement

    Suppose a baseline NER score is:

    70.0.

    The reported Hindi-transfer improvement is:

    +3.5.

    Then:

    70.0+3.5 = \boxed{73.5}.

    For slot filling, suppose:

    60.0

    baseline.

    Then:

    60.0+10.6 = \boxed{70.6}.

    These are illustrative starting scores; the actual source provides the gains, not these hypothetical baselines. (Source: indicxtreme-slides)

    5.29.31 A very important conceptual distinction

    Don't confuse these three experiments.

    Strict IndicXTREME zero-shot
    \boxed{ \text{English train} \rightarrow \text{Indic test} }
    Gold Hindi transfer
    \boxed{ \text{Hindi train} \rightarrow \text{other Indic test} }
    Silver Hindi transfer
    \boxed{ \text{machine-translated Hindi train} \rightarrow \text{other Indic test} }

    All are evaluating transfer, but they answer different scientific questions.

    5.29.32 Why the benchmark starts with English

    Because English is the conventional high-resource transfer language.

    So the baseline question is:

    \boxed{ \text{Can multilingual pretraining transfer task knowledge from English into Indic languages?} }

    Then the Hindi experiments ask a deeper question:

    \boxed{ \text{Would a linguistically closer Indic transfer language work better?} }

    That is a much more sophisticated benchmark study.

    5.29.33 Exam-style numerical question

    Suppose:

    \text{English transfer score}=65.0

    and Hindi transfer gives:

    +10.6.

    Then:

    65.0+10.6 = \boxed{75.6}.

    Relative improvement:

    \frac{10.6}{65.0}\times100 \approx \boxed{16.31\%}.

    Again, the +10.6 is source-derived for slot filling; 65.0 is hypothetical.

    5.29.34 Another exam question: strict zero-shot

    A student says:

    “The model was fine-tuned on English and Hindi before being evaluated on Bengali, so this is zero-shot Bengali.”

    Under the deck's strict protocol, that statement is:

    \boxed{\text{incorrect}}

    because Hindi-language training data was used.

    Strict zero-shot requires:

    \boxed{ \text{no target Indic-language training data} }

    and the benchmark's main protocol uses English training only. (Source: indicxtreme-slides)

    5.29.35 Another exam question: model selection

    Suppose there are three learning rates:

    10^{-5},\;2\times10^{-5},\;5\times10^{-5}.

    Their English-dev accuracies are:

    80,\;84,\;82.

    Choose:

    \boxed{2\times10^{-5}}.

    Then test this configuration on Hindi.

    Suppose Hindi accuracy is:

    78.

    You must not go back and select the learning rate because another learning rate gave:

    82

    on Hindi test.

    That would contaminate the evaluation.

    This is exactly why model selection is restricted to English development data.

    5.29.36 Why this protocol is experimentally clean

    The sequence:

    \boxed{ \text{Train on English} }
    \downarrow
    \boxed{ \text{Choose using English dev} }
    \downarrow
    \boxed{ \text{Freeze the choice} }
    \downarrow
    \boxed{ \text{Test on Indic} }

    means the target-language test set is truly an unseen evaluation environment.

    This reduces the chance that the benchmark score is inflated by target-language adaptation.

    5.29.37 But there is still a deeper question

    Suppose English is a very different language from Hindi.

    Then perhaps:

    \boxed{ \text{English transfer} }

    is simply a poor experimental baseline for Indic languages.

    The Hindi experiments investigate exactly that.

    If Hindi is a better transfer language, then the problem isn't necessarily:

    \text{multilingual model failure}.

    It may partially be:

    \boxed{ \text{choice of source/transfer language} }.

    This is one of the most interesting implications of the deck's later analysis. (Source: indicxtreme-slides)

    5.29.38 Complete conceptual picture

    We started with:

    \boxed{ \text{English} \rightarrow \text{Indic} }

    and discovered that transfer is imperfect.

    Then we tested:

    \boxed{ \text{in-language dev} }

    and:

    \boxed{ \text{in-family dev} }

    and found that in-family selection can approach in-language selection in the reported experiments. (Source: indicxtreme-slides)

    Then we tested:

    \boxed{ \text{Hindi} \rightarrow \text{other Indic} }

    and found substantial gains on some tasks. (Source: indicxtreme-slides)

    So the experiment evolves from:

    \boxed{ \text{Can English transfer?} }

    to:

    \boxed{ \text{Does language-aware model selection help?} }

    to:

    \boxed{ \text{Is a related Indic language a better transfer source?} }

    That is the logic of the entire section.

    5.29.40 Final mental model

    The most important equation from this whole section is:

    \boxed{ \underbrace{ \text{English supervision} }_{\text{task learning}} \rightarrow \underbrace{ \text{Indic evaluation} }_{\text{language transfer}} }

    \boxed{ \text{“Does the model know the task?”} }

    from:

    \boxed{ \text{“Can the model transfer that knowledge across languages?”} }

    \boxed{ \text{“Which language is the best source for cross-lingual transfer?”} }
