Step 5.17 — From the 800K Dataset to Actual Student Training

Plan node: I8 · chat order #58

Now we take everything from Steps 5.14–5.16 and turn it into an actual training process.

We know:

\boxed{\text{R1 generates the data}}
\boxed{\text{rejection sampling cleans the data}}
\boxed{\text{student receives teacher-response tokens}}

Now the question is:

What happens during every training step?

The source's training loop is deliberately close to a standard PyTorch language-model fine-tuning loop. The special part is the answer-only distillation loss; the rest is ordinary optimization machinery. (Source: Build a Reasoning Model (From Scratch))

5.17.1 The whole training loop first

The source's flow is:

800K curated examples
        ↓
   Training set
        ↓
   shuffle examples
        ↓
 choose one example
        ↓
 answer-only CE loss
        ↓
    backward()
        ↓
 optional gradient clipping
        ↓
   optimizer.step()
        ↓
 periodic validation
        ↓
 save checkpoint

This is repeated for multiple epochs. (Source: Build a Reasoning Model (From Scratch))

The key insight is:

\boxed{ \text{Distillation training itself looks like ordinary SFT} }

There is no GRPO rollout, reward calculation, advantage estimation, policy ratio, or KL-to-reference stage in this student-training loop.

5.17.2 Step 1 — Start from a pretrained base model

The student is not initialized randomly.

For the practical source example, the student is a pretrained Qwen model. More generally, the DeepSeek distilled models retain their underlying Qwen/Llama pretrained base and fine-tune it with R1-generated data.

So:

\boxed{ \theta_0=\text{pretrained student parameters} }

Then training transforms:

\theta_0 \rightarrow \theta_1 \rightarrow \theta_2 \rightarrow \cdots \rightarrow \theta_{\text{final}}.

The teacher's parameters are not copied into this process.

5.17.3 Step 2 — Initialize AdamW

The source implementation uses:

optimizer = torch.optim.AdamW(model.parameters(), lr=lr)

(Source: Build a DeepSeek Model (From Scratch))

So the optimizer maintains information that helps adapt the parameter updates.

At the most basic level, think:

\boxed{ \theta \leftarrow \theta-\text{adaptive update based on }\nabla_\theta L }

The exact AdamW update contains first- and second-moment statistics and weight decay; the supplied distillation section does not derive those equations, so we will not pretend the chapter does.

The important source-grounded fact here is simply:

\boxed{\text{AdamW is used}}

for the training loop. (Source: Build a DeepSeek Model (From Scratch))

5.17.4 Step 3 — Choose the number of epochs

The practical function has:

epochs=2

by default. (Source: Build a Reasoning Model (From Scratch))

The larger DeepSeek-style configuration described elsewhere in the source uses:

\boxed{2\text{–}3\text{ epochs}}

over the 800K dataset. (Source: Build a DeepSeek Model (From Scratch))

5.17.5 What exactly is an epoch?

An epoch means:

\boxed{\text{one complete pass through the training set}}

Suppose:

N=800,000.

One epoch exposes the student to all approximately 800K examples once.

Two epochs:

800,000\times2 = \boxed{1.6\text{ million example presentations}}.

Three epochs:

800,000\times3 = \boxed{2.4\text{ million example presentations}}.

This does not mean 2.4 million unique samples. The same dataset is revisited.

5.17.6 Step 4 — Shuffle the training examples

The source explicitly does:

epoch_examples = list(train_examples)
rng.shuffle(epoch_examples)

at the start of every epoch. (Source: Build a Reasoning Model (From Scratch))

Why?

Suppose the dataset is stored:

Math
Math
Math
Math
...
Code
Code
Code
...
General
General
...

If you train in that fixed order, the optimizer may see long runs of similar examples.

Shuffling produces a less structured ordering:

Math → Code → General → Math → Logic → Code → ...

The model still sees the same distribution overall, but the order of gradient updates changes.

5.17.7 Why does order matter if the data is the same?

Because optimization is sequential.

Let:

g_1=\nabla L_1

and:

g_2=\nabla L_2.

The model first updates using g_1, changing its parameters before seeing g_2.

So:

\theta_1=\operatorname{Update}(\theta_0,g_1)

then:

\theta_2=\operatorname{Update}(\theta_1,g_2).

Changing the order changes the parameter trajectory.

Thus shuffling is a standard way to avoid an unnecessarily structured update sequence. The source explicitly includes it in every epoch. (Source: Build a Reasoning Model (From Scratch))

5.17.8 Step 5 — Take one training example

The source's simple implementation processes examples one at a time:

for example in epoch_examples:

(Source: Build a Reasoning Model (From Scratch))

This is intentionally pedagogical.

It is not meant to imply that production-scale training must use batch size 1.

The source explicitly notes that batching was omitted from the compact implementation and discusses throughput-oriented batching separately. (Source: Build a Reasoning Model (From Scratch))

5.17.9 Step 6 — Prepare input and target

For the teacher-generated token sequence:

t_1,t_2,\ldots,t_L

we construct:

X=[t_1,\ldots,t_{L-1}]

and:

Y=[t_2,\ldots,t_L].

Thus:

\boxed{ X=t[:-1] }
\boxed{ Y=t[1:] }

The model predicts the next token.

5.17.10 Step 7 — Run the student forward pass

The student computes:

Z=f_{\theta}(X).

For a sequence length L-1 and vocabulary size V:

\boxed{ Z\in\mathbb R^{(L-1)\times V} }

for the simple single-example implementation.

Each row represents:

\boxed{ \text{logits for the next-token prediction at one position} }

5.17.11 Step 8 — Throw away prompt-only loss positions

Suppose prompt length is:

P.

Then:

\boxed{ s=P-1 }

and:

answer_logits = logits[s:]
answer_targets = target_ids[s:]

(Source: Build a Reasoning Model (From Scratch))

This is extremely important.

The prompt still enters the model.

But the prompt-only predictions do not affect the optimization objective.

5.17.12 Step 9 — Compute cross-entropy

The source uses:

loss = torch.nn.functional.cross_entropy(
    answer_logits,
    answer_targets
)

(Source: Build a Reasoning Model (From Scratch))

Mathematically:

\boxed{ L = -\frac1N \sum_{t=1}^N \log P_\theta(y_t\mid x,y_{<t}) }

for the selected teacher-response positions.

So the student is trained to increase the probability of the teacher's demonstrated sequence.

5.17.13 Step 10 — Backpropagation

Now:

loss.backward()

(Source: Build a Reasoning Model (From Scratch))

PyTorch computes:

\boxed{ \nabla_\theta L }

for all trainable parameters.

This is where the error signal moves backward through:

\text{output logits} \rightarrow \text{output projection} \rightarrow \text{Transformer blocks} \rightarrow \text{embeddings}

and all relevant trainable components.

5.17.14 Why does only the student change?

Because the target sequence is already fixed.

The teacher generated:

y_1,\ldots,y_N

before student training.

Therefore the target doesn't depend on current student parameters.

So the gradient is:

\boxed{ \nabla_{\theta_S}L }

but there is no corresponding teacher-update path.

This is exactly the source's teacher-offline design. (Source: Build a DeepSeek Model (From Scratch))

5.17.15 Step 11 — Gradient clipping

The source allows:

if grad_clip_norm is not None:
    torch.nn.utils.clip_grad_norm_(
        model.parameters(),
        grad_clip_norm
    )

(Source: Build a Reasoning Model (From Scratch))

The supplied example uses:

\boxed{1.0}.

(Source: Build a Reasoning Model (From Scratch))

5.17.16 Why do we clip gradients?

Suppose:

\|\nabla_\theta L\|

becomes extremely large.

Then the update could be excessively large:

\Delta\theta \propto -\nabla_\theta L.

This can destabilize optimization.

With a max norm c, the gradient can be rescaled so that:

\boxed{ \|\nabla_\theta L\|\le c }

after clipping.

The supplied source uses gradient clipping as an optional stability mechanism. (Source: Build a Reasoning Model (From Scratch))

5.17.17 Numerical example: gradient clipping

Suppose:

\|\nabla L\|=5.

Set:

c=1.

The scale factor is:

\frac{1}{5}=0.2.

So every gradient component is effectively multiplied by approximately:

\boxed{0.2}

under simple norm clipping.

Thus the resulting norm becomes:

\boxed{1}.

This is an illustrative calculation of norm clipping.

5.17.18 Step 12 — Optimizer step

Then:

optimizer.step()

(Source: Build a Reasoning Model (From Scratch))

This actually changes the student parameters:

\boxed{ \theta_{\text{new}} = \operatorname{AdamW}( \theta_{\text{old}}, \nabla_\theta L ) }

The exact AdamW formula is not expanded in this distillation section, so the key point is:

\boxed{ \text{backward computes the direction} }

and:

\boxed{ \text{optimizer.step applies the parameter update} }.

5.17.19 Step 13 — Repeat

Now take the next example.

Again:

X,Y \rightarrow \text{student} \rightarrow L \rightarrow \text{backward} \rightarrow \text{clip} \rightarrow \text{optimizer.step}.

Repeat until all examples in the epoch have been processed.

Then:

\boxed{ \text{next epoch} }

and shuffle again.

5.17.20 One full update in mathematical form

For example i:

Input
X_i
Targets
Y_i
Forward
Z_i=f_{\theta}(X_i)
Select response positions
Z_i^{(a)},Y_i^{(a)}
Loss
L_i = CE(Z_i^{(a)},Y_i^{(a)})
Gradient
g_i=\nabla_\theta L_i
Optional clipping
\tilde g_i=\operatorname{Clip}(g_i)
Update
\boxed{ \theta\leftarrow \operatorname{AdamW}(\theta,\tilde g_i) }

That is one student training step.

5.17.21 Important: source implementation vs large-scale configuration

There are two different things in the supplied material.

Book's compact practical implementation

It uses:

\boxed{\text{one example at a time}}

and a tiny demonstration training subset.

For example:

train_examples=train_examples[:10]

with:

\boxed{2\text{ epochs}}

and:

\boxed{lr=5\times10^{-6}}

in that particular demonstration. (Source: Build a Reasoning Model (From Scratch))

DeepSeek-style reported larger training

The source separately reports:

\boxed{2\text{–}3\text{ epochs}}
\boxed{\text{batch size}=64}
\boxed{\text{context}=32,768}

with model-size-specific learning rates. (Source: Build a DeepSeek Model (From Scratch))

Do not mix the tiny demonstration hyperparameters with the reported large-scale DeepSeek configuration.

5.17.22 Why did the book use only 10 examples?

Because it is a teaching experiment.

The source explicitly says the training run is intentionally short and uses only the first 10 examples. (Source: Build a Reasoning Model (From Scratch))

So:

\boxed{ 10\text{ examples} \neq \text{the actual 800K production training set} }

It is simply a sanity-check implementation.

5.17.23 Numerical: the tiny demonstration

Suppose:

N=10

training examples and:

E=2

epochs.

Then:

\boxed{10\times2=20}

example-level optimizer steps.

Because the source's compact loop calls optimizer.step() once per example. (Source: Build a Reasoning Model (From Scratch))

This is different from the large-scale batch-size-64 configuration.

5.17.24 Why batching changes the calculation

Suppose:

N=800,000

and:

B=64.

Then approximately:

\frac{800,000}{64} = 12,500

batches per epoch.

For 2 epochs:

25,000

optimizer steps.

For 3 epochs:

37,500.

So:

\boxed{ \text{optimizer steps} \neq \text{number of examples} }

once batching is introduced.

5.17.25 Example-level vs token-level

There are two different counts you must keep separate.

Suppose:

800K

examples.

But each example averages:

5,355

tokens.

Then the model sees a huge number of token prediction events:

800,000\times5,355 \approx 4.28\times10^9.

So:

\boxed{ 800K\text{ examples} }

is not equivalent to:

\boxed{ 800K\text{ token targets} }.

The dataset contains billions of target-token prediction events.

5.17.26 Variable-length examples create a batching problem

Suppose three sequences have lengths:

100,\;150,\;300.

You cannot directly stack them as a rectangular tensor without padding.

You need:

[100]\rightarrow[300]

and:

[150]\rightarrow[300].

The source's earlier LLM batching material explains the standard solution:

\boxed{\text{pad to the longest sequence in the batch}}

rather than the longest sequence in the entire dataset. (Source: Build a Large Language Model (From Scratch))

5.17.27 Why pad only within the batch?

Suppose the entire dataset's maximum length is:

32,768.

But your current batch contains:

1,000,\;1,200,\;1,500

token examples.

Padding all of them to:

32,768

would waste enormous computation.

Instead, pad only to:

\boxed{1,500}.

This is why the source describes batch-local dynamic padding as minimizing unnecessary padding. (Source: Build a Large Language Model (From Scratch))

5.17.28 Numerical: padding waste

Suppose a batch contains:

100,\;200,\;500

tokens.

Without padding, total tokens:

100+200+500 = 800.

With padding to the batch maximum:

500\times3 = 1500.

Padding overhead:

1500-800 = \boxed{700\text{ token positions}}.

So:

\boxed{46.7\%}

of the padded positions are unnecessary in this simplified calculation:

\frac{700}{1500}\times100 \approx46.7\%.

This is why length-aware batching can matter.

5.17.29 Padding must not contribute to the loss

This is another critical detail.

Suppose:

Sequence A: [1, 2, 3, 4, 5]
Sequence B: [6, 7]

Pad B:

[6, 7, PAD, PAD, PAD]

The model needs a rectangular tensor.

But we do not want:

PAD

to become a supervised target.

The source's LLM batching treatment uses an ignore_index such as:

\boxed{-100}

for padding targets so that those positions do not contribute to cross-entropy.

5.17.30 This creates two independent masking ideas

You should now distinguish:

Prompt masking

Do not train on:

\text{prompt target positions}.
Padding masking

Do not train on:

\text{padding target positions}.

So the final loss mask is effectively:

\boxed{ \text{valid response token} }

and only those positions should influence the student.

5.17.31 There is a third masking concept in the Transformer

Do not confuse loss masking with causal attention masking.

Causal mask

Controls what a token is allowed to attend to.

\boxed{ \text{future tokens hidden} }
Loss mask

Controls which predictions contribute to training loss.

\boxed{ \text{prompt/padding excluded} }

These are completely different mechanisms.

This distinction is very exam-worthy.

5.17.32 A useful four-layer picture

For each token position:

                INPUT
                  │
                  ▼
           Causal Transformer
                  │
                  ▼
                LOGIT
                  │
                  ▼
             Loss mask
             /        \
          include     ignore
             │
             ▼
        Cross-entropy
             │
             ▼
          gradients

The causal mask operates inside attention.

The loss mask operates after prediction, when constructing the objective.

5.17.33 What is the role of validation loss?

The source defines:

\boxed{\text{training loss}}

as loss on examples being optimized.

And:

\boxed{\text{validation loss}}

as loss on a held-out set without updating the weights.

The source recommends validation loss as the cleaner indicator of generalization because training loss can fluctuate with recent updates and example ordering. (Source: Build a Reasoning Model (From Scratch))

5.17.34 Why can training loss be noisy?

Suppose one example is extremely easy:

L=0.2

and the next is difficult:

L=2.5.

The reported per-example training loss can jump around.

But validation loss is measured on a fixed held-out set, producing a more stable signal.

So:

\boxed{ L_{\text{train}}\downarrow }

is useful, but:

\boxed{ L_{\text{val}}\downarrow }

is often more informative for whether improvement generalizes.

(Source: Build a Reasoning Model (From Scratch))

5.17.35 But lower validation loss is not the same as benchmark accuracy

This is important.

You can have:

L_{\text{val}}\downarrow

without guaranteeing:

\text{AIME accuracy}\uparrow

by the same amount.

Loss measures next-token prediction on the validation distribution.

A benchmark measures task-specific behavior.

So:

\boxed{ \text{training metric}\neq\text{final capability metric} }

5.17.36 Periodic evaluation

The source's loop performs validation every:

log_every

steps, by default 50 in the compact function. (Source: Build a Reasoning Model (From Scratch))

Then it records:

\boxed{ \text{train loss} }

and:

\boxed{ \text{validation loss} }.

5.17.37 Why save checkpoints?

The source saves a model checkpoint at evaluation points/epoch boundaries. (Source: Build a Reasoning Model (From Scratch))

A checkpoint stores the current student parameters:

\boxed{ \theta_t }

so training can be resumed or a particular stage can be evaluated later.

This also protects against losing the entire run if something fails.

5.17.38 What does one checkpoint represent?

It is a snapshot:

\boxed{ \theta^{(t)} }

of the student after some number of updates.

You can then compare:

\theta^{(1000)}

versus:

\theta^{(5000)}

versus:

\theta^{(10000)}.

And evaluate the corresponding models.

5.17.39 The source also records CSV metrics

The compact implementation writes:

epoch,total_steps,train_loss,val_loss

to a CSV log. (Source: Build a Reasoning Model (From Scratch))

So you can later plot:

\text{step}\rightarrow L_{\text{train}}

and:

\text{step}\rightarrow L_{\text{val}}.

This is ordinary experiment tracking, but it becomes important when diagnosing training behavior.

5.17.40 What should healthy training look like?

Conceptually:

loss
│\
│ \
│  \
│   \__
│
└────────── training step

Training loss tends to decline.

Validation loss should also generally improve, at least for some period.

A later rise in validation loss while training loss continues falling can indicate overfitting.

The source doesn't claim a specific overfitting curve for the DeepSeek 800K run, so this is the standard interpretation of the metric rather than a source-reported result.

5.17.41 The source's practical memory result

For its compact implementation, the source states that with maximum sequence length:

\boxed{2,048}

the full demonstration training run requires approximately:

\boxed{15\text{ GB GPU memory}}.

(Source: Build a Reasoning Model (From Scratch))

It notes that lowering the maximum length to:

1024

or:

512

can reduce resource requirements. (Source: Build a Reasoning Model (From Scratch))

This is the practical reason sequence-length filtering matters.

5.17.42 Why does maximum sequence length affect memory so much?

Because Transformer computation depends strongly on sequence length.

As we learned earlier, dense self-attention has:

\boxed{ O(N^2) }

attention-score complexity with sequence length N.

So increasing sequence length can be expensive.

This is why:

\boxed{ \text{data filtering} }

and:

\boxed{ \text{context-length control} }

are not merely preprocessing details; they are computational decisions.

5.17.43 But sequence truncation has a tradeoff

Suppose a reasoning trace has:

4,000

tokens.

If your maximum length is:

2,048,

you cannot retain the entire trace.

You gain:

\text{lower memory and compute}

but potentially lose:

\text{later reasoning + final answer}.

Therefore:

\boxed{ \text{max length} }

must balance:

\boxed{ \text{training feasibility} }

against:

\boxed{ \text{reasoning information retained} }.

5.17.44 This is why the source filters examples

The supplied implementation discusses filtering examples based on a maximum length before training. (Source: Build a Reasoning Model (From Scratch))

This is not simply:

“throw away long examples.”

It is:

\boxed{ \text{fit the computational budget} }

while trying to retain useful reasoning supervision.

5.17.45 A complete training example with numbers

Suppose:

P=5

prompt tokens and:

A=8

teacher-response tokens.

Total:

L=13.

After shifting:

13-1=12

prediction positions.

Answer starts at:

5-1=4.

Therefore number of response-loss positions:

12-4 = \boxed{8}.

Exactly equal to the answer token count.

Now suppose the student assigns correct-token probabilities:

[0.9,0.8,0.7,0.6,0.9,0.8,0.5,0.95].

The loss is:

L = -\frac18 \sum_{i=1}^8\ln p_i.

Approximate terms:

0.105,\;0.223,\;0.357,\;0.511,\;0.105,\;0.223,\;0.693,\;0.051.

Sum:

2.268.

Mean:

\boxed{ L\approx0.284 }.

Then:

\boxed{ \texttt{loss.backward()} }

computes gradients, followed by clipping and the AdamW update.

That is one complete student training step.

5.17.46 Now compare two students after one update

Suppose Student A predicts the selected tokens well:

L_A=0.3.

Student B predicts poorly:

L_B=1.8.

Student B receives a much larger error signal.

This does not mean:

\Delta\theta_B = 6\times\Delta\theta_A

because AdamW, gradient structure, parameter scaling, and clipping all affect the actual update.

But qualitatively:

\boxed{ \text{higher prediction error} \rightarrow \text{larger learning signal} }

before optimizer-specific transformations.

5.17.47 Why response masking changes the learning signal

Suppose sequence has:

100\text{ prompt tokens}

and:

20\text{ answer tokens}.

If you mistakenly train on all 120 target positions, then:

\frac{100}{120} = 83.3\%

of the target positions are prompt-related.

Only:

16.7\%

would be teacher-response supervision.

The source's answer-only objective avoids that distortion. (Source: Build a Reasoning Model (From Scratch))

5.17.48 This is an excellent implementation interview question

Suppose an interviewer asks:

“Why don't you compute CE over the entire prompt+response sequence?”

A strong answer is:

Because the training objective is intended to teach the student to reproduce the teacher-generated response conditioned on the prompt. The prompt is context, not the behavior being distilled, so prompt-only target positions are excluded from the loss.

That is exactly the source's logic. (Source: Build a Reasoning Model (From Scratch))

5.17.49 Another interview question

“Why can't you simply delete the prompt from the input?”

Because the response is conditional on the prompt:

\boxed{ P(y_t|q,y_{<t}) }

The student needs q to know what problem it is solving.

Therefore:

\boxed{ \text{prompt retained in input} }

but:

\boxed{ \text{prompt excluded from loss} }.

5.17.50 One more critical distinction

You may hear:

“Distillation is just copying the teacher.”

Not exactly.

The student does not copy:

W_T.

It minimizes an empirical loss on teacher-generated sequences:

\boxed{ L_{\text{SFT}} = -\sum \log P_S(y_t|x,y_{<t}) }

and updates its own parameters.

So the student is learning an approximation of the teacher's demonstrated behavior, constrained by its own architecture and capacity.

5.17.52 The entire student pipeline

Memorize this:

\boxed{ \begin{aligned} &\text{Load pretrained student}\\ &\downarrow\\ &\text{Shuffle training examples}\\ &\downarrow\\ &\text{Build shifted input/target}\\ &\downarrow\\ &\text{Run student forward pass}\\ &\downarrow\\ &\text{remove prompt-only loss positions}\\ &\downarrow\\ &\text{Cross-entropy}\\ &\downarrow\\ &\text{Backward}\\ &\downarrow\\ &\text{Gradient clipping}\\ &\downarrow\\ &\text{AdamW update}\\ &\downarrow\\ &\text{Validation / checkpoint}\\ &\downarrow\\ &\text{repeat} \end{aligned} }

5.17.55 Final mental model

There are now four different layers in the complete process:

\boxed{\textbf{Layer 1 — Teacher generation}}

R1 produces candidate reasoning.

\boxed{\textbf{Layer 2 — Data curation}}

Verification + rejection sampling turns candidates into high-quality supervision.

\boxed{\textbf{Layer 3 — Student optimization}}

Shifted targets + answer-only CE + backprop + AdamW.

\boxed{\textbf{Layer 4 — Evaluation}}

Validation loss, checkpoints, and finally reasoning benchmarks.

So:

\boxed{ \text{teacher intelligence} \rightarrow \text{curated data} \rightarrow \text{gradient updates} \rightarrow \text{compressed student behavior} }

That is the complete mechanics from R1 output to student parameters.
