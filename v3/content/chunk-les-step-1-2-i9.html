Motivation

Motivation: convert categorical text into trainable vectors without treating arbitrary token ID order as semantic distance. Prerequisites: vocabulary indexing, matrix rows and gradients. Distinguish an ID, a static input embedding, a position-dependent input and a contextual hidden state.

Prerequisites

  • Read the prerequisite chain stated in the original lesson and this review motivation.

Notation and units

  • X_{btj}=W_E[\mathrm{id}_{bt},j]
  • \frac{\partial L}{\partial W_E[v,j]}=\sum_{b,t:\mathrm{id}_{bt}=v}\frac{\partial L}{\partial X_{btj}}

Assumptions

  • Use zero-based IDs, W_E of shape [V,d], integer inputs [B,T] and output [B,T,d]. The inherited numbers are rounded displayed book values, not a promised seeded random output from the unseeded inherited snippet. The CPU companion uses a declared fixed toy vocabulary; it does not implement a production tokenizer.

    Continuation · checked fixture T15 — BPE training versus BPE encoding

    Checked continuation mechanism and declared fixture; this is not certification of every inherited claim.

    Subwords allow a finite vocabulary to represent many words without storing every whole word.

    Prerequisites: Embedding lookup and one-hot equivalence

    Notation and assumptions

    Toy character alphabet, explicit </w>, frequency-weighted words. Actual byte-level tokenizers also specify bytes, normalization, pre-tokenization and special tokens.

    Derivation and mechanism

    1. Start with character sequences for each word and its count.
    2. Count adjacent pairs, weighting each occurrence by word frequency.
    3. Merge the most frequent pair, break ties lexically, and recount.
    4. Encoding replays the learned merge ranks; it does not retrain on the new word.

    Worked example

    For low×5 and lower×2, (l,o) and (o,w) each count 7. The declared tie rule chooses (l,o), then (lo,w), then (low,</w>) with count5. lower encodes as [low,e,r,</w>]. The companion prints every learned merge.

    Limitations

    • This is a BPE mechanism fixture, not a byte-for-byte tiktoken replacement.
    • Unseen characters need a defined fallback alphabet; bytes solve a different representation contract.

    Connections to later concepts

    • Tokenization defines vocabulary IDs used by T02 embedding lookup. Fertility also changes how much context fits within a fixed token budget.

    Why this matters

    An ID identifies a vocabulary row; an embedding turns that identifier into a learned feature vector.

    Prerequisites: Matrix multiplication and shape contracts

    Symbols, shapes and assumptions

    E has shape V×d. IDs must be integers in [0,V). One-hot selection is mathematically equivalent to gathering a row; it is usually less efficient to materialize.

    Derivation or mechanism

    1. Construct the indicator row e_id with one 1.
    2. Multiply e_id E; all unselected rows vanish.
    3. Gather that same E row directly in executable code.
    x_t=e_{id_t}E=E[id_t,:]

    Worked numerical

    For E=[[1,0],[0,1],[1,1]] and IDs [2,0,2], the embeddings are [[1,1],[1,0],[1,1]]. Repeated ID 2 retrieves the same vector before positional information. A NumPy one-hot multiplication independently reproduces the gather.

    Edge cases and limits

    • ID 2 is not semantically twice ID 1.
    • Out-of-range IDs are rejected.
    • This fixture checks lookup, not a BPE tokenizer or learned semantic quality; those remain separate audit concepts.

    Step 1.2 — Tokens → Token IDs → Embeddings

    Plan node: I1 · chat order #9

    Now we move one level deeper.

    In Step 1.1, we established that the language model works on a sequence

    x_1,x_2,\ldots,x_T

    and predicts

    P(x_t\mid x_{<t})

    But there is a problem:

    A neural network cannot directly consume the raw string "The cat sat" as matrix input.

    We therefore need the pipeline:

    \boxed{ \text{Raw text} \rightarrow \text{tokens} \rightarrow \text{token IDs} \rightarrow \text{embedding vectors} \rightarrow X }

    The Transformer slides show exactly this first conversion:

    \text{Tokens}\rightarrow\text{Embeddings}

    with a learned embedding matrix.

    Raschka's book expands this into tokenization, vocabulary construction, token IDs, BPE, and embedding lookup.

    1.2.1 Why Can't We Just Feed Text Directly?

    Suppose the input is:

    I love Transformers

    A neural network performs mathematical operations such as:

    XW
    QK^T
    \operatorname{softmax}(z)

    These require numerical representations.

    But the string

    "I"
"love"
"Transformers"

    is categorical data.

    There is no meaningful operation such as:

    \text{"love"}\times 2.7

    So we need to convert the language into numbers.

    Raschka explicitly introduces embeddings for this reason: raw text is categorical, whereas neural networks need continuous-valued numerical representations.

    1.2.2 Stage 1 — Tokenization

    The first question is:

    How should we split text into units?

    These units are called tokens.

    For example:

    "The cat is sleeping."

    could conceptually become:

    ["The", "cat", "is", "sleeping", "."]

    Now the text is no longer one large string.

    It is a sequence:

    x_1=\text{"The"}
    x_2=\text{"cat"}
    x_3=\text{"is"}
    x_4=\text{"sleeping"}
    x_5=\text{"."}

    Raschka first demonstrates a simple tokenizer that separates words and punctuation.

    1.2.3 Token Does NOT Necessarily Mean Word

    This distinction is extremely important.

    A token can be:

    • a complete word,
    • part of a word,
    • punctuation,
    • whitespace-related representation,
    • a special symbol.

    For example, a modern tokenizer might represent:

    "unbelievable"

    as something conceptually like:

    ["un", "believ", "able"]

    The exact result depends on the tokenizer.

    Therefore, in all of our mathematics:

    x_t

    means a token, not necessarily a whole word.

    This is why modern LLM literature almost always says:

    next-token prediction

    rather than strictly next-word prediction.

    1.2.4 Why Not Use One Token for Every Possible Word?

    Suppose English contains millions of possible word forms.

    Then a word-level vocabulary would become enormous.

    Worse, consider:

    play
played
playing
playful
player
players

    Many of these share useful structure.

    And new words can appear.

    For example:

    quantization-aware

    or a person's unusual name.

    A tokenizer that can break unknown words into reusable smaller pieces is more flexible.

    This motivates subword tokenization, including BPE.

    Raschka's book first builds intuition using a simple word/punctuation tokenizer and then transitions to byte-pair encoding.

    1.2.5 Stage 2 — Token IDs

    The Transformer still does not want strings.

    So we create a vocabulary:

    V=\{v_0,v_1,\ldots,v_{|V|-1}\}

    and assign each token a unique integer.

    For example:

    Token ID
    "I" 17
    "love" 42
    "Transformers" 815
    "." 9

    Then:

    "I love Transformers ."

    becomes:

    [17, 42, 815, 9]

    These are token IDs.

    Raschka's vocabulary construction explicitly maps each unique token to a unique integer ID.

    1.2.6 Why Integer IDs?

    Notice something subtle.

    We don't claim:

    42 > 17

    means "love" is somehow mathematically greater than "I".

    The integer is simply an index.

    Think:

    17  → row 17
42  → row 42
815 → row 815

    The numerical value itself has no semantic meaning.

    This is why it would be wrong to simply feed token IDs directly into the Transformer as though:

    I = 17
love = 42
Transformers = 815

    were meaningful continuous features.

    The next stage fixes this.

    1.2.7 Stage 3 — The Embedding Matrix

    We introduce a learnable matrix:

    \boxed{ W_E\in\mathbb R^{|V|\times d} }

    where:

    • |V| = vocabulary size
    • d = embedding dimension

    Suppose:

    |V|=6

    and

    d=3

    Then:

    W_E\in\mathbb R^{6\times3}

    For example:

    W_E= \begin{bmatrix} 0.3&-0.2&0.5\\ 0.8&0.1&-0.4\\ -0.7&0.6&0.2\\ 0.4&0.9&-0.1\\ -0.5&0.2&0.8\\ 0.1&-0.8&0.3 \end{bmatrix}

    Each row corresponds to one token.

    So:

    W_E[0]

    is the vector for token ID 0.

    And:

    W_E[3]

    is the vector for token ID 3.

    1.2.8 Embedding = Lookup

    Suppose the token sequence is:

    [2,3,5,1]

    Then the embedding operation retrieves:

    W_E[2],W_E[3],W_E[5],W_E[1]

    giving:

    X= \begin{bmatrix} W_E[2]\\ W_E[3]\\ W_E[5]\\ W_E[1] \end{bmatrix}

    Therefore:

    X\in\mathbb R^{4\times3}

    The key idea is:

    \boxed{ \text{token ID} \rightarrow \text{row lookup in }W_E }

    Raschka demonstrates this directly with a PyTorch Embedding layer: each token ID retrieves the corresponding row of the embedding weight matrix.

    1.2.9 Let's Do the Exact Numerical Example

    Suppose:

    W_E= \begin{bmatrix} 0.3374&-0.1778&-0.1690\\ 0.9178&1.5810&1.3010\\ 1.2753&-0.2010&-0.1606\\ -0.4015&0.9666&-1.1481\\ -1.1589&0.3255&-0.6315\\ -2.8400&-0.7849&-1.4096 \end{bmatrix}

    This is essentially the small example used in Raschka's book.

    Suppose:

    \text{input IDs}=[2,3,5,1]

    Then:

    ID 2
    W_E[2] = [1.2753,-0.2010,-0.1606]
    ID 3
    W_E[3] = [-0.4015,0.9666,-1.1481]
    ID 5
    W_E[5] = [-2.8400,-0.7849,-1.4096]
    ID 1
    W_E[1] = [0.9178,1.5810,1.3010]

    So:

    X= \begin{bmatrix} 1.2753&-0.2010&-0.1606\\ -0.4015&0.9666&-1.1481\\ -2.8400&-0.7849&-1.4096\\ 0.9178&1.5810&1.3010 \end{bmatrix}

    and:

    \boxed{X\in\mathbb R^{4\times3}}

    The book gives this exact lookup behavior and resulting 4\times3 matrix example.

    1.2.10 Why Are These Vectors Random Initially?

    This is extremely important.

    At the beginning, the embedding matrix is generally initialized from small random values.

    So initially, there is no reason for:

    cat

    to have a useful relationship with:

    dog

    The model has to learn those representations.

    Raschka explicitly states that the embedding weights are initialized and later optimized as part of LLM training.

    So:

    W_E^{(0)}

    is the initial embedding matrix.

    After training:

    W_E^{(*)}

    is the learned embedding matrix.

    1.2.11 The Embeddings Are Trainable Parameters

    This connects directly to our Step 0.6 on gradients.

    Suppose:

    W_E\in\mathbb R^{|V|\times d}

    The loss is:

    L

    Backpropagation calculates:

    \frac{\partial L}{\partial W_E}

    Then gradient descent updates it:

    W_E \leftarrow W_E-\eta\frac{\partial L}{\partial W_E}

    So the embedding matrix is not a fixed dictionary.

    It is a learned part of the neural network.

    The Transformer slides also emphasize that W_E is learned end-to-end using the same next-token loss used for the rest of the model.

    1.2.12 One-Hot Encoding Connection

    There is another mathematically beautiful way to understand embedding lookup.

    Suppose the vocabulary contains 5 tokens and token ID is 2.

    One-hot encoding gives:

    e_2= [0,0,1,0,0]

    Now multiply:

    e_2W_E

    where:

    e_2\in\mathbb R^{1\times5}

    and

    W_E\in\mathbb R^{5\times d}

    Then:

    e_2W_E=W_E[2]

    because the one-hot vector selects exactly one row.

    Therefore:

    \boxed{ \text{Embedding lookup} \equiv \text{one-hot vector}\times W_E }

    conceptually.

    But explicitly creating a giant one-hot vector is wasteful.

    So frameworks use an efficient lookup operation.

    Raschka explains this equivalence directly.

    1.2.13 Why Embeddings Are Better Than Raw IDs

    Suppose:

    cat  = 100
dog  = 101
car  = 102

    The integer IDs suggest:

    101-100=1

    But this difference has no semantic interpretation.

    After embedding:

    E(\text{cat})=[0.7,0.2,-0.1,\ldots]
    E(\text{dog})=[0.65,0.25,-0.05,\ldots]
    E(\text{car})=[-0.4,0.8,0.9,\ldots]

    Now the geometry of the vectors can encode useful relationships.

    For example:

    \cos(E(\text{cat}),E(\text{dog}))

    could be relatively high.

    This idea connects directly to our earlier discussion of vectors and dot products.

    1.2.14 But There Is an Important Modern-LM Nuance

    A token embedding by itself is not necessarily contextual.

    Consider:

    bank

    in:

    I deposited money in the bank.

    and:

    We sat beside the river bank.

    The initial embedding lookup for "bank" is the same token vector.

    But after passing through the Transformer, the representations can differ because the surrounding context is different.

    So think:

    \boxed{ \text{Token embedding} = \text{initial representation} }

    while:

    \boxed{ \text{Transformer hidden state} = \text{contextual representation} }

    This distinction becomes crucial when we reach self-attention.

    Raschka distinguishes the learned input embeddings from contextualized representations produced later by the Transformer.

    1.2.15 Where BPE Enters

    Now we return to the tokenization question.

    A simple word tokenizer has a problem with rare or unseen words.

    Suppose our vocabulary has:

    play
playing
played

    but encounters:

    playfulness

    A word-level tokenizer may not know that whole word.

    BPE instead works with smaller reusable units.

    Conceptually:

    playfulness
   ↓
play + ful + ness

    The exact segmentation is determined by the learned tokenizer vocabulary/merges.

    Raschka's book explains that GPT-family models use BPE-style tokenization and presents BPE after the simpler tokenizer.

    1.2.16 The Main Idea Behind BPE

    You don't need to memorize the implementation yet. Understand the intuition first.

    Start with smaller pieces.

    Suppose the data contains:

    low
lower
lowest

    The tokenizer notices frequent pieces such as:

    l
o
w
e
r
s
t

    and repeatedly merges frequent neighboring pieces.

    For example, conceptually:

    l+o\rightarrow lo
    lo+w\rightarrow low
    low+e\rightarrow lowe

    and so on.

    The final tokenizer vocabulary contains reusable subword units.

    This gives a compromise:

    \boxed{ \text{character-level flexibility} \quad+\quad \text{word-level efficiency} }

    Raschka notes that GPT-2 and GPT-3 and the original ChatGPT model used BPE tokenization, and uses tiktoken to demonstrate it.

    1.2.17 Why Subwords Are So Useful

    Imagine we encounter:

    unbelievability

    A word-level tokenizer may treat it as one unknown item.

    A subword tokenizer can potentially decompose it into reusable components.

    That means the model can represent previously unseen combinations using pieces it has already encountered.

    This is particularly important for:

    • rare words,
    • names,
    • technical terminology,
    • morphology,
    • new combinations.

    1.2.18 Special Tokens

    The tokenizer can also contain tokens whose purpose is structural rather than linguistic.

    The book discusses:

    BOS

    Beginning of sequence.

    [\text{BOS},x_1,x_2,\ldots]
    EOS

    End of sequence.

    [x_1,x_2,\ldots,\text{EOS}]
    PAD

    Used to make sequences in a batch the same length.

    For example:

    Sequence A:
[I, like, AI]

Sequence B:
[I, really, like, AI]

after padding:

[I, like, AI, PAD]
[I, really, like, AI]

    The book also discusses <|endoftext|> and how special-token handling depends on the tokenizer/model.

    The important lesson is:

    Not every token represents ordinary natural-language content. Some tokens help the model structure sequences.

    1.2.19 Complete Representation Pipeline

    Let's put everything together.

    Take:

    "I love AI."
    Stage 1 — Raw text
    \text{"I love AI."}
    Stage 2 — Tokenization

    Conceptually:

    [\text{"I"},\text{"love"},\text{"AI"},\text{"."}]
    Stage 3 — Token IDs

    Suppose:

    [17,42,815,9]
    Stage 4 — Embedding lookup
    X= \begin{bmatrix} W_E[17]\\ W_E[42]\\ W_E[815]\\ W_E[9] \end{bmatrix}

    Therefore:

    X\in\mathbb R^{4\times d}
    Stage 5

    Now this matrix enters the Transformer.

    But there's a problem.

    The Transformer currently sees:

    vector
vector
vector
vector

    How does it know which vector is first, second, third, fourth?

    This brings us to the next concept:

    \boxed{\text{POSITION}}

    1.2.20 Batch Shapes

    Suppose:

    B=2
    T=5
    d=768

    Then:

    Token IDs
    \boxed{[2,5]}
    Embeddings
    \boxed{[2,5,768]}

    Interpretation:

    2 sequences
 ×
5 tokens each
 ×
768 numbers per token

    For example:

    Token IDs

[B,T]

       5 tokens
    ┌─────────────┐
 B=2│ 17 42 81 9 5│
    │ 23 11 72 4 8│
    └─────────────┘

    After embedding:

    [B,T,d]

2 × 5 × 768

    Each integer has been replaced by a 768-dimensional vector.

    1.2.21 Executable PyTorch Example

    Let's reproduce the central idea ourselves.

    import torch
import torch.nn as nn


# ---------------------------------------------------------
# Configuration
# ---------------------------------------------------------
vocab_size = 6
embedding_dim = 3

# ---------------------------------------------------------
# Input token IDs
# Four tokens
# ---------------------------------------------------------
input_ids = torch.tensor([2, 3, 5, 1])

# ---------------------------------------------------------
# Create learnable embedding table
# Shape = [vocab_size, embedding_dim]
#         [6, 3]
# ---------------------------------------------------------
embedding = nn.Embedding(
    num_embeddings=vocab_size,
    embedding_dim=embedding_dim
)

print("Embedding matrix:")
print(embedding.weight)

print("\nEmbedding matrix shape:")
print(embedding.weight.shape)

# ---------------------------------------------------------
# Lookup embeddings
# ---------------------------------------------------------
output = embedding(input_ids)

print("\nInput IDs:")
print(input_ids)

print("\nOutput embeddings:")
print(output)

print("\nOutput shape:")
print(output.shape)

    Expected shape:

    Embedding matrix:
[6, 3]

Input IDs:
[4]

Output:
[4, 3]

    So:

    [4] \rightarrow [4,3]

    1.2.22 Batch Example

    Now:

    import torch
import torch.nn as nn

vocab_size = 10000
embedding_dim = 768

# Two sequences, five tokens each
input_ids = torch.tensor([
    [10, 25, 17, 42, 91],
    [13, 81,  5, 72,  6]
])

embedding = nn.Embedding(
    num_embeddings=vocab_size,
    embedding_dim=embedding_dim
)

X = embedding(input_ids)

print("Input shape :", input_ids.shape)
print("Output shape:", X.shape)

    The shapes are:

    Input:
[2, 5]

Embedding:
[10000, 768]

Output:
[2, 5, 768]

    Mathematically:

    \boxed{ [B,T] \rightarrow [B,T,d] }

    This is the tensor that will enter the Transformer.

    1.2.23 Why Is the Embedding Matrix So Large?

    This is a useful parameter-count connection.

    If:

    |V|=50,000

    and:

    d=4,096

    then:

    \text{parameters in }W_E = 50,000\times4,096
    =204,800,000

    So the embedding table alone contains about:

    \boxed{205\text{ million parameters}}

    This is why vocabulary size and hidden dimension matter substantially in model size.

    1.2.24 A Crucial Distinction: Token IDs vs Embeddings vs Hidden States

    Do not mix these three.

    Token ID
    17

    A discrete integer index.

    Token embedding
    [0.32,-0.81,0.14,\ldots]

    A learned vector from W_E.

    Contextual hidden state
    h_t = [0.71,0.12,-0.35,\ldots]

    after Transformer processing.

    So:

    ID
 ↓ lookup
embedding
 ↓ Transformer
contextual hidden state

    This distinction will be essential for understanding Q/K/V.

    1.2.25 Where the Learning Happens

    The complete forward path is now:

    \text{text} \rightarrow \text{token IDs} \rightarrow W_E \rightarrow X \rightarrow \text{Transformer} \rightarrow H \rightarrow Z \rightarrow \text{softmax} \rightarrow P \rightarrow L

    During backpropagation:

    L \rightarrow Z \rightarrow H \rightarrow X \rightarrow W_E

    So the embedding table itself receives gradients.

    That means the model learns:

    "What numerical representation should this token have so that, together with the rest of the network, next-token prediction improves?"

    That is much deeper than simply assigning fixed meanings to words.

    For this step, the primary grounding is:

    Raschka, Chapter 2: provides the detailed progression:

    \text{raw text} \rightarrow \text{tokens} \rightarrow \text{token IDs} \rightarrow \text{special tokens} \rightarrow \text{BPE} \rightarrow \text{embedding vectors}

    and gives executable Python/PyTorch examples for these stages.

    1.2.28 One More Important Connection

    Look back at Step 0.1.

    We learned:

    X\in\mathbb R^{T\times d}

    and:

    Q=XW_Q

    Now we know where X actually comes from.

    It is not magical.

    It comes from:

    \boxed{ \text{text} \rightarrow \text{token IDs} \rightarrow \boxed{W_E\text{ lookup}} \rightarrow X }

    Therefore the beginning of the Transformer computation is:

    X \rightarrow Q=XW_Q
    X \rightarrow K=XW_K
    X \rightarrow V=XW_V

    How can the Transformer know that token 4 should pay attention to token 1, but not token 5?
